# Конструктор сущностей (метаданные + JSONB)

Реализовано на этапе 3. Код: схема `packages/db/src/schema/meta.ts` (миграция `0003_meta.sql`), общая логика
`packages/shared/src/fields.ts` и `schemas/meta.ts`, API `apps/api/src/routes/meta.ts`, `routes/records.ts`, `meta/*`,
клиент `apps/web/src/app/meta/*` и `settings/data-model.tsx`.

Таблицы на лету не создаются. Структура описывается метаданными:

- `entities (workspace_id, key, name, kind: system|custom, icon, title_field, settings, sort_order, archived_at)` —
  сущности, включая системные (task, project, deal, company, contact, product), чтобы к ним можно было добавлять поля.
  Системные регистрируются при создании воркспейса (`registerSystemEntities`), в сидах и миграцией для уже существующих
  воркспейсов. Ключ (`key`) не меняется. Для системных `title_field` — имя колонки (`title` / `name`); встроенные
  колонки (статус, сумма…) в `fields` **не** заводятся: это обычные колонки таблицы, `fields` описывает только
  пользовательские поля (`is_system` зарезервирован под будущее).
- `fields (entity_id, key, name, type, required, unique, filterable, options jsonb, sort_order, is_system, archived_at)` —
  типы: text, long_text, number, money, percent, date, datetime, boolean, select, multi_select, user, ref (связь с
  записью другой сущности — системной или пользовательской), refs, url, email, phone. `file` и `formula` — позже
  (нужны хранилище файлов и тип поля-формулы; **язык выражений при этом есть** — `packages/shared/src/expr.ts`,
  этап 7: он используется в спецификациях производства, а не как тип поля конструктора). `options`: варианты select/multi_select `{value,label,color}`, `refEntity`
  (ключ целевой сущности), `min`/`max`, `maxLength`, `currency`. Ключ и тип поля после создания не меняются: от них
  зависят уже записанные данные.
- Хранение значений: у системных таблиц — колонка `custom jsonb` (есть у tasks, projects, deals, companies, contacts);
  пользовательские сущности — общая таблица `records (id, workspace_id, entity_id, data jsonb, created_by, created_at,
  updated_at, archived_at)`. Числа лежат числами, даты — ISO-строками, ссылки — uuid.
- Все три таблицы — арендаторские: `app_secure_tenant_table` (владелец app_owner, ENABLE + FORCE RLS, политика по
  `workspace_id`); составные FK `(workspace_id, entity_id)`.
- Проверка — zod-схема, собираемая из `fields` функцией `buildRecordSchema(fields, 'create'|'patch')`
  (`packages/shared`): на сервере перед записью и в формах клиента (`validateRecord`). create — обязательные поля
  заполнены, пустые значения не сохраняются; patch — проверяются только присланные ключи, `null` очищает поле (для
  обязательного — ошибка). Лишние ключи и ключи удалённых полей отклоняются. Сервер дополнительно проверяет, что
  ссылки (`user`/`ref`/`refs`) указывают на существующие записи **этого** воркспейса, и уникальность (`unique`).
- Запись `custom` у системных сущностей — те же маршруты (`/tasks`, `/deals`, `/companies`, `/contacts`, `/projects`),
  свойство `custom`: при PATCH присланные ключи проверяются и сливаются с имеющимися, `null` удаляет ключ,
  неизменённые значения не проверяются (клиент присылает объект целиком).
- Индексы: для полей с флагом `filterable` — индекс по выражению `((data->>'ключ'))` (для number/money/percent —
  `((data->>'ключ')::numeric)`), для записей пользовательских сущностей частичный (`WHERE entity_id = …`), для
  системных — по `custom` таблицы. Имя `idx_cf_<id поля>`. `CREATE INDEX CONCURRENTLY` нельзя выполнять в транзакции,
  а права владельца у API нет, поэтому **построение и удаление индекса — задача в таблице `jobs`** (очередь `ddl`, типы
  `index.create` / `index.drop`, `payload = {fieldId}`), которую запрос API вставляет в той же транзакции, что и изменение поля
  (откат запроса отменяет и задачу). Задачу берёт воркер и выполняет на отдельном подключении `DATABASE_URL_DDL` (роль-владелец).
  Белый список: воркер не доверяет содержимому задачи — из `payload` берётся только uuid поля, а ключ, тип и сущность читаются из
  метаданных; в SQL попадает лишь выражение над ключом, проверенным по `FIELD_KEY_RE`, таблица — из списка системных таблиц либо `records`
  (любой другой `type` задачи, негодный uuid или несуществующее поле — ошибка либо пропуск без DDL). Задача сверяется с метаданными
  **на момент выполнения**, а не постановки: `index.create` пропускается, если поле уже удалено, скрыто или не `filterable`;
  `index.drop` — если поле снова требует индекса (восстановлено раньше), поэтому порядок и повторы задач безопасны. DDL идёт строго по одному
  на всех воркерах (рекомендательная блокировка `pg_try_advisory_lock` с ожиданием в коде: ждущий `pg_advisory_lock` — открытая транзакция,
  а `CONCURRENTLY` ждёт такие, получился бы взаимный дедлок); сбой оставляет INVALID-индекс — его убираем, задача повторяется с паузой. Пока индекс не
  построен, фильтры работают без него. Запросы строят выражение из ключа, проверенного по метаданным и регулярке, значения идут
  параметрами. Поиск `q` — `ILIKE` по заголовку и текстовым полям (без индекса). GIN `jsonb_path_ops` по `records.data` ускоряет `@>`
  (фильтры по multi_select/refs).
- API (чтение — любой участник, изменение метаданных — admin и выше, записи — member и выше):
  `GET/POST /entities`, `GET/PATCH/DELETE /entities/:key`, `POST /entities/:key/restore`,
  `GET/POST /entities/:key/fields`, `PATCH/DELETE /entities/:key/fields/:id`, `POST …/fields/:id/restore`,
  `POST /entities/:key/fields/reorder`; записи — `GET/POST /data/:entity`, `GET/PATCH/DELETE /data/:entity/:id`,
  `POST /data/:entity/:id/restore`; поиск для палитры — `GET /data-search?q=`. Список записей:
  `filter=ключ:оператор:значение` (повторяется; eq, ne, gt, gte, lt, lte, in, contains, empty, notempty — набор
  зависит от типа поля), `sort=ключ,-ключ2`, `q`, `limit/offset`, `archived`.
- Удаление поля и сущности — с подтверждением (`DELETE …?confirm=<ключ>`), в два шага. Без `purge` поле/сущность только
  скрываются (`archived_at`): значения остаются в `records.data` / `custom`, ключ остаётся занятым, индекс убирается;
  `POST …/restore` возвращает всё, включая данные и индекс. С `purge=true` значения вычищаются из jsonb (`data - 'ключ'`),
  а строка метаданных (для сущности — вместе с записями) удаляется навсегда. Нельзя удалить поле-заголовок и сущность,
  на которую ссылаются поля других сущностей; системные сущности не удаляются и не переименовываются. Данные «скрытого»
  поля до очистки видны в БД и в сыром ответе API (`custom`), но не в интерфейсе.
- Интерфейс пользовательской сущности собирается автоматически из метаданных на готовых компонентах:
  `DataTable`, `Kanban` (по полю select), `EntityDrawer`, `FilterBar`, формы. Маршрут `/data/:key/:recordId?`, группа
  «Data» в сайдбаре, поиск в палитре команд. Пользовательские поля системных сущностей показываются в карточке задачи,
  колонками таблицы задач (меню Columns), в карточках сделки и контакта и на странице компании. Редактор модели —
  Settings → Data model.
- События outbox: `entity.*`, `field.*` (entity = `entity` / `field`) и `record.*` (entity = `record`, ключ сущности в
  `payload.entityKey`); клиент по ним перечитывает метаданные и списки записей.
- Если сущность станет «горячей» (миллионы записей, тяжёлая аналитика) — её можно материализовать в
  настоящую таблицу; это исключение, а не основной путь.

Известные ограничения этапа: порядок карточек внутри колонки доски не хранится (перетаскивание меняет только
значение select); сортировка в таблице пользовательской сущности — на клиенте по загруженным записям (до 2000); индексы
не покрывают поиск `q`; уникальность проверяется при записи (без уникального индекса БД, возможна гонка двух
одновременных записей); у проектов пользовательские поля доступны через API, но интерфейса для них нет.
