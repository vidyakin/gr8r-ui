# Документооборот — решения и план задач

> **Дата:** 2026-10-29. **TaskFlow:** сессия 48 «Документооборот» (проект gr8r-ui), задачи 1191–1204.
>
> Решения пользователя приняты на опросе 2026-10-29 и записаны в разделах задач ниже. Пункты с пометкой
> **«по умолчанию»** — решения исполнителя плана там, где ответ пользователя не стыкуется с кодом; их можно поправить.
> УНФ здесь — ориентир по функциональности; модель данных своя, в стиле `docs/architecture.md`.

**Цель:** модуль документооборота поверх учёта: файлы и вложения к любому объекту в S3, шаблоны договоров с подстановкой
реквизитов, учёт оригиналов, обмен XML форматов ФНС, простая электронная подпись, согласование по маршрутам,
внутренние документы и журналы корреспонденции.

**Связанные документы:** `docs/architecture/documents.md` (печать, PDF, `document_files`), `docs/architecture/quotes.md`
(шаблоны КП, `doc_templates`), `docs/architecture/counterparties.md` (организации, подписанты), `docs/architecture/billing.md`
(договоры `contracts`), `docs/architecture/payments.md` (заявки на расход), `docs/architecture/secrets.md`,
`docs/architecture/deploy.md`; `docs/plans/2026-10-21-unf-services.md` (раздел задачи 1190).

## Задача 1191 — хранилище файлов S3 и вложения к любым объектам (решения 2026-10-29)

1. **S3-клиент** — один на `packages/db` (его используют API и воркер): `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`,
   `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_FORCE_PATH_STYLE` (MinIO — да). Подписи запросов SigV4; выбор библиотеки
   (`@aws-sdk/client-s3` или лёгкий `aws4fetch`) — решение исполнителя, записать в архитектуру. Ключ объекта —
   `<workspace>/<attachment>/<version>` (без имени файла: имя в БД). В тестах — MinIO из compose или заглушка-стор
   в памяти с тем же интерфейсом.
2. **Модель.** `attachments` (воркспейс, тип объекта `entity_type`, id объекта `entity_id`, имя, вид `kind` как у
   `files`, текущая версия, автор, создан, `archived_at`) и `attachment_versions` (вложение, номер, `storage_key`,
   размер, `mime`, `sha256`, автор, комментарий, создана). Привязка полиморфная, поэтому составного FK на объект нет:
   список допустимых `entity_type` (документ, договор, компания, контакт, сделка, лид, задача, проект, товар, внутренний
   документ, письмо корреспонденции…) — реестр в `packages/shared`, проверка существования объекта — в сервисе.
3. **Права «как у объекта»** (**по умолчанию**). RLS даёт только изоляцию по `workspace_id`; доступ к родителю
   проверяет сервис по реестру типов (закрытые проекты, «только автор» у шаблонов и т.п.): видит файл тот, кто видит
   объект; загружает — кто может править объект; удаляет (в архив) — автор или admin+. Удаление объекта
   архивирует его вложения.
4. **Загрузка и выдача — через API потоком** (**по умолчанию**): MinIO в compose слушает `127.0.0.1:9000`, браузер
   на VPS до него напрямую не достучится, а presigned URL раскрыли бы адрес хранилища. `POST /attachments`
   (multipart, объект, файл) → вложение и версия 1; `POST /attachments/:id/versions` — новая версия;
   `GET /attachments/:id/content?version=N` — файл (по умолчанию текущая версия, `Content-Disposition` с именем).
   Presigned URL можно добавить позже как опцию окружения.
5. **Версии:** новая версия поверх файла, старые доступны для скачивания, видно кто и когда; удаление версии не
   делаем (только архив всего вложения). Сборка мусора — задача воркера: удаляет из S3 объекты вложений, архивных
   дольше N дней (настройка окружения), и осиротевшие ключи незавершённых загрузок.
6. **Лимиты.** `FILE_MAX_BYTES` (по умолчанию 50 МБ) — 413 при превышении. **Квота воркспейса (по умолчанию):**
   тарифов нет, поэтому `workspaces.storage_quota_bytes` (пусто — без ограничения, значение по умолчанию из
   `STORAGE_QUOTA_BYTES`) и учёт занятого объёма суммой размеров всех версий неархивных вложений; превышение — 422
   `storage_quota_exceeded`. Занято / квота — в настройках воркспейса (меняет owner).
7. **Перенос `files`.** Файлы задач и проектов становятся вложениями (`entity_type` `task` / `project`); миграция
   переносит метаданные (строк с настоящим содержимым нет — загрузки не было), маршрут `/files` и экраны задач и
   проектов переходят на `/attachments`, таблица `files` удаляется.
8. **Интерфейс:** общий компонент вкладки «Файлы» (список, перетаскивание для загрузки, версии в раскрывающейся строке,
   скачать, в архив) — в карточке документа, договора, компании, контакта, сделки, лида, товара, задачи и проекта.
   Тексты через `t()`.
9. **PDF печатных форм остаются в БД** (ответ пользователя): `dbPdfStore` не меняется, `s3PdfStore` остаётся заготовкой.
10. **Готово, когда:** загрузка, версии, скачивание и архив работают в карточках; лимит и квота проверяются на сервере;
    права проверены тестами (закрытый проект, чужой воркспейс); RLS-тест новых таблиц; раздел
    `docs/architecture/attachments.md`, обновлены `deploy.md` (бакет, переменные) и `.env.example`.

## Задача 1192 — картинки товаров (решения 2026-10-29)

1. Картинки товара — вложения `entity_type = product` с `mime image/*`; основная — `products.image_attachment_id`
   (пусто — первая загруженная). Галерея в карточке номенклатуры (сделать основной, порядок).
2. **Миниатюры** делает API при выдаче (`GET /attachments/:id/content?thumb=128`) с кэшем в S3 рядом с версией;
   библиотека (например `sharp`) — решение исполнителя. Миниатюры в списке номенклатуры и в подборе в документ.
3. **Шаблоны КП:** параметр строки «Картинка» в блоке `{{Товары}}` (флажок шаблона «с картинками»). PDF не ходит в
   сеть — воркер перед рендером читает миниатюру из S3 и подставляет `data:`.
4. **Готово, когда:** картинки грузятся и показываются в карточке, списке и подборе; КП с картинками печатается в PDF.

## Задача 1193 — внешние ссылки для контрагента (решения 2026-10-29)

1. `share_links` (воркспейс, что отдаём: вложение (текущая или конкретная версия) или PDF документа из `document_files`,
   хеш токена `sha256`, срок `expires_at`, отозвана, автор, создана) и `share_link_downloads` (ссылка, когда, IP, user-agent).
2. Публичный маршрут `GET /s/:token` — вне `TENANT_PATHS`, без сессии; токен в БД только хешем; по истёкшей или
   отозванной ссылке — 404. Rate-limit как у входа.
3. Создание — в меню файла и печати документа («Получить ссылку»: срок 1 / 7 / 30 дней или дата, копировать);
   список ссылок объекта с числом скачиваний, отзыв.
4. Почта отложена (задача 1092) — ссылку отправляют вручную.
5. **Готово, когда:** ссылка открывается без входа, истекает и отзывается; журнал скачиваний пишется; тест на
   подбор токена чужого воркспейса.

## Задача 1194 — шаблоны договоров в редакторе (решения 2026-10-29)

1. API `doc-templates` принимает все назначения 1С: `contract` («Договор контрагента»), `contract_order`
   («Договор + Заказ покупателя»), `contract_invoice` («Договор + Счёт»), `contract_work_order` («Договор +
   Заказ-наряд»). Редактор и разметка — те же, что у КП (`docs/architecture/quotes.md`).
2. **Параметры договора:** номер, дата, срок действия, вид, отсрочка оплаты; стороны — организация и контрагент
   (наименование, ИНН/КПП, ОГРН, адреса, банковские реквизиты, руководитель с должностью и основанием,
   «в лице … действующего на основании …»). Для составных назначений — параметры документа и блок `{{Товары}}`.
   Рендер — чистая функция в `packages/shared/src/print` рядом с `quote.ts`, общий разбор разметки.
3. **Печать:** в карточке договора меню «Печать» — шаблоны с `purpose = contract`; в заказе покупателя, счёте и
   заказ-наряде — шаблоны своего составного назначения (договор берётся из `documents.contract_id`, без договора —
   пункт недоступен). Предпросмотр и PDF — тем же путём, что КП (`document_files.template_id`); для договора без
   документа — PDF договора (`document_files` или своя таблица — решение исполнителя).
4. Стандартный встроенный шаблон «Договор поставки» / «Договор оказания услуг» — по одному на назначение.
5. **Готово, когда:** у договора и трёх видов документов печатается договор по шаблону; параметры сторон
   подставляются; тесты рендера в `packages/shared`.

## Задача 1195 — шаблоны договоров DOCX (решения 2026-10-29)

1. Шаблон может быть загруженным `.docx` (вложение шаблона, `doc_templates.source = 'docx'`) с теми же
   `{{параметрами}}`; строки документа — повтор строки таблицы Word с меткой `{{#Товары}}…{{/Товары}}`.
2. **Подстановка** — разбор `word/document.xml` (склеивание разорванных Word «прогонов» внутри `{{…}}`), библиотека
   (например `docxtemplater` + `pizzip`) — новая зависимость, решение записать в план. Работает в воркере (задача
   `document.docx`), результат — вложение договора / документа (версия при повторной генерации).
3. **На выходе только `.docx`** для правки юристом. PDF из DOCX не делаем (нужен LibreOffice в образе — отдельная
   задача, если понадобится).
4. Проверка шаблона при загрузке: список найденных параметров, незнакомые — предупреждение.
5. **Готово, когда:** загруженный `.docx` заполняется реквизитами и строками; файл открывается в Word / LibreOffice;
   тест на шаблон с разорванными прогонами.

## Задача 1196 — учёт оригиналов (решения 2026-10-29)

1. **Как в УНФ:** у первичных документов (реализация, акт, заказ-наряд, поступление, возвраты, счёт-фактура в составе
   УПД) и договоров — состояние оригинала `original_state`: `none` («не получен»), `scan` («получена копия / скан»),
   `original` («получен оригинал»); дата и кто отметил. Список видов документов — флаг в `DOCUMENT_META`.
2. **Договоры (по умолчанию):** `contracts.is_signed` заменяется состоянием оригинала — миграция переводит
   `is_signed = true` в `original`, остальные в `none`; колонку удаляет, а признак «подписан» во всех местах читается как
   `original_state = 'original'` (API отдаёт `isSigned` вычисляемым для совместимости, только чтение). Один источник
   правды.
3. «Скан» можно отметить загрузкой файла (вложение к документу ставит `scan`, если был `none`).
4. **Журнал «Учёт первичных документов»:** отбор по организации, контрагенту, периоду, виду, состоянию; массовая
   отметка выделенных; в журналах продаж и закупок — колонка и фильтр.
5. Узел автоматизации «Оригинал не получен N дней» — не в этой задаче (можно сделать на расписании позже).
6. **Готово, когда:** состояние ставится в карточке и журналом массово; `is_signed` удалён без потери данных;
   тесты API и миграции.

## Задача 1197 — простая электронная подпись (решения 2026-10-29)

1. **Что это:** подтверждение участника внутри программы — не криптография. `signatures` (воркспейс, что подписано:
   версия вложения или файл PDF документа, `sha256` подписанного содержимого, кто, должность на момент подписи, когда,
   IP, основание: «согласование» / «вручную», отозвана).
2. Подписать можно только конкретную версию: новая версия файла подпись не наследует; проверка — пересчёт `sha256`
   и сравнение («подпись действительна / файл изменён»).
3. **Штамп в PDF** (**по умолчанию**): воркер дописывает к PDF документа лист «Подписано простой электронной
   подписью» (ФИО, должность, дата, хеш) — рисуется текстом, без картинок, сети не требует. Печать и подписи
   организации остаются ссылками (ответ пользователя).
4. **Готово, когда:** подпись версии и PDF, проверка, штамп; тест «изменённый файл не проходит проверку».

## Задача 1198 — внутренние документы (решения 2026-10-29)

1. Новый вид учётного документа `internal_doc` (группа `docflow`, без строк — как `payment_request`), вид внутреннего
   документа — справочник (приказ, служебная записка, положение, распоряжение…), номер по префиксу вида, организация,
   тема, текст (разметка как в шаблонах), ответственный, вложения.
2. Проведение = регистрация (присваивает номер). Печать — по тексту, с подписантами.
3. Раздел меню «Документооборот»: внутренние документы, корреспонденция (1200), учёт оригиналов (1196),
   согласования (1199).
4. **Готово, когда:** документ создаётся, регистрируется, печатается; тест API.

## Задача 1199 — согласование (решения 2026-10-29)

1. **Маршруты** — справочник `approval_routes`: название, к чему применяется (вид объекта: договор, вид учётного
   документа, заявка на расход, вид внутреннего документа), условие (организация, сумма от / до), обязательный ли
   («без согласования нельзя провести / подписать»), этапы `approval_route_steps` (порядок, режим этапа
   `sequential | parallel`, участники — конкретный участник или должность (задача 1172), срок в часах).
2. **Процесс:** «Отправить на согласование» создаёт `approvals` (объект, маршрут — снимок этапов, состояние
   `in_progress | approved | rejected | cancelled`) и задачи согласующим (`approval_tasks`: решение
   `approve | reject | comment`, комментарий, когда). Отклонение — процесс `rejected`, автор правит и отправляет
   заново (новый круг, история кругов сохраняется). Согласование с ПЭП (1197): решение «согласовать» подписывает
   текущую версию PDF / вложения.
3. **Связь с учётом:** при обязательном маршруте проведение документа и отметка «подписан» отвечают 422
   `approval_required`, пока процесс не `approved`. **Заявки на расход:** если для заявки есть маршрут, состояния
   `pending → approved / rejected` ведёт процесс согласования вместо ручного согласования admin+; без маршрута —
   как сейчас.
4. **Лист согласования** — печатная форма (кто, решение, когда, комментарий, подпись) и вкладка в карточке объекта.
5. **Уведомления и просрочка:** уведомление согласующему, автору — о решении; проход воркера по сроку этапа
   (просрочено — уведомление и событие).
6. **Автоматизации:** триггеры «Согласование завершено (согласовано / отклонено)», «Этап просрочен»; действие
   «Отправить на согласование».
7. **Интерфейс:** «Мои согласования» (входящие решения), кнопки в карточке объекта, настройка маршрутов (admin+).
8. **Готово, когда:** последовательный и параллельный маршрут проходят; обязательный блокирует проведение; заявка на
   расход согласуется маршрутом; лист печатается; тесты API, RLS и узлов.

## Задача 1200 — журналы корреспонденции (решения 2026-10-29)

1. `correspondence` (воркспейс, направление `in | out`, рег. номер (автонумерация по направлению и году) и дата
   регистрации, номер и дата у отправителя, корреспондент — компания / контакт, организация, тема, содержание кратко,
   способ доставки (почта, курьер, email, ЭДО, лично), «в ответ на» — ссылка на другое письмо, вложения).
2. **Исполнение входящего:** исполнитель и срок ответа — через задачу (`tasks`, модуль `docflow`), статус письма
   «на исполнении / исполнено» по задаче; исходящий ответ закрывает входящее.
3. Журналы «Входящие» и «Исходящие» с отборами, карточка письма, вкладка «Переписка» у компании.
4. **Готово, когда:** регистрация, нумерация, связь «в ответ на», задача исполнителю; тест API.

## Задача 1201 — ЭДО без оператора, выгрузка XML (решения 2026-10-29)

1. Выгрузка УПД (реализация, заказ-наряд; функция СЧФДОП / ДОП) и акта (формат передачи результатов работ) в XML
   форматов ФНС. **Версию формата и XSD исполнитель сверяет по актуальным приказам ФНС сам** — по памяти не вписываем.
2. Имя файла и идентификаторы участников по правилам формата (без оператора — идентификаторы-заглушки, описать).
3. Генерация — чистые функции в `packages/shared` с проверкой по XSD в тестах; кнопка «Выгрузить XML» в печати
   документа и пакетная выгрузка архивом (как выгрузка PDF, `document_exports`).
4. **Готово, когда:** XML проходит XSD; выгружается одиночно и архивом.

## Задача 1202 — ЭДО без оператора, загрузка XML (решения 2026-10-29)

1. Загрузка входящего УПД / акта (XML ФНС) → черновик поступления (`receipt`) или акта поставщика с сопоставлением:
   контрагент по ИНН/КПП (нет — предложить создать), номенклатура по коду / артикулу / наименованию поставщика
   (запоминаем соответствие в справочнике «Номенклатура поставщика»), единицы по ОКЕИ, НДС.
2. Мастер сопоставления: несопоставленные строки, создать товар или выбрать существующий.
3. Исходный XML — вложение созданного документа (1191); повторная загрузка того же файла — предупреждение о дубле.
4. **Готово, когда:** входящий УПД превращается в черновик поступления; соответствия запоминаются; тест на образце.

## Риски

- **Полиморфные вложения** без FK — проверка объекта и прав только в сервисе; нужен тест на каждый тип объекта.
- **Хранилище в проде:** бакет, ключи и резервное копирование MinIO на VPS — дописать в `docs/architecture/deploy.md`;
  без S3 загрузка файлов не работает (dev — MinIO из compose).
- **Форматы ФНС** меняются приказами; привязка к версии и XSD — в задаче 1201.
- **DOCX:** сложные шаблоны (поля Word, вложенные таблицы) могут не поддерживаться выбранной библиотекой.
