# Объектный учёт (стройка, электромонтаж, EPC)

Статус: **ядро начато**: справочник объектов (задача 1268), смета объекта (задача 1269), бюджет с контролем затрат по категориям
(задача 1270), табель прораба с бейджами и стоимостью часа (задача 1271), процент выполнения и вехи (задача 1272) реализованы, сессия 57. Решения пользователя — [docs/plans/2026-11-06-construction.md](../plans/2026-11-06-construction.md).
Блок включается отраслевой опцией `construction` (задача 1258). Раздел «Объект» ниже описывает фактическую реализацию; остальные разделы — проект.

## Слои

- **Ядро** (любая проектная компания): объект, смета-бюджет, факт затрат, вехи и процент выполнения, прогноз прибыли, контроль бюджета.
- **Полевые работы** (пилот электромонтажа): табель прораба с бейджами, сменный отчёт объёмов, щиты из производства.
- **Стройка РФ**: акты КС-2/КС-3, субподряд с актами субподрядчика.

## Объект

`objects` (схема `packages/db/src/schema/objects.ts`, миграция `0093_objects`): `workspace_id`, `number` (код, уникален в воркспейсе),
`name`, `customer_id` (`companies`, составной FK), `address`, `start_date`, `due_date`, статус (`planning | active | hold | done | closed`),
`manager_id` (`members`), способ выручки (`revenue_mode`: `acts | milestones | hours`), `overhead_pct numeric(5,2)`,
`budget_policy` (`none | warn | block`, по умолчанию `warn`, миграция `0096_object_budget` — контроль бюджета, задача 1270),
`progress_mode` (`tasks_closed | tasks_avg | task_weights | estimate_volume | manual`, по умолчанию `tasks_closed`) и
`progress_manual numeric(5,2)` — способ расчёта процента выполнения (задача 1272, раздел «Процент выполнения»),
`project_id` (проект задач, составной FK с `ON DELETE SET NULL (project_id)`), `warehouse_id` (склад объекта), `note`, `archived_at`.
У задач есть вес `tasks.weight numeric(10,2)` (null — 1) для расчёта по весам.
Прорабы — `object_foremen (workspace_id, object_id, member_id)`, договоры — `object_contracts (workspace_id, object_id, contract_id)`;
ссылки на проекты, склады и договоры — составные FK, добавленные миграцией.

Аналитика «объект» (`object_id`, составной FK с `ON DELETE SET NULL (object_id)`, индекс) у документов (`documents`),
строк платежей (`payment_lines`), задач (`tasks`) и записей времени (`time_logs`). Затраты и выручка объекта собираются из этих
источников, отдельного регистра-дубля нет. В документах, задачах и времени объект проверяется при записи: свой воркспейс, не в архиве.

Настройка воркспейса `workspaces.object_overhead_pct numeric(5,2) NOT NULL DEFAULT 0` подставляется в новый объект, если процент
не указан. При создании объекта без `project_id` сервис заводит проект задач модуля `general` с именем объекта и уникальным ключом.

Права: видеть объект может участник; создание и правка — member и выше; архивирование (`DELETE /objects/:id`, удаление = архив) —
admin и выше. Деньги карточки (суммы документов и платежей, себестоимость остатков) — owner и admin (`canSeeCost`), остальным
сервер отдаёт `null`. Прораб ведёт табель только назначенных ему объектов (следующие задачи блока).

Маршруты API (`apps/api/src/routes/objects.ts`, путь `/objects` в TENANT_PATHS и модуле `trade`): `GET/POST /objects`,
`GET/PATCH/DELETE /objects/:id`, `GET /objects/:id/summary`, `GET /objects/:id/budget`, `GET /objects/:id/progress`
и CRUD вех `GET/POST /objects/:id/milestones`, `PATCH/DELETE /objects/:id/milestones/:milestoneId`,
`POST …/done` и `…/accept`. Карточка: список, форма и вкладки «Смета», «Вехи», «Бюджет»,
«Задачи», «Документы», «Платежи», «Склад»
(`apps/web/src/app/objects/`). Раздел скрыт без опции `construction` (`INDUSTRY_OF_SECTION`), поля «Объект» в документе, строке платежа
и задаче показываются при включённой опции или если значение уже задано.

## Смета

**Реализовано (задача 1269).** Схема — `packages/db/src/schema/objects.ts` (миграция `0095_object_estimates`), расчёт итогов —
`packages/shared/src/estimates.ts`, сервис — `packages/db/src/estimates.ts`, API — `apps/api/src/routes/estimates.ts`,
интерфейс — вкладка «Смета» карточки объекта (`apps/web/src/app/objects/EstimateTab.tsx`), статья — `docs/user/construction/estimates.md`.

| Таблица | Что хранит |
|---|---|
| `object_estimates` | смета: `number`, `name`, `status draft\|approved`, `approved_at`, `approved_by` (members), `parent_id` (основная смета для допработ), `kind main\|change`, `change_status draft\|approved\|rejected` (только у допработ), `note` |
| `object_estimate_sections` | раздел сметы: название, порядок |
| `object_estimate_items` | позиция: вид `work\|material\|panel\|subcontract\|other`, наименование, `product_id` (материал, субподряд), `manufactured_item_id` (щит), единица ОКЕИ, `qty numeric(18,3)`, `price numeric(18,2)` (заказчику, без НДС), `vat_rate`, `cost_price numeric(18,2)` (плановая внутренняя стоимость единицы), `labor_hours numeric(18,3)` (норма часов на единицу), `note` |

У объекта ровно одна основная смета — частичный уникальный индекс по `(workspace_id, object_id) where kind = 'main'`; допработ
у объекта сколько угодно. Все связи — составные FK `(workspace_id, id)`, удаление объекта и сметы каскадное, `ON DELETE SET NULL`
у необязательных ссылок (`section_id`, `product_id`, `manufactured_item_id`, `approved_by`).

- **Согласование.** `draft → approved` фиксирует снимок цен и норм — базу план-факта; правка каталога и закупочных цен его не меняет.
  Согласованную смету нельзя править, дополнять и удалять (422 `estimate_approved`), согласовать можно только смету с позициями (422 `no_items`).
  Возврат в черновик — только owner/admin (403 остальным); пока фактов затрат нет, возврат разрешён всегда (TODO задачи 1275 — запретить при наличии фактов).
- **Допработы** — отдельные сметы `kind = 'change'` с `parent_id` основной; создаются только к согласованной основной смете (422 `estimate_not_approved`),
  имеют свой статус (`change_status`), несогласованные стоимость договора не увеличивают.
- **Ввод:** вручную (разделы и позиции таблицей), копирование сметы другого объекта (создаёт основную смету этого объекта), импорт таблицы
  с сопоставлением колонок в интерфейсе (файл разбирает тот же модуль `apps/api/src/xlsx.ts`, что и прайс-лист). Нормативных баз (ГЭСН/ФЕР) нет.
- **Итоги** — чистые функции `computeEstimateTotals` / `estimateLineTotals` / `estimatePlanFact` на десятичных (`dec`/`fmt`): сумма заказчику,
  плановая себестоимость, плановые часы, маржа и маржа в процентах (при нулевой сумме не считается). Округление — до копейки по строке (часы — до тысячных),
  итоги складывают округлённые строки, как в документах.
- **План-факт:** по позиции отдаётся план (сумма, себестоимость, часы), факт и остаток. Факт по-прежнему нулевой: источники подключат задачи 1274/1275;
  точка расширения — `estimateFacts()` в `packages/db/src/estimates.ts`. Выполненный объём `done_qty` уже растёт от сменного отчёта прораба (задача 1271).
- **Заказы из позиций.** Заказ поставщику — позиции «материал» и «субподряд» с `product_id` (цена строки — закупочная цена товара),
  заказ на производство — позиции «щит» с `manufactured_item_id`; у обоих документов `object_id` — объект сметы. Пустой набор позиций — 422 `nothing_to_create`.
- **Права.** Чтение — участник, запись (смета, позиции, согласование, допработы, импорт, заказы) — member и выше, возврат в черновик — admin и выше.
  Себестоимость, маржа и `cost_price` отдаются только owner/admin (`canSeeCost`), остальным — `null`.
- **Маршруты API** (`/objects` и `/estimates` — пути в TENANT_PATHS, модуль `trade`): `GET/POST /objects/:id/estimates`,
  `POST /objects/:id/estimates/copy`, `GET/PATCH/DELETE /estimates/:id`, `PUT /estimates/:id/items` (пакетное сохранение разделов и позиций),
  `POST /estimates/:id/approve|unapprove|changes|import|supplier-order|production-order`, `POST /estimates/import/preview` (разбор файла для сопоставления колонок).
  События outbox: `object_estimate.created|updated|deleted|approved|unapproved|imported`.

## Факт затрат

**Реализовано по категориям (задача 1270)** — сервис `packages/db/src/object-budget.ts` (функция `objectCostFacts`): факт считается
по проведённым документам и платежам с аналитикой объекта, без НДС. По позициям сметы факт пока не распределяется — смета показывает
его в итогах по категориям, у строк факт нулевой. Распределение по позициям, труд и накладные — задачи 1271/1274/1275.

| Категория | Источник факта (реализовано) |
|---|---|
| Материалы (`material`) | Себестоимость расхода по движениям склада (`stock_moves` × цена с корректировками закрытия) проведённых документов объекта с ролью «расход»: списание, выпуск, распределение материалов, заказ-наряд. Перемещение на склад объекта и накладные о приходе затратой не являются |
| Труд (`labor`) | Сумма `cost_amount` строк подтверждённых смен объекта (табель прораба, задача 1271). Строка без стоимости часа (нет ни почасовой ставки, ни оклада) даёт пробел, а не ноль |
| Субподряд (`subcontract`) | Строки поступлений (`receipt`) с объектом, где товар — услуга (`products.kind = 'service'`), сумма строки без НДС |
| Прочие прямые (`other`) | Документы «Прочие затраты» (`other_costs`) с объектом целиком плюс расходные строки платежей с объектом без документа-основания (см. правило ниже) |
| Накладные | Процент объекта от прямых затрат — не реализовано (прогноз, задача 1274) |

**Правило учёта платежей.** Факт «прочие прямые» берёт только расходные строки платёжных документов (`cash_payment`, `bank_payment`,
`advance_report`) с `payment_lines.object_id`, у которых пуст `settlement_document_id` (ссылка на документ расчётов) и статья ДДС
расходная; перемещение денег между своими счетами исключено. Оплата поставщику по поступлению приходит со ссылкой на документ
и в факт не попадает — иначе субподряд по поступлению посчитался бы дважды. Аванс поставщику без документа-основания в факт попадает:
это платёж, а не оплата уже учтённого документа.

**Стоимость часа** — из зарплаты (чистая функция `laborHourCost`, `packages/shared/src/labor-cost.ts`, тест `packages/shared/test/labor-cost.test.ts`):
почасовая ставка `employee_payroll.hourly_rate numeric(18,2)`, если она задана; иначе оклад (действующее на дату работы начисление
`employee_accruals` вида `salary`) / норма часов месяца (рабочие дни месяца по графику сотрудника — `members.calendar_id`, иначе график
воркспейса, — × `work_calendars.hours_per_day`); сверху взносы `workspaces.payroll_insurance_rate` процентом. Деньги — `dec`/`fmt`, без float.
Нет ни ставки, ни оклада — стоимости нет (`null`, пробел, не ноль): смена подтверждается, а в факте и интерфейсе видно «нет ставки».
Снимок стоимости часа (`cost_rate`) и суммы строки (`cost_amount`) фиксируется при подтверждении смены.

## Табель прораба

**Реализовано (задача 1271).** Итог часов за смену: прораб выбирает объект и дату, бригаду (вручную или сканом бейджа), ставит часы пакетом
с исключениями и распределяет по позициям сметы. Часы живут **только в новых таблицах смен** (`time_logs` не трогаем) — второй копии
часов нет. Работа онлайн. Схема — `packages/db/src/schema/objects.ts` (миграция `0099_object_shifts`), сервис — `packages/db/src/object-shifts.ts`,
API — `apps/api/src/routes/object-shifts.ts`, интерфейс — экран «Смена прораба» (`apps/web/src/app/shifts/`) и вкладка «Табель» карточки объекта
(`apps/web/src/app/objects/ShiftsTab.tsx`), статья — `docs/user/construction/shifts.md`.

| Таблица | Что хранит |
|---|---|
| `object_shifts` | смена: `object_id`, `work_date`, `foreman_id` (members), `status draft\|confirmed` (CHECK + согласованность с `confirmed_at`/`confirmed_by`), `confirmed_by`, `confirmed_at`, `note`, `created_by`; уникальна `(object_id, work_date, foreman_id)` |
| `object_shift_hours` | часы работника: `member_id`, `estimate_item_id` (позиция вида `work`, необязательна; `ON DELETE SET NULL (estimate_item_id)`), `hours numeric(6,2)` > 0 и ≤ 24 (CHECK), снимок `cost_rate`, `cost_amount`, `note` |
| `object_shift_volumes` | сменный отчёт объёмов: `estimate_item_id` (каскад), `qty numeric(18,3)` > 0, уникально `(shift_id, estimate_item_id)` — объём один раз на бригаду |
| `object_shift_log` | журнал смены: `author_id`, `at`, `action` (`created\|updated\|confirmed\|unconfirmed`), `before`/`after` (jsonb — часы и объёмы), `reason` |

- **Статусы.** `draft → confirmed`. Подтверждает прораб объекта (участник в `object_foremen`) или admin/owner. Правка и отмена подтверждения —
  только admin/owner и только с причиной: пишется строка журнала (кто, когда, что было → что стало, причина) и событие outbox
  `object_shift.created|updated|confirmed|unconfirmed`. Черновик правит прораб своего объекта.
- **Пакетный ввод.** Тело `PUT /shifts/:id` — массив строк «работник × часы × позиция» и массив объёмов; строки одной пары работник × позиция
  складываются (повторный скан не создаёт дубль), сумма часов работника за смену ≤ 24 (422 `shift_hours_exceed`). Позиции часов — только
  вида `work` сметы этого объекта.
- **Снимок и затраты.** При подтверждении в каждой строке фиксируются `cost_rate` (стоимость часа из зарплаты, раздел «Факт затрат») и
  `cost_amount` = часы × ставка до копейки; новая ставка прошлые затраты не меняет. Факт труда объекта (`labor` в `objectCostFacts`) —
  сумма `cost_amount` подтверждённых смен. После записи вызывается `assertObjectBudget`: `warn` возвращает коды `budget_exceeded:<категория>`
  в `warnings` ответа и пишет событие `object.budget_exceeded`, `block` бросает 422 `budget_exceeded` и откатывает подтверждение.
- **Объёмы и выполнение.** Объём смены прибавляется к `object_estimate_items.done_qty` при подтверждении и вычитается при отмене
  (не ниже нуля); больше `qty` позиции — 422 `done_qty_exceeds`. Правка подтверждённой смены откатывает старый объём и применяет новый.
  Так выполнение сметы растёт от сменного отчёта, ручной ввод `done_qty` во вкладке «Смета» остаётся.
- **Права.** Прораб (роль `member`) ведёт смены только объектов, где он в `object_foremen`, и только от своего имени (403 `forbidden`);
  admin/owner — любые объекты и любой `foreman_id`. Ставки и суммы (`cost_rate`, `cost_amount`, `totalAmount`) отдаются только owner/admin
  (`canSeeCost`), прорабу — `null`. Бейджи, табельные номера, печать и рабочие без входа — admin и выше.
- **Рабочие без входа.** Участник воркспейса без `user_id` и **без `membership`** (`POST /members/workers`: имя, табельный номер, служебная
  уникальная почта `worker-…@workers.invalid`); инвариант «есть `user_id` — есть `membership`» не нарушается. Место в лимите пользователей
  тарифа они не занимают.
- **Бейджи.** `members.badge_code` (уникален в воркспейсе среди непустых, `'W'` + 8 символов base32 без 0/O и 1/I — `badgeCode` в
  `packages/shared/src/badge.ts`) и `members.personnel_number` (табельный номер, text). Выпуск и перевыпуск (`POST /members/:id/badge`) просто
  заменяют код — старый отзывается. Скан: камера через `BarcodeDetector` (если браузер умеет) плюс ручной ввод кода; поиск
  `GET /members/badge/:code` отвечает 404 `badge_not_found` для неизвестного и отозванного кода, запись не создаётся. Печать —
  `GET /members/badges/print` (HTML A4: имя, табельный номер, QR через `qrSvg`, печатная форма `packages/shared/src/print/badges.ts`).
- **Табель за период.** `GET /objects/:id/timesheet?from&to` — работник × дни по подтверждённым сменам; `GET /objects/:id/shifts` — смены
  объекта за период (статус, часы, сумма только admin/owner, число работников без ставки). `GET /shifts/objects` — объекты, на которых
  участник может вести смену.
- **Маршруты API.** Пути `/objects` и `/members` (модуль `trade`/`core`) и новый `/shifts` (`TENANT_PATHS`, модуль `trade`):
  `GET/POST /objects/:id/shifts`, `GET /objects/:id/shifts/options`, `GET /objects/:id/timesheet`, `GET /shifts/objects`, `GET/PUT /shifts/:id`,
  `POST /shifts/:id/confirm|unconfirm`, `POST /members/workers`, `GET /members/badge/:code`, `GET /members/badges/print`, `POST /members/:id/badge`.
  Коды ошибок: `shift_hours_exceed`, `shift_confirmed`, `shift_not_confirmed`, `shift_reason_required`, `shift_empty`, `badge_not_found`
  (`errors.*` в словарях en/ru). Событие `object_shift` инвалидирует кэш смен, объектов и смет во фронтенде.
- **Демо.** Три рабочих без входа с табельными номерами и бейджами, у первого почасовая ставка, у второго оклад, у третьего ставки нет;
  две подтверждённые смены прошлой недели с распределением по позициям и объёмом (`packages/db/src/seed-objects.ts`).
- **Не сделано:** офлайн-черновик на телефоне (после пилота), фото и комментарии смены, материалы смены, проверка пересечений смен,
  ночные и сверхурочные правила.

## Выручка

- **Акты (КС-2/КС-3):** принятые объёмы по позициям × цена согласованной сметы и допработ; печатные формы по-русски.
- **Вехи:** фиксированная сумма или процент договора за этап; аванс — отдельно, не выполнение.
- **Часы:** подтверждённые часы × ставка для заказчика.

Состояния не смешиваются: выполнено, принято заказчиком, выставлено, оплачено — разные показатели.

## Процент выполнения

**Реализовано (задача 1272).** Способ хранится на объекте (`objects.progress_mode`), процент не хранится и считается на лету
чистой функцией `computeObjectProgress` (`packages/shared/src/object-progress.ts`) — её же использует интерфейс.
Результат — строка с одним знаком после запятой (десятичная арифметика `dec`/`fmt`, без float); `null` — базы расчёта нет.
Сервис — `packages/db/src/object-progress.ts` (`objectProgress`), маршрут `GET /objects/:id/progress`.

| Режим | Процент | База отсутствует |
|---|---|---|
| `tasks_closed` (по умолчанию) | доля неархивных задач объекта в завершённых статусах | у объекта нет задач |
| `tasks_avg` | средний прогресс задач: у задачи нет поля прогресса, поэтому завершённая = 100, остальные = 0 | у объекта нет задач |
| `task_weights` | доля завершённых с весами задач; `tasks.weight` (null или 0 — 1) | нет задач или сумма весов 0 |
| `estimate_volume` | `Σ done_qty × price / Σ qty × price` позиций согласованной основной сметы и согласованных допработ | нет согласованной сметы или её сумма нулевая |
| `manual` | `objects.progress_manual` (0–100) | ручной процент не задан |

Завершённый статус задачи — встроенный `done` (ключи `done`/`closed`, `CLOSED_TASK_STATUSES`): категории статусов в схеме нет,
пользовательские колонки получают случайный ключ. Выполненный объём позиции (`done_qty`) вводится вручную во вкладке «Смета»
и правится **и у согласованной сметы** — это факт, а не состав (`PATCH /estimates/:id/done-qty`, маршрут в `apps/api/src/routes/estimates.ts`);
`done_qty > qty` — 422 `done_qty_exceeds`. Сменный отчёт прораба (задача 1271) прибавляет объём при подтверждении смены и вычитает при отмене. Ответ прогресса содержит
режим, процент, базу (число задач и закрытых, веса, суммы сметы) и стоимость договора — интерфейс показывает индикатор `Progress`
в шапке карточки и поле «Как считать выполнение» (ручной процент — только в режиме `manual`).

## Вехи

**Реализовано (задача 1272).** Таблица `object_milestones` (миграция `0098_object_progress`, составной FK на объект с каскадом):
`name`, `due_date`, `kind` (`stage` — этап, `advance` — аванс), `sort_order`, `amount numeric(18,2)` **или** `pct numeric(5,2)`
(ровно одно — CHECK), `done_at` и `accepted_at` (выполнено и принято заказчиком — разные события; принято только после выполнено),
`note`. Сервис — `packages/db/src/object-progress.ts`, интерфейс — вкладка «Вехи» (`apps/web/src/app/objects/MilestonesTab.tsx`),
статья — `docs/user/construction/milestones.md`.

- **Сумма вехи** для отображения: `amount` или `pct × стоимость договора`. Стоимость договора — сумма заказчику согласованной
  основной сметы и согласованных допработ без НДС (`objectContractValue`). Нет согласованной сметы — у вехи-процента сумма `null`.
- **Сводка** (`summarizeMilestones`): по вехам этапов «выполнено» и «принято»; аванс — отдельной строкой и в выполнение **не входит**.
  «Выставлено» и «Оплачено» здесь не хранятся: их даст задача 1273 (акты и счета) — в ответе `invoiced`/`paid` равны `null`.
  Сумма не считается (`null`), если хотя бы у одной вехи-процента нет стоимости договора.
- **Права.** Чтение — участник, запись (создание, правка, удаление, отметки) — member и выше. Деньги вех — это цена для заказчика,
  а не себестоимость, поэтому их видят все участники (в отличие от бюджета и себестоимости карточки).
- **Маршруты.** `GET /objects/:id/milestones` (список, сумма каждой вехи и сводка), `POST /objects/:id/milestones`,
  `PATCH/DELETE /objects/:id/milestones/:milestoneId`, `POST …/done` и `…/accept` (тело `{done}`/`{accepted}`, снятие отметки).
  События outbox: `object_milestone.created|updated|deleted|done|undone|accepted|unaccepted`;
  realtime перечитывает объекты по событию `object_milestone`.

## Прогноз прибыли и бюджет

**Бюджет реализован (задача 1270).** Бюджет категории = сумма `qty × cost_price` позиций согласованной основной сметы объекта
плюс согласованных допработ (`kind = 'change'`, `change_status = 'approved'`). Вид позиции → категория: `material` и `panel` → `material`,
`work` → `labor`, `subcontract` → `subcontract`, `other` → `other` (маппинг — `ESTIMATE_KIND_CATEGORY` в `packages/shared/src/estimates.ts`).
Нет согласованной сметы — бюджета нет, контроль не действует. Бюджет, факт, остаток и перерасход — функция `objectBudget`,
правила факта — `objectCostFacts` (`packages/db/src/object-budget.ts`). Вкладка «Бюджет» карточки объекта
(`apps/web/src/app/objects/BudgetTab.tsx`) показывает категории, полосу заполнения и перерасход красным; вкладка «Смета» повторяет
факт и остаток по категориям. Суммы — только owner/admin (`canSeeCost`), остальным сервер отдаёт `null` (структура категорий видна).

**Контроль бюджета.** Поле объекта `objects.budget_policy`: `none` — не контролировать, `warn` — предупредить (по умолчанию),
`block` — запретить. При проведении документа, который даёт факт (`write_off`, `production`, `material_allocation`, `work_order`,
`receipt`, `other_costs`), или платёжного документа с объектом в строках вызывается `assertObjectBudget` **внутри транзакции проведения
после записи движений**: факт считается заново, и если он больше бюджета категории — `block` бросает 422 `budget_exceeded`
(`details: { category, budget, fact }`, проведение откатывается), `warn` добавляет код `budget_exceeded:<категория>` в `warnings`
ответа проведения и пишет событие `object.budget_exceeded`. Предупреждения проверяют все четыре категории, поэтому одна проводка
может дать несколько кодов. Документы, которые факт не меняют (заказы, счета, продажи), бюджет не проверяют.

- Прогноз (остаток по темпу, прибыль, дата прогноза) — задача 1274, не реализован.
- Остаток по позиции — по темпу: (факт затрат / факт объёма) × оставшийся объём; ответственный может заменить оценку с причиной.
- Прогноз себестоимости = факт + остаток; прибыль = подтверждённая стоимость (смета + согласованные допработы) − прогноз; маржа при нулевой стоимости не считается.
- Показываются источник и дата прогноза, пробелы данных (нет ставки, цены, оценки).
