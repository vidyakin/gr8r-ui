# План производства и пополнение

Реализовано на этапе 5 (сессия «УНФ: Производство»). Код: схема — `packages/db/src/schema/production.ts`
(миграция `0020_production_plans.sql`), чистый расчёт — `packages/shared/src/replenishment.ts`, сервисы —
`packages/db/src/production-plans.ts`, `stock-levels.ts` и `replenishment.ts`, API — `apps/api/src/routes/production-plans.ts`
и `routes/stock-levels.ts` (+ `/production/needs/*` в `routes/production.ts`), клиент — `apps/web/src/app/production/ProductionPlansPage.tsx`,
`ProductionPlanPage.tsx`, `PlanOrdersPage.tsx`, `ProductionNeedsPage.tsx`, `plans-data.ts` и вкладка `catalog/stock-levels.tsx`.

- **План производства — объём выпуска по периодам.** `production_plans (workspace_id, name, period_from, period_to,
  step: week|month, status: draft|approved, warehouse_id, work_center_id?, semi_dirty, comment)` и
  `production_plan_lines (plan_id, item_id, period_start, qty, is_semi)`. Строка — «изделие × период»:
  **дата начала периода = дата выпуска**, ячейка в интерфейсе — сколько выпустить к этой дате. Разрез плана —
  склад готовой продукции (обязателен) и участок-диспетчер (необязателен); несколько планов на период допустимы.
  Заказы создаются **только по утверждённым** (`422 plan_not_approved`). Полуфабрикаты — обычные строки с флагом
  `is_semi`, добавленные кнопкой.
- **Периоды и срок изготовления.** Периоды считает чистая функция `planPeriods` (неделя или месяц; последний день
  месяца и дальше идёт последним днём). Дата запуска = выпуск минус `manufactured_items.lead_days` рабочих дней
  по календарю воркспейса (`startBeforeLead`, `calendarContext` этапа 4г) — показывается в плане и переносится
  в плановый старт заказа. Для закупки срок поставки — `products.lead_days`.
- **Заполнение плана** (`POST /production-plans/:id/fill`) — вручную в таблице, **по статистике выпуска**
  (среднее по проведённым `production` за N прошлых периодов), **по статистике продаж** (среднее по проведённым
  `realization`) и **по заказам покупателей** (неотгруженный и не покрытый производством остаток открытых заказов —
  в период по сроку отгрузки). Режимы `replace` и `add` (add суммирует по изделию и периоду). Пустая история даёт
  пустой результат, а не ошибку.
- **Полуфабрикаты кнопкой** (`POST /production-plans/:id/semi`): для ПФ в режиме `semi_mode = stock` строки
  добавляются пропорционально продукции (чистая функция `semiPlan`), одинаковые суммируются, дата сдвигается
  на срок изготовления и попадает в тот период плана, куда она попала. Правка продукции ставит флаг
  `semi_dirty` — интерфейс показывает предупреждение «перепланировать полуфабрикаты»; кнопка снимает флаг.
  `POST …/semi/remove` удаляет только строки ПФ.
- **Потребности плана** (`GET /production-plans/:id/needs`, считаются запросом): материалы и работы —
  развёрткой `explodeBom` по каждой строке плана; **полуфабрикаты** — потребление / выпуск / излишек-дефицит;
  **часы участков против мощности** — `loadVsCapacity` и `periodCapacity` по календарю участка, нехватка помечается;
  **трудозатраты** — часы × ставка участка (сумма видна только admin и owner, `canSeeCost`).
- **План-факт** — по каждой строке плана: запланировано, заказано (позиции заказов на производство этой строки,
  связь `production_items.plan_line_id`) и выпущено (проведённые выпуски по этим заказам).
- **Заказы по плану** — рабочее место `/production/plan-orders`: утверждённые планы по периодам, строки с
  остатком «план − уже заказано». `POST /production-plans/:id/orders` создаёт черновики `production_order`
  (финиш = дата выпуска, старт = дата запуска, склад продукции — цель); повторный запуск не дублирует, потому что
  заказанным считается всё, что уже стоит в заказах по этой строке плана. Связь заказа со строкой плана — колонка
  `production_items.plan_line_id`: она же даёт план-факт «заказано» и остаток, отдельная таблица дублировала бы
  те же данные.
- **Нормы запаса** — `stock_levels (workspace_id, product_id, warehouse_id?, min_qty, max_qty,
  replenishment: purchase|production|transfer, source_warehouse_id?)`. Строка без склада — **норма по компании**
  (действует в расчёте по компании), строки со складом — в расчёте по складам (частичные уникальные индексы).
  CHECK: `min ≤ max`; перемещение — только у нормы склада, нужен склад-источник, отличный от склада-получателя
  (`422 source_warehouse_required` / `same_warehouse`). Способ пополнения по умолчанию
  берётся из `product_manufacturing.replenishment`. Служебные функции: `GET/PUT /stock-levels`,
  `GET /stock-levels/suppliers?productId=` (цены поставщиков маскируются по роли).
- **Общий расчёт потребностей** (`GET /production/needs/calculate`) — обработка УНФ «Расчёт потребностей в запасах»:
  остатки, резервы, заказы покупателей, заказы поставщикам, заказы на производство и **утверждённые планы
  производства (только та часть, что ещё не передана в заказах)**. Расчёт по складам (строки норм складов; движения
  только своего склада: склад документа, у заказа на производство — склад продукции для прихода и склад материалов для
  расхода, у плана — его склад для продукции и склад участка-диспетчера для материалов; документ без склада — склад
  по умолчанию) или по компании (строки норм без склада, все движения),
  фильтр по способу пополнения, шаг день/неделя/месяц, число периодов и дата начала. **Резерв показывается
  отдельной колонкой и в прогноз не вычитается** — иначе потребность заказа покупателя считалась бы дважды.
  Три шага: рекомендации → планирование → заказы (`POST /production/needs/orders`, `POST /production/needs/post`).
  На шаге планирования у строки правятся способ пополнения, дата и источник (поставщик, участок, склад-источник);
  перемещение без склада-получателя пропускается (`no_target_warehouse`). Дата черновика — дата дефицита, но не раньше «сегодня + срок» (поставки или изготовления). Черновики: закупка → `supplier_order` на склад строки (поставщик строки выбирается на шаге планирования из тех, у кого
  товар покупали, — с ценой и датой последнего поступления; по умолчанию `default_supplier_id` или последнее поступление;
  цена — последняя цена этого поставщика), производство → `production_order` (старт = поступление минус срок изготовления),
  перемещение → черновик `stock_transfer` со склада-источника. Группировка: способ, контрагент (поставщик строки, участок
  или склад-источник), склад-получатель и дата; переключатели «одной датой» и «отдельно под каждый заказ покупателя». Документы создаются
  непроведёнными, список с массовым проведением. Воркера и уведомлений на этом этапе нет.
- **Методики** (чистые функции `packages/shared/src/replenishment.ts`): *по заказам + мин./макс.* — прогноз остатка
  по периодам (`stockForecast`), правило «по итогу периода остаток не выше минимума → заказать максимум плюс
  потребление минус излишек над минимумом» (`minMaxRecommendation`; пример мин 10, макс 20, отгрузки 5, остаток 2 → 25),
  колонка **Overdue** — движения с прошедшей датой плюс добор до максимума при остатке ниже минимума;
  *по продажам min-max* (`salesMinMax`) — только остаток против минимума и максимума; *по статистике продаж*
  (`salesStatistics`) — средние продажи в день (проведённые реализации за N прошлых периодов до даты начала, дни — по
  календарю шага) × (срок поставки + страховые дни) либо в процентах от плановой потребности
  (процент может быть отрицательным); количества округляются до тысячных.
- **Интерфейс:** `/production/plans` — журнал планов, `/production/plans/:id` — карточка с периодами в колонках,
  вкладками **Needs** (материалы, полуфабрикаты, часы участков, трудозатраты) и **Plan vs fact**;
  `/production/plan-orders` — рабочее место «Orders by plan»; `/production/needs` — общий экран расчёта потребностей
  (вкладка **Stock needs** с тремя шагами и вкладка **Production orders** — сводная потребность этапа 3);
  пункт **Stock needs** есть и в группе Trade (закупки и склад). В карточке товара — вкладка **Stock levels** и
  поле **Lead days**; в карточке изделия — **Lead days** рядом с партией и накладными.
- **Права.** Планы, нормы, заполнение, заказы и расчёт — member и выше (справочники по складам и участкам —
  admin и выше, как у соседних маршрутов); чтение — любой участник; цены поставщиков и суммы заказа видят
  admin и owner (`maskCost`).
