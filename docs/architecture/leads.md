# Лиды (задача 1175)

Код: `packages/db/src/schema/leads.ts` (миграция `0042_leads.sql`), сервис `packages/db/src/leads.ts`, чистые правила `packages/shared/src/leads.ts`,
схемы `packages/shared/src/schemas/leads.ts`, API `apps/api/src/routes/leads.ts` и `routes/hooks.ts`, узлы `packages/shared/src/automations/nodes/*lead*.ts`,
порты воркера `apps/worker/src/flows/records.ts`, интерфейс `apps/web/src/app/leads/` и `settings/leads.tsx`. Тесты: `apps/api/test/leads.test.ts`, `packages/shared/test/leads.test.ts`.

Лид — человек или компания **до** появления клиента. Раньше лидом называлась стадия сделки (`deals.stage = 'lead'`): такие сделки остаются сделками, перенос не делался. С задачи 1176 стадии сделки — этапы воронок ([pipelines.md](pipelines.md)).

## Данные (миграция 0042)
Все таблицы арендатора: `workspace_id`, `unique(workspace_id, id)`, составные FK, `app_secure_tenant_table`.
- `lead_statuses` — название (уникально без учёта регистра), `category` (`new | in_progress | converted | rejected`), `color`, `sort_order`. Механизм общий: этапы воронок (1176) могут переиспользовать его.
  В новом воркспейсе — пять статусов по умолчанию (`ensureLeadStatuses`: New / Contacted / Qualified / Converted / Rejected); миграция создаёт их в существующих. Демо — «Новый», «Связались», «Квалифицирован», «Сконвертирован», «Отказ».
- `leads` — имя, компания текстом, телефон и `phone_norm` (E.164), email и `email_norm`, комментарий, источник (`source_id` / `campaign_id`, текст `source` — кэш названия; справочник и кампании — [ad-campaigns.md](ad-campaigns.md)), ответственный, статус, причина отказа, форма-источник, `custom`, `converted_at`, ссылки `company_id` / `contact_id` / `deal_id`. Индексы по статусу, `phone_norm`, `email_norm`.
- `lead_forms` — форма сайта: название, секрет `token` (уникален), источник, ответственный по умолчанию, `enabled`.
- `lead_assign_cursor` — курсор распределения «по кругу» (строка на воркспейс).
- `crm_activities.lead_id` — касание лида (FK каскадом). Касания лида — те же `crm_activities`: тип, тема, текст.
- Системная сущность конструктора `lead` (`SYSTEM_ENTITIES`, `SYSTEM_TABLES`): пользовательские поля лежат в `leads.custom`, правятся в Settings → Data model, показываются в карточке. Миграция регистрирует сущность в существующих воркспейсах.

## Статусы
Категория определяет логику. Новый лид получает первый статус категории `new`. В категорию `converted` лид попадает **только конвертацией** (422 `lead_use_convert` при ручной смене); статус сконвертированного лида менять нельзя (409). При смене статуса на категорию кроме `rejected` причина отказа очищается.
Статус не удаляется, пока им пользуются лиды (409 `lead_status_in_use`); нельзя удалить или перевести в другую категорию последний статус `new` / `converted` (422 `lead_status_last_of_category`). Правят admin и owner.

## Дубли
`findDuplicates`: совпадение телефона (последние 10 цифр — одинаково для `+7…`, `8…` и номера без кода) и email (без учёта регистра) среди **лидов, контактов**; контрагент находится через найденный контакт (`by: contact`) или по точному названию компании лида (`by: name`) — у `companies` своих телефона и email нет. Ответ: список `{ kind, id, name, by }`.
API: `GET /leads/duplicates?phone&email&companyName&excludeId` (форма нового лида, с задержкой) и `GET /leads/:id/duplicates` (карточка). Предупреждение в интерфейсе со ссылками; у дубля-лида — кнопка «Объединить с этим лидом».
`POST /leads/:id/merge { intoId }` (`mergeLeads`): исходный лид вливается в целевой — касания переезжают, пустые поля целевого заполняются, `custom` целевого приоритетнее, комментарии склеиваются, ответственный целевого сохраняется; исходный лид удаляется (событие `lead.deleted` с `mergedInto`), на целевом остаётся системная заметка. Сконвертированные лиды не объединяются.

## Конвертация
`POST /leads/:id/convert { company, contact, deal }` (`convertLead`), каждый из `company` / `contact`: `{ mode: 'existing', id } | { mode: 'new', name } | { mode: 'none' }`; `deal` — `{ name, amount? } | null`.
Новый контакт получает телефон, email и `custom` лида и привязывается к контрагенту; сделка создаётся на этапе «квалифицирован» основной воронки (второй открытый этап, иначе первый — см. pipelines.md), контакт добавляется в её участники. Касания лида переезжают (`lead_id` очищается): к сделке, если она создана, иначе к контакту и контрагенту. Лид получает первый статус категории `converted`, `converted_at` и ссылки. Повторная конвертация — 409 `lead_already_converted`. Всё в одной транзакции с событиями `company.created`, `contact.created`, `deal.created`, `lead.updated`.
В мастере (`ConvertDialog`) найденные дубли подставляются сами (контрагент и контакт), иначе создаётся новый (контрагент — если у лида указана компания).

## Распределение
Ответственный: вручную (поле, `POST /leads/:id/assign { mode: 'manual', memberId }`) либо по кругу (`mode: 'round_robin'`). «По кругу» — активные участники с функцией `sales_manager` (`membersWithFunction`: если такой должности нет вообще — все активные), по порядку id после последнего назначенного (`lead_assign_cursor`, строка блокируется — гонки нет). Список выбора в карточке — те же менеджеры продаж. При создании через API по умолчанию ответственный — автор; через форму — ответственный формы, а без него — по кругу.

## Публичный вебхук `POST /hooks/leads/:token`
Без сессии и без `X-Workspace-Id`. Токен = `<workspace_id>.<секрет формы>`: идентификатор воркспейса нужен, чтобы выставить контекст RLS (`app.workspace_id`, роль `app_user`), секрет сверяется с включённой формой этого воркспейса. Неверный формат, чужой воркспейс, неизвестный секрет, выключенная форма — один и тот же `404 not_found`; успех — `201 {"ok": true}` без данных воркспейса.
- Тело: JSON или `application/x-www-form-urlencoded`, ≤ 32 КБ. Поля `name`, `phone`, `email`, `company`, `comment`; нужен хотя бы один из `name` / `phone` / `email` (422). `utm_*` попадают в `custom` лида (без проверки конструктором: ключей полей для них нет), остальные поля игнорируются. Источник и кампания — по `utm_campaign` (код кампании), иначе кампания или источник формы, иначе источник с названием формы (см. ad-campaigns.md); форма сохраняется в `form_id`.
- Ограничение частоты — таблица `rate_limits`: `lead-hook:ip:<ip>` (по умолчанию 30 обращений за 60 с, `LEAD_HOOK_RATE_LIMIT_MAX`, `LEAD_HOOK_RATE_LIMIT_WINDOW_SEC`) до разбора токена и `lead-hook:form:<секрет>` (10× от лимита IP). Превышение — 429 `rate_limited`. За прокси нужен `TRUST_PROXY=1`, иначе все обращения считаются с одного адреса.
- CORS: `Access-Control-Allow-Origin: *`, методы POST/OPTIONS, заголовок `Content-Type`, без cookie; глобальный CORS на `/hooks/*` не применяется.
- Секрет меняется `POST /lead-forms/:id/rotate` (старый адрес перестаёт работать). Полный токен видит только admin/owner: остальным `webhookToken` пуст.

## Автоматизации
Сущность `lead` доступна в обычных узлах («запись создана», «поле изменилось», условия, подстановки `{{trigger.record.…}}`). Дополнительно, по одному файлу на узел:
- триггеры `trigger.lead_created` («Лид создан») и `trigger.lead_status_changed` («Статус лида изменён», необязательный целевой статус; в форме — выбор статуса, подсказка `ui: 'lead_status'`);
- действия `action.create_lead` («Создать лид», статус по умолчанию, ответственный необязателен) и `action.assign_lead` («Назначить ответственного»: `manual` или `round_robin`, лид по умолчанию `{{trigger.recordId}}`).
Порты `createLead` и `assignLead` в `NodeRuntime` реализует воркер (`records.ts`) теми же функциями сервиса, события несут метку `via` (защита от зацикливания). Встроенные поля `lead` для «Обновить поле»: имя, компания, комментарий, ответственный, причина отказа (источник убран в задаче 1177 — его пишет только сервер); телефон, email и статус автоматизацией не меняются (нормализация и правила статусов живут в сервисе).

## API
`/leads` (CRUD, фильтры `statusId`, `category` зарезервирован в схеме, `ownerId`, `source`, поиск `q`; архив мягкий, `?hard=true` — admin), `/lead-statuses` (+ `POST /reorder`; запись — admin), `/lead-forms` (+ `POST /:id/rotate`; запись и токен — admin), `/crm-activities?leadId=`. События `lead.*`, `lead_status.*`, `lead_form.*`; клиент обновляет по ним ключ кэша `['ws', id, 'leads', …]` (вместе с событиями компаний, контактов, сделок и касаний).

## Интерфейс
CRM → «Лиды» (`/crm/leads`): доска по статусам (перетаскивание меняет статус; бросок в колонку «сконвертирован» открывает мастер) и таблица, поиск, фильтр по ответственному. Карточка: поля, предупреждение о дублях, «Объединить», лента касаний с добавлением, кнопка «Конвертировать», пользовательские поля, utm-метки. Settings → Lead statuses (категории, цвет, порядок) и Lead forms (источник, ответственный, адрес вебхука с копированием, смена секрета). Тексты — `leads.*` в обоих словарях.
