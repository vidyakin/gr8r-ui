# Заказы на производство и выпуск

Реализовано на этапе 2 (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/production.ts`, метаданные типов и расчёт — `packages/shared/src/documents.ts`
и `packages/shared/src/bom.ts`, схема — `packages/db/src/schema/production.ts` (миграция `0009_production_orders.sql`), API — `apps/api/src/routes/production-orders.ts`,
клиент — `apps/web/src/app/production/ProductionOrdersPage.tsx` и `ProductionOrderPage.tsx`.

- **Два типа документов** группы `production`, оба без контрагента (`party: null`): `production_order` (ЗП, заказ на производство) и `production` (ПР, выпуск).
  Заказ живёт по общим правилам: номер выдаётся при проведении, состояние — отдельное поле `documents.state` (`planned → in_progress → done → closed`),
  вид операции — `assembly` («Сборка»; разборка — позже). Выпуск — обычный документ: `stock_role` строки задаёт сторону (`in` — продукция, `out` — материалы),
  цены и НДС у строк нет, стоимость — по себестоимости (видна admin и owner).
- **Производственные данные лежат рядом с документом**, а не в `document_lines`: строка документа — всегда товар каталога, а в заказе бывают изделия без товара и работы.
  `production_items` — что выпускает документ (продукция, количество, строка заказа покупателя, строка заказа на производство, строка документа с продукцией);
  `production_components` — снимок состава (материалы, полуфабрикаты, работы: норма, ставка, плановая и фактическая стоимость);
  `production_headers` — изготовитель (участок), плановые старт и финиш, родительский заказ. Связи — составные внешние ключи `(workspace_id, id)`.
  Из-за этого `document_lines` не ссылается на производственные таблицы (иначе схема документов зациклилась бы на спецификациях) — связь идёт с производственной стороны.
- **Способ пополнения товара и спецификация по умолчанию** — `product_manufacturing (workspace_id, product_id, replenishment: purchase|production, default_item_id)`:
  товар с `replenishment = 'production'` производится, а `default_item_id` говорит, что именно. Отдельная таблица (а не колонки в `products`) — по той же причине:
  `products` не может ссылаться на спецификацию без цикла импорта схем.
- **Снимок спецификации** (`POST /production-orders/:id/fill-from-bom`): `explodeBom` по количеству позиции даёт материалы, полуфабрикаты и работы, стоимость — по
  источнику цены воркспейса (как `computeBomCost`). Снимок можно править до проведения; полуфабрикат без товара каталога в режиме `stock` — ошибка `item_not_stockable`.
- **Выпуск**: списывает материалы и полуфабрикаты по средней склада и приходует продукцию по **фактической себестоимости** — материалы (по средней на момент списания)
  + работы (`hours × ставка` + фиксированная стоимость) + накладные (`overhead_pct` изделия от прямых затрат). Цена прихода считается в той же двухфазной записи
  (`applyStockMoves` с `inCost`), что и перемещение: сначала расходы, потом приход по цене, которая узнаётся из фактических расходов. План и факт считает одна
  функция `computeProductionCost` (shared). Отмена проведения возвращает остатки и среднюю и снимает резерв продукции.
- **Остаток к выпуску** считается по позициям заказа: выпустить больше заказанного нельзя (`over_fulfilment`). То же — по строке заказа покупателя, когда выпуск идёт напрямую.
- **Автоматический резерв продукции под заказ покупателя** (фича 1.5): выпуск, связанный с заказом покупателя (напрямую или через заказ на производство),
  резервирует выпущенную продукцию за этим заказом — `stock_reservations.production_line_id` (строка выпуска) на складе готовой продукции; ограничение — заказано
  минус отгружено. Если заказ покупателя уже резервирует этот товар на этом складе, второй резерв не создаётся.
- **Один документ выпуска за день на участок**: выпуск за ту же дату и тот же участок дописывается в существующий документ `production` (как в 1С): у проведённого
  документа снимается проведение, добавляются строки, документ проводится заново — всё в одной транзакции, при нехватке материалов она откатывается целиком.
- **Обеспечение материалов заказа на производство** (этап 3): резерв материалов, размещение и потребность — [отдельный раздел](production-materials.md).
- **Автоперемещение у участка**: у участка три склада — `warehouse_id` («списывать из»), `output_warehouse_id` («продукция в») и `waste_warehouse_id` («отходы в»);
  выпуск подставляет их, пользователь может поменять склады в документе.
- **API:** `/production-orders` (журнал с фильтром по состоянию и плановым срокам, карточка с позициями, составом и выпусками), `POST /:id/fill-from-bom`,
  `POST /:id/production` (выпуск по заказу), `POST /:id/state`, `POST /production` (выпуск прямо из заказа покупателя), `POST /from-customer-order`
  (заказ на производство по заказу покупателя), `GET/POST /product-settings` (способ пополнения и спецификация по умолчанию). Производственные документы создаются
  только здесь: общий `POST /documents` отвечает `production_api_only`. «На основании» заказа покупателя умеет и заказ на производство, и выпуск.
- **Интерфейс:** `/production/orders` — журнал заказов (вкладки по состоянию), `/production/orders/:id` — карточка: позиции, снимок состава, кнопки
  **Fill from BOM / Create production / Post**, состояние заказа. Выпуск открывается в общей карточке документа: в шапке — склады материалов и готовой продукции,
  в строках — роль (материал или продукция).
- **Права:** заказы и выпуски — member и выше; себестоимость (плановые и фактические стоимости состава) — только admin и owner (`maskCost`).
- **Выпуск из давальческого сырья** (этап 8) — обычный выпуск с двумя отличиями: заказ и выпуск ссылаются на **заказ на переработку**
  (`production_headers.processing_order_id`), а у строк состава есть признак **«чей материал»** (`production_components.owner_kind`,
  `own | customer`; по умолчанию `customer`, если заказ сделан по заказу на переработку, правится вручную). Давальские строки списываются
  с остатка давальца, свои — со своего склада по средней, продукция приходуется на остаток давальца, а наши затраты становятся
  себестоимостью услуги. Подробности — раздел «Переработка».
