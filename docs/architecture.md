# Архитектура платформы gr8r

Документ фиксирует решения для перехода от фронтенд-шаблона к многоарендной платформе (задачи, CRM,
каталог, документы продаж и закупок, склад, автоматизации, конструктор сущностей). Любой новый код
следует этим решениям; меняя решение — обнови документ в том же коммите.

## Стек

| Слой | Выбор |
| --- | --- |
| Рантайм | Bun (workspaces, `Bun.password`, `Bun.serve`, `bun test`) |
| HTTP | Hono (`hono/bun`), валидация `@hono/zod-validator`, типизированный клиент `hono/client` |
| БД | PostgreSQL 16, Drizzle ORM + drizzle-kit (миграции SQL в репозитории) |
| Схемы | Zod — общие для API и фронтенда (`packages/shared`) |
| Фронтенд | React 19 + Vite (текущее приложение), TanStack Query для серверного состояния |
| Реальное время | WebSocket (`upgradeWebSocket` из `hono/bun`), события по арендатору |
| Файлы | S3-совместимое хранилище (MinIO локально) |
| Фоновые задачи | таблица `jobs` + воркер на `FOR UPDATE SKIP LOCKED` (без внешних брокеров) |
| Запуск | Docker Compose: postgres, minio, api, worker, web; тот же compose — на VPS |

## Монорепозиторий

```
apps/
  web/        фронтенд (текущий src/, vite)
  api/        HTTP API + WebSocket
  worker/     фоновые задачи: автоматизации, печать PDF, пересчёты
packages/
  shared/     zod-схемы, типы, константы (статусы, приоритеты 1–10, ставки НДС, единицы ОКЕИ)
  db/         drizzle-схема, миграции, политики RLS, сиды
docs/
docker-compose.yml
```

Команды из корня: `bun install`, `bun run dev` (api + worker + web), `bun run db:migrate`, `bun run db:seed`,
`bun test`. Переменные окружения — `.env` по образцу `.env.example`.

## Арендаторы и доступ

- `users` — глобальные учётные записи; `workspaces` — арендаторы; `memberships (user_id, workspace_id, role)`
  с ролями owner / admin / member / guest. Пользователь может состоять в нескольких воркспейсах.
- Вход: email + пароль (Argon2id через `Bun.password`), сессии в таблице `sessions`, cookie httpOnly + SameSite=Lax.
  OAuth (Google и т.п.) — позже, отдельной таблицей `identities`.
- Активный воркспейс передаётся заголовком `X-Workspace-Id`; API проверяет членство.
- **Каждая таблица с данными арендатора** имеет `workspace_id uuid not null` и политику RLS
  `workspace_id = current_setting('app.workspace_id')::uuid`. API выполняет запрос арендатора в транзакции с
  `set local app.workspace_id = …` под ролью `app_user` без BYPASSRLS. Миграции — под ролью-владельцем.
  Так ошибка в запросе не может вернуть чужие данные.
- Крупному клиенту позже можно выделить отдельную схему или БД — код от этого не меняется.

## Общие соглашения по данным

- Идентификаторы — UUID v7 (сортируются по времени). Человекочитаемые ключи (`WEB-109`, `СЧ-2026-00042`)
  — отдельные поля с нумерацией по арендатору.
- Время — `timestamptz`; даты без времени — `date`.
- Деньги — `numeric(18,2)`, количества — `numeric(18,3)`; в JSON передаются строками, на фронте —
  десятичная арифметика (без float).
- Мягкое удаление — `archived_at`; жёсткое — только из Archive.
- **Журнал событий (outbox)**: любое изменение в той же транзакции пишет строку в
  `events (id, workspace_id, type, entity, record_id, actor_id, payload jsonb, created_at)`. Из него
  питаются realtime-рассылка, лента Activity, уведомления и автоматизации.

## Конструктор сущностей (метаданные + JSONB)

Таблицы на лету не создаются. Структура описывается метаданными:

- `entities (workspace_id, key, name, kind: system|custom, icon, title_field, settings)` — сущности, включая
  системные (task, project, deal, company, contact, product, document), чтобы к ним можно было добавлять поля.
- `fields (entity_id, key, name, type, required, unique, options jsonb, order, is_system)` — типы: text, long_text,
  number, money, percent, date, datetime, boolean, select, multi_select, user, ref (связь с записью другой
  сущности), refs, file, url, email, phone, formula (позже).
- Хранение значений: у системных таблиц — колонка `custom jsonb`; пользовательские сущности — общая таблица
  `records (id, workspace_id, entity_id, data jsonb, created_by, created_at, updated_at, archived_at)`.
- Проверка — zod-схема, собираемая из `fields` (на сервере перед записью, на клиенте в формах).
- Индексы по часто фильтруемым полям — индексы по выражению `((data->>'key'))`, создаются по требованию
  (`CREATE INDEX CONCURRENTLY`, без блокировок); плюс GIN по `data` для поиска.
- Интерфейс пользовательской сущности собирается автоматически из метаданных на готовых компонентах:
  `DataTable`, `Kanban` (по полю select), `EntityDrawer`, `FilterBar`, формы.
- Если сущность станет «горячей» (миллионы записей, тяжёлая аналитика) — её можно материализовать в
  настоящую таблицу; это исключение, а не основной путь.

## Каталог: товары и услуги

- `product_categories` — дерево (`parent_id` + `path` для выборки поддерева).
- `attribute_defs (category_id, key, name, type, unit, options, required, order)` — характеристики задаются у
  категории и наследуются потомками.
- `products (kind: goods|service, sku, name, unit_code (ОКЕИ), vat_rate, price, category_id, attrs jsonb,
  barcode, is_active, custom jsonb)`; `attrs` проверяются по схеме категории (тот же механизм, что поля
  конструктора). Варианты товара (размер/цвет) — позже, отдельной таблицей.
- `units` — справочник единиц ОКЕИ (шт 796, кг 166, ч 356, усл. ед 876 …).

## Контрагенты и организации (Россия)

- `companies` (из CRM) получают реквизиты: ИНН, КПП, ОГРН/ОГРНИП, юр. и факт. адрес; `bank_accounts`
  (БИК, р/с, к/с, банк); тип: юрлицо / ИП / физлицо.
- `organizations` — собственные юрлица арендатора (их может быть несколько): реквизиты, руководитель,
  главбух, система налогообложения (ОСН / УСН), ставка НДС по умолчанию, печать и подпись (файлы).

## Документы продаж и закупок

- `documents (type, number, date, status: draft|posted|cancelled, organization_id, counterparty_id,
  contract_id?, warehouse_id?, currency 'RUB', price_includes_vat, totals…, based_on_id, custom jsonb)`.
- `document_lines (document_id, product_id, name, unit_code, qty, price, discount, vat_rate, vat_amount, total)`.
- Типы: продажи — коммерческое предложение, заказ покупателя, счёт на оплату, реализация (УПД / ТОРГ-12),
  акт оказания услуг, возврат от покупателя; закупки — заказ поставщику, поступление (УПД поставщика),
  возврат поставщику; оплаты — входящая и исходящая (позже — банковская выписка).
- Цепочки «на основании»: заказ → счёт → реализация; заказ поставщику → поступление.
- Нумерация — по (арендатор, организация, тип, год), без дыр при проведении.
- НДС: ставки 0 / 5 / 7 / 10 / 20 / без НДС; расчёт построчно, сумма «в т.ч.» или «сверху».
- Печатные формы — HTML-шаблоны → PDF в воркере (headless Chromium): счёт, УПД, акт, ТОРГ-12.
  ЭДО — позже.

## Склад

- `warehouses`; проведение реализации/поступления/возврата пишет `stock_moves (warehouse_id, product_id,
  document_id, qty ±, cost, moved_at)`; услуги на склад не влияют.
- Остатки — из движений (агрегирующая таблица `stock_balances`, обновляется в той же транзакции).
- Себестоимость — средняя скользящая; резервы под заказы покупателей — `stock_reservations`.
- Инвентаризация и перемещения между складами — следующим шагом.

## Производство: спецификации и себестоимость

- `manufactured_items` — справочник продукции (изделия и полуфабрикаты): код, название, единица, ссылка на
  товар каталога для продажи/склада (`product_id`, необязательно), выход на партию (`batch_qty`), процент накладных.
- `bom_lines (item_id, kind: material|semi|work, order, …)` — спецификация на `batch_qty` единиц:
  - material — `product_id` из каталога, `qty`, `unit_code`, `scrap_pct` (отход);
  - semi — `child_item_id` (другая продукция со своей спецификацией), `qty`; дерево любой глубины,
    циклы запрещены (проверка при сохранении);
  - work — `operation` (название), `work_center_id` (участок, необязательно), `hours` и `rate` за час
    либо `fixed_cost`.
- `work_centers` — участки/исполнители со ставкой за час по умолчанию.
- Себестоимость на единицу считается рекурсивно чистой функцией в `packages/shared` (одна и та же на
  сервере и в интерфейсе): материалы (цена × qty × (1 + отход)) + работы + полуфабрикаты по их
  себестоимости, плюс накладные; результат — дерево с разбивкой «материалы / работы / накладные» по каждому
  узлу. Источник цены материала — настройка: цена каталога, закупочная цена или средняя себестоимость склада.
- Версии спецификаций (действует с даты) и производственные заказы со списанием материалов и выпуском
  продукции на склад — следующими шагами.

## Автоматизации

- `flows (workspace_id, name, enabled, version, graph jsonb)` — граф React Flow (узлы и связи) с версиями;
  `flow_runs` и `flow_run_steps` — журнал запусков с входом и выходом каждого шага.
- Триггеры читают журнал `events` (создание / изменение записи, изменение поля, расписание, вебхук);
  воркер находит подходящие flow и выполняет граф по шагам (условия, действия, задержки через `jobs`).
- Набор узлов — отдельным документом; редактор — React Flow в `apps/web`.

## Фронтенд на сервере

- Текущий `WorkspaceProvider` (useReducer + seed) заменяется серверным состоянием на TanStack Query.
  Действия `dispatch({ type, … })` сохраняют форму, но выполняются как мутации API с оптимистичным
  обновлением и откатом при ошибке.
- Realtime-события инвалидируют или патчат кэш запросов.
- Демо-данные переезжают в сиды (`bun run db:seed`) — создают демо-воркспейс с текущими задачами, CRM и т.д.

## Этапы

1. **Фундамент**: монорепозиторий, `packages/db` со схемой текущих данных (задачи, проекты, комментарии,
   активность, уведомления, файлы, учёт времени, статусы, виды, команды, события календаря, CRM), RLS,
   авторизация и воркспейсы, API + WebSocket, журнал событий, сиды, docker-compose, тесты изоляции арендаторов.
2. **Фронтенд на API**: TanStack Query, вход/регистрация на настоящей авторизации, переключатель воркспейсов,
   realtime.
3. **Движок метаданных**: пользовательские поля системных сущностей → пользовательские сущности → экраны из
   метаданных.
4. **Каталог и производство**: категории, характеристики, товары и услуги, единицы; справочник продукции,
   дерево спецификаций с материалами, полуфабрикатами и работами, расчёт себестоимости.
5. **Документы и склад**: организации, реквизиты, документы продаж и закупок, проведение, остатки, печатные формы.
6. **Автоматизации**: журнал событий → движок → редактор React Flow → узлы.
