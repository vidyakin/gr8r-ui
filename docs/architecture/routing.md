# Маршруты и карта

Задача 1213 (TaskFlow, сессия 50); решения — `docs/plans/2026-10-30-tms.md`, пункты 4 и 5. Модуль тарифов `transport` ([licensing.md](licensing.md)); рейсы — [trips.md](trips.md), секреты — [secrets.md](secrets.md), прод-compose — [deploy.md](deploy.md).

Код: чистый расчёт `packages/shared/src/routing.ts` (типы, настройки, расчёт без провайдера, ETA, плитки) и адаптеры `routing-adapters.ts`; схемы `schemas/routing.ts`; сервис `packages/db/src/routing.ts` (настройки, защищённый fetch, адаптер арендатора, геокодирование) и `routing-trips.ts` («Распределить», «Оптимизировать порядок»); задачи воркера в `apps/worker/src/handlers.ts`;
API — `/trips/routing…` и `/trips/:id/optimize` (`apps/api/src/routes/trips.ts`); экраны `apps/web/src/app/trips/` (`RouteMap.tsx`, `map.tsx`, `RoutingSettings.tsx`, диспетчер, карточка рейса). Миграция `0066_routing`. Тесты: `packages/shared/test/routing.test.ts`, `apps/api/test/routing.test.ts`.

## Провайдер (настройка арендатора)
Хранится в `workspaces.settings.routing` (`RoutingSettings`); правит admin: **Рейсы → Маршрутизация**. Три значения:
- **Нет** (по умолчанию) — порядок точек вручную, расстояние по прямой × 1,3 (коэффициент дорог), время по средней скорости (город 30, трасса 60 км/ч — настройки). «Распределить» и «Оптимизировать порядок» работают и без провайдера (см. ниже); адреса не геокодируются — координаты вводятся вручную.
- **Яндекс** — Геокодер, Матрица расстояний, Маршрутизация (VRP). Ключи — секреты `routing.yandex_geocoder_key` и `routing.yandex_router_key` (вводятся в диалоге настроек, пишутся в хранилище секретов, назад не отдаются; `readSecret` — только в серверном коде). Ключ карты (JavaScript API) — в настройках открытым текстом: он виден в браузере по определению (ограничивается по сайту в кабинете Яндекса); с ним карта строится на плитках Яндекса в проекции EPSG:3395 (`L.CRS.EPSG3395`), без него — OSM.
- **OSRM + VROOM** — свой сервер на данных OpenStreetMap (без пробок): `osrmUrl` (матрица `/table`), `vroomUrl` (VRP), необязательный `nominatimUrl` (геокодирование; без него адреса не геокодируются). Пустой адрес — серверный адрес оператора из окружения (`ROUTING_OSRM_URL`, `ROUTING_VROOM_URL`, `ROUTING_NOMINATIM_URL`).
У адаптера есть только те возможности, что настроены (`geocode?`, `matrix?`, `solve?`); чего нет — считается по прямой. Прочее в настройках: база машин (адрес, широта и долгота вручную — пусто: маршрут начинается с первой точки), минут на точке (10), начало дня (09:00).

## Защита сети (SSRF)
Исходящие запросы — только `routingFetcher` (`packages/db/src/routing.ts`): разрешены хосты из настроек — фиксированные хосты Яндекса (только https), адрес арендатора (http/https без учётных данных, имя не `localhost`/`.local`/`.internal`/`.lan`, IP-литерал и все адреса DNS не частные и не служебные — функции `isPrivateAddress` и др. из `packages/shared/src/automations/net.ts`, те же, что у вебхуков) и серверные адреса оператора из окружения — им доверяют (сервисы в сети compose живут на частных адресах). Редиректы не выполняются, ответ до 20 МБ, таймаут 20 с. Адрес проверяется ещё при сохранении настроек (`routingUrlError`, 400). `ROUTING_ALLOW_PRIVATE=1` — только для закрытых установок и тестов. Между DNS-проверкой и соединением адрес теоретически может смениться (DNS rebinding) — как у узла «HTTP-запрос».

## Геокодирование в фоне
`deliveries.lat/lon` и `fleet_trip_stops.lat/lon` + `geo_source` (`manual | geocoder`) и `geo_status` (`pending | ok | approx | not_found | error`). При сохранении доставки или точки с новым адресом (и без координат вручную) строка помечается `pending` и ставится задача `routing.geocode` (одна на объект). Воркер геокодирует вне транзакции, пишет координаты, статус и переносит их в точки рейсов этой доставки. Координаты, введённые вручную, геокодер не перезаписывает (в карточке доставки уходят только правленные руками поля); смена адреса сбрасывает найденные геокодером. Временный сбой повторяется, на последней попытке — статус `error`. Точка из доставки при добавлении в рейс копирует координаты доставки. Любое изменение порядка, точек или координат сбрасывает расчёт рейса (`clearRoute`): участки, ETA и итоги пустеют — устаревших ETA в карточке нет.

## «Распределить» и «Оптимизировать порядок»
Оба действия — запуск `fleet_routing_runs` (`distribute | optimize`, статус `queued → running → done | failed`, источник расчёта, предупреждение, итог) и задача воркера (`routing.distribute`, `routing.optimize`, без повторов — иначе рейсы задвоились бы). Ход виден в полосе над диспетчером и в карточке рейса по событиям `fleet_routing_run.*` (realtime обновляет кэш `fleet`). Три шага: чтение данных (короткая транзакция) → расчёт у провайдера (без транзакции) → запись через обычные сервисы рейсов (`createTrip`, `addStop`, `reorderStops`: занятость, вместимость, курьер и статус доставки остаются в силе).
- **Распределить** (`POST /trips/routing/distribute {date, vehicleIds?}`): берёт нераспределённые доставки дня (те же, что слева на диспетчере) и свободные машины с водителем (занятые рейсом на этот день, без водителя, с занятым или отключённым водителем пропускаются с причиной), решает задачу с вместимостью по весу и окнами, создаёт **новые** городские рейсы в плане с точками в порядке объезда и ETA; не вошедшие остаются нераспределёнными с причиной. Диспетчер правит результат обычными средствами. Существующие рейсы не перестраиваются. 409 `routing_run_busy` — на этот день уже идёт расчёт.
- **Оптимизировать порядок** (`POST /trips/:id/optimize {reorder}`): `reorder: true` — переставить точки (только рейс в плане, 409 `trip_not_planned`), `false` — «Пересчитать время» без перестановки. Городской рейс решает провайдер VRP (одна машина), междугородний и без провайдера — ближайший сосед с учётом окон и 2-opt внутри каждого дня. Рейс, изменённый за время расчёта, не затирается (409 `trip_changed`).
- **Без VRP у провайдера или при его ошибке** — жадный подбор (`solveGreedy`): каждый шаг — ближайшая допустимая по вместимости и окну точка среди всех машин сразу (нагрузка делится; срочные окна идут раньше), опоздавшие добираются вторым проходом, точки без координат — в конец маршрутов по окнам. Ошибка провайдера не ломает запуск: расчёт по прямой, причина — в `warning`.
- **ETA и время в пути.** `computeEta`: выезд (время начала рейса или начало дня) + участок по матрице + время на точке; раньше окна — ждём его начала; новый день междугороднего рейса начинается с начала дня; позже конца окна — `eta_late`. Хранится в точке: `leg_km`, `leg_min`, `eta_min` (минуты от полуночи первого дня рейса), `eta_late`; в рейсе — `route_km`, `route_min`, `route_source`, `routed_at`.

## Карта
Leaflet 1.9 без обёрток (`RouteMap.tsx`, грузится лениво — в основной пакет не входит), номерные метки точек (`divIcon`, без картинок), ломаная по порядку объезда, база, нераспределённые доставки серыми метками. На диспетчере — рейсы дня (цвет на рейс, клик открывает карточку), в карточке рейса — его маршрут. Плитки: OSM по умолчанию (`https://tile.openstreetmap.org`), Яндекс при провайдере Яндекс и ключе карты. Точки без координат на карте не показываются — у них бейдж «нет координат» и поля широты/долготы (в карточке доставки и в диалоге точки). CSP в проекте не настроена, плиточные хосты в список ничего добавлять не требуют.

## Что не проверено и ограничения
- **Живых вызовов нет** (ключей Яндекса нет, OSRM/VROOM не поднимались): формы запросов и ответов Яндекса (Геокодер, Матрица расстояний — блоки 10×10, Маршрутизация — отправка `add/mvrp` и опрос `result/mvrp/<id>`) и VROOM/OSRM собраны по документации и проверены только на подменённом `fetch`. Сверить с боевыми API до включения у арендатора; образы и команды `osrm`/`vroom` в прод-compose — тоже по документации.
- Распределение не перестраивает существующие рейсы и не двигает уже поставленные доставки; машины с ограничениями по типу груза не различаются.
- База машин одна на арендатора; координаты базы вводятся вручную (адрес базы не геокодируется).
- Пробки учитываются только Яндексом и только если так настроен его API (в запросе нет времени отправления).
- Запуск «Распределить» в один момент — один на день; результат записывается одной транзакцией, но между расчётом и записью доставки могли занять — тогда они уходят в нераспределённые с кодом ошибки.
