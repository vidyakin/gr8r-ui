# Вложения и хранилище файлов

Задачи 1191 и 1192 (картинки товаров), решения — `docs/plans/2026-10-29-docflow.md`. Файлы к любым объектам с версиями, лимитом файла и квотой воркспейса.
Код: `packages/db/src/file-store.ts` (хранилище), `packages/db/src/attachments.ts` (сервис, права, квота, сборка мусора),
`apps/api/src/routes/attachments.ts`, `apps/worker/src/attachment-gc.ts`, интерфейс — `apps/web/src/components/gr8r/attachments-panel.tsx`.

## Хранилище
- Любое S3-совместимое: MinIO из compose, Yandex Object Storage, AWS. Клиент — встроенный в Bun `Bun.S3Client` (подпись SigV4,
  своих зависимостей нет), обёрнут интерфейсом `FileStore` (`put / get / delete / list`). Выбор вместо `@aws-sdk/client-s3`: клиент нужен
  и API, и воркеру, а ему достаточно четырёх операций; проверено на настоящем MinIO (put, get, отсутствующий ключ, list с префиксом, delete).
- Переменные: `S3_ENDPOINT`, `S3_REGION` (по умолчанию `us-east-1`), `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
  `S3_FORCE_PATH_STYLE` (по умолчанию да — MinIO; для Yandex/AWS `0`). Бакет должен существовать: в compose его создаёт `minio-init`.
  Без `S3_ENDPOINT`/`S3_BUCKET` хранилища нет, загрузка и скачивание отвечают 503 `storage_unavailable`.
- Ключ объекта — `<workspace>/<attachment>/<version>`: имени файла в ключе нет, оно живёт в БД. Тесты подставляют `MemoryFileStore`
  через `setFileStore`.
- PDF печатных форм остаются в БД (`document_files`, `PDF_STORE=db`); `s3PdfStore` — по-прежнему заготовка.

## Модель
- `attachments` — воркспейс, `entity_type` + `entity_id` (полиморфная привязка, внешнего ключа на объект нет), имя, вид `kind`,
  `current_version`, автор, `archived_at`. `attachment_versions` — номер, `storage_key` (null у перенесённых из старой `files`: содержимого
  у них не было), размер, `mime`, `sha256`, комментарий, автор. Составной FK версий на вложение, RLS по `workspace_id` на обеих.
- `workspaces.storage_quota_bytes` — квота воркспейса (null — значение по умолчанию из `STORAGE_QUOTA_BYTES`, пусто — без ограничения).
- Допустимые типы объектов — реестр `ATTACHMENT_ENTITY_TYPES` (`packages/shared/src/attachments.ts`): `document`, `contract`, `company`,
  `contact`, `deal`, `lead`, `task`, `project`, `product`. Внутренние документы и письма корреспонденции (задачи 1198, 1200) добавятся
  в реестр, когда появятся их таблицы: тип в `ATTACHMENT_ENTITY_TYPES` + функция проверки в `RESOLVERS` сервиса.

## Права «как у объекта»
RLS даёт только изоляцию по воркспейсу, права на родителя проверяет сервис (`entityAccess`): `none` — объекта нет или он скрыт
(для вложения это 404, существование не раскрывается), `read` — видит, `write` — правит.
- Обычные объекты: видит любой участник, пишет member и выше (guest — только читает).
- Проект и задача: закрытый проект (`is_private` или `access = private`) видят участники проекта, его лид и admin+; право `view` в `project_members` — только чтение.
  Замечание: остальные маршруты API закрытые проекты пока не фильтруют (отложено в `CLAUDE.md`), вложения — первое место, где это правило действует.
- В архив вложение переносит автор или admin+ (и нужно право на запись в объект). Версии не удаляются, удаляется только вложение целиком (в архив).
- Удаление и архивирование объекта (`crud()`, договор, черновик документа) архивирует его вложения (`archiveAttachmentsOf`).
  Возврат объекта из архива вложения не возвращает — их возвращают вручную («Показать архив» → «Вернуть»).

## API (`/attachments`, модуль «ядро»)
| Запрос | Что делает |
|---|---|
| `GET /attachments?entityType=&entityId=&entityTypes=a,b&q=&archived=1` | вложения, доступные участнику; текущая версия: `sizeBytes`, `mime`, `versionCount`; для задач и проектов — `projectId` |
| `POST /attachments` (multipart: `entityType`, `entityId`, `file`, `comment?`) | вложение и версия 1 |
| `POST /attachments/:id/versions` (multipart: `file`, `comment?`, `rename=1?`) | новая версия поверх; номер занимается атомарным `UPDATE` |
| `GET /attachments/:id` | карточка с историей версий |
| `GET /attachments/:id/content?version=N&inline=1` | файл (по умолчанию текущая версия), `Content-Disposition` с именем, `nosniff`, `private, no-store`; `inline` — только картинки и PDF |
| `GET /attachments/:id/content?thumb=128\|256\|512` | миниатюра текущей версии: только для `image/*` (иначе 422 `not_an_image`), без номера версии; `private, max-age=3600` |
| `PATCH /attachments/:id` | имя, вид |
| `DELETE /attachments/:id`, `POST /attachments/:id/restore` | архив и возврат (возврат проверяет квоту) |
| `GET /attachments/storage`, `PATCH /attachments/storage` | занято / квота / предел файла; квоту меняет только owner (`null` — по умолчанию) |

Загрузка и выдача идут через API потоком: MinIO в compose не публикуется наружу, presigned URL раскрыли бы адрес хранилища.
Файл целиком читается в память процесса (предел 50 МБ). События: `attachment.created / version_added / updated / archived / restored`.

## Лимиты
- `FILE_MAX_BYTES` (50 МБ по умолчанию): заголовок `Content-Length` проверяется до чтения тела, затем размер файла — 413 `attachment_too_large`.
  Перед API стоит nginx — в `docker/nginx.conf` для `/api/` задан `client_max_body_size 55m`.
- Квота воркспейса: занято = сумма размеров всех версий неархивных вложений (+ PDF документов и архивы выгрузки, как раньше) —
  `app_usage_of()`; превышение — 422 `storage_quota_exceeded`. Архив освобождает место, возврат проверяет квоту заново.
- Лимит тарифа `storageMb` (лицензия, задача 1207) проверяется там же (`assertLimit`) — 403 `limit_exceeded`. Он сильнее квоты по смыслу «тарифа»;
  квота — настройка самого воркспейса.

## Картинки товаров и миниатюры (задача 1192)
- `products.image_attachment_id` — основная картинка товара (FK на `attachments`, при удалении вложения — `set null`).
  Проставляется автоматически при первой загрузке картинки (mime `image/*`) к товару, у которого основной картинки ещё нет;
  смена — в карточке товара («Сделать основной»), сброс — передача `imageAttachmentId: null` в `PATCH /products/:id`.
- Миниатюры: `thumbOf` на sharp (`rotate` по EXIF, `resize` `inside` без апскейла), размеры 128/256/512, кэш в хранилище рядом
  с версией — ключ `<ws>/<att>/<version>/t<size>`. При ошибке ресайза (не картинка, битые данные) отдаётся исходный файл.
- `inlineAttachmentImages(db, html)` — заменяет в HTML печатной формы `src="…/attachments/<id>/content…"` на `data:<mime>;base64`
  (миниатюра 256): PDF-воркер не ходит в сеть, а предпросмотр печати в iframe не грузит относительные ссылки. Используется
  в `renderDocumentHtml` для КП.
- Сборка мусора удаляет миниатюры вместе с версиями: ключ `<ws>/<att>/<version>/t<size>` считается принадлежащим версии.

## Сборка мусора
Воркер раз в час (`runAttachmentGcOnce`): удаляет из хранилища объекты версий вложений, архивных дольше `ATTACHMENT_RETENTION_DAYS`
(30), и обнуляет `storage_key` (строка версии остаётся, скачивание отвечает 404 `file_content_missing`); удаляет осиротевшие ключи
без строки версии, старше суток (упавшая загрузка); сиротой считается только ключ вида `<uuid>/<uuid>/<номер>` — в том же бакете будут лежать
и другие файлы (картинки товаров, задача 1192), их проход не трогает. Без настроенного хранилища ничего не делает.
Порядок записи при загрузке: объект в хранилище → строка версии; если запись в БД не удалась (откат транзакции), объект удаляется сразу.

## Интерфейс
- Общий компонент `AttachmentsPanel` (`entityType`, `entityId`): список, перетаскивание и выбор файлов, версии в раскрывающейся строке,
  скачивание любой версии, новая версия, переименование, архив с «Отменить», показ архива. Подключён во вкладках/блоках: документ,
  договор (диалог редактирования), компания, контакт, сделка, лид, товар.
- Файлы задач и проектов — те же вложения (`entity_type` `task` / `project`). Коллекция `files` данных воркспейса читает
  `GET /attachments?entityTypes=task,project`; загрузка из карточки задачи, формы задачи и вкладки «Файлы» проекта — настоящий multipart-запрос
  (создание из локальной модели на сервер не уходит: `canCreate: () => false`), переименование и архив идут через движок. Пункта «Дублировать» больше нет.
- Галерея товара в карточке (`ProductGallery` в `apps/web/src/app/catalog/product-ui.tsx`): загрузка картинок, «Сделать основной»
  (бейдж главной), архив; порядок — по дате загрузки. Миниатюры основной картинки — 28×28 в каталоге (`CatalogPage`), 20×20 в выборе товара (`ProductPicker`).
- Квота и занятое место — «Настройки → Рабочее пространство» (меняет owner).
- Скачивание: `fetch` с cookie и `X-Workspace-Id`, затем blob (ссылка `<a href>` не передаёт заголовок воркспейса).

## Ограничения
- Список `GET /attachments` отдаёт не более 1000 строк (постранично через `limit/offset`, сортировка — от новых к старым).
- Выгрузка и загрузка арендатора (`bun run tenant export/import`) переносит строки БД, но **не содержимое S3**: после загрузки на другой установке версии указывают
  на ключи, которых в новом бакете нет (скачивание — 404 `file_content_missing`). Содержимое копируют вместе с бакетом (`mc mirror`), ключ содержит id воркспейса.
- Файл читается в память процесса целиком (предел 50 МБ); потоковой передачи в хранилище нет.
- Интерфейс в браузере и полный стек compose при разработке не проверялись, только API-тесты, типы и `S3FileStore` против MinIO.

## Перенос `files`
Миграция `0062_attachments` переносит строки `files` (файл задачи → вложение к задаче, иначе → к проекту) с тем же `id`, версия 1 без содержимого
(`storage_key` null: настоящей загрузки не было), затем удаляет таблицу `files`, маршрут `/files` заменён на `/attachments`. Функция `app_usage_of`
считает размеры из `attachment_versions`. Проверено на непустой `files` (задача, проект, архивная строка): id, тип, размер, `archived_at` и объём сходятся;
строка без задачи и проекта (в схеме это допустимо) не переносится.
