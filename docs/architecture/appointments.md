# Запись клиентов на приём

Задача 1171. Код: схема `packages/db/src/schema/appointments.ts` (миграция `0038_appointments.sql`), правила слотов без БД — `packages/shared/src/appointments.ts`,
сервисы — `packages/db/src/appointments.ts`, API — `apps/api/src/routes/appointments.ts` (`/appointments`), воркер — `apps/worker/src/appointments.ts`,
экраны — `apps/web/src/app/crm/` (`AppointmentsPage`, `appointments-ui`, `ScheduleEditor`, `ServiceDayPage`, `ClientAppointments`), раздел CRM «Запись» (`/crm/appointments`).
Тесты — `apps/api/test/appointments.test.ts`, `packages/shared/test/appointments.test.ts`.

- **График специалиста** (`specialist_schedules`, один на участника): длительность слота (15/30/45/60/90 мин), диапазон сетки (`day_start_min`–`day_end_min`, минуты от полуночи)
  и недельная сетка `week` — день недели 1–7 → начала рабочих слотов. Исключения на дату (`specialist_schedule_exceptions`): `slots = null` — выходной, массив — свой набор слотов на день.
  Праздники воркспейса (`workspace_holidays`) — выходные, если на дату нет исключения со слотами. Порядок: исключение → праздник → недельная сетка; слоты вне сетки отбрасываются
  (`workingSlots`). Правят admin/owner и сам специалист (чужой график — 403). Менять график или исключение так, чтобы сломать будущую активную запись, нельзя (`409 schedule_has_appointments`).
- **Запись** (`appointments`): специалист, клиент (контакт CRM или компания; физлицо с телефоном создаётся прямо в диалоге — `POST /appointments/clients`), услуга каталога
  (у услуги `products.appointment_minutes`, цена записи берётся из каталога и правится), дата и начало (минуты). Слотов подряд — `ceil(длительность / слот)`, число и длина слота сохраняются в записи.
  Проверки под блокировкой строки графика: начало и все слоты подряд внутри рабочих — иначе `422 outside_working_slots`; пересечение с активной записью специалиста — `409 slot_taken`.
  Статусы `booked → confirmed → came | no_show | cancelled` (`booked` может сразу в любой из трёх); отмена — с причиной (`422 cancel_reason_required`). Время занимают `booked`, `confirmed`, `came`:
  отмена и неявка освобождают слоты. Перенос (`POST /:id/move`) — на другой слот/к другому специалисту теми же проверками, свою запись пересечением не считаем.
- **Сетки.** `GET /day?date` — колонки всех специалистов с графиком; `GET /week?specialistId&from` — семь дней специалиста (рабочие слоты, записи, признак «день не закрыт»);
  `GET /free?productId[&specialistId&from]` — ближайшее свободное время на 60 дней (`findNearestFree`). Сетка в интерфейсе: строка = наибольший общий шаг слотов колонок, слот
  специалиста занимает `слот/шаг` строк; клик по свободному — запись, по занятому — карточка, перенос — выбором слота или перетаскиванием; на телефоне сетка прокручивается горизонтально.
- **Документ «Оказанные услуги за день»** (`documents.type = 'service_day'`, группа продаж, префикс `ОУ`, `DOCUMENT_META.own` — в журнале есть, в меню «Создать» нет; создаётся и открывается в разделе
  «Запись»). Шапка `service_day_docs` (специалист; дата — в `documents`), строки `service_day_lines` (покупатель — компания, контакт, товар/услуга, время, количество, цена). Один неотменённый
  документ на специалиста и дату (`409 service_day_exists`, блокировка `pg_advisory_xact_lock`). «Заполнить» добавляет строки из записей `came`, ещё не попавших в строки (`appointments.day_line_id`,
  FK `ON DELETE SET NULL (day_line_id)`: удалённая строка делает запись снова «незакрытой»); физлицо без компании получает компанию-покупателя вида `individual`, привязанную к контакту.
  **Проведение** — общий `postDocument` с хуком типа: по каждому покупателю создаётся и проводится продажа (акт, если в строках только услуги, иначе реализация со складом по умолчанию),
  т. е. выручка, долг клиента, списание товаров, дата следующего контакта идут штатным путём; связь — `service_day_sales`. Отмена проведения снимает и удаляет (или отменяет, если у продажи уже есть
  номер) созданные продажи. Себестоимость — как у актов и реализаций: у услуг своей себестоимости нет, у товаров — средняя по складу.
- **Контроль.** День специалиста «не закрыт», пока есть запись `came` без строки проведённого документа дня. Список — `GET /unclosed-days` и вкладка «Незакрытые дни»; день подсвечен в сетках.
  Воркер (`runAppointmentsOnce`, раз в проход вместе с биллингом, время и день — по `workspaces.timezone`): с 20:00 — уведомление за сегодня, с 08:00 — за прошедшие дни; получатели — специалист
  и все admin/owner; журнал `appointment_day_alerts (специалист, дата, evening|morning)` делает проход идемпотентным.
- **Напоминание накануне.** За день до приёма запись в статусе `booked` получает дело `crm_activities` типа `task` «Подтвердите запись: …» (срок — сегодня) и уведомление ответственному контакта,
  иначе компании, иначе владельцу воркспейса; журнал `appointment_reminders` (ключ — запись) — ровно одно дело. Подтверждённые записи напоминания не требуют; SMS — после задачи 1092.
- **История клиента.** Вкладка «Записи» в карточке компании и в панели контакта (`GET /appointments?contactId|companyId`; у компании — и записи её контактов): будущие, прошлые, неявки.
- **Права.** Читают все участники воркспейса, пишут member и выше (гость — только чтение). Таблицы под RLS (`app_secure_tenant_table`); воркер ходит под `app_worker`, поэтому его запросы
  фильтруют по `workspace_id` явно.
- **Заказ-наряд из записи (задача 1252).** `POST /appointments/:id/work-order` (`createAppointmentWorkOrder`): заказчик — как у продажи документа дня (`saleCompanyOf`), строка — услуга по цене записи, исполнитель — специалист (назначение с плановыми часами по слотам). Ссылка — `appointments.work_order_id` (составной FK, SET NULL при удалении заказ-наряда, миграция `0075`). Повтор — `409 work_order_exists`, отменённая запись и неявка — `409 invalid_status`. Не смешивать с документом дня: услуга, оформленная заказ-нарядом, проводится им, а не продажей дня.
