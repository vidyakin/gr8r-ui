# Архитектура платформы gr8r

Документ фиксирует решения для перехода от фронтенд-шаблона к многоарендной платформе (задачи, CRM,
каталог, документы продаж и закупок, склад, автоматизации, конструктор сущностей). Любой новый код
следует этим решениям; меняя решение — обнови документ в том же коммите.

## Стек

| Слой | Выбор |
| --- | --- |
| Рантайм | Bun (workspaces, `Bun.password`, `Bun.serve`, `bun test`) |
| HTTP | Hono (`hono/bun`), валидация `@hono/zod-validator`, типизированный клиент `hono/client` |
| БД | PostgreSQL 16, Drizzle ORM + drizzle-kit (миграции SQL в репозитории) |
| Схемы | Zod — общие для API и фронтенда (`packages/shared`) |
| Фронтенд | React 19 + Vite, TanStack Query для серверного состояния; клиент API — `@gr8r/api/client` (hono/client) |
| Реальное время | WebSocket (`upgradeWebSocket` из `hono/bun`), события по арендатору |
| Файлы | S3-совместимое хранилище (MinIO локально); пока PDF печатных форм лежат в БД (`document_files`), интерфейс `PdfStore` готов под S3 |
| Фоновые задачи | таблица `jobs` + воркер на `FOR UPDATE SKIP LOCKED` (без внешних брокеров) |
| Запуск | Docker Compose: postgres, minio, api, worker, web; тот же compose — на VPS |

## Монорепозиторий

```
apps/
  web/        фронтенд (бывший корневой src/, vite); алиас `@/…` → apps/web/src
  api/        HTTP API (Hono) + WebSocket
  worker/     фоновые задачи: outbox событий, очередь jobs (DDL по белому списку — индексы полей конструктора; PDF печатных форм в headless Chromium), движок автоматизаций (`src/flows`); позже — пересчёты
packages/
  shared/     доменные типы, zod-схемы API, константы (статусы, приоритеты 1–10, роли, ставки НДС, единицы ОКЕИ),
              демо-данные (`@gr8r/shared/demo`: их используют и фронтенд в локальном режиме, и сид БД)
  db/         drizzle-схема, SQL-миграции (`drizzle/`), RLS, uuid v7, сид, утилиты администрирования БД
docs/
test/         preload для `bun test` (тестовая БД пересоздаётся при каждом запуске)
scripts/      dev.ts (api + worker + web), smoke.ts (сквозной сценарий против запущенного API)
docker/       конфиги контейнеров (nginx для web)
Dockerfile    цели api, worker, migrate, web (oven/bun; web раздаёт nginx)
docker-compose.yml
```

Команды из корня: `bun install`, `bun run dev` (api + worker + web), `bun run build`, `bun run typecheck`, `bun test`,
`bun run db:generate | db:migrate | db:seed | db:wipe | db:reset`. Переменные окружения — `.env` по образцу `.env.example`
(пакеты читают корневой `.env`, поэтому скрипты работают из любой папки).

## Арендаторы и доступ

- `users` — глобальные учётные записи; `workspaces` — арендаторы; `memberships (user_id, workspace_id, role)`
  с ролями owner / admin / member / guest — источник правды для проверки доступа. Пользователь может состоять в нескольких воркспейсах.
- **Профиль участника** — отдельная таблица `members` (имя, должность, цвет, команда, часовой пояс, статус active / invited /
  deactivated). У `members.user_id` может быть NULL (приглашённый, ещё не зарегистрированный). На `members.id` ссылаются задачи,
  комментарии, сделки и т. д. (а не на `users.id`), поэтому участник остаётся в истории и после деактивации. Инвариант:
  если `members.user_id` задан, существует `memberships` с той же ролью — смена роли обновляет обе таблицы в одной транзакции.
- Вход: email + пароль (Argon2id через `Bun.password`), сессии в таблице `sessions` (в БД хранится sha256 токена, не сам токен),
  cookie httpOnly + SameSite=Lax (+ Secure в production, `COOKIE_SECURE`). Токен только в cookie — в теле ответов его нет.
  Вход и регистрация ограничены rate-limit'ом (таблица `rate_limits`, счётчики по IP и по email). OAuth (Google и т.п.) — позже,
  отдельной таблицей `identities`.
- Активный воркспейс передаётся заголовком `X-Workspace-Id` (для WebSocket — параметром `?workspace=`); API проверяет членство.
- Приглашения: `invites` с токеном вида `<workspace_id>.<секрет>` (в БД — sha256), срок 7 дней, принимается тем аккаунтом,
  чей email совпал с приглашённым. Воркспейс зашит в токен, поэтому принять приглашение можно до вступления в арендатора.
  Отправка писем — позже; пока токен возвращается администратору один раз.
- **Каждая таблица с данными арендатора** имеет `workspace_id uuid not null` и политику RLS по
  `current_setting('app.workspace_id', true)::uuid`; на таблицах `ENABLE` + `FORCE ROW LEVEL SECURITY` (владелец тоже подчиняется политикам).
  Исключения, у которых собственные политики: `workspaces` (арендатор — сама строка) и `memberships` (свои членства видны по
  `app.user_id`, чтобы определить, в какие воркспейсы пользователь может войти и вывести «мои воркспейсы»; изменять — только в рамках арендатора).
  Глобальные таблицы без RLS: `users`, `sessions`, `rate_limits` (минимальные права).
- **Роли БД** (создаёт миграция 0002, идемпотентно): `app_owner` — владелец таблиц, NOLOGIN; `app_user` — под ней работает API, NOLOGIN,
  NOBYPASSRLS; `app_worker` — воркер, BYPASSRLS (фоновые задачи и outbox идут через всех арендаторов). Рантайм подключается
  логин-ролью (`gr8r_app`, создаётся `db:migrate` по `APP_DB_USER`/`APP_DB_PASSWORD`): она не суперпользователь и NOINHERIT — сама прав на таблицы
  не имеет, пока код не сделает `SET ROLE`. Миграции выполняются под `ADMIN_DATABASE_URL` (суперпользователь/владелец БД); таблицы
  передаются `app_owner`. Таблица `events` для `app_user` только на добавление (UPDATE/DELETE отозваны).
- **DDL вне API.** Логин-роль API права владельца не получает (`SET ROLE app_owner` — ошибка): эту выдачу, появившуюся на этапе 3 ради
  индексов конструктора, этап 4 убрал. DDL выполняет только воркер через отдельное подключение `DATABASE_URL_DDL` — логин-роль
  `gr8r_ddl` (создаёт `db:migrate` по `DDL_DB_USER`/`DDL_DB_PASSWORD`): она наследует права `app_owner` (владельца таблиц), не суперпользователь,
  `SET ROLE` ей не нужен. API и сид лишь ставят задачу в `jobs`; воркер выполняет её по белому списку операций (см. «Конструктор сущностей»).
- **Конвейер запроса API**: сессия → пользователь → заголовок воркспейса → одна транзакция: `SET LOCAL ROLE app_user`,
  `app.user_id`, проверка членства, `app.workspace_id` → обработчик → COMMIT (при ответе ≥ 400 — ROLLBACK). Обработчики используют только
  `c.var.db` этого контекста; ручных фильтров по `workspace_id` в запросах нет — изоляцию гарантирует БД. `SET LOCAL` не «протекает»
  между запросами через пул соединений. Пустая настройка даёт NULL → строк не видно (fail closed).
- **Целостность между арендаторами**: связи внутри арендатора — составные внешние ключи `(workspace_id, id)`, поэтому запись одного
  арендатора не может сослаться на запись другого даже в обход API (FK-проверки обходят RLS, составной ключ их закрывает).
- Новая таблица с `workspace_id` обязана вызвать в своей миграции `select app_secure_tenant_table('имя')` (владелец, ENABLE+FORCE,
  политика, права); тест покрытия RLS падает, если таблица пропущена.
- Крупному клиенту позже можно выделить отдельную схему или БД — код от этого не меняется.

## Общие соглашения по данным

- Идентификаторы — UUID v7 (сортируются по времени). В PostgreSQL 16 нативной `uuidv7()` нет (появилась в 18), поэтому первичные ключи
  по умолчанию получают значение от SQL-функции `uuid_generate_v7()` (миграция 0000, без расширений); в коде (сиды, заранее известные id)
  та же схема — `uuidv7()` из `@gr8r/db` с монотонным счётчиком внутри миллисекунды. Человекочитаемые ключи (`WEB-109`, `СЧ-2026-00042`)
  — отдельные поля с нумерацией по арендатору: ключ задачи выдаёт атомарный счётчик проекта (`projects.task_counter`).
- Время — `timestamptz`; даты без времени — `date`.
- Деньги — `numeric(18,2)`, количества — `numeric(18,3)`; в JSON передаются строками, на фронте —
  десятичная арифметика (без float).
- Мягкое удаление — `archived_at`; жёсткое — только из Archive.
- Мягкое удаление в API: `DELETE /:id` архивирует (`archived_at`), `?hard=true` (только admin и выше) удаляет, `POST /:id/restore` возвращает.
  Статусы задач хранятся ключом (`tasks.status` → `statuses.key`), а не id: ключ неизменен.
- **Журнал событий (outbox)**: любое изменение в той же транзакции пишет строку в
  `events (id, workspace_id, type, entity, record_id, actor_id, payload jsonb, created_at, processed_at)`. Из него
  питаются realtime-рассылка, лента Activity, уведомления и автоматизации. Типы: `task.created`, `task.updated` (payload `changes`:
  `{поле: {from, to}}`), `task.archived|restored|deleted`, `member.role_changed` и т. д. `actor_id` — `members.id`.
- **Realtime**: `recordEvent` делает `pg_notify('gr8r_events', конверт без payload)` в той же транзакции (доставка — только после коммита).
  Каждый экземпляр API держит одно соединение LISTEN и раздаёт события по WebSocket-комнатам воркспейсов. Это выбрано вместо опроса
  таблицы: нет периодической нагрузки, задержка — миллисекунды, масштабируется горизонтально. NOTIFY при обрыве теряется, поэтому
  клиент подключается с `?since=<id последнего события>` (uuid v7 сортируется по времени) и получает пропущенное из `events`;
  то же — `GET /events?since=`. Клиент дедуплицирует по `event.id`.
- **Воркер**: события берутся по `processed_at is null … FOR UPDATE SKIP LOCKED` (а не курсором по id: транзакции коммитятся не в порядке id,
  курсор пропустил бы поздно закоммиченное событие); очередь `jobs` — тот же SKIP LOCKED, повторы с экспоненциальной паузой, возврат
  «зависших» задач. Обработчик событий подбирает автоматизации (раздел «Автоматизации»); обработчики задач: `noop`, `index.create` / `index.drop` (DDL конструктора, подключение `DATABASE_URL_DDL`), `document.pdf`, `billing.export_zip` (ZIP-архив счетов) и `flow.run` (выполнение запуска автоматизации).

## Конструктор сущностей (метаданные + JSONB)

Реализовано на этапе 3. Код: схема `packages/db/src/schema/meta.ts` (миграция `0003_meta.sql`), общая логика
`packages/shared/src/fields.ts` и `schemas/meta.ts`, API `apps/api/src/routes/meta.ts`, `routes/records.ts`, `meta/*`,
клиент `apps/web/src/app/meta/*` и `settings/data-model.tsx`.

Таблицы на лету не создаются. Структура описывается метаданными:

- `entities (workspace_id, key, name, kind: system|custom, icon, title_field, settings, sort_order, archived_at)` —
  сущности, включая системные (task, project, deal, company, contact, product), чтобы к ним можно было добавлять поля.
  Системные регистрируются при создании воркспейса (`registerSystemEntities`), в сидах и миграцией для уже существующих
  воркспейсов. Ключ (`key`) не меняется. Для системных `title_field` — имя колонки (`title` / `name`); встроенные
  колонки (статус, сумма…) в `fields` **не** заводятся: это обычные колонки таблицы, `fields` описывает только
  пользовательские поля (`is_system` зарезервирован под будущее).
- `fields (entity_id, key, name, type, required, unique, filterable, options jsonb, sort_order, is_system, archived_at)` —
  типы: text, long_text, number, money, percent, date, datetime, boolean, select, multi_select, user, ref (связь с
  записью другой сущности — системной или пользовательской), refs, url, email, phone. `file` и `formula` — позже
  (нужны хранилище файлов и тип поля-формулы; **язык выражений при этом есть** — `packages/shared/src/expr.ts`,
  этап 7: он используется в спецификациях производства, а не как тип поля конструктора). `options`: варианты select/multi_select `{value,label,color}`, `refEntity`
  (ключ целевой сущности), `min`/`max`, `maxLength`, `currency`. Ключ и тип поля после создания не меняются: от них
  зависят уже записанные данные.
- Хранение значений: у системных таблиц — колонка `custom jsonb` (есть у tasks, projects, deals, companies, contacts);
  пользовательские сущности — общая таблица `records (id, workspace_id, entity_id, data jsonb, created_by, created_at,
  updated_at, archived_at)`. Числа лежат числами, даты — ISO-строками, ссылки — uuid.
- Все три таблицы — арендаторские: `app_secure_tenant_table` (владелец app_owner, ENABLE + FORCE RLS, политика по
  `workspace_id`); составные FK `(workspace_id, entity_id)`.
- Проверка — zod-схема, собираемая из `fields` функцией `buildRecordSchema(fields, 'create'|'patch')`
  (`packages/shared`): на сервере перед записью и в формах клиента (`validateRecord`). create — обязательные поля
  заполнены, пустые значения не сохраняются; patch — проверяются только присланные ключи, `null` очищает поле (для
  обязательного — ошибка). Лишние ключи и ключи удалённых полей отклоняются. Сервер дополнительно проверяет, что
  ссылки (`user`/`ref`/`refs`) указывают на существующие записи **этого** воркспейса, и уникальность (`unique`).
- Запись `custom` у системных сущностей — те же маршруты (`/tasks`, `/deals`, `/companies`, `/contacts`, `/projects`),
  свойство `custom`: при PATCH присланные ключи проверяются и сливаются с имеющимися, `null` удаляет ключ,
  неизменённые значения не проверяются (клиент присылает объект целиком).
- Индексы: для полей с флагом `filterable` — индекс по выражению `((data->>'ключ'))` (для number/money/percent —
  `((data->>'ключ')::numeric)`), для записей пользовательских сущностей частичный (`WHERE entity_id = …`), для
  системных — по `custom` таблицы. Имя `idx_cf_<id поля>`. `CREATE INDEX CONCURRENTLY` нельзя выполнять в транзакции,
  а права владельца у API нет, поэтому **построение и удаление индекса — задача в таблице `jobs`** (очередь `ddl`, типы
  `index.create` / `index.drop`, `payload = {fieldId}`), которую запрос API вставляет в той же транзакции, что и изменение поля
  (откат запроса отменяет и задачу). Задачу берёт воркер и выполняет на отдельном подключении `DATABASE_URL_DDL` (роль-владелец).
  Белый список: воркер не доверяет содержимому задачи — из `payload` берётся только uuid поля, а ключ, тип и сущность читаются из
  метаданных; в SQL попадает лишь выражение над ключом, проверенным по `FIELD_KEY_RE`, таблица — из списка системных таблиц либо `records`
  (любой другой `type` задачи, негодный uuid или несуществующее поле — ошибка либо пропуск без DDL). Задача сверяется с метаданными
  **на момент выполнения**, а не постановки: `index.create` пропускается, если поле уже удалено, скрыто или не `filterable`;
  `index.drop` — если поле снова требует индекса (восстановлено раньше), поэтому порядок и повторы задач безопасны. DDL идёт строго по одному
  на всех воркерах (рекомендательная блокировка `pg_try_advisory_lock` с ожиданием в коде: ждущий `pg_advisory_lock` — открытая транзакция,
  а `CONCURRENTLY` ждёт такие, получился бы взаимный дедлок); сбой оставляет INVALID-индекс — его убираем, задача повторяется с паузой. Пока индекс не
  построен, фильтры работают без него. Запросы строят выражение из ключа, проверенного по метаданным и регулярке, значения идут
  параметрами. Поиск `q` — `ILIKE` по заголовку и текстовым полям (без индекса). GIN `jsonb_path_ops` по `records.data` ускоряет `@>`
  (фильтры по multi_select/refs).
- API (чтение — любой участник, изменение метаданных — admin и выше, записи — member и выше):
  `GET/POST /entities`, `GET/PATCH/DELETE /entities/:key`, `POST /entities/:key/restore`,
  `GET/POST /entities/:key/fields`, `PATCH/DELETE /entities/:key/fields/:id`, `POST …/fields/:id/restore`,
  `POST /entities/:key/fields/reorder`; записи — `GET/POST /data/:entity`, `GET/PATCH/DELETE /data/:entity/:id`,
  `POST /data/:entity/:id/restore`; поиск для палитры — `GET /data-search?q=`. Список записей:
  `filter=ключ:оператор:значение` (повторяется; eq, ne, gt, gte, lt, lte, in, contains, empty, notempty — набор
  зависит от типа поля), `sort=ключ,-ключ2`, `q`, `limit/offset`, `archived`.
- Удаление поля и сущности — с подтверждением (`DELETE …?confirm=<ключ>`), в два шага. Без `purge` поле/сущность только
  скрываются (`archived_at`): значения остаются в `records.data` / `custom`, ключ остаётся занятым, индекс убирается;
  `POST …/restore` возвращает всё, включая данные и индекс. С `purge=true` значения вычищаются из jsonb (`data - 'ключ'`),
  а строка метаданных (для сущности — вместе с записями) удаляется навсегда. Нельзя удалить поле-заголовок и сущность,
  на которую ссылаются поля других сущностей; системные сущности не удаляются и не переименовываются. Данные «скрытого»
  поля до очистки видны в БД и в сыром ответе API (`custom`), но не в интерфейсе.
- Интерфейс пользовательской сущности собирается автоматически из метаданных на готовых компонентах:
  `DataTable`, `Kanban` (по полю select), `EntityDrawer`, `FilterBar`, формы. Маршрут `/data/:key/:recordId?`, группа
  «Data» в сайдбаре, поиск в палитре команд. Пользовательские поля системных сущностей показываются в карточке задачи,
  колонками таблицы задач (меню Columns), в карточках сделки и контакта и на странице компании. Редактор модели —
  Settings → Data model.
- События outbox: `entity.*`, `field.*` (entity = `entity` / `field`) и `record.*` (entity = `record`, ключ сущности в
  `payload.entityKey`); клиент по ним перечитывает метаданные и списки записей.
- Если сущность станет «горячей» (миллионы записей, тяжёлая аналитика) — её можно материализовать в
  настоящую таблицу; это исключение, а не основной путь.

Известные ограничения этапа: порядок карточек внутри колонки доски не хранится (перетаскивание меняет только
значение select); сортировка в таблице пользовательской сущности — на клиенте по загруженным записям (до 2000); индексы
не покрывают поиск `q`; уникальность проверяется при записи (без уникального индекса БД, возможна гонка двух
одновременных записей); у проектов пользовательские поля доступны через API, но интерфейса для них нет.

## Каталог: товары и услуги

Реализовано на этапе 4. Код: схема `packages/db/src/schema/catalog.ts` (миграция `0004_catalog.sql`), схемы API
`packages/shared/src/schemas/catalog.ts`, API `apps/api/src/routes/catalog.ts` и `catalog/service.ts`, клиент `apps/web/src/app/catalog/*`.
Чтение — любой участник; единицы, категории и характеристики меняет admin и выше, товары — member и выше.

- `units (workspace_id, code, name, symbol, is_base)` — справочник единиц ОКЕИ **в каждом воркспейсе**: базовый набор (`OKEI_UNITS` в
  `packages/shared/src/constants.ts`: шт 796, кг 166, ч 356, усл. ед 876 …) воркспейс получает при создании (`registerBaseUnits`; для существующих —
  миграция), свои единицы добавляются рядом (код 3–4 цифры, не меняется). Базовые не удаляются; единица, на которую ссылаются товары и
  спецификации, не удаляется (составной внешний ключ). Единица товара — составной FK `(workspace_id, unit_code)`.
- `product_categories` — дерево: `parent_id` + материализованный `path` (id предков и самой категории через «/»), выборка поддерева по префиксу
  (`path = X or path like X/%`, индекс `text_pattern_ops`). Перенос ветки пересчитывает `path` всего поддерева; в себя и в потомков перенести нельзя.
  Удалить можно только пустую категорию (без подкатегорий и товаров).
- `attribute_defs (category_id, key, name, type, required, unit, options, sort_order)` — характеристики категории. Типы — как у полей
  конструктора, кроме ссылок (`user`/`ref`/`refs`) и `datetime`; `options` те же (варианты select, min/max, maxLength). **Наследование:** действующий набор
  категории = характеристики всех предков (от корня) + свои (`GET /product-categories/:id/attributes` отдаёт их с признаком `inherited` и названием
  категории-источника). Ключ уникален вдоль всей ветки: нельзя завести ключ, который уже есть у предка, самой категории или потомка
  (409), и перенести ветку к родителю с таким же ключом. Ключ и тип не меняются. Удаление характеристики — с подтверждением (`?confirm=<ключ>`) и
  необратимо: значения стираются у товаров всей ветки (`attrs - ключ`).
- `products (kind: goods|service|work|operation, sku, name, description, barcode, unit_code, vat_rate, price, purchase_price, category_id, default_supplier_id, attrs jsonb, is_active,
  custom jsonb)`. `vat_rate` — `none|0|5|7|10|20`; `price` — цена продажи, `purchase_price` — закупочная (`numeric(18,2)`, строками). `default_supplier_id` — поставщик по умолчанию
  (составной FK на `companies`): заказы поставщикам по потребности производства создаются на него. `lead_days` —
  срок поставки в днях (для закупки): им считается потребность на обеспечение в расчёте потребностей и заказы
  поставщикам. Нормы запаса товара — `stock_levels`, см. раздел «План производства и пополнение». `sku` и
  `barcode` уникальны в воркспейсе (частичные уникальные индексы по непустым; sku — без учёта регистра), штрихкод — 8–14 цифр. Мягкое удаление — `archived_at`.
  Варианты товара (размер/цвет) — позже, отдельной таблицей. `product` — системная сущность конструктора: пользовательские поля товара лежат
  в `custom` (индексы по ним строит воркер, `SYSTEM_TABLES.product = products`).
- **Проверка `attrs` — тем же механизмом, что поля конструктора:** характеристики категории (с унаследованными) превращаются в `FieldDef`, значения проверяет
  `buildRecordSchema` (`packages/shared/src/fields.ts`) — на сервере (`validateAttrs`) и в формах клиента (`validateRecord`, те же `FieldInput` / `FieldValue`).
  Создание — обязательные заполнены, лишние ключи (в том числе характеристики соседней категории) отклоняются; без категории характеристик нет,
  любые `attrs` — ошибка. PATCH той же категории проверяет только изменённые ключи (как `custom`), `null` убирает ключ. Смена категории проверяет
  итоговый набор целиком по новой схеме, как создание: значения, которых в новой схеме нет, нужно убрать явно (`null`). Перенос категории с товарами,
  у которых есть значения унаследованных характеристик, пропадающих из цепочки, запрещён (422).
- API: `/units`, `/product-categories` (+ `/:id/attributes`), `/attribute-defs/:id`, `/products` (список: `categoryId` с подкатегориями — `subtree=false` отключает,
  `kind`, `active`, `q` по названию / sku / штрихкоду, `sort`). События outbox: `unit.*`, `product_category.*`, `attribute_def.*`, `product.*`.
- Интерфейс (маршрут `/catalog/:productId?`, группа «Catalog» в сайдбаре): дерево категорий слева (счётчики с подкатегориями, меню категории — подкатегория,
  характеристики, переименование и перенос, удаление), таблица товаров справа на `DataTable` + `FilterBar` (категория — из дерева, `?category=` в адресе;
  фильтры тип / активность, поиск), карточка товара на `EntityDrawer` (поля по типам, характеристики категории теми же `FieldInput`, пользовательские поля
  конструктора), форма создания с характеристиками выбранной категории. Редактор характеристик категории показывает унаследованные (только чтение, с
  пометкой «from …») и свои. Палитра команд находит товары и продукцию (`useCatalogHits`).

## Контрагенты и организации (Россия)

Реализовано на этапе 5. Код: схема `packages/db/src/schema/documents.ts` и `crm.ts` (миграция `0005_documents.sql`), проверки реквизитов
`packages/shared/src/ru.ts`, схемы API `schemas/documents.ts` и `schemas/crm.ts`, API `apps/api/src/routes/documents.ts`.
Чтение — любой участник; организации, склады и настройки склада меняет admin и выше, банковские счета контрагентов и документы — member и выше.

- `companies` (из CRM) получают реквизиты: `kind` (`legal` юрлицо / `sole_proprietor` ИП / `individual` физлицо), `inn`, `kpp`, `ogrn` (ОГРН для юрлица,
  ОГРНИП для ИП), `legal_address`, `actual_address`. Всё необязательно (реквизиты заполняют по мере появления), но если заполнено — проверяется
  **по итоговому состоянию записи** (`validateRequisites`, и при создании, и при PATCH — тип, ИНН и КПП зависят друг от друга): ИНН — 10 цифр у юрлица и 12 у ИП/физлица

  (остаток от деления на 11 / 13), у физлица ОГРН нет. Контрольный ключ расчётного счёта (`accountKeyOk`, веса 7-1-3) есть в `ru.ts`, но не навязывается: счёт проверяется

  ровно один; составные внешние ключи; первый счёт владельца становится счётом по умолчанию, «по умолчанию» один). БИК — 9 цифр с `04`, счета — 20 цифр.
  API: `/companies/:id/bank-accounts`, `/organizations/:id/bank-accounts`, `/bank-accounts/:id` (счета организаций правит admin+).
- `organizations` — собственные юрлица воркспейса (их несколько; одна — по умолчанию, частичный уникальный индекс): краткое и полное название, реквизиты (те же проверки),
  телефон, email, руководитель с должностью, главбух, `tax_system` (`osn` ОСН / `usn` УСН), `default_vat_rate`, файлы печати и подписей руководителя и бухгалтера
  (`stamp_file`, `director_signature_file`, `accountant_signature_file`). **Файлы пока — ссылка и метаданные** `{ name, url, size?, mimeType? }`: допускаются `http(s)://`, путь на
  этом сервере и картинка в `data:image/(png|jpeg|gif|webp);base64,` (другие схемы, включая `javascript:` и SVG, отклоняются); загрузка файлов появится вместе с хранилищем S3.

## Документы продаж и закупок

Реализовано на этапе 5. Код: схема `packages/db/src/schema/documents.ts`, расчёт сумм `packages/shared/src/documents.ts` (+ `decimal.ts`), сервис проведения
`packages/db/src/documents.ts` (им же пользуется сид), API `apps/api/src/routes/documents.ts`, клиент `apps/web/src/app/docs/*`.

- `documents (type, number, number_year, number_seq, date, due_date, status: draft|posted|cancelled, organization_id, counterparty_id, warehouse_id?, currency 'RUB',
  price_includes_vat, amount_net, vat_total, total, based_on_id, responsible_id, comment, posted_at, custom jsonb)`. Договор документа — `contract_id` (составной внешний ключ
  `(workspace_id, contract_id)` → `contracts`, добавлен на этапе 8 «УНФ: Услуги», см. раздел «Договоры, тарифные планы и биллинг»); оплаты (входящая и исходящая) — позже;
  валюта пока одна — рубль.
- `document_lines (document_id, product_id, name, unit_code, qty, price, discount_pct, vat_rate, net, vat_amount, total, source_line_id, origin_line_id)`. Строка — всегда товар или услуга
  каталога (название, единица и ставка НДС копируются из товара и дальше правятся в строке); `qty > 0`; суммы строки хранятся (их считает сервер, клиентские значения не принимаются).
- Типы: продажи — `quote` коммерческое предложение, `customer_order` заказ покупателя, `invoice` счёт на оплату, `realization` реализация (УПД / ТОРГ-12), `act` акт оказания услуг,
  `customer_return` возврат от покупателя, `work_order` заказ-наряд (см. раздел «Заказ-наряд: работы, материалы и состояния»); закупки — `supplier_order` заказ поставщику,
  `receipt` поступление, `supplier_return` возврат поставщику. Метаданные типов (префикс номера, движение склада, допустимые основания, печатные формы) — `DOCUMENT_META` в `shared`.
- **Статусы и операции.** Новый документ — черновик (`draft`), правится целиком. `post` — проведение (draft → posted); `unpost` — отмена проведения (posted → draft, правка снова доступна);
  `cancel` — отмена документа (draft → cancelled; проведённый сначала снимают с проведения), `restore` — вернуть отменённый в черновик. Проведённый документ не правится и не удаляется.
  Проведение проверяет: выбран контрагент, есть строки, для документов, двигающих товар, — склад, документ-основание проведён, исполнение не превышает заказанное, остатка хватает (см. «Склад»).
  Отмена проведения запрещена, пока проведены документы, созданные на его основании (`has_posted_children`), и пока позднейшие движения склада нуждаются в этом приходе (`stock_conflict`).
- **Суммы** — чистые функции `computeLine` / `computeTotals` / `computeDocument` на десятичных `decimal.ts`, одни и те же на сервере (при сохранении и проведении) и в форме (мгновенный пересчёт).
  Цены «НДС в т.ч.» (`price_includes_vat = true`): стоимость строки = qty × цена × (1 − скидка%), из неё выделяется НДС (`стоимость × ставка / (100 + ставка)`), без НДС = остаток;
  «НДС сверху»: НДС = `стоимость × ставка / 100` добавляется. Ставки `none` и `0` дают НДС 0. **Округление — до копейки по каждой строке** (половина от нуля, единственное округление
  на строку: произведение считается точными целыми, поэтому 0,0249996 не превращается в 0,03), а **итоги документа — суммы округлённых строк**, а не пересчёт от общей суммы (3 строки
  по 0,10 с НДС 20% «в т.ч.» дают НДС 0,06, а не 0,05) — так итоги всегда сходятся со строками печатной формы. Итоги по ставкам НДС (`byRate`) — для печати. Тесты округления — `packages/shared/test/documents.test.ts`.
- **Нумерация — номер присваивается при проведении**, а не при создании: черновик номера не имеет, и бросать черновики можно без дыр в последовательности. Формат `СЧ-2026-00042`
  (префикс типа, год даты документа, порядковый номер из пяти цифр). Последовательность — по (организация, тип, год): строка `document_counters` увеличивается
  `INSERT … ON CONFLICT DO UPDATE` в транзакции проведения, поэтому параллельные проведения встают в очередь на блокировке строки, а откат проведения (ошибка склада, проверки)
  откатывает и счётчик — **номера идут подряд, без дыр и без повторов** (конкурентный тест: 12 параллельных проведений дают 1…12, затем ещё 6 с тремя отказами — 13…15). Номер сохраняется
  за документом навсегда: после отмены проведения и повторного проведения он тот же; поэтому у документа с номером нельзя сменить организацию или год даты (422 `number_locked`),
  а удалять можно только черновик, у которого номера никогда не было (иначе — отмена документа). Уникальность — частичный индекс `(workspace, organization, type, year, seq)`.
- **«На основании»** (`POST /documents/:id/based-on { type }`): допустимые цепочки — КП → заказ / счёт; заказ покупателя → счёт / реализация / акт; счёт → реализация / акт; реализация →
  возврат от покупателя; заказ поставщику → поступление; поступление → возврат поставщику. Шапка и строки копируются (новый черновик), связь — `based_on_id` и в строках
  `source_line_id` (откуда скопирована) и `origin_line_id` (строка исходного **заказа** — для остатка по всей цепочке, в том числе через счёт). Количество строки документа-исполнителя
  (реализация, акт, поступление) = минимум из количества в источнике и **остатка к исполнению** (заказано − уже в непроведённых и проведённых, но не отменённых документах-исполнителях),
  для возврата — остаток к возврату; строки с нулём пропускаются, если не осталось ничего — 422 `nothing_to_create`. В карточке заказа по каждой строке: исполнено (проведёнными) и запланировано
  (с черновиками). При проведении исполнение не может превысить заказанное (`over_fulfilment`), возврат — исходное количество (`over_return`).
- API: `/documents` (журнал: `type`, `group`, `status`, `organizationId`, `counterpartyId`, `from`/`to`, `q` по номеру / комментарию / названию контрагента, `sort`; ответ содержит суммы по выборке без
  отменённых), `/documents/:id` (карточка со строками, ссылками, остатками), `POST /documents`, `PATCH` (строки заменяются списком: существующие по `id` обновляются, чтобы ссылки потомков не терялись),
  `DELETE`, `POST …/post|unpost|cancel|restore|based-on`. События outbox: `document.created|updated|deleted|posted|unposted|cancelled|restored`.
- **Печатные формы** — счёт на оплату (он же для КП и заказа), УПД, акт оказания услуг, ТОРГ-12. Шаблон — чистая функция «данные → HTML-строка» (`packages/shared/src/print`), данные собирает
  `buildPrintData` (документ, обе стороны с реквизитами и банком по умолчанию, строки с единицами ОКЕИ, итоги по ставкам). Страница — A4 (портрет у счёта и акта, альбом у УПД и ТОРГ-12),
  поля и размер заданы `@page`, разрывы — `break-inside: avoid` у строк, подписей и итогов, шапка таблицы повторяется (`thead` как `table-header-group`); все значения экранируются, ответ
  отдаётся с `Content-Security-Policy: default-src 'none'`. **Сумма прописью** — `amountInWordsRu` (род и склонение разрядов, копейки цифрами: «Сто двадцать три рубля 45 копеек»), тесты — `ru.test.ts`.
  Режим печати в браузере: `GET /documents/:id/print/:form` отдаёт HTML, страница `/documents/:id/print/:form` показывает его в iframe и печатает `window.print()` iframe.
  **PDF** — задача `document.pdf` в воркере: `POST /documents/:id/pdf { form }` создаёт строку `document_files` (pending) и задачу в `jobs`; воркер собирает ту же страницу и печатает её в headless
  Chromium (`playwright-core`; путь — `CHROMIUM_PATH` или каталоги playwright), результат кладёт в `document_files.data` (**пока в БД**; интерфейс `PdfStore` в `apps/worker/src/pdf/storage.ts`,
  `PDF_STORE=s3` — заготовка, бросает «not implemented»), статус — `GET /documents/:id/pdf/:fileId`, файл — `?download=1`. Страница PDF **не ходит в сеть** (разрешены только `data:`): ссылки на печать и подписи
  организации по http(s) видны в браузерном предпросмотре, а в PDF картинки попадут только как `data:`-URL — иначе администратор мог бы заставить воркер обращаться к внутренним адресам. Ошибка формирования
  не повторяется вслепую: файл получает статус `failed` с текстом, форму запрашивают заново. ЭДО — позже.
- **Выгрузка архивом.** `document_files` привязан к одному документу, поэтому архив из нескольких счетов лежит в своей таблице `document_exports` (`workspace_id`, `name`, `status`,
  `size`, `data`, `document_ids`, `requested_by`; миграция `0020_billing_export_zip.sql`): строка создаётся API (статус `pending`), воркер кладёт туда байты архива тем же интерфейсом
  хранилища (`PdfStore` в `apps/worker/src/pdf/storage.ts`; пока в БД, `PDF_STORE=s3` — заготовка). Статус — `GET /billing/export/:id`, файл — `?download=1`.
- Интерфейс (`apps/web/src/app/docs`): журналы **Sales** (`/sales`) и **Purchases** (`/purchases`) — вкладки по типам, `FilterBar` (статус, организация, поиск), `DataTable` с суммами; форма
  документа `/documents/:id` — шапка (организация, контрагент с поиском, склад, дата, номер, способ указания НДС), табличная часть с подбором из каталога (`ProductPicker`, поиск на сервере),
  клавиатура (↑ ↓ между строками, Enter — следующая строка или новая, Insert — вставить строку, стрелки в списке подбора), итоги и НДС внизу и сумма прописью, кнопки **Post / Unpost / Create based on / Print**,
  связанные документы. Черновик **сохраняется сам** через паузу после правки (последняя правка выигрывает: одновременная правка одного черновика двумя пользователями не сливается).
  Палитра команд находит документы по номеру, контрагенту и комментарию.

## Внутренние складские документы

Реализовано на этапе 0а (сессия «УНФ: Производство»). Код: метаданные типов и чистая функция `stockPlan` — `packages/shared/src/documents.ts`,
сервисы — `packages/db/src/documents.ts` и `packages/db/src/stock.ts`, справочник статей — `cost_items` (миграция `0007_stock_docs.sql`),
API — `apps/api/src/routes/documents.ts`, клиент — `apps/web/src/app/docs/*`.

- **Внутренний документ — документ без контрагента.** У типа в `DOCUMENT_META` поле `party: null`; контрагент не нужен и не хранится,
  НДС у строк — `none`, продажной цены нет. Направление движения задаёт **роль строки** (`document_lines.stock_role`: `in` | `out`), а не тип документа:
  сервер проставляет её сам (`lineRole`), клиент её не присылает. План движений — чистая функция `stockPlan(doc, lines) → PlannedMove[]`
  (тесты — `packages/shared/test/documents.test.ts`): у продаж и закупок направление задаёт тип, у внутренних — роль строки и шапки.
- **Типы:** `stock_transfer` (ПМ, перемещение между складами: расход со склада шапки и приход на `target_warehouse_id` по каждой строке),
  `write_off` (СП, списание: расход, статья затрат обязательна), `stock_posting` (ОП, оприходование: приход, статья доходов обязательна),
  `inventory_count` (ИНВ, инвентаризация: остатки не двигает, результат сверки оформляется списанием и оприходованием на основании).
  Вид операции — `documents.operation` (`transfer`; `in_transit`, `to_operation`, `from_operation` — этап 0б). Перемещение требует склад-получатель,
  отличный от склада-источника (иначе 422 `target_warehouse_required`; в БД — CHECK `documents_transfer_chk`).
- **Статьи затрат и доходов** — `cost_items (workspace_id, name, kind: expense|income, system_key, archived_at)`, арендаторская таблица
  (`app_secure_tenant_table`), имя уникально среди неархивных. `documents.cost_item_id` — составной FK. Вид статьи должен совпадать с типом документа
  (списание — расходная, оприходование — доходная): иначе 422 `cost_item_kind_mismatch`; статья обязательна при проведении — `cost_item_required`.
  Системные статьи («Брак», «Порча», «Недостача», «Отходы», «Передача в эксплуатацию», «Излишки») заводит код при создании воркспейса (`ensureCostItems`).
  Справочник — Settings → Cost items (меняет admin и выше).
- **Цена оприходования** — себестоимость единицы прихода: по умолчанию текущая средняя (склад, товар), иначе цена последнего проведённого поступления,
  иначе закупочная цена товара (`GET /stock/default-cost?warehouseId=&productId=`; `defaultPostingCost`). Задать цену вправе admin и owner;
  member'у сервер подставляет среднюю, а присланную цену игнорирует.
- **Состояние документа отдельно от проведения** — `documents.state` (NULL у типов без состояний), допустимые значения и переходы — в метаданных типа
  (`DOCUMENT_META[type].states`, чистые правила — `stateTransitions` / `canChangeState` в `shared`). Действие `POST /documents/:id/state { state }`
  пишет событие `document.updated` с `changes.state {from, to}` — автоматизация «поле изменилось» срабатывает без нового триггера
  (`state` добавлен в `BUILTIN_FIELDS.document`). Хук типа на смену состояния живёт в слое БД (`STATE_HOOKS` в `packages/db/src/document-hooks.ts`):
  им пользуются перемещение «в пути» (этап 0б), заказ на производство (этап 2) и заказ-наряд (план услуг). Первый тип с состояниями — перемещение «в пути»
  (`shipped` → `received`, обратный переход отменяет приёмку).
- **Инвентаризация (ИНВ).** Остатки не двигают: у строки документа `qty` — **фактическое** количество, `document_lines.book_qty` — **учётное**
  (по остаткам склада на момент заполнения), разница — недостача или излишек. Строки заполняются кнопкой «Fill by stock»
  (`POST /documents/:id/fill-count-sheet`, опись — `GET /stock/count-sheet?warehouseId=`). По проведённой инвентаризации создаются
  **списание** (недостача, статья «Недостача») и **оприходование** (излишек, статья «Излишки», цена — по умолчанию) — строго по разнице:
  сколько уже оформлено, столько ещё можно (своя проверка в `packages/db/src/inventory.ts`). Снять инвентаризацию с проведения нельзя,
  если по ней есть проведённые документы (общее правило `has_posted_children`).
- **Перемещение «в пути»** (`stock_transfer` с `operation = 'in_transit'`) — одно состояние документа вместо двух документов:
  при проведении товар уходит со склада отправителя и приходит на **служебный склад вида `transit`** (один на воркспейс, создаётся лениво),
  документ получает состояние `shipped`. Переход в `received` (хук `STATE_HOOKS`) — расход с `transit` и приход получателю по **принятому количеству**
  (`document_lines.received_qty`, не больше отправленного); непринятое остаётся на `transit`. Возврат `received → shipped` отменяет вторую партию
  движений. Движения помечены **фазой** (`stock_moves.phase`: 1 — отправка, 2 — приёмка), поэтому отмена идёт по фазам.
- **Передача в эксплуатацию** (`operation = 'to_operation'`) — расход со склада (себестоимость — на статью затрат, например «Передача в эксплуатацию»)
  и количественный учёт «у кого»: `in_use_balances (workspace_id, product_id, member_id?, work_center_id?, qty)` и движения `in_use_moves`
  (получатель ровно один — сотрудник или участок; CHECK). Возврат из эксплуатации (`from_operation`) уменьшает остаток у получателя
  (без прихода на склад). Остаток пересчитывается по движениям, поэтому отмена одного документа не ломает остаток; если после отмены остаток
  ушёл бы в минус — 422 `in_use_conflict`. Экран «In use» (`/stock/in-use`, `GET /stock/in-use`).
- **Стоимость видят только admin и owner** (`canSeeCost` / `maskCost` в `packages/db/src/cost.ts`): `stock_moves.cost`, средняя и стоимость остатка
  (`/stock/balances`), `/stock/avg-costs`, цена оприходования в строке документа и «стоимость по себестоимости» в журнале. Member и guest видят количество,
  но не стоимость (в ответах — `null`). Количество участник видит всегда.
- **Журнал** — `group=stock` (`/stock-docs`): вкладки по типам, колонка «Cost» — сумма `qty × cost` по движениям документа (у перемещения берётся расходная
  сторона, иначе приход и расход сократились бы). Внутренние документы не входят в суммы продаж и закупок.
- **Печатные формы внутренних документов:** **ИНВ-3** (инвентаризационная опись: учётное, фактическое и разница по каждой позиции),
  **ТОРГ-16** (акт о списании: количество и себестоимость по средней, статья затрат), **ТОРГ-13** (накладная на внутреннее перемещение:
  склад-отправитель, склад-получатель, получатель в эксплуатацию). Себестоимость строк берётся из движений документа (`documentLineCosts`),
  она видна только admin и owner.
- **Обобщение логики заказов:** проверки по именам типов заменены чтением метаданных — `isOrder` (строки заказа — источник `origin_line_id`),
  `reservedUntil` (типы-исполнители, снимающие резерв), `isReturn`, `fulfils`, `reserves`. Поведение продаж и закупок не изменилось.

## Склад

Реализовано на этапе 5. Код: `packages/db/src/stock.ts` (движения, остатки, резервы), `packages/shared/src/documents.ts` (средняя скользящая — `stockIn`, `stockOut`, `replayMoves`),
API `/stock/*`, клиент `apps/web/src/app/docs/InventoryPage.tsx`.

- `warehouses`; проведение реализации (расход), поступления (приход), возврата от покупателя (приход) и возврата поставщику (расход), а также внутренних документов
  (списание — расход, оприходование — приход, перемещение — расход и приход) пишет `stock_moves (warehouse_id, product_id, document_id,
  document_line_id, qty ±, cost, moved_at, seq)` по строкам-**товарам**; услуги на склад не влияют. `seq` — identity-колонка: порядок движений для пересчёта средней; `moved_at` — дата документа.
- Остатки — таблица `stock_balances (warehouse_id, product_id, qty, avg_cost)`, обновляется **в той же транзакции**, что и движения. Строка остатка блокируется `FOR UPDATE` (ключи в одном порядке — без
  взаимных блокировок), поэтому параллельные проведения не могут вместе уйти в минус, а `seq` совпадает с порядком блокировок (тест: 4 параллельные отгрузки по 2 при остатке 5 — проходят две).
- **Себестоимость — средняя скользящая по (склад, товар)**, 4 знака. Приход пересчитывает среднюю взвешенно (`(остаток × средняя + приход × цена) / новый остаток`); если остаток был нулевым или отрицательным,
  средней становится цена прихода. Расход списывается по текущей средней и её не меняет. Цена прихода по поступлению — сумма строки **без НДС** (у организации на УСН входной НДС входит в себестоимость, берётся
  сумма с НДС) / количество; возврат от покупателя приходуется по себестоимости исходной реализации (по `source_line_id`), без неё — по текущей средней; возврат поставщику списывается по средней.
- **Двухфазная запись.** `applyStockMoves` пишет сначала расходы, потом приходы: цена прихода перемещения — **фактическая цена расхода той же строки**
  (`costFromLine`), поэтому товар переезжает по своей себестоимости, а не по средней получателя. Нехватка остатка проверяется после расходов (приходы остаток не уменьшают).
  Тот же приём использует выпуск: цена прихода продукции — себестоимость партии из списанных материалов и работ (в `applyStockMoves` её считает колбэк `inCost`).
  У движения есть **фаза** (`stock_moves.phase`: 1 — основная, 2 — приёмка перемещения «в пути»): отмена приёмки откатывает только свою фазу.
- **Отмена проведения** удаляет движения документа и **пересчитывает остаток и среднюю по оставшимся движениям** (`replayMoves`): расходы после отменённого прихода переоцениваются; если после этого остаток
  уходит в минус — отмена запрещена (422 `stock_conflict`: сначала снимите с проведения зависимые документы).
- **Минус.** Настройка воркспейса `workspaces.settings.allowNegativeStock` (по умолчанию выключена; `GET/PATCH /stock/settings`, меняет admin; интерфейс — Settings → Warehouses). Выключена — проведение
  расхода, которому не хватает остатка, отклоняется (422 `insufficient_stock`, в `details.items` — товар, доступно, нужно), ничего не записывается и номер не выдаётся. Настройка общая для воркспейса, не по складам.
- **Резервы.** `stock_reservations (document_line_id | production_line_id | production_component_id, warehouse_id, product_id, qty)` — владелец резерва ровно один
  (CHECK `stock_reservations_owner_chk`), уникальность — по владельцу (для материала — по строке состава и складу). Три вида резерва:
  (1) по строке-товару проведённого заказа покупателя со складом: резерв = заказано − отгружено проведёнными реализациями цепочки, пересчитывается при проведении и отмене
  проведения заказа и реализаций; (2) выпущенная продукция под заказ покупателя (`production_line_id`, строка выпуска) — см. «Заказы на производство и выпуск»;
  (3) **материалы заказа на производство** (`production_component_id`, строка состава заказа) — см. «Обеспечение материалов заказа на производство».
  В остатках: `reserved` и `available = on hand − reserved` (сумма всех резервов); проведение расхода резервами не блокируется (проверяется физический остаток).
  Свободное количество для нового резерва считается под блокировкой строк остатков (`FOR UPDATE`) — два заказа не займут одно и то же количество.
- API: `GET /stock/balances` (склад, товар, `q`, `nonZero`; количество, резерв, доступно, средняя, стоимость, итог стоимости), `GET /stock/moves` (карточка движений: документ, склад, количество, себестоимость
  и остаток после движения по складу), `GET /stock/avg-costs`, `GET /stock/default-cost` (цена оприходования по умолчанию). Стоимость в этих ответах видят только admin и owner (см. «Внутренние складские документы»).
  Интерфейс: **Inventory** (`/inventory/:productId?`) — остатки с фильтром по складу и поиском, показатели (стоимость, позиции, резервы), карточка товара
  (`EntityDrawer`: остатки по складам и журнал движений со ссылками на документы).
- **Производство:** источник цены материала `avg_cost` (Settings → Production) берёт `loadAvgCosts` — среднюю по складам, взвешенную остатком; товар без остатка оценивается закупочной ценой. Снимок производства
  (`/production/snapshot`) отдаёт `avgCost` каждого материала, расчёт на клиенте и на сервере — одна функция.
- **Корректировки себестоимости закрытия периода.** Движений с нулевым количеством не бывает (CHECK `stock_moves_qty_chk`), поэтому изменение
  себестоимости записи движением невозможно: цена прихода/расхода меняется прибавкой в отдельной таблице
  `stock_cost_adjustments (workspace_id, move_id, delta_cost, own_delta, closing_id)`, у движения — не больше одной корректировки
  (уникальный индекс по `(workspace_id, move_id)`). **Себестоимость читается как `cost + delta` везде:** остаток средней
  (`stock_balances.avg_cost` пересчитывается при закрытии), стоимость документа в журнале (`documentCosts`), себестоимость строки
  документа (`documentLineCosts`), цена возврата от покупателя (`sourceMoveCosts`) и карточка движений (`GET /stock/moves`).
  Корректировку создаёт и снимает закрытие периода (раздел «Закрытие месяца»); она принадлежит своему закрытию (`closing_id`),
  поэтому отмена закрытия возвращает прежние значения.
- Инвентаризация, перемещения «в пути» и передача в эксплуатацию реализованы в этапе 0б (раздел «Внутренние складские документы»);
  закрытие периода — этап 6 (раздел «Закрытие месяца»); ордера и партионный учёт — следующими шагами.
## Производство: спецификации и себестоимость

Реализовано на этапе 4. Код: схема `packages/db/src/schema/production.ts`, расчёт `packages/shared/src/bom.ts` (+ `decimal.ts`), схемы API
`schemas/production.ts`, API `apps/api/src/routes/production.ts`, клиент `apps/web/src/app/production/*`.
Чтение — любой участник; участки и настройки меняет admin и выше, продукцию и спецификации — member и выше.

- `manufactured_items` — справочник продукции (изделия и полуфабрикаты): код, название, `kind` (`product` — изделие, `semi` — полуфабрикат; на уровне
  данных разницы нет: любую продукцию можно включить в другую), единица, ссылка на товар каталога для продажи/склада (`product_id`, необязательно),
  выход на партию (`batch_qty`), процент накладных (`overhead_pct`) и **дней на изготовление** (`lead_days`, рабочих, по умолчанию 0 —
  дата запуска минус этот срок по календарю воркспейса, см. «План производства и пополнение»). Архивируется; продукцию,
  которая входит в чужие спецификации, убрать нельзя.
- `bom_lines (item_id, kind: material|semi|work, sort_order, …)` — спецификация на `batch_qty` единиц (форма строки по типу проверяется `CHECK` в БД):
  - material — `product_id` из каталога (только товары: услуга материалом быть не может, её место — работа), `qty`, `scrap_pct` (отход);
  - semi — `child_item_id` (другая продукция со своей спецификацией), `qty`, **режим полуфабриката `semi_mode`** (`stock` — полуфабрикат выпускается
    отдельно и списывается со склада, `explode` — «фантом», разворачивается до материалов и работ в том же выпуске; по умолчанию `stock`,
    `CHECK` в БД: значение задано только у строк `semi`; миграция `0007_bom_semi_mode.sql`); дерево любой глубины, **циклы запрещены**: при записи строки сервер
    проверяет, достижимо ли изделие из включаемого полуфабриката (`wouldCreateCycle`), под рекомендательной блокировкой воркспейса, чтобы параллельные
    правки разных изделий не замкнули цикл (422 `bom_cycle`); интерфейс не предлагает полуфабрикаты, которые замкнули бы цикл;
  - work — `operation` (название), `work_center_id` (участок, необязательно), `hours`, `rate` за час (пусто — ставка участка) и `fixed_cost`;
    стоимость работы = hours × ставка + fixed_cost; `product_id` — **операция** из каталога (вид номенклатуры «операция»),
    если она есть: работа без операции остаётся текстовой, её стоимость по-прежнему оценивается по норме (этап 4в);
  - `unit_code` строки заполняет сервер из единицы товара / продукции (преобразования единиц нет: строка в единице своего товара).
- `work_centers` — участки со ставкой за час по умолчанию; `warehouse_id` — склад-цех участка (составной FK на `warehouses`, вид `workshop`; проверяется в сервисе).
- Настройка воркспейса `workspaces.settings.materialPriceSource` (`GET/PATCH /production/settings`, меняет admin; интерфейс — Settings → Production) задаёт
  **источник цены материала**: `purchase` (закупочная, по умолчанию), `price` (цена продажи) или `avg_cost` (средняя себестоимость склада, этап 5: взвешенная остатком
  по складам; товар без остатка оценивается закупочной ценой). Нулевая цена считается незаданной: материал оценивается в 0, строка помечается «No price».
- **Себестоимость единицы** считает чистая функция `computeBomCost` в `packages/shared` — одна и та же на сервере (`GET /manufactured-items/:id/cost`, тесты)
  и в интерфейсе (мгновенный пересчёт при правке строки, без ожидания сервера). Арифметика десятичная на BigInt (`decimal.ts`, масштаб 10^-6), без float;
  результат — строки с 4 знаками. Правила: стоимость партии / `batch_qty` = себестоимость единицы; material = цена × qty × (1 + отход%/100);
  semi = qty × себестоимость единицы полуфабриката (его спецификация считается рекурсивно, со своими накладными); **накладные узла = overhead_pct от
  прямых затрат его собственных строк (материалы + работы)** — полуфабрикат уже включает свои накладные, поэтому на него накладные родителя не начисляются
  (нет двойного счёта). Результат — дерево с разбивкой «материалы / работы / накладные / итого» по каждому узлу (партия и единица); затраты полуфабриката
  входят в разбивку родителя по своим статьям. Цикл — `BomCycleError` с цепочкой id.
- **Развёртка и потребность** считают чистые функции `packages/shared/src/bom.ts` — одна и та же на сервере и в тестах. `explodeBom(items, rootId, qty)`:
  спецификация задана на партию, поэтому нормы пропорциональны `qty / batch_qty` (кратности партиям нет, как в УНФ); материал — с отходом, работа — часами,
  полуфабрикат по `semi_mode` строки: `stock` — строка на списание, `explode` — его материалы и работы рекурсивно; цикл — `BomCycleError`.
  `computeNeeds(explosion, availability)` — потребность с учётом остатков: нужно / доступно / дефицит по каждому товару. **Дефицит полуфабриката в режиме
  `stock` разворачивается дальше**: на недостающее количество считаются его материалы и работы (строка «выпустить ПФ × N»). Требования одного товара с разных
  уровней агрегируются и сравниваются с остатком один раз — остаток не списывается дважды. Количества — 3 знака.
- `GET /production/snapshot` отдаёт одним запросом всё для клиентского расчёта: продукцию со строками, участки, материалы из спецификаций (цены) и настройки.
  Клиент кэширует снимок, правит его оптимистично, realtime по событиям `manufactured_item` / `bom_line` / `work_center` / `product` / `workspace`
  перечитывает его. API: `/work-centers`, `/manufactured-items` (+ `/:id/lines`, `/:id/lines/reorder`, `/:id/cost`, `/:id/explode`), `/bom-lines/:id`, `/production/*`.
- `GET /manufactured-items/:id/explode?qty=&warehouseId=` — развёртка спецификации на количество и потребность: остаток склада минус резерв (по складу
  или по всем складам воркспейса), дефицит и строки «выпустить ПФ». Стоимость в ответе не отдаётся: маскирование себестоимости по роли приходит с этапом 0а.
- Интерфейс: `/production` — список продукции с себестоимостью единицы; `/production/:id` — шапка (тип, код, единица, партия, накладные), дерево спецификации
  (иконки по типу строки, количество и стоимость строки, количество правится на месте, перестановка перетаскиванием или «Move up/down», полуфабрикат раскрывается
  в своё дерево — только чтение, строки приведены к вкладу в партию родителя, накладные полуфабриката — отдельной строкой — и открывается переходом) и итог внизу
  (материалы / работы / накладные для партии и для единицы, себестоимость единицы); переключатель **Needs** с полем «Need for» показывает потребность
  (нужно / доступно / дефицит, у полуфабриката — пометка «Produce N»), режим полуфабриката выбирается в форме строки; `/work-centers` — справочник участков; Settings → Production — источник цены.

### Параметрические спецификации, варианты и калькуляция заказа (этап 7)

Код: язык выражений и параметры — `packages/shared/src/expr.ts` и `parameters.ts`, схема — `packages/db/src/schema/production.ts`
и `schema/calculations.ts` (миграция `0023_stage7_parametric_specs.sql`), сервисы — `packages/db/src/specs.ts`, `variants.ts`,
`calculations.ts`, API — `apps/api/src/routes/production.ts`, `production-orders.ts`, `calculations.ts`, `catalog.ts`,
клиент — `apps/web/src/app/production/*` и `apps/web/src/app/docs/calculation.tsx`.

- **Параметры спецификации** — `manufactured_items.params jsonb`: список описаний (`FieldDef`: `number`, `select`, `boolean`,
  ключ, название, обязательность, варианты) и у каждого флажок **«разрез склада»** (`stockDimension`). К параметрам
  спецификации добавляются характеристики категории её товара (с унаследованными); ключ параметра не может совпадать с
  ключом характеристики (422). Значения параметров хранятся в строке заказа (`document_lines.params`) и в позиции заказа
  на производство (`production_items.params`) и проверяются той же схемой значений, что и характеристики категории
  (`checkParamValues` в `specs.ts`: тип, варианты select, лишние ключи — 422 `invalid_params`; обязательность — при расчёте
  состава, незаполненный параметр формулы даёт 422).
- **Формулы строк** — `bom_lines.qty_expr` (количество) и `bom_lines.condition` (условие включения строки в состав);
  длина до 500 символов (`CHECK` в БД). Выражения считает **безопасный вычислитель** `packages/shared/src/expr.ts`:
  свой токенизатор и парсер (без `eval` и `Function`), числа десятичные (BigInt, `decimal.ts`), строки в кавычках,
  параметры-идентификаторы, `+ − * /`, скобки, унарный минус, сравнения `= <> != < <= > >=`, логика `and/or/not`,
  функции `if`, `round`, `ceil`, `floor`, `min`, `max`, `abs`; пределы: длина 500, вложенность 16, аргументов 8;
  зарезервированные имена (`__proto__`, `constructor`, `prototype`) запрещены. При сохранении строки спецификации
  выражение разбирается и сверяется со списком параметров (неизвестный параметр — 422 с текстом ошибки); при вычислении
  понятные ошибки: незаполненный параметр, деление на ноль, несовпадение типов, отрицательное количество.
  Вложенной продукции значения передаются **по совпадающим ключам**; без параметров поведение строго прежнее.
- **Несколько спецификаций на товар** (`resolveSpecForProduct` в `specs.ts`): у обычного товара — спецификация по
  умолчанию (`product_manufacturing.default_item_id`), без неё — самая ранняя своя (`manufactured_items.product_id`);
  у варианта — своя спецификация варианта, иначе спецификация по умолчанию родителя. Параметры товара (проверка
  значений, варианты) берутся из той же спецификации. Флажок `is_invalid` («Недействительна»): такая спецификация не предлагается в новых документах и не
  выбирается по умолчанию, старые документы не ломаются.
- **Варианты товара** (`products.parent_product_id` + `variant_values`): комбинация значений параметров с флажком «разрез
  склада» даёт отдельную складскую позицию. Вариант создаётся **лениво** при первом заказе комбинации (строка заказа
  покупателя ссылается уже на вариант; при смене значений строка, уже ссылающаяся на вариант, переходит на вариант той
  же основы; позиция заказа на производство без строки заказа покупателя получает вариант по своим значениям) или заранее кнопкой «Create all combinations» по select-параметрам с флажком
  (лимит 200 комбинаций, сверх — 422). Гонка двух одновременных созданий одной комбинации даёт одну строку
  (уникальный индекс + `ON CONFLICT DO NOTHING` по нему). Артикул варианта — артикул родителя и значения через «-»;
  занятый артикул — вариант без артикула. Выпуск по строке с параметрами приходует вариант; остаток родителя
  не меняется.
- **Строка «Расход»** (`bom_lines.kind = 'expense'`): услуга подрядчика. Входит в плановую себестоимость и калькуляцию,
  но со склада не списывается и в потребности, резервы и заказы поставщику не попадает (`CHECK` на `kind` пересозданы
  в миграции 0023 — и в `bom_lines`, и в `production_components`).
- **Снимок под заказ:** состав по параметрам считается при создании заказа на производство и при выпуске, а кнопка
  «Recalculate composition» (`POST /production-orders/:id/fill-from-bom`) пересчитывает снимок в черновике; в проведённом
  заказе — 422 (сначала отмена проведения). Ручная правка снимка остаётся.
- **Калькуляция заказа покупателя** — `order_calculations` (документ, источник цены `avg|last_purchase|purchase_price`,
  наценка, итоги) и `order_calculation_lines` (строка заказа, тип `material|semi|work|expense|extra`, товар, количество,
  цена, сумма; `extra` — разовые расходы, например доставка). Источник цены: выбранный, при отсутствии цены — следующий
  по порядку `avg → last_purchase → purchase_price`. Себестоимость единицы — та же, что плановая (`computeBomCost`:
  материалы, работы с фиксированными затратами, полуфабрикаты по своим спецификациям, накладные %), только с ценами по
  источнику калькуляции; строки состава — расшифровка развёртки, фиксированные затраты и накладные — отдельная строка
  «Fixed costs and overhead». Итог цены — сумма «цена единицы × количество». «Apply price to lines» переносит в строки
  заказа цену себестоимости единицы × (1 + наценка) — **только в черновике** (в проведённом заказе 422 `not_draft`). Себестоимость видят только admin и owner: у member суммы скрыты, пересчёт и
  применение цены — 403.
- **Печать спецификации:** «кратко» (только эта спецификация) и «развёрнуто» (все переделы до исходных материалов) —
  `GET /manufactured-items/:id/print/short|expanded`, шаблон `packages/shared/src/print/bom.ts`. Фильтр списка
  спецификаций «Contains material/operation» — по конкретному товару (материал, расход) или операции:
  `GET /manufactured-items?contains=<productId>`.
- **Ограничения:** строки плана производства и расчёта потребностей не несут значений параметров — изделие с формулами,
  которые требуют значений, в потребности по плану не попадает (строка пропускается, как при цикле); изделие без своих
  параметров с параметрическим полуфабрикатом не разворачивается (значения взять неоткуда); полуфабрикат в режиме
  `stock` по параметрам не делится на варианты; «Расход» входит в фактическую себестоимость выпуска по плановой цене
  (поступление той же услуги со статьёй и участком закрытие месяца распределит ещё раз).

### Заказы на производство и выпуск

Реализовано на этапе 2 (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/production.ts`, метаданные типов и расчёт — `packages/shared/src/documents.ts`
и `packages/shared/src/bom.ts`, схема — `packages/db/src/schema/production.ts` (миграция `0009_production_orders.sql`), API — `apps/api/src/routes/production-orders.ts`,
клиент — `apps/web/src/app/production/ProductionOrdersPage.tsx` и `ProductionOrderPage.tsx`.

- **Два типа документов** группы `production`, оба без контрагента (`party: null`): `production_order` (ЗП, заказ на производство) и `production` (ПР, выпуск).
  Заказ живёт по общим правилам: номер выдаётся при проведении, состояние — отдельное поле `documents.state` (`planned → in_progress → done → closed`),
  вид операции — `assembly` («Сборка»; разборка — позже). Выпуск — обычный документ: `stock_role` строки задаёт сторону (`in` — продукция, `out` — материалы),
  цены и НДС у строк нет, стоимость — по себестоимости (видна admin и owner).
- **Производственные данные лежат рядом с документом**, а не в `document_lines`: строка документа — всегда товар каталога, а в заказе бывают изделия без товара и работы.
  `production_items` — что выпускает документ (продукция, количество, строка заказа покупателя, строка заказа на производство, строка документа с продукцией);
  `production_components` — снимок состава (материалы, полуфабрикаты, работы: норма, ставка, плановая и фактическая стоимость);
  `production_headers` — изготовитель (участок), плановые старт и финиш, родительский заказ. Связи — составные внешние ключи `(workspace_id, id)`.
  Из-за этого `document_lines` не ссылается на производственные таблицы (иначе схема документов зациклилась бы на спецификациях) — связь идёт с производственной стороны.
- **Способ пополнения товара и спецификация по умолчанию** — `product_manufacturing (workspace_id, product_id, replenishment: purchase|production, default_item_id)`:
  товар с `replenishment = 'production'` производится, а `default_item_id` говорит, что именно. Отдельная таблица (а не колонки в `products`) — по той же причине:
  `products` не может ссылаться на спецификацию без цикла импорта схем.
- **Снимок спецификации** (`POST /production-orders/:id/fill-from-bom`): `explodeBom` по количеству позиции даёт материалы, полуфабрикаты и работы, стоимость — по
  источнику цены воркспейса (как `computeBomCost`). Снимок можно править до проведения; полуфабрикат без товара каталога в режиме `stock` — ошибка `item_not_stockable`.
- **Выпуск**: списывает материалы и полуфабрикаты по средней склада и приходует продукцию по **фактической себестоимости** — материалы (по средней на момент списания)
  + работы (`hours × ставка` + фиксированная стоимость) + накладные (`overhead_pct` изделия от прямых затрат). Цена прихода считается в той же двухфазной записи
  (`applyStockMoves` с `inCost`), что и перемещение: сначала расходы, потом приход по цене, которая узнаётся из фактических расходов. План и факт считает одна
  функция `computeProductionCost` (shared). Отмена проведения возвращает остатки и среднюю и снимает резерв продукции.
- **Остаток к выпуску** считается по позициям заказа: выпустить больше заказанного нельзя (`over_fulfilment`). То же — по строке заказа покупателя, когда выпуск идёт напрямую.
- **Автоматический резерв продукции под заказ покупателя** (фича 1.5): выпуск, связанный с заказом покупателя (напрямую или через заказ на производство),
  резервирует выпущенную продукцию за этим заказом — `stock_reservations.production_line_id` (строка выпуска) на складе готовой продукции; ограничение — заказано
  минус отгружено. Если заказ покупателя уже резервирует этот товар на этом складе, второй резерв не создаётся.
- **Один документ выпуска за день на участок**: выпуск за ту же дату и тот же участок дописывается в существующий документ `production` (как в 1С): у проведённого
  документа снимается проведение, добавляются строки, документ проводится заново — всё в одной транзакции, при нехватке материалов она откатывается целиком.
- **Обеспечение материалов заказа на производство** (этап 3): резерв материалов, размещение и потребность — см. отдельный раздел ниже.
- **Автоперемещение у участка**: у участка три склада — `warehouse_id` («списывать из»), `output_warehouse_id` («продукция в») и `waste_warehouse_id` («отходы в»);
  выпуск подставляет их, пользователь может поменять склады в документе.
- **API:** `/production-orders` (журнал с фильтром по состоянию и плановым срокам, карточка с позициями, составом и выпусками), `POST /:id/fill-from-bom`,
  `POST /:id/production` (выпуск по заказу), `POST /:id/state`, `POST /production` (выпуск прямо из заказа покупателя), `POST /from-customer-order`
  (заказ на производство по заказу покупателя), `GET/POST /product-settings` (способ пополнения и спецификация по умолчанию). Производственные документы создаются
  только здесь: общий `POST /documents` отвечает `production_api_only`. «На основании» заказа покупателя умеет и заказ на производство, и выпуск.
- **Интерфейс:** `/production/orders` — журнал заказов (вкладки по состоянию), `/production/orders/:id` — карточка: позиции, снимок состава, кнопки
  **Fill from BOM / Create production / Post**, состояние заказа. Выпуск открывается в общей карточке документа: в шапке — склады материалов и готовой продукции,
  в строках — роль (материал или продукция).
- **Права:** заказы и выпуски — member и выше; себестоимость (плановые и фактические стоимости состава) — только admin и owner (`maskCost`).

### Разборка (вид операции «Разборка»)

Реализовано в задаче #1134 (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/production.ts` (`disassemblySplit`, ветки проведения и
пересчёта выпуска), схема — `packages/db/src/schema/production.ts` (миграция `0024_disassembly.sql`), чистые функции — `packages/shared/src/bom.ts`
(`allocateDisassembly`, `outputBases`, `checkCostShares`), API — `apps/api/src/routes/production.ts` и `routes/production-orders.ts`,
клиент — `apps/web/src/app/production/ItemPage.tsx`, `line-dialog.tsx`, `ProductionOrderPage.tsx`, `apps/web/src/app/docs/DocumentPage.tsx`.

- **Вид операции документа** — `documents.operation`: у заказа на производство и выпуска `assembly` (сборка, по умолчанию) или `disassembly`
  (разборка). Выбор вида — в шапке заказа; выпуск наследует вид операции заказа (у выпуска он только показывается). Вид операции заказа должен
  совпадать с видом спецификации каждой позиции, иначе 422 `operation_mismatch`. Существующие документы не меняются: вид операции по умолчанию — сборка.
- **Спецификация разборки** — у `manufactured_items` поле `mode` (`assembly | disassembly`, по умолчанию `assembly`). У разборки товар спецификации —
  **исходный** (что разбирают), а строки спецификации — только `output` (выходной продукт: товар, количество на партию, **доля стоимости** `cost_share`)
  и `work` (операции). Строки `material` / `semi` / `expense` в спецификации разборки запрещены, а `output` — в спецификации сборки (422
  `spec_kind_forbidden`). Формулы этапа 7 (`qty_expr`, `condition`) у выходов разрешены — они считаются так же, как у материалов.
- **Доли стоимости.** Если доля задана хоть у одной строки, заданы все, и сумма ровно 100 %; иначе 422 (`share_incomplete` / `share_sum`).
  Проверка — при сохранении спецификации и при проведении выпуска (строки добавляются по одной, поэтому проверка суммы не висит на каждой строке).
- **Заказ на производство с видом «разборка».** В «Продукции» — исходный товар и количество (что разбирают); снимок `production_components` содержит
  строку `material` с исходным товаром (он списывается со склада и обеспечивается как материал — резерв, потребности и заказы поставщику),
  строки `output` (выходные продукты) и `work`. «Fill from BOM» собирает снимок по спецификации разборки. Выходные продукты в потребности
  не попадают: они не расходуются, а ожидаются поступлением.
- **Выпуск с видом «разборка».** Списывает исходный товар по средней склада и приходует выходные продукты. Себестоимость разборки — списанное
  + работы + накладные (`overhead_pct` спецификации) — делится между выходами: по долям стоимости, иначе по цене продажи × количество, иначе по
  количеству; остаток округления — на последней строке, сумма приходов равна распределяемой стоимости. Чистая функция `allocateDisassembly`
  (`packages/shared/src/bom.ts`) — та же логика на сервере и в тестах. Поэтапный выпуск и сдельный наряд работают как при сборке: работы разборки
  оцениваются нормой, фактическая стоимость нарядов пересчитывает распределение (`recalcReleaseCost`).
- **Пересчёты стоимости.** `recomputeStockCosts` (`packages/db/src/stock.ts`) переносит удорожание исходного товара на выходные продукты
  в обратную сторону, чем при сборке: удорожание списанного исходного товара (с накладными) делится между приходами выходов пропорционально
  их стоимости при проведении (`production_components.actual_cost`; без стоимости — по количеству), а не по текущим ценам продажи.
  Закрытие месяца распределяет косвенные затраты участка на выходные продукты разборки (`loadReleaseTargets`); часы работ позиции
  разборки делятся между выходами по их стоимости, чтобы база «по часам работ» не считала их по разу на каждый выход.
- **Разборка — в один этап:** вид производства у спецификации разборки запрещён (422 `disassembly_stages`). Спецификация разборки не
  может быть спецификацией по умолчанию товара (`product-settings`: только сборка этого же товара), а выбор спецификации товара
  (`resolveSpecForProduct`) берёт только сборки.
- **Ограничения:** база «по объёму выпуска» у разборки — количество выходов; потребности плана производства по спецификации разборки не
  показывают исходный товар.
- **Интерфейс:** переключатель **Assembly / Disassembly** в шапке спецификации, строки «Output» с полем **Cost share, %**, вид операции в шапке
  заказа на производство, подписи по виду («What we disassemble» вместо продуктов, «Outputs» вместо состава), роль строки выпуска
  («To disassemble» / «Output»), печать спецификации с колонкой доли и подписью «Исходный товар».
- **Не сделано (по решению пользователя):** складской документ «Комплектация запасов», возвратные отходы при разборке (задача 1136),
  разборка давальческого сырья, распределение по итогам смены.

### Обеспечение материалов заказа на производство

Реализовано на этапе 3 (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/materials.ts` (резерв, размещение, покрытие) и
`packages/db/src/needs.ts` (сводная потребность), чистая функция покрытия — `packages/shared/src/supply.ts` (`materialCoverage`),
схема — `packages/db/src/schema/production.ts` (`production_placements`) и `schema/documents.ts` (`stock_reservations.production_component_id`),
API — `apps/api/src/routes/production-orders.ts` и `routes/production.ts`, клиент — `apps/web/src/app/production/material-stock.tsx` и `ProductionNeedsPage.tsx`.

- **Что обеспечивается.** Строки состава заказа на производство (`production_components`): материалы и полуфабрикаты. Покрытие строки считает чистая функция
  `materialCoverage` (нужно, списано, зарезервировано, размещено, не обеспечено, свободно, к поступлению, статус `full | partial | none`) — одна и та же на сервере и в интерфейсе.
- **Резерв автоматический.** При проведении заказа резервируется столько, сколько свободно на складе материалов (не больше «нужно − списано выпусками»):
  `stock_reservations.production_component_id` (строка состава) + склад + товар. Остатки блокируются — два заказа не займут одно и то же количество.
- **Резерв ручной.** В строке материала правятся «To reserve» и «Reserve warehouse»: уменьшить можно всегда, увеличить — в пределах свободного остатка склада
  (иначе 422 `insufficient_free`), смена склада переносит резерв. Резерв строки держится на одном складе.
- **Движение резерва.** Выпуск снимает резерв на списанное количество (`production_components.source_component_id` — строка состава заказа, из которой взята строка выпуска);
  отмена проведения выпуска возвращает его; отмена проведения заказа снимает весь резерв; закрытие заказа снимает остаток резерва.
- **Размещение.** Строка заказа поставщику может быть привязана к строке материала заказа на производство — `production_placements` (компонент, документ, строка документа, количество).
  Привязка делается при создании заказа поставщику на основании заказа на производство (`POST /production-orders/:id/supplier-orders`); поступление по такому заказу
  (строка поступления ссылается на строку заказа через `source_line_id`) при проведении сразу резервирует товар под заказ, отмена проведения поступления этот резерв
  снимает. Привязанное непоступившее количество — «Размещено» в карточке заказа. «К поступлению» — только **свободные** заказы поставщикам: строки, не привязанные
  ни к одному заказу на производство.
- **Дочерние заказы на полуфабрикаты.** Кнопка «Create semi-finished orders» (`POST /production-orders/:id/semi-orders`) по дефициту полуфабриката создаёт черновики
  `production_order` с `parent_document_id` и записью размещения у строки материала родителя. Выпуск дочернего заказа резервирует полуфабрикат под строку материала родителя.
- **Сводная потребность.** `GET /production/needs` — по материалам проведённых незакрытых заказов: нужно, в резерве, размещено, свободно, к поступлению, дефицит
  (дефицит = нужно − резерв − размещено − свободно; свободно не бывает меньше нуля — перерезерв заказов покупателей дефицит не раздувает; в карточке заказа «Не обеспечено» = нужно − резерв − размещено, без учёта свободного остатка — как в 1С).
  `POST /production/needs/supplier-orders` создаёт черновики заказов поставщику по поставщику товара: `products.default_supplier_id`, иначе — поставщик последнего
  проведённого поступления по товару; строки без поставщика возвращаются отдельной группой, заказ по ним не создаётся.
- **Интерфейс.** В карточке заказа — переключатель **Show stock** (колонки обеспечения с цветом и расшифровками: резервы по складам, размещение по документам,
  к поступлению по документам с датой), правка резерва и кнопки **Create semi-finished orders** / **Create supplier orders**. Отдельный экран **Needs**
  (`/production/needs`, вкладка **Production orders**) со сводным дефицитом и выбором строк; общий расчёт потребностей
  живёт на той же странице во вкладке **Stock needs** (см. «План производства и пополнение»). В карточке товара —
  поля **Default supplier** (`products.default_supplier_id`, составной FK на `companies`), **Lead days** и вкладка
  **Stock levels**.
- **Права.** Чтение — любой участник; резервирование, размещение и заказы — member и выше (как у соседних маршрутов производства).

### Рабочее место «Выпуск продукции»

Реализовано на этапе 2а (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/production.ts` (`listWorkbench`, `executeWorkbench`),
API — `apps/api/src/routes/production-workbench.ts`, клиент — `apps/web/src/app/production/ProductionWorkbenchPage.tsx` и `workbench-data.ts`.

- **Что показывает.** Заказы покупателей и заказы на производство, у которых есть что выпускать: у товара способ пополнения «производство»
  и спецификация по умолчанию (`product_manufacturing`), у заказа на производство — позиции с изделием, у которого есть товар каталога
  (без товара на склад не приходуется). По строке: заказано, выпущено, отгружено и осталось к выпуску. Строка заказа покупателя, закрытая
  открытым заказом на производство, в рабочем месте не показывается — она уже учтена в заказе на производство. Заказы покупателей видны
  по остатку к отгрузке, заказы на производство — по остатку к выпуску; закрытые (состояния «выполнен» и «закрыт») не показываются.
- **Режимы.** «Простой» — выпускается весь остаток, «расширенный» — своё количество (не больше остатка, иначе 422 `over_fulfilment`).
- **Участок-изготовитель** — на заказ (все его строки) или на строку; без участка выпуск не выполняется (422 `work_center_required`).
  Склады документа — по автоперемещению участка.
- **Документ выпуска — один на участок, дату и этап** (как в 1С): строки разных заказов одного этапа попадают в один документ. Если документ
  на эту дату, участок и этап уже есть, он снимается с проведения, дополняется и проводится заново — всё в одной транзакции запроса; при нехватке
  материалов (422 `insufficient_stock`) транзакция откатывается целиком и ничего не создаётся.
- **Этапы выпуска.** У изделия без вида производства единственный этап — «Завершение производства» (`PRODUCTION_STAGES` в `shared`).
  У изделия с видом производства этапы задаёт его вид (см. «Виды производства и этапы»): в рабочем месте появляются колонки этапов
  с остатком по каждому. Исполнитель операции — этап 4в.
- **Выполнение** (`POST /production/workbench/execute`) переиспользует сервис выпуска этапа 2: планы строк собираются теми же функциями
  (`orderPlans` / `customerPlans`), что и выпуск по заказу на производство и выпуск прямо из заказа покупателя; документ создаётся
  (`createOrAppendProduction`) и проводится.
- **API:** `GET /production/workbench` (фильтры: заказ покупателя, заказ на производство, заказчик, товар, состояние, плановый срок с даты и по дату,
  поиск; отдаёт заказы со строками и список участков), `POST /production/workbench/execute` (дата, режим, строки). Права: чтение — любой участник,
  выполнение — member и выше; себестоимость в рабочем месте не показывается.
- **Интерфейс:** `/production/workbench` — таблица с группировкой по заказам, колонки «Заказано / Выпущено / Осталось», колонка на каждый
  этап вида производства (отметка этапа и остаток по нему; в расширенном режиме — количество) и «Участок», отметка строк и заказов,
  правая сворачиваемая панель «Фильтры и настройки» (поиск, состояние, плановый срок, участок по умолчанию), кнопки **Fill / Clear / Release**
  («Fill» отмечает следующий доступный этап строки), отметка «Changed» до выполнения. Пункт в сайдбаре (Production).

### Виды производства и этапы

Реализовано на этапе 4б (сессия «УНФ: Производство»). Код: сервис справочника и этапов — `packages/db/src/production-stages.ts`,
сервис выпуска — `packages/db/src/production.ts`, схема — `packages/db/src/schema/production.ts` (миграция `0012_production_stages.sql`),
API — `apps/api/src/routes/production-stages.ts`, клиент — `apps/web/src/app/production/ProductionStagesPage.tsx`.

- **Справочник «Этапы»** — вид производства и его упорядоченные этапы: `production_kinds (workspace_id, name, note, archived_at)`
  и `production_stages (workspace_id, kind_id, sort_order, name, is_final)`; обе таблицы арендаторские (`app_secure_tenant_table`).
  **Последний этап вида — финальный** («Завершение производства»): он один (частичный уникальный индекс), и только он приходует продукцию.
  Этап, на который ссылаются строки спецификации или выпуски, удалить нельзя (422 `in_use`); вид производства, который использует
  изделие, архивировать нельзя. Меняет admin и выше, читает любой участник.
- **Спецификация без вида производства** работает как раньше: единственный предопределённый этап «Завершение производства»
  (`PRODUCTION_STAGES` в `shared`). Вид задаёт изделию этапы: `manufactured_items.production_kind_id`, а каждая строка спецификации
  (`bom_lines.stage_id`) — этап, на котором расходуется материал или выполняется операция. Этап строки должен принадлежать виду
  изделия (иначе 422 `stage_mismatch`), а у изделия с видом этап обязателен (422 `stage_required`).
- **Выпуск по этапам.** Этап выпуска хранится в шапке (`production_headers.stage_id`) и в позициях (`production_items.stage_id`);
  снимок состава копирует этап строки (`production_components.stage_id`). Документ этапа списывает **только свои материалы и работы**:
  строка продукции в документе есть лишь у финального этапа, поэтому промежуточный этап продукцию на склад не приходует.
  Склад готовой продукции у промежуточного этапа не нужен.
- **Порядок этапов.** Этап нельзя выполнить больше, чем выполнен предыдущий: предел этапа — минимум из заказанного количества и
  выполненного на предыдущем этапе (422 `stage_order`). Для изделия без вида производства предел — заказанное количество
  (422 `over_fulfilment`, как раньше).
- **Незавершённое производство (НЗП).** Затраты промежуточных этапов копятся как себестоимость этапа в позиции выпуска
  (`production_items.stage_cost`: материалы по средней + работы + накладные этапа). Себестоимость прихода на финальном этапе —
  **затраты этапа плюс НЗП предыдущих этапов** (по средней стоимости единицы каждого выполненного этапа). Поэтому при одинаковых
  количествах по этапам выполняется равенство: сумма списанного на всех этапах = стоимость прихода продукции на финальном этапе.
  Накладные начисляются на прямые затраты своего этапа, поэтому по сумме дают тот же результат, что и накладные на весь выпуск.
- **Отмена проведения.** Промежуточный этап нельзя снять с проведения, если следующий уже выполнен (409 `stage_conflict`); финальный
  этап и этапы изделия без вида производства снимаются как раньше. Проверка — хук типа документа (`beforeUnpost`).
- **Документ дня** — на участок, дату **и этап**: выпуски разных этапов одного дня попадают в разные документы, одного этапа — в один.
- **API:** `GET/POST /production/kinds`, `PATCH/DELETE /production/kinds/:id` (справочник); у выпуска — `stageId` в строках
  (`POST /production-orders/:id/production`, `POST /production-orders/production`, `POST /production/workbench/execute`); у рабочего места —
  фильтры `productionKindId` и `staged`, а в строке заказа — список этапов (`stages`: выполнено, осталось, сколько можно выполнить сейчас).
- **Интерфейс:** `/production/stages` — справочник видов и этапов (Production → Production stages); в карточке изделия — поле
  «Production kind» и бейдж этапа у каждой строки спецификации, в форме строки — выбор этапа; в рабочем месте — колонки этапов.

Версии спецификаций (действует с даты) — следующий шаг.

## Заказ-наряд: работы, материалы и состояния

Реализовано на этапе 1 (сессия «УНФ: Услуги»). Код: сервис — `packages/db/src/work-orders.ts`, схема — `packages/db/src/schema/services.ts`
(состояния, материалы, назначения) и `schema/documents.ts` (виды заказ-нарядов), метаданные и правила категорий — `packages/shared/src/documents.ts`,
API — `apps/api/src/routes/work-orders.ts`, клиент — `apps/web/src/app/docs/work-orders.tsx`.

- **Заказ-наряд сам является продажей** (`work_order`, группа `sales`, префикс `ЗН`, контрагент — покупатель). При входе в состояние категории
  `done` документ проводится целиком: выручка и долг клиента по строкам, расход товаров со склада, списание материалов — движениями самого заказ-наряда
  (отдельный `write_off` не создаётся). Частичной отгрузки нет. Выход из `done` в рабочую категорию снимает проведение (товар возвращается, выручка уходит).
  Проводить и отменять проведение вручную нельзя (`422 work_order_state_only`) — это делает состояние. Счёт на основании заказ-наряда выставляют
  до выполнения (предоплата), поэтому заказ-наряд — единственный тип, счёт по которому можно провести, не проводя основание.
- **Состояния задаёт воркспейс.** `work_order_kinds (workspace_id, name, sort_order, is_default)` — виды заказ-нарядов (вид по умолчанию один на воркспейс),
  `document_states (workspace_id, document_type, kind_id, key, label, color, category, sort_order)` — состояния: у каждого вида свой упорядоченный набор.
  Логика привязана к **категории** состояния (`new | scheduled | in_progress | done | delivered | cancelled`), а не к ключу: воркспейс переименовывает
  состояния и добавляет свои, но «выполнен» всегда узнаётся по категории. Вид по умолчанию с состояниями (по одному на категорию) создаёт код при
  создании воркспейса (`ensureWorkOrderKind`), для существующих воркспейсов — миграцией. Состояние, на котором есть заказ-наряды, удалить нельзя (409
  `state_in_use`), последнее состояние категории — тоже (409 `last_state_in_category`).
- **Динамические состояния.** У заказ-наряда состояний нет в метаданных типа, поэтому их отдаёт провайдер типа (`STATE_PROVIDERS` в
  `packages/db/src/document-hooks.ts`), а побочные действия (проведение и его отмена) делает хук смены состояния (`STATE_HOOKS`). Всё в одной транзакции
  запроса: нехватка товара даёт `422 insufficient_stock`, и состояние не меняется. Из завершённых категорий (`delivered`, `cancelled`) выходят только
  admin и выше. Отмена (категория `cancelled`) требует причину (`cancelReason` в теле смены состояния) и снимает проведение выполненного заказа.
- **Материалы** — `work_order_materials (workspace_id, document_id, product_id, qty, unit_code, warehouse_id)`: израсходованы на работу, только товары
  (`products.kind = 'goods'`), склад списания — свой или склад документа. Списываются при выполнении (движения заказ-наряда, `document_line_id` пуст).
- **Исполнители** — `work_order_assignments (workspace_id, document_id, task_id, line_id, work_center_id, planned_hours)`: исполнитель это задача модуля
  `services` в системном проекте `Services` (время пишется на неё, `time_logs` не меняется). Чужой участник отклоняется: составной внешний ключ
  `(workspace_id, assignee_id)` и проверка в сервисе (`422 invalid_reference`).
- **Вид номенклатуры `work`** (`products.kind`) — работы заказ-наряда: к ним относятся материалы и исполнители; услуги остаются `service`.
  Список видов расширяют вместе с CHECK в БД (`products_kind_chk`).
- **Печатные формы** заказ-наряда: бланк приёма заказа (`work_order`), акт, УПД, ТОРГ-12 и счёт — те же шаблоны, что и у актов и реализаций.
- **API:** `/work-orders` (журнал с состояниями, карточка с материалами и назначениями, `POST /:id/materials`, `POST /:id/assignments`),
  `/work-order-assignments/:taskId` (правка и удаление), `/work-order-kinds` и `/document-states` (справочники, admin и выше).
- **Интерфейс:** журнал **Work orders** (`/work-orders`) с фильтром по состояниям; в карточке документа — блок состояния и вида, таблицы материалов
  и исполнителей; настройка видов и состояний — Settings → Work order kinds.

## Учёт времени и нормы работ

Реализовано на этапе 2 (сессия «УНФ: Услуги»). Код: сервис — `packages/db/src/services.ts`, схема — `packages/db/src/schema/services.ts`
(строки работ заказ-наряда) и `schema/work.ts` (заказчик задачи), API — `apps/api/src/routes/services.ts` и `apps/api/src/routes/work-orders.ts`,
клиент — `apps/web/src/app/docs/timesheet.tsx`, `apps/web/src/app/docs/work-orders.tsx` и `apps/web/src/app/catalog/product-ui.tsx`.

- **Время пишется на задачи модуля `services`** — `time_logs` не меняется: у назначения заказ-наряда уже есть задача.
  Недельный табель сотрудника — **отчёт** по этим записям (`GET /services/timesheet`), отдельного документа-табеля нет.
  Строки табеля: дата, сотрудник, заказчик (контрагент заказ-наряда или заказчик задачи), вид работ (товар строки заказ-наряда), задача, часы.
  Admin и owner видят табель любого сотрудника, участник — только свой.
- **Заказчик у задачи** — `tasks.company_id` (необязательный, составной внешний ключ на `companies`): так пишут время по заказчику
  без заказ-наряда (консультация по договору). В БД — CHECK: заказчик бывает только у задач модуля `services`.
  Назначение заказ-наряда получает заказчика из контрагента заказ-наряда автоматически.
  В вебе поле **Customer** есть только у задач модуля `services` — в панели задачи (`task-drawer`) это выбор компании
  из справочника с поиском и очисткой (`CounterpartyPicker`, тот же выбор, что в документах), в списках и таблицах
  задач модуля `services` — колонка **Customer**. Локальное поле `tasks.company` ↔ API `companyId`
  (`apps/web/src/app/data/specs.ts`); ошибки `company_not_allowed` и `invalid_reference` показываются понятным текстом
  (`apps/web/src/app/data/api.ts`).
- **Норма времени и участок** живут в таблице `operations` (1:1 к товару каталога) — как у операций производства; вид товара задаёт смысл записи:
  `operation` — производство, `work` — услуги. Норма применяется к новому назначению заказ-наряда: плановые часы = количество строки × норма,
  участок — по умолчанию из нормы (если не указан). Норма задаётся у работы в карточке каталога (`PUT /services/work-norms/:productId`).
- **Выставление клиенту выбирается в строке работы заказ-наряда**: `work_order_lines (workspace_id, line_id, document_id, billing)`,
  `billing = norm | hours`. `norm` — количество × цена (как раньше), `hours` — фактические часы задач-назначений строки × цена.
  Перед проведением заказ-наряда (вход в состояние категории `done`) количество таких строк пересчитывается по фактическим часам
  в той же транзакции; записанных часов нет — `422 no_hours_billed`, заказ-наряд не проводится.
- **API:** `/services/work-norms` (нормы работ), `/services/timesheet` (табель), `GET /work-orders/:id/time` (план и факт по назначениям,
  сводка по исполнителям и строкам работ), `POST /work-orders/:id/billing` (способ выставления строк работ).
- **Интерфейс:** в карточке заказ-наряда — блок **Works** (способ выставления строки, фактические часы) и план/факт по исполнителям;
  в карточке работы в каталоге — норма времени и участок по умолчанию; экран **Timesheet** (`/services/timesheet`) — недельный табель;
  на странице участника — фильтр часов по модулю.

## Договоры, тарифные планы и биллинг

Реализовано на этапе 8 (сессия «УНФ: Услуги»). Код: схема `packages/db/src/schema/billing.ts` (миграция `0017_contracts_billing.sql`),
чистый расчёт — `packages/shared/src/billing.ts`, сервис — `packages/db/src/contracts.ts` и `packages/db/src/billing.ts`,
API — `apps/api/src/routes/contracts.ts` и `apps/api/src/routes/billing.ts`, задача воркера — `apps/worker/src/billing.ts`,
клиент — `apps/web/src/app/docs/contracts.tsx`, `billing.tsx`, `billing-data.ts`.

- **Договоры — общий справочник** `contracts (workspace_id, company_id, organization_id, number, date, kind: customer|supplier|other, category, is_signed,
  is_default, valid_from, valid_to, payment_days, price_type, is_service, tariff_plan_id, periodicity, billing_day, document_package, note, archived_at)`.
  Виды: с покупателем, с поставщиком, прочее (комиссия, эквайринг и доставка — вне объёма). Номер **не уникальный**: совпадение даёт предупреждение
  в ответе API, а не ошибку. Срок действия: `valid_to` пуст — бессрочный договор. Договор по умолчанию контрагента (`is_default`, частичный уникальный
  индекс по контрагенту) подставляется в новые документы; срок оплаты (`payment_days`) подставляется в `due_date`. Вид цен (`price_type`) и категория
  хранятся как условия договора: справочника видов цен в платформе нет, поэтому цена строк документа считается как раньше.
- **Договор в документах** — `documents.contract_id`, составной внешний ключ `(workspace_id, contract_id)` → `contracts` (добавлен миграцией вручную,
  так как таблица `contracts` ссылается на `documents`): договор чужого арендатора нельзя подставить даже в обход API. Проведение документа по договору
  проверяет, что договор того же контрагента и организации и действует на дату документа (`422 contract_mismatch`, `422 contract_not_valid`).
- **Тарифные планы** — `tariff_plans (workspace_id, name, extra_product_policy: allow|warn|forbid, note)` и
  `tariff_plan_lines (tariff_plan_id, product_id, qty, price, is_subscription, invoice_as_product_id?, sort_order)`. Позиция с `is_subscription` —
  абонплата: выставляется каждый период по цене плана. `invoice_as_product_id` — «представление в счёте»: такие строки сливаются в одну строку счёта
  с номенклатурой-представителем, исходные строки остаются в расшифровке.
- **Правило внеплановых позиций** (`extra_product_policy`) проверяется при проведении документов по договору обслуживания: `allow` — без вопросов,
  `warn` — предупреждение в событии проведения, `forbid` — `422 extra_product_forbidden`. В биллинге позиции вне плана при `forbid` не выставляются.
- **Счёт периода** (чистые функции `packages/shared/src/billing.ts`, без БД): абонплата за **текущий** период (аванс) + работы по факту за **прошедший** период.
  Первичные документы — выполненные заказ-наряды, проведённые отгрузки (`realization`) и учёт времени (задачи модуля `services` с заказчиком и без
  заказ-наряда, вид работ — `tasks.work_product_id`). **Абонентская позиция:** абонплата текущего периода выставляется всегда (по плану, с пропорцией);
  работы прошедшего периода в пределах его абонплаты уже оплачены, поэтому в счёт идёт только **перерасход** — количество сверх плана прошедшего
  периода (план покрывает работы по порядку дат) по цене первичного документа, а учёт времени без цены — по прайсу. Так правила 1С (рассчитанные
  на счёт по факту) переложены на абонплату авансом — решение пользователя 2026-10-22. После окончания договора строки абонплаты нет, выставляются
  только работы его последнего периода. **Неполный первый и последний период — пропорционально дням** действия договора в периоде (`contractCoverage`, `prorate`).
  Период в названии строки — по-русски («за октябрь 2026»): печатные формы русские. Группировка по `invoice_as_product_id` — в расчёте,
  исходные строки — в расшифровке.
- **Идемпотентность.** `billing_runs (contract_id, period)` — уникальный индекс: один счёт на договор и период; повторный запуск и два воркера
  параллельно не создают двух счетов (вставка строки запуска блокируется на индексе). `billing_sources (contract_id, source_kind, source_id, document_id)` —
  каждый первичный документ и каждая запись времени попадают в счёт ровно один раз. Расшифровка счёта — `billing_breakdowns (document_id, payload jsonb)`
  (вкладка «Billing breakdown»). **Отменённый счёт не держит период:** следующий запуск снимает его строку запуска и выставленные им первички
  и выставляет период заново; проведённый и черновой счёт период держат.
- **Пакет «счёт + акт»:** в акт идут только абонплата и учёт времени. Заказ-наряд и отгрузка уже признали выручку и долг клиента при своём
  проведении — второй раз в акт они не попадают (`actLines`); строка, где проданное сгруппировано с непроданным, идёт в акт суммой своей части.
- **Запуск.** Ручной — `POST /billing/run { period, contractIds? }` (admin+), период — ключ «2026-10», «2026-Q3», «2026»; предпросмотр — `GET /billing/preview`
  (ничего не записывает). Автоматический — задача воркера `billing.run` (`apps/worker/src/billing.ts`): раз в час проверяются договоры обслуживания,
  у которых наступил день выставления (в коротком месяце день 31 приходится на последний день), и создаётся счёт за текущий период.
- **Часовой пояс воркспейса** — `workspaces.timezone` (IANA, проверка по `Intl`): в нём считаются «сегодня» для биллинга и день выставления,
  в нём же живут расписания автоматизаций (`scheduleFlowsOnce` переводит «сейчас» в стенные часы арендатора перед сравнением с cron).
  Миграция ставит существующим арендаторам `UTC` (их расписания не должны сдвинуться), новые воркспейсы получают `Europe/Moscow`. Настройка — admin+,
  интерфейс — Settings → Date & time.
- **Отчёт по договору** — `GET /billing/report`: доходы — документы продажи (реализация, акт, заказ-наряд; счёт — только требование оплаты,
  его сумма уже есть в продаже) и расходы — поступления (заказ поставщику — ещё не расход) по `documents.contract_id`. Отдельного справочника направлений деятельности нет: он вне объёма (решение пользователя).
- **Выгрузка PDF** — `POST /billing/export { documentIds }` (admin+): одна задача воркера `billing.export_zip` собирает ZIP-архив из PDF печатных форм счетов (тот же рендер в headless Chromium, что у `document.pdf`).
  Ответ — id выгрузки (`document_exports`): статус — `GET /billing/export/:id`, архив — `?download=1`. В архиве по файлу на счёт, имя — номер счёта (одинаковые номера не сливаются).
  Чужие счета (`422 document_not_found`), не-счета (`422 not_an_invoice`) и пустой список (`422 no_documents`) отклоняются; ошибка формирования помечает выгрузку `failed` с текстом.

## Операции, исполнители и сдельный наряд

Реализовано на этапе 4в (сессия «УНФ: Производство»). Код: сервис — `packages/db/src/piecework.ts`, схема — `packages/db/src/schema/production.ts`
(миграция `0014_piecework.sql`), API — `apps/api/src/routes/piecework.ts`, клиент — `apps/web/src/app/production/PieceworkPage.tsx`.

- **Операция — вид номенклатуры.** `products.kind` знает `goods | service | work | operation`. Операция не продаётся и склад не двигает;
  её данные — `operations (workspace_id, product_id, norm_hours, work_center_id)` (норма времени на единицу и участок по умолчанию)
  и `operation_rates (workspace_id, product_id, valid_from, rate, unit)` — **история расценок** с датой начала действия.
  Способ расчёта: `per_unit` (за единицу продукции) или `per_hour` (по норме времени). В наряд идёт расценка, действующая
  **на дату наряда**; сумма строки правится вручную до проведения.
- **Работа спецификации может ссылаться на операцию:** у строки `bom_lines.kind = 'work'` поле `product_id` — операция
  (текстовые работы без операции работают как раньше, оценка `hours × rate` сохраняется). Та же ссылка попадает в снимок
  состава (`production_components.product_id`).
- **Назначение операции исполнителю** — `production_operations (workspace_id, document_id, item_id, component_id, operation_id,
  member_id, task_id, stage_id, work_center_id, planned_qty, planned_hours, done_qty)`. Правила: сумма назначений по операции
  не больше количества позиции заказа (иначе 422 `operation_over_assigned`); без исполнителя задачи нет; у каждого назначения
  есть **задача модуля production** (системный проект `Production`), снятие назначения архивирует задачу. Одна операция
  делится между несколькими исполнителями по количеству.
- **Сдельный наряд** — тип документа `piecework_order` (СН) группы `production`, без контрагента, номер выдаётся при проведении.
  Свои строки лежат в `piecework_lines` (операция, продукция, заказ и выпуск, назначение, **план** и **факт** количества,
  нормочасы, расценка, сумма), шапка — `piecework_headers` (исполнитель и участок): **один наряд на (исполнитель, дата)**,
  повторная отметка дописывает строку. Ввод на основании — `POST /production/piecework/from-document` (заказ на производство,
  выпуск или заказ покупателя): остаток работы каждого исполнителя попадает в наряд за день.
- **Выполнение отмечают оба.** Мастер — в рабочем месте «Выпуск продукции» (отметка строки: `assignments: [{ assignmentId, qty }]`),
  исполнитель — в своей задаче (блок «Production operation» в карточке задачи). Оба пути пишут в наряд исполнителя за день.
- **Проведение наряда** закрепляет выполненное количество за назначением (`done_qty`), закрывает задачу исполнителя, когда
  выполнено всё назначенное, и **пересчитывает себестоимость выпуска**: фактическая стоимость работ (сумма проведённых нарядов)
  заменяет оценку `hours × rate`, цена прихода продукции и средняя склада пересчитываются в той же транзакции
  (`revalueMove` в `packages/db/src/stock.ts`). Если продукцию уже отгрузили — 422 `cost_locked` (корректировка — этап 6).
  До проведения наряда выпуск считает работы по норме — оценка не ломается.
- **Права.** Суммы и расценки видят admin и owner и **сам исполнитель — только свои**; остальным участникам в ответах API
  они приходят пустыми (`maskCost`). Отчёт выработки участнику отдаёт только его строки. Назначать и проводить наряды — member и выше.
- **API:** `GET/PUT /production/operations`, `GET/POST /production/operation-rates`, `GET /production/operations/:id`,
  `POST /production/operations/:id/done`, `GET/POST/PATCH /production/piecework`, `GET /production/piecework/report`,

- **Интерфейс:** `/production/piecework` — журнал нарядов, отчёт выработки и расценки операций; в карточке заказа на производство —

## Планирование загрузки ресурсов

Реализовано на этапе 4г (сессия «УНФ: Производство»). Код: схема — `packages/db/src/schema/calendars.ts` и `schema/planning.ts`
(миграция `0015_planning.sql`), расчёт — `packages/shared/src/planning.ts`, сервис — `packages/db/src/planning.ts`,
API — `apps/api/src/routes/planning.ts`, клиент — `apps/web/src/app/production/PlannerPage.tsx` и `ResourcesPage.tsx`,
общая сетка времени — `apps/web/src/app/components/time-grid.tsx`.

- **Ресурсы трёх видов:** сотрудники (`members`), участки (`work_centers`) и **оборудование** — справочник ключевых
  ресурсов `resources (workspace_id, name, kind: equipment|other, work_center_id?, capacity_units, calendar_id?)`.
  Мощность участка — `work_centers.capacity_hours_per_day` (пусто — по графику), у ресурса мощность в день =
  `capacity_units × часов графика`.
- **Потребность в ресурсах — в нормативе и в документе.** Норматив: `product_resources (product_id, resource_id,
  hours_per_unit)` — у операции (вид номенклатуры `operation`) или работы; в документе — закладка «Ресурсы»:
  `document_resources (document_id, line_id?, resource_id, start_at, end_at, hours)` (заказ на производство и заказ-наряд).
- **Сменные графики.** `work_calendars (workspace_id, name, kind: weekly|cycle, pattern jsonb, cycle_start, hours_per_day,
  is_default)`: недельный (рабочие дни недели и часы) или циклический (2/2, сутки через трое) с датой начала цикла.
  График назначается участнику (`members.calendar_id`), участку (`work_centers.calendar_id`) и ресурсу
  (`resources.calendar_id`); без назначения — график воркспейса по умолчанию (`is_default`, он один), а если его нет —
  пятидневка 8 часов. **Праздники воркспейса** — `workspace_holidays (workspace_id, date, name)`; **исключения**
  (отпуск, больничный, ремонт) — `calendar_exceptions (scope: member|work_center|resource, scope_id, date_from, date_to)`:
  они снимают рабочий день у конкретного сотрудника, участка или ресурса.
- **Расчёт загрузки** — чистая функция `computeLoad` в `packages/shared/src/planning.ts`: часы записей распределяются
  по дням интервала, мощность дня берётся из графика (в выходной — ноль). **Перегрузка — предупреждение, не запрет:**
  день помечается `overloaded`, но план сохраняется. Записи: операции производства (`production_operations` с
  плановыми датами), назначения заказ-наряда (даты задачи) и работы ресурсов (`document_resources`).
- **Автопланирование** — `autoSchedule` (shared) и `POST /production-orders/:id/schedule`: операции расставляются
  **от даты старта заказа по порядку этапов** в пределах свободной мощности сотрудника, участка и ресурсов
  (по их графикам и исключениям), прогнозный финиш возвращается ответом и попадает в плановый финиш заказа.
  **Ручные даты не двигаются:** у назначения есть `production_operations.auto_planned` — даты, проставленные
  автопланированием, можно переставить, а ручные (проставленные пользователем) автопланирование оставляет на месте.
- **Общая сетка времени.** `components/time-grid.tsx` — левая панель со строками и правая с колонками дней, полосами
  и подсветкой выходных. Её используют диаграмма Ганта задач (`components/timeline-view.tsx`) и планировщик загрузки:
  перетаскивание полосы в планировщике меняет даты операции (`PATCH /production/operations/:id/move`) или назначения
  заказ-наряда (`PATCH /work-order-assignments/:taskId`) и приходит другим вкладкам по realtime.
- **API:** `/production/calendars`, `/production/holidays`, `/production/calendar-exceptions`, `/production/resources`,
  `/production/product-resources`, `/production/document-resources`, `/production/load?from=&to=&rowType=`,
  `POST /production-orders/:id/schedule`, `PATCH /production/operations/:id/move`. Справочники меняет admin и выше,
  план — member и выше.
- **Интерфейс:** `/production/planner` — строки (сотрудники, участки или ресурсы), полосы — операции и назначения,
  масштаб день/неделя/месяц, перетаскивание меняет даты, перегруженные строки помечаются; `/production/resources` —
  справочник ресурсов, сменные графики, праздники и исключения. В карточке заказа на производство — кнопка **Schedule**
  и раздел **Resources**; в карточке заказ-наряда — раздел **Resources**.

## План производства и пополнение

Реализовано на этапе 5 (сессия «УНФ: Производство»). Код: схема — `packages/db/src/schema/production.ts`
(миграция `0020_production_plans.sql`), чистый расчёт — `packages/shared/src/replenishment.ts`, сервисы —
`packages/db/src/production-plans.ts`, `stock-levels.ts` и `replenishment.ts`, API — `apps/api/src/routes/production-plans.ts`
и `routes/stock-levels.ts` (+ `/production/needs/*` в `routes/production.ts`), клиент — `apps/web/src/app/production/ProductionPlansPage.tsx`,
`ProductionPlanPage.tsx`, `PlanOrdersPage.tsx`, `ProductionNeedsPage.tsx`, `plans-data.ts` и вкладка `catalog/stock-levels.tsx`.

- **План производства — объём выпуска по периодам.** `production_plans (workspace_id, name, period_from, period_to,
  step: week|month, status: draft|approved, warehouse_id, work_center_id?, semi_dirty, comment)` и
  `production_plan_lines (plan_id, item_id, period_start, qty, is_semi)`. Строка — «изделие × период»:
  **дата начала периода = дата выпуска**, ячейка в интерфейсе — сколько выпустить к этой дате. Разрез плана —
  склад готовой продукции (обязателен) и участок-диспетчер (необязателен); несколько планов на период допустимы.
  Заказы создаются **только по утверждённым** (`422 plan_not_approved`). Полуфабрикаты — обычные строки с флагом
  `is_semi`, добавленные кнопкой.
- **Периоды и срок изготовления.** Периоды считает чистая функция `planPeriods` (неделя или месяц; последний день
  месяца и дальше идёт последним днём). Дата запуска = выпуск минус `manufactured_items.lead_days` рабочих дней
  по календарю воркспейса (`startBeforeLead`, `calendarContext` этапа 4г) — показывается в плане и переносится
  в плановый старт заказа. Для закупки срок поставки — `products.lead_days`.
- **Заполнение плана** (`POST /production-plans/:id/fill`) — вручную в таблице, **по статистике выпуска**
  (среднее по проведённым `production` за N прошлых периодов), **по статистике продаж** (среднее по проведённым
  `realization`) и **по заказам покупателей** (неотгруженный и не покрытый производством остаток открытых заказов —
  в период по сроку отгрузки). Режимы `replace` и `add` (add суммирует по изделию и периоду). Пустая история даёт
  пустой результат, а не ошибку.
- **Полуфабрикаты кнопкой** (`POST /production-plans/:id/semi`): для ПФ в режиме `semi_mode = stock` строки
  добавляются пропорционально продукции (чистая функция `semiPlan`), одинаковые суммируются, дата сдвигается
  на срок изготовления и попадает в тот период плана, куда она попала. Правка продукции ставит флаг
  `semi_dirty` — интерфейс показывает предупреждение «перепланировать полуфабрикаты»; кнопка снимает флаг.
  `POST …/semi/remove` удаляет только строки ПФ.
- **Потребности плана** (`GET /production-plans/:id/needs`, считаются запросом): материалы и работы —
  развёрткой `explodeBom` по каждой строке плана; **полуфабрикаты** — потребление / выпуск / излишек-дефицит;
  **часы участков против мощности** — `loadVsCapacity` и `periodCapacity` по календарю участка, нехватка помечается;
  **трудозатраты** — часы × ставка участка (сумма видна только admin и owner, `canSeeCost`).
- **План-факт** — по каждой строке плана: запланировано, заказано (позиции заказов на производство этой строки,
  связь `production_items.plan_line_id`) и выпущено (проведённые выпуски по этим заказам).
- **Заказы по плану** — рабочее место `/production/plan-orders`: утверждённые планы по периодам, строки с
  остатком «план − уже заказано». `POST /production-plans/:id/orders` создаёт черновики `production_order`
  (финиш = дата выпуска, старт = дата запуска, склад продукции — цель); повторный запуск не дублирует, потому что
  заказанным считается всё, что уже стоит в заказах по этой строке плана. Связь заказа со строкой плана — колонка
  `production_items.plan_line_id`: она же даёт план-факт «заказано» и остаток, отдельная таблица дублировала бы
  те же данные.
- **Нормы запаса** — `stock_levels (workspace_id, product_id, warehouse_id?, min_qty, max_qty,
  replenishment: purchase|production|transfer, source_warehouse_id?)`. Строка без склада — **норма по компании**
  (действует в расчёте по компании), строки со складом — в расчёте по складам (частичные уникальные индексы).
  CHECK: `min ≤ max`; перемещение — только у нормы склада, нужен склад-источник, отличный от склада-получателя
  (`422 source_warehouse_required` / `same_warehouse`). Способ пополнения по умолчанию
  берётся из `product_manufacturing.replenishment`. Служебные функции: `GET/PUT /stock-levels`,
  `GET /stock-levels/suppliers?productId=` (цены поставщиков маскируются по роли).
- **Общий расчёт потребностей** (`GET /production/needs/calculate`) — обработка УНФ «Расчёт потребностей в запасах»:
  остатки, резервы, заказы покупателей, заказы поставщикам, заказы на производство и **утверждённые планы
  производства (только та часть, что ещё не передана в заказах)**. Расчёт по складам (строки норм складов; движения
  только своего склада: склад документа, у заказа на производство — склад продукции для прихода и склад материалов для
  расхода, у плана — его склад для продукции и склад участка-диспетчера для материалов; документ без склада — склад
  по умолчанию) или по компании (строки норм без склада, все движения),
  фильтр по способу пополнения, шаг день/неделя/месяц, число периодов и дата начала. **Резерв показывается
  отдельной колонкой и в прогноз не вычитается** — иначе потребность заказа покупателя считалась бы дважды.
  Три шага: рекомендации → планирование → заказы (`POST /production/needs/orders`, `POST /production/needs/post`).
  На шаге планирования у строки правятся способ пополнения, дата и источник (поставщик, участок, склад-источник);
  перемещение без склада-получателя пропускается (`no_target_warehouse`). Дата черновика — дата дефицита, но не раньше «сегодня + срок» (поставки или изготовления). Черновики: закупка → `supplier_order` на склад строки (поставщик строки выбирается на шаге планирования из тех, у кого
  товар покупали, — с ценой и датой последнего поступления; по умолчанию `default_supplier_id` или последнее поступление;
  цена — последняя цена этого поставщика), производство → `production_order` (старт = поступление минус срок изготовления),
  перемещение → черновик `stock_transfer` со склада-источника. Группировка: способ, контрагент (поставщик строки, участок
  или склад-источник), склад-получатель и дата; переключатели «одной датой» и «отдельно под каждый заказ покупателя». Документы создаются
  непроведёнными, список с массовым проведением. Воркера и уведомлений на этом этапе нет.
- **Методики** (чистые функции `packages/shared/src/replenishment.ts`): *по заказам + мин./макс.* — прогноз остатка
  по периодам (`stockForecast`), правило «по итогу периода остаток не выше минимума → заказать максимум плюс
  потребление минус излишек над минимумом» (`minMaxRecommendation`; пример мин 10, макс 20, отгрузки 5, остаток 2 → 25),
  колонка **Overdue** — движения с прошедшей датой плюс добор до максимума при остатке ниже минимума;
  *по продажам min-max* (`salesMinMax`) — только остаток против минимума и максимума; *по статистике продаж*
  (`salesStatistics`) — средние продажи в день (проведённые реализации за N прошлых периодов до даты начала, дни — по
  календарю шага) × (срок поставки + страховые дни) либо в процентах от плановой потребности
  (процент может быть отрицательным); количества округляются до тысячных.
- **Интерфейс:** `/production/plans` — журнал планов, `/production/plans/:id` — карточка с периодами в колонках,
  вкладками **Needs** (материалы, полуфабрикаты, часы участков, трудозатраты) и **Plan vs fact**;
  `/production/plan-orders` — рабочее место «Orders by plan»; `/production/needs` — общий экран расчёта потребностей
  (вкладка **Stock needs** с тремя шагами и вкладка **Production orders** — сводная потребность этапа 3);
  пункт **Stock needs** есть и в группе Trade (закупки и склад). В карточке товара — вкладка **Stock levels** и
  поле **Lead days**; в карточке изделия — **Lead days** рядом с партией и накладными.
- **Права.** Планы, нормы, заполнение, заказы и расчёт — member и выше (справочники по складам и участкам —
  admin и выше, как у соседних маршрутов); чтение — любой участник; цены поставщиков и суммы заказа видят
  admin и owner (`maskCost`).

## Планирование услуг по часам

Реализовано на этапе 5 (сессия «УНФ: Услуги»). Код: схема — `packages/db/src/schema/services.ts` (интервал назначения),
расчёт — `packages/shared/src/planning.ts` (`shiftOf`, `zonedParts`/`zonedInstant`, `computeHourlyLoad`),
сервис — `packages/db/src/planning.ts` (`servicesSchedule`, `syncWorkOrderResources`) и `packages/db/src/work-orders.ts`
(правка назначения), API — `apps/api/src/routes/services.ts` и `apps/api/src/routes/work-orders.ts`,
клиент — `apps/web/src/app/docs/service-planner.tsx` и `apps/web/src/app/docs/work-orders.tsx`,
общая сетка времени — `apps/web/src/app/components/time-grid.tsx`. Миграция `0017_service_schedule.sql`.

- **Интервал по часам — в строке назначения:** `work_order_assignments.start_at/end_at` (timestamptz). Назначение —
  место, где живут плановые данные заказ-наряда (строка работы, участок, плановые часы), а задача — общая сущность
  модуля `services` со своими `start_date`/`due_date` (дни, а не часы). Так же сделано в производстве (этап 4г:
  даты операции хранятся в назначении, задача получает те же даты). **Даты задачи согласованы с интервалом:**
  `start_date` — дата начала интервала, `due_date` — дата конца (в часовом поясе воркспейса).
  Начало и конец задаются вместе; начало раньше конца — `422 invalid_dates`. **Назначение без интервала** запланировано
  по дням (даты задачи): в часовом плане оно видно полосой на эти дни, но в часовую загрузку и предупреждения не входит.
  Перенос по дням (дневной планировщик производства, `startDate`/`dueDate` без интервала) сдвигает интервал на те же дни,
  часы сохраняются.
- **Часы смены — в шаблоне графика:** `work_calendars.pattern.startHour/endHour` (часы от полуночи); если их нет —
  09:00 и `hours_per_day`. Конец не больше начала — **смена через полночь** (ночная 22:00–06:00): её хвост относится
  к следующему дню. Мощность дня по-прежнему `hours_per_day` (этап 4г), часы смены задают только границы работы внутри дня.
- **Часовая загрузка** — чистая функция `computeHourlyLoad` (`packages/shared/src/planning.ts`): слоты по часу,
  занятость строки в часах, мощность слота (часы смены × единиц ресурса) и **перегрузка — предупреждение, не запрет**:
  `member_overlap` (два назначения одного исполнителя в одно время), `resource_overload` (одновременно идёт больше работ, чем `capacity_units`; одно предупреждение на каждый такой отрезок),
  `outside_shift` (интервал вне смены или в выходной), `over_capacity` (занято больше длительности смены).
  Назначения встык (конец одного = начало другого) перегрузкой не считаются.
  **Часовой пояс:** `workspaces.timezone` (этап 8 услуг) — часы смены и границы дней считаются в поясе воркспейса.
- **API:** `GET /services/schedule?from=&to=&resource=member|resource` — строки (сотрудники или ресурсы), слоты, полосы
  и предупреждения; `PATCH /work-order-assignments/:taskId` — интервал и исполнитель, ответ содержит `warnings`.
  Исполнителя нельзя сменить, если по назначению уже записано время (`422 assignment_has_time` — по аналогии с
  `operation_has_work` в производстве); закрытый (`delivered`) или отменённый заказ-наряд не перепланируют (`422 invalid_state`).
  Изменения приходят другим вкладкам по realtime (события `task.updated` и `document.updated`).
- **Ресурсы заказ-наряда:** ресурсы из норматива работ (`product_resources`) подставляются в закладку «Ресурсы»
  при сохранении строк заказ-наряда; интервал назначения переносится на них.
- **Интерфейс:** `/services/planner` — планировщик услуг на общей сетке времени (`components/time-grid.tsx`, часовые линии):
  строки — сотрудники или ресурсы, полосы — назначения заказ-нарядов и работы их ресурсов, нерабочие часы и перегрузка
  подсвечены, предупреждения — списком под сеткой; перетаскивание полосы меняет интервал, перенос на другую строку
  сотрудников — исполнителя. В карточке заказ-наряда — колонки «From»/«To» и выбор исполнителя у назначения.
  Производственный планировщик остаётся по дням (этап 4г).

## Закрытие месяца

Реализовано на этапе 6 (сессия «УНФ: Производство»). Код: схема — `packages/db/src/schema/production.ts`
(`period_costs`, `stock_cost_adjustments`, `production_cost_closings`, `other_cost_lines`), сервис — `packages/db/src/cost-closing.ts`
и `other-costs.ts`, чистый расчёт — `packages/shared/src/cost-closing.ts`, задача воркера — `apps/worker/src/production-closing.ts`,
API — `apps/api/src/routes/production-closing.ts`, клиент — `apps/web/src/app/production/MonthClosingPage.tsx` и `OtherCostsPage.tsx`.
Модель — обработка УНФ «Закрытие месяца» (решения пользователя 2026-10-22 в `docs/plans/2026-10-21-unf-production.md`):
только расчёт прямых затрат, распределение косвенных и фактическая себестоимость; амортизация, курсовые разницы, финансовый результат и ЕНС — вне объёма.

- **Оценка остаётся средней скользящей.** Средневзвешенной за месяц и FIFO нет. Записанная цена движения (`stock_moves.cost`) —
  «базовая», какой её дало проведение; закрытие её не трогает. Корректировка движения хранит свою часть `own_delta`
  (косвенные, распределённые закрытием на приход продукции, принадлежит закрытию `closing_id`) и итог `delta_cost` = своя часть +
  удорожание, пришедшее по цепочке. Итог считает **один проход по всем движениям воркспейса в порядке `seq`**
  (`recomputeStockCosts` в `packages/db/src/stock.ts`): расход списывается по средней пары с учётом корректировок; приход
  перемещения (в том числе «в пути») получает удорожание расхода той же строки; приход продукции выпуска — удорожание списанных
  на неё материалов и полуфабрикатов (с накладными % спецификации), делённое на количество; приход возврата покупателя —
  удорожание исходной реализации. Так косвенные доходят по цепочке «выпуск → перемещение → выпуск → реализация» без потерь
  (сумма удорожания остатков и себестоимости продаж равна распределённому). Отмена проведения (`revertStockMoves`) и переоценка
  прихода (`revalueMove`) после своего базового пересчёта вызывают тот же проход — иначе средняя потеряла бы косвенные.
  Воркспейс без корректировок не пересчитывается; при их наличии проход блокирует все остатки воркспейса в порядке ключей
  (как `lockBalances`) и пишет только среднюю — количество ведут проведения. Цена: после первого закрытия каждая отмена
  проведения пересчитывает все движения воркспейса (при росте объёмов — инкремент с первого затронутого `seq`). Ограничение: удорожание материалов промежуточного этапа до финального этапа
  (НЗП) не доходит — задача 1137.
- **База распределения задаёт статья затрат** (`cost_items.distribution_method`): `none` — не распределять (затрата остаётся
  нераспределённой, ручного документа распределения в платформе нет), `output_qty` — доля количества выпуска, `direct_costs` — доля
  прямых затрат позиции (`production_items.stage_cost`), `work_hours` — доля нормочасов позиции (работы снимка состава и нарядов).
  Существующие статьи после миграции получают `none` (значение по умолчанию колонки).
- **Порядок распределения — как в УНФ:** сначала на выпуски своего участка (позиции с продукцией), если выпуска своего участка
  не было — на все выпуски месяца («общий выпуск»), если выпуска не было совсем — затраты остаются нераспределёнными, а закрытие
  завершается с предупреждением. Остаток округления уходит на последнюю строку: сумма распределённого равна сумме затрат
  (`distributeOverhead` / `planOverhead` в `packages/shared/src/cost-closing.ts`, тесты — `packages/shared/test/cost-closing.test.ts`).
- **Косвенные затраты месяца** (`period_costs (period, cost_item_id, work_center_id?, amount, source, document_id, document_line_id?)`)
  набираются при проведении документа и очищаются при отмене (общий код `syncAfterChange` в `packages/db/src/documents.ts`):
  строки-услуги поступления со статьёй и участком (`document_lines.cost_item_id`, `work_center_id`; сумма строки — без НДС,
  при УСН с НДС), списание материалов на участок (`documents.work_center_id` + статья; берётся себестоимость списания по движениям)
  и документ «Прочие затраты». Источник строки поступления уникален индексом по `(workspace_id, document_line_id)` — повторное
  проведение перезаписывает запись, а не дублирует её.
- **Закрытие — задача воркера `production.close_period`** (очередь `production`, ставится из `POST /production/periods/:month/close`,
  admin и выше). Месяцы режима «за период» выполняются последовательно по порядку, отмена — в обратном, каждый месяц — своя
  транзакция: ошибка одного не откатывает предыдущие (в статус уходит `failed`). Внутри месяца держится рекомендательная блокировка
  воркспейса (`pg_advisory_xact_lock`), поэтому два закрытия одного воркспейса не идут одновременно. Порядок: обнулить свою часть
  прошлого закрытия месяца → пересчитать цепочку (прямые затраты выпусков — с удорожанием материалов прошлых закрытий) →
  распределить и записать свою часть в приход продукции → пересчитать цепочку → сохранить результат.
  Повторное закрытие идемпотентно (те же значения), отмена (`POST /production/periods/:month/reopen`, owner) обнуляет свою часть
  закрытия и пересчитывает цепочку обратно; отменять можно только от последнего закрытого месяца (иначе 422 `later_month_closed`).
  Закрытие раннего месяца при закрытых поздних расширяет диапазон до последнего закрытого — поздние перезакрываются следом.
  Снятие даты запрета (`closedThrough: null`) — тоже сдвиг назад, только owner. Сдвиг назад отменяет закрытия месяцев, конец которых
  позже новой даты (снятие — все закрытия), задачей воркера от последнего к раннему; ответ содержит список `reopened`.
- **Результат закрытия** — `production_cost_closings (period, status: running|done|reopened|failed, totals jsonb, run_at)`, по одному
  на месяц (уникальный индекс). В `totals`: распределение по статьям и участкам (`byCostItem`), по позициям выпуска
  (`byRelease`), нераспределённое, предупреждения, общее, число переоценённых движений. Промежуточный этап (у позиции нет строки
  продукции) косвенных не получает: его затраты идут в НЗП следующего этапа, как и при выпуске.
- **Дата запрета редактирования** — `workspaces.closed_through` и настройка `workspaces.close_moves_lock` (по умолчанию выключена;
  `PATCH /production/periods/settings`, Settings → Production). При успешном закрытии и включённой настройке дата сдвигается на конец
  закрытого месяца. Проведение, отмена проведения и смена даты документа с датой не позже даты запрета отклоняются
  **422 `period_closed`** — общая проверка `assertPeriodOpen` в проведении и отмене документов и в смене состояния, поэтому
  производственные сервисы (выпуск, сдельный наряд, прочие затраты) следуют тем же правилам. Вперёд дату двигает admin и выше,
  назад — только owner (403 `owner_required`).
- **Предварительная проверка** (`GET /production/periods/:month/preview`) — косвенные затраты месяца по статьям и участкам,
  выпуски месяца и проблемы: отрицательные остатки склада, непроведённые документы месяца и месяц без выпусков — со ссылками
  на расшифровку (документы и позиции остатка).
- **Документ «Прочие затраты»** (`other_costs`, префикс ПЗ, группа production, без склада и без строк товаров): строки —
  `other_cost_lines (cost_item_id, work_center_id?, amount, comment)`. Проведение и нумерация общие (хук типа проверяет статьи,
  считает итоги и набирает косвенные затраты), но создаётся документ только своим сервисом — общий `POST /documents` отвечает
  `production_api_only`, как у производственных документов.
- **API:** `GET /production/periods`, `GET /production/periods/:month/preview`, `POST /production/periods/:month/close`,
  `POST /production/periods/:month/reopen`, `PATCH /production/periods/settings`, `/other-costs` (журнал, карточка, создание,
  правка, проведение, отмена, удаление). Суммы закрытия, предварительного анализа и прочих затрат видят admin и owner
  (`maskCost` в ответах API; member получает `null` и видит только состав).
- **Интерфейс:** `/production/closing` (Production → Month closing) — выбор месяца или режима «за период», предварительный анализ
  с проблемами и ссылками, запуск и статус задачи, результат закрытия (распределение по статьям, по выпускам, нераспределённое,
  предупреждения), журнал закрытых месяцев и отмена закрытия (owner); `/other-costs` — журнал и форма документа со строками
  (статья, участок, сумма, комментарий); статья затрат в справочнике (Settings → Cost items) получила поле «Allocation base»;
  в форме поступления у строк-услуг появились колонки «Cost item» и «Work center», в списании — поле «Work center» в шапке.
- **Права.** Закрытие и настройки — admin и выше, отмена закрытия и движение даты запрета назад — owner, документы и статьи —
  member и выше, себестоимость — admin и owner.

## Модули задач

Реализовано на этапе 4а (сессия «УНФ: Производство»). Код: схема `packages/db/src/schema/work.ts` (миграция `0010_task_modules.sql`),
сервис модулей — `packages/db/src/modules.ts`, константы и схемы — `packages/shared/src/constants.ts` и `schemas/work.ts`,
API — `apps/api/src/routes/work.ts`, клиент — `apps/web/src/app/data/*`.

- **Модуль — вид задач.** `tasks.module` и `projects.module` — `general | production | services` (CHECK в БД, индекс по `(workspace_id, module)`).
  Существующие задачи и проекты — `general` (значение по умолчанию в миграции), поэтому старые экраны не меняются. Модуль задачи
  **наследуется от проекта**: задача модуля `production` лежит в проекте модуля `production`, иначе 422 `module_mismatch`.
  Перенос задачи в другой проект меняет её модуль и ключ (ключ задачи — `PROD-1`, `SERV-3`).
- **Системный проект на модуль.** В воркспейсе есть один проект на модуль: `Production` (ключ `PROD`) и `Services` (ключ `SERV`) —
  создаются при регистрации воркспейса и сиде, для существующих — миграцией; уникальность — частичный индекс
  `(workspace_id, module) WHERE module <> 'general'`. Ключ проекта уникален в воркспейсе, поэтому занятый ключ обходится суффиксом
  (`ensureModuleProject`). Пользовательские проекты всегда `general`: модуль проекта задаёт сервер.
- **Фильтр по модулю** — в списках задач, «Моих задачах», досках и сохранённых видах (поле фильтра `module` в `saved_views.filters`).
  Общие списки по всем проектам (Tasks, Calendar, Timeline) по умолчанию показывают только `general`: задачи модулей живут отдельно
  и видны там только с фильтром «Module» (`generalScope` в `apps/web/src/app/data/selectors.ts`). «Мои задачи» и страница проекта
  показывают модульные задачи всегда.
  В обычных проектах по умолчанию видны только задачи `general` — так и есть: модульные задачи лежат в своих проектах;
  в общих списках и «Моих задачах» они видны (фильтр по модулю — по желанию).
- **API:** `GET /tasks?module=`, `GET /projects?module=`. Поле `module` задачи — только для чтения в автоматизациях
  (`BUILTIN_FIELDS.task`, writable = false): сменить модуль можно только переносом задачи в проект другого модуля.

## Автоматизации

Реализовано на этапе 6. Код: общая часть — `packages/shared/src/automations` (реестр узлов, шаблоны, граф, cron, защита от SSRF), схема —
`packages/db/src/schema/automations.ts` (миграция `0006_automations.sql`), движок — `apps/worker/src/flows`, API — `apps/api/src/routes/flows.ts`,
интерфейс — `apps/web/src/app/automations`.

**Модель.** Все таблицы под RLS, как остальные.
- `flows` — название, `enabled`, **черновик** `graph jsonb`, `published_version`, `created_by` (members.id: от его имени flow создаёт задачи и пишет
  комментарии). Включить можно только опубликованный flow (CHECK в БД).
- `flow_versions` — неизменяемые опубликованные версии графа (`flow_id, version, graph, trigger_type`). Правка черновика на работающую версию не влияет.
- `flow_runs` — запуск: версия, статус (`queued → running → waiting → succeeded | failed`; `skipped` — отклонён защитой от зацикливания или выключенным flow),
  вид триггера, контекст триггера (`trigger`: запись и изменения на момент запуска), ход выполнения (`state`: очередь узлов, выходы шагов,
  счётчики), цепочка flow (`chain`), ошибка. Уникальность `(flow_id, event_id)` и `(flow_id, dedupe_key)` делает запуск по событию и по минуте
  расписания идемпотентным: повторная обработка события второго запуска не создаёт.
- `flow_run_steps` — шаг: узел, попытка, статус, **вход** (параметры после подстановок, секреты вроде `Authorization` скрыты), **выход**, ошибка, время.

**Граф.** `{ nodes: [{ id, type, position, params }], edges: [{ id, source, sourceHandle?, target }] }`; `sourceHandle` — идентификатор выхода узла
(`out` по умолчанию, `true` / `false` у условия, `case_N` / `else` у ветвления). Редактор превращает его в узлы и связи React Flow и обратно.
Перед публикацией `validateGraph` (тот же код проверяет и редактор): ровно один триггер, нет висящих узлов (всё достижимо от триггера), нет циклов,
у узла не больше одной входящей связи (слияние ветвей запрещено — запуск идёт по дереву, каждый узел выполняется не более раза), параметры
каждого узла проходят его zod-схему, лимиты (60 узлов, 150 связей).

**Реестр узлов — расширяемый.** Узел = **один файл** в `packages/shared/src/automations/nodes/` + строка в `nodes/index.ts`. Файл экспортирует
`defineNode({ type, category, label, description, icon, params, outputs?, match?, execute })`:
- `category`: `trigger | condition | action | flow`; `params` — zod-схема; подсказки интерфейса задаются в `.meta({ title, description, ui, dependsOn, … })`
  (`ui`: `entity`, `field`, `value`, `member`, `project`, `textarea`, `cron`, `url`);
- `outputs` — статический список или функция от параметров (ветвление строит выходы по своим вариантам);
- `match(params, event, { entity, action, changes })` — только у триггеров по событиям;
- `execute(params, rt)` возвращает `{ output?, next?, delayMs? }`. Исполнитель **не касается БД и сети напрямую**, а действует через порты `NodeRuntime`
  (`updateField`, `createTask`, `addComment`, `notify`, `http`), которые реализует воркер. Поэтому узел целиком проверяется тестом с подставными портами,
  а новый узел, которому хватает существующих портов, не требует правок воркера. Новый порт — метод в `NodeRuntime` и реализация в `apps/worker/src/flows/records.ts`.
- Форма параметров в редакторе строится из JSON Schema схемы (`z.toJSONSchema`) — писать UI узла не нужно. Иконка — имя lucide в `icon`; имена, которых нет в
  `app/automations/node-meta.tsx`, получают иконку по умолчанию.

Базовый набор: триггеры «запись создана», «запись изменена», «поле изменилось» (сущность: системные task / project / deal / company / contact / product,
`document` и пользовательские; необязательные фильтры from / to), «по расписанию» (cron в часовом поясе арендатора), «ручной запуск»; логика — «условие» (eq, ne, gt, gte, lt, lte,
contains, empty, not_empty; числа сравниваются как числа), «задержка» (до 30 суток), «ветвление»; действия — «обновить поле записи» (встроенного или пользовательского
поля; значение проверяется схемой поля конструктора, как в API), «создать задачу», «уведомить участника», «HTTP-запрос», «записать комментарий» (к задаче; к сделке — заметка CRM).

**Подстановки.** Любой строковый параметр поддерживает `{{путь}}` по контексту: `trigger.record.title`, `trigger.record.custom.<поле>` (у записей пользовательских
сущностей значения — на верхнем уровне), `trigger.changes.<поле>.from|to`, `trigger.project.leadId`, `trigger.recordId`, `steps.<id узла>.<выход>`, `flow.name`, `run.id`, `now`.
Шаблонизатор без eval: только путь через точку, индексы массивов числом, доступны лишь собственные свойства объектов (`__proto__`, `constructor`, `prototype` закрыты);
вызовов, операторов и фильтров нет. Результат всегда строка (объекты — JSON), недостающее значение — пустая строка; нужный тип получается при проверке схемой поля или узла.

**Движок (воркер).**
1. Событие outbox → `handleEvent` → `startRunsForEvent`: берёт опубликованные включённые flow арендатора события, проверяет `match` триггера, создаёт `flow_runs` и ставит
   задачу `flow.run` (очередь `flows`). Запись для контекста читается сразу (близко к моменту события). Расписание: раз в минуту `scheduleFlowsOnce` (UTC; пропущенные
   при остановке воркера минуты не догоняются). Ручной запуск — `POST /flows/:id/run` ставит запуск напрямую.
2. Задача `flow.run` → `executeRun`: **каждый шаг — отдельная транзакция под ролью `app_user` с `app.workspace_id` арендатора** (RLS действует, `BYPASSRLS` воркера здесь не
   используется; чужие записи недоступны даже по известному id). В транзакции: подстановки → проверка параметров схемой узла → действие под `SAVEPOINT` → запись шага → сдвиг курсора.
   Ошибка действия откатывает его записи, но журнал шага сохраняется; упавший воркер откатывает всю транзакцию, и шаг выполнится заново (для HTTP — «минимум один раз»).
3. **Задержка** не держит воркер: запуск уходит в `waiting`, задача `flow.run` ставится в `jobs` с `run_at`; досрочно пришедшая задача ничего не делает (`state.resumeAt`).
   Выключенный flow не продолжает ждущие запуски (они завершаются как `skipped`); ручные запуски от `enabled` не зависят.
4. **Повтор временных ошибок** (`TransientError`: сеть, таймаут, 408 / 429 / 5xx): шаг повторяется до `FLOW_MAX_ATTEMPTS` (3) раз с паузой `FLOW_RETRY_BASE_SEC` (5 с) × 2^(попытка−1),
   тоже через `jobs.run_at`; остальные ошибки (4xx, неверные параметры, запись не найдена) сразу завершают запуск как `failed`.
5. **Ограничения:** `FLOW_MAX_STEPS` (100) шагов на запуск; задержка ≤ 30 суток; HTTP — таймаут `FLOW_HTTP_TIMEOUT_MS` (10 с), ответ ≤ 1 МБ, ≤ 3 редиректов; вход и выход шага в журнале ≤ 20 КБ.
6. **Защита от зацикливания.** Каждое событие, которое порождает действие flow, несёт в payload метку `via: { runId, flowId, chain }` (`actor_id` у таких событий пуст). Flow, уже стоящий в цепочке события,
   этим событием не запускается — запуск фиксируется как `skipped` с причиной; другой flow может отреагировать (цепочка растёт), но длина цепочки ограничена (`MAX_FLOW_CHAIN` = 4).
   Действие, не менявшее значение, события не пишет. События служебных сущностей (`flow`, `flow_run`, `notification`…) триггерами не бывают.
7. Действия пишут события в outbox (`task.updated` с `changes {поле: {from, to}}`, `task.created`, `comment.created`, `notification.created`…), поэтому realtime и лента Activity видят их так же, как изменения из API;
   побочные эффекты API дублируются там, где они определяют целостность (ключ задачи по счётчику проекта, `prev_status` / `completed_at`, `closed_at` и заметка о смене этапа сделки, уведомление исполнителю).

**HTTP и SSRF.** Допустимы только `http(s)` без учётных данных в адресе. Имя хоста и **все** его адреса из DNS не должны быть частными / служебными (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16 с метаданными облака, 100.64/10,
multicast, `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped и NAT64 и т. д.); `localhost`, `*.local`, `*.internal` запрещены; редиректы идут вручную с той же проверкой на каждом шаге. `FLOW_HTTP_ALLOW_PRIVATE=1`
снимает запрет (закрытые установки, тесты). Известное ограничение: между проверкой DNS и подключением адрес теоретически может смениться (DNS rebinding) — полностью закрывает только исходящий прокси / фаервол сети.

**API** (`/flows`, `/flow-runs`; чтение — любой участник, изменение и запуск — admin и выше, потому что flow выполняет действия и HTTP-запросы от имени воркспейса): CRUD flow (`PATCH` — имя, описание, черновик, `enabled`),
`POST /flows/:id/publish` (`{ enable? }`; неверный граф — 422 `invalid_graph` со списком замечаний), `POST /flows/:id/run`, `GET /flow-runs?flowId=&status=&failed=`, `GET /flow-runs/:id` (с шагами).
Включить непубликованный flow и запустить его — 409 `not_published`. События `flow.*` и `flow_run.*` (запуск завершился / ждёт) обновляют интерфейс по realtime.

**Интерфейс.** Раздел Automations в сайдбаре: список (включение, версия и «unpublished changes», последний запуск, число ошибок за 7 дней) и общий журнал Runs. Редактор — `@xyflow/react`: палитра по категориям, холст,
правая панель с формой параметров из схемы (сущность и поля берутся из метаданных конструктора, включая пользовательские поля; участники и проекты — из воркспейса; меню `{}` вставляет переменные), живая проверка графа
(узлы с замечаниями подсвечиваются), Save draft / Publish / Enabled / Run (для ручного триггера), вкладка Runs flow: запуски, шаги со входом, выходом и ошибкой. Цвета — токены приложения, тёмная тема работает без отдельных правил.

**Демо-сид.** Два включённых flow: «Task moved to Review → notify the project lead» (поле `status` задачи стало `review` → уведомление `{{trigger.project.leadId}}`) и «Deal won → create a Kickoff task» (стадия сделки стала `won` → задача «Kickoff» в проекте).

**Что пока не так.** Нет слияния ветвей, циклов и «для каждой записи»; расписание живёт в часовом поясе арендатора (у существующих арендаторов после миграции — UTC) и без догона пропущенных минут; запуски и шаги не очищаются (политики хранения нет); действия flow не проверяют
доступ к закрытым проектам и существование записей, на которые ссылаются пользовательские поля `ref` / `refs` (внешние ключи системных колонок проверяет БД); запись в ленту Activity делается только для задач;
редактор рассчитан на одного автора (правка того же flow в двух вкладках — «последний сохранил»); входящий вебхук-триггер не реализован.

## Фронтенд на сервере

Реализовано на этапе 2. Код — `apps/web/src/app/data` (`session.tsx`, `store.tsx`, `engine.ts`, `specs.ts`, `realtime.ts`, `api.ts`).

- **Сессия и воркспейсы.** `SessionProvider` держит `GET /auth/me` (TanStack Query, ключ `['session']`): пользователь и мои воркспейсы. Вход,
  регистрация и выход — настоящие `/auth/*` (cookie httpOnly; токена в JS нет). Без сессии `RequireAuth` ведёт на `/signin`, без воркспейсов — на
  онбординг. Ответ API с кодом `unauthorized` (сессия истекла) сам возвращает на экран входа. Активный воркспейс — настройка просмотра, хранится
  в `localStorage` (`gr8r-ui.workspace`), уходит в запросы заголовком `X-Workspace-Id` (`apiFor(workspaceId)` — типизированный клиент
  `@gr8r/api/client`, по экземпляру на воркспейс), в WebSocket — `?workspace=`. Переключатель в сайдбаре, создание воркспейса — `POST /workspaces`,
  удаление — `DELETE /workspaces/:id` (только owner, данные арендатора уходят каскадом).
- **Данные = кэш запросов.** Каждая коллекция воркспейса — один запрос `['ws', id, имя]` (все страницы по 200; активность — только свежие 200;
  задачи и проекты — с архивными, у них есть флаг `archived`). Строка API превращается в локальную сущность на границе (`specs.ts`: uuid, время в
  epoch-миллисекундах, `null` → `''`/`undefined`, `Project.last` и `Member.last` — минуты с `lastActivityAt`/`lastSeenAt`, `numeric` → число,
  размер файла ↔ байты). Компоненты и reducer остались на прежней модели (`app/data/types.ts`). `useWorkspace()` отдаёт `{ data, dispatch }`,
  `data` собирается из кэша: вложения задач — это `files` с `taskId`, порядок проектов — из `sortOrder`. Пока данные не загружены, показывается
  экран ожидания; ошибка загрузки — экран с «Try again».
- **dispatch = мутации.** Семантика действий по-прежнему описана одним reducer'ом (`store.tsx`, `crm/store.tsx`). Слой `engine.ts`:
  `before → reducer → after`, diff по коллекциям (добавлено / изменено с перечнем полей / удалено), `after` пишется в кэш (интерфейс обновляется
  сразу), diff превращается в запросы и уходит в **одну очередь воркспейса** (порядок записи сохраняется: родители раньше детей, удаление — в
  обратном порядке). Соответствие «локальное поле → поля API» — таблицы `fields` в `specs.ts`; PATCH уходит только с изменёнными полями.
  После очереди изменённые коллекции перечитываются (ключ задачи `WEB-109`, активность и уведомления считает сервер). Ошибка запроса: toast с
  сообщением сервера, остаток запросов этого действия пропускается, коллекции перечитываются — оптимистичное состояние откатывается к серверному.
- **Идентификаторы создаёт клиент.** `uid()` — uuid v7; все схемы создания принимают необязательный `id`, поэтому карточку можно открыть и менять
  до ответа сервера, а повторное создание при Undo возвращает ту же запись. Повторное использование id — 409. Статус-колонка идентифицируется
  ключом (`StatusDef.id` = `statuses.key`), uuid строки хранится рядом. Задача при повторном создании (Undo удаления) может принести прежний
  `key` — он должен принадлежать проекту и быть свободным, счётчик проекта не уменьшается.
- **Undo (`data/restore`).** Компоненты по-прежнему передают снимок `data`, захваченный до действия. Для снимка запоминается состояние ПОСЛЕ
  действия (`WeakMap`), и откатывается только разница между ними — чужие изменения, пришедшие по WebSocket в промежутке, не затрагиваются.
  Что делает откат на сервере: удалённая задача/проект создаются заново вместе с зависимыми записями (комментарии, часы, файлы, виды) под теми же
  id, мягко удалённые (файл, сделка) возвращаются через `POST /:id/restore`, архив задачи снимается, изменённые поля возвращаются PATCH'ем.
- **Удаление.** Задачи, проекты, комментарии, часы, статусы, команды удаляются насовсем (`?hard=true`; для задач и проектов это права admin и выше —
  у остальных будет toast и откат), файлы и CRM-сделки — архивированием (`DELETE` без `hard`, Undo = restore). У сделки активности остаются на
  сервере и скрываются на клиенте, пока сделка в архиве. «Архив» задачи и проекта — флаг `archived` (`DELETE` без `hard` / `restore`).
  Участник «удаляется» деактивацией (`status: deactivated`): профиль остаётся в истории.
- **Realtime.** Один WebSocket `/ws?workspace=` на вкладку (`realtime.ts`). Событие журнала (конверт без payload) помечает коллекции сущности
  устаревшими (`collectionsFor`), они перечитываются целиком; пока в полёте свои запросы — после них, чтобы не затереть оптимистичное
  состояние. Точка отсчёта — последнее событие на момент загрузки, обрыв — переподключение с `?since=<id>` и полное перечитывание. Дедупликация
  по `event.id`. Перечитывание целой коллекции выбрано вместо точечных патчей: код проще, а при 50–500 записях на воркспейс запрос дешёв;
  точечный патч (`GET /:id` + upsert) — следующий шаг, если коллекции вырастут.
- **Формат API** (для границы слоя): строки таблиц в camelCase, даты `YYYY-MM-DD` / ISO 8601, `numeric` — строки, реакции комментариев —
  `re: {эмодзи: [member id]}`, участники проекта — `members: [{memberId, permission}]`, контакты сделки — `contactIds`. Демо-данные
  генерируются в `packages/shared/src/demo` и общие для сида БД (`bun run db:seed`); типы `Task`, `Project`, … — в `packages/shared/src/domain.ts`
  (фронтенд реэкспортирует их из `app/data/types.ts`).
- **Локально остаётся только настройка просмотра**: тема, акцент, плотность, свёрнутый сайдбар, фильтры видов, плавающие окна задач, активный
  воркспейс (`localStorage`).
- Отладка и браузерные тесты (только `import.meta.env.DEV`): `window.__qc` (QueryClient), `window.__ws.dispatch/read/settled()`, `window.__crm`.

Что пока не так, как в локальной модели:
  «избранное» (`fav`) общее для воркспейса (позже — по пользователю); дерево подзадач хранится JSON'ом в задаче, поэтому одновременная правка
  подзадач двумя людьми — «последний записал»; вложения — только метаданные файла (загрузки в S3/MinIO нет); активность — последние 200 записей;
  доступ к закрытым проектам (`isPrivate`/`access`) хранится, но API ещё не фильтрует по нему; сброс пароля и подтверждение почты (нужна отправка писем)
  и вход через внешних провайдеров не реализованы — экраны остались, но честно сообщают об этом.
