# Пользовательская документация

Справка для людей, которые работают в gr8r, а не для разработчиков. Один источник: из этих файлов собираются справка в приложении («?» в шапке экрана) и сайт документации. Решения — `docs/plans/2026-10-30-user-docs.md`.

Писать только по-русски. Внутренние термины (RLS, job, outbox, воркер, арендатор, ключи словаря) в тексте не нужны — называем так, как это видно на экране.

## Папки

```
docs/user/
  README.md           это описание
  pending.json        разделы, для которых статья ещё не написана (временный список)
  _templates/         шаблоны section.md и howto.md (не статьи)
  <группа>/<раздел>.md  статьи разделов
  howto/<сценарий>.md   сквозные сценарии «как сделать»
  img/                скриншоты <ключ>.png (делает docs:shots)
```

Папка `<группа>` — ключ группы меню из `NAV_GROUPS` (`apps/web/src/app/routes.ts`): `production`, `trade`, `services`, `transport`, `finance`. Разделы вне групп меню:

| Папка | Что внутри |
|---|---|
| `general` | главная, входящие, уведомления, избранное, мои задачи, проекты, задачи, календарь, таймлайн, участники, активность, архив, поиск, настройки |
| `crm` | разделы CRM (`crm*`) |
| `catalog` | номенклатура |
| `automations` | автоматизации |

Имя файла — короткое латинское имя раздела (`notifications.md`, `fleet-vehicles.md`). Одна статья может описывать несколько близких разделов (`sections: [a, b]`), но обычно — один.

## Шапка статьи

```yaml
---
title: Уведомления
sections: [notifications]
module: core
sources:
  - apps/web/src/app/pages/NotificationsPage.tsx
  - apps/api/src/routes/work.ts
verified: 07885f0abc
screenshots: []
---
```

| Поле | Что это |
|---|---|
| `title` | заголовок статьи, как его увидит пользователь |
| `sections` | id разделов из `SECTIONS`, которые статья описывает. У сценариев можно не указывать |
| `module` | модуль из каталога лицензий (`MODULE_IDS` в `packages/shared/src/licensing.ts`): по нему справка прячет статьи выключенных модулей. У сценариев — по желанию |
| `sources` | глобы файлов, по которым написана статья: экран, API, сервис. Чем точнее, тем меньше ложных «устарело». Глоб без файлов — ошибка |
| `verified` | коммит, на котором статья сверена с кодом. Не пишется руками: `bun run docs:verify <файл>` |
| `screenshots` | ключи снимков из `docs/user/img/<ключ>.png`; файла нет — ошибка |

Разбор шапки простой: `ключ: значение`, списки `[a, b]` или строки `- a`. Других конструкций YAML нет.

## Как держать статью свежей

- Меняешь экран или поведение — в том же коммите обнови статью и поставь `verified`: `bun run docs:verify docs/user/<папка>/<файл>.md`. Коммит, который правит и код из `sources`, и саму статью, считается сверенным.
- `bun run docs:check` — полная проверка (нужен git): шапки, неизвестные id и модули, битые ссылки и картинки, устаревшие статьи (код из `sources` менялся после `verified`, выводятся эти коммиты), разделы без статьи. Битые ссылки и неизвестные id — ошибка (код выхода 1); устаревание и непокрытые разделы — предупреждение, с `--strict` тоже ошибка. Запускать при сведении веток.
- Тест `apps/web/src/i18n/docs-coverage.test.ts` (быстрый, без git): каждый раздел из `SECTIONS` описан в статье или записан в `pending.json`. Новый раздел без статьи роняет тест. Написал статью — убери id из `pending.json`.

## Стиль

- Пишем для пользователя: что он видит и что может сделать. Называем кнопки и поля так, как они подписаны на экране (русский словарь), в «ёлочках» или **жирным**.
- Коротко, действиями («Нажмите…», «Откройте…»), без объяснения устройства.
- Только то, что реально есть в приложении. Не знаешь — проверь в браузере на демо-данных (`demo@gr8r.dev`), на отдельной базе `*_test`, не на рабочей.
- Ссылки на другие статьи — относительные (`../finance/payments.md`); абсолютные и несуществующие `docs:check` ловит.
- Коды ошибок показываем по-человечески («Период закрыт — документ нельзя изменить»), без `errors.*`.

## Структура статьи раздела

Шаблон — `_templates/section.md`. Заголовки второго уровня, в таком порядке:

1. **Для чего раздел** — одно-два предложения.
2. **Что на экране** — из чего состоит экран, поля и кнопки.
3. **Типовые действия** — короткие нумерованные шаги.
4. **Права** — кто видит и что может; от чего зависит доступ (должность, модуль).
5. **Частые ошибки** — симптом и что делать.
6. **Связанные статьи** — ссылки.

Если пункта нет по смыслу, его всё равно оставляем с пометкой «Особых ограничений нет», чтобы структура была одинаковой.

## Структура сценария

Шаблон — `_templates/howto.md`. Сквозная цепочка через несколько разделов, например «от лида до оплаты»:

1. **Что получится** и **что понадобится заранее**.
2. **Шаги** — нумерованные; в каждом шаге раздел, где это делается, со ссылкой на статью раздела.
3. **Как проверить результат**.
4. **Если что-то пошло не так**.
5. **Связанные статьи**.
