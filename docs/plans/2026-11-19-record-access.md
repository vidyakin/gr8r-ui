Статус: **не начато**, план для будущей работы (задачи — сессия TaskFlow №65 «Права доступа к записям и полям», задачи 1432–1439).
Повод: пробел из сравнения с EspoCRM (`2026-11-19-espocrm-gap.md`, п. 7): менеджер видит всех клиентов и все суммы воркспейса.

## Что есть сейчас

- Изоляция только между воркспейсами: RLS по `workspace_id` (`docs/architecture/tenancy.md`). Внутри воркспейса участник видит всё.
- Роли `owner | admin | member | guest`; должности задают разделы меню и функции (`docs/architecture/positions.md`). Серверная проверка раздела —
  только для путей одного раздела (`SECTION_OF_API_PATH`, задача 1284); общие пути (контрагенты, сделки, лиды, документы) не ограничены.
- Поле «Ответственный» (`owner_id`) есть у `leads`, `companies`, `contacts`, `deals`; у дел CRM — автор/исполнитель; у обращений (`cases`) — `owner_id`.
- Подразделения с руководителем (`docs/architecture/departments.md`, миграция 0124) — основа для «руководитель видит записи своих».
- Образцы: курьер видит только свои доставки (`courierScope`); себестоимость и закупочные цены скрыты от участников (`isCostKind`, `pricing.md`;
  маскирование себестоимости в калькуляциях и отчётах производства).
- Стор CRM (`apps/web/src/app/crm/store.tsx`) загружает контрагентов, контакты, сделки целиком в шапку, палитру и поиск — фильтровать
  только в интерфейсе нельзя, данные уже в браузере.

## Часть 1 — область видимости записей («только свои»)

### Решения, которые нужно принять с пользователем перед началом
1. Кто «свои»: только записи, где участник ответственный, или ещё записи подчинённых (руководитель подразделения видит записи всех в своём
   подразделении и дочерних).
2. Записи без ответственного: видны всем с областью «свои» (общий пул, удобно для лидов) или только администраторам.
3. Какие сущности: лиды, контрагенты, контакты, сделки, обращения; документы продаж (по ответственному документа или по контрагенту?);
   дела CRM и письма — наследуют видимость родителя.
4. Сводные экраны (сводка CRM, воронка, план продаж, отчёт рекламы, дебиторка): менеджер видит только свои цифры или общие итоги.
5. Нужен ли уровень «записи команды» (команды уже есть), кроме «свои» и «подразделение».

### Модель
- В должности — уровень видимости CRM: `all` (по умолчанию, как сейчас) | `department` | `own`. Если у участника несколько должностей —
  берётся самый широкий. owner/admin — всегда `all`. Хранить в `positions` (новая колонка `record_scope`), выдавать в `GET /positions/me`.
- Функция БД `app_visible_owner_ids()` (SECURITY DEFINER, STABLE): по `app.user_id`/`app.workspace_id` возвращает null (видно всё) или
  массив id участников (сам участник + подчинённые для `department`). Кэш в пределах транзакции (`set_config` или временная таблица).

### Где проверять — рекомендация: RLS
- Дополнительная политика RLS на каждую сущность из списка: `owner_id is null and <пул разрешён> or app_visible_owner_ids() is null or
  owner_id = any(app_visible_owner_ids())`. Тогда любой запрос API, поиск, палитра, экспорт, MCP-агент, автоматизации под `app_user`
  автоматически видят только своё — ничего не забыть.
- Воркер под `app_worker` (BYPASSRLS) видит всё — это правильно для системных проходов; запуски автоматизаций идут под `app_user` с контекстом
  автора/системы — проверить, что системный контекст (`system: true`) видит всё.
- Связанные таблицы (дела CRM, письма, касания лида, обращения контакта, документы по контрагенту) — политика через `exists` к родителю
  или денормализованный `owner_id`; решить по производительности (индексы `(workspace_id, owner_id)`).
- Запись: смена ответственного на чужого участника участником с областью `own` — запрещена или с потерей доступа (решить; в EspoCRM —
  отдельное право «назначать»).

### Затронуто
- db: миграция (колонка в `positions`, функция, политики, индексы), тесты RLS для каждой сущности и связанных таблиц.
- api: `GET /positions/me`, проверки назначения ответственного, ошибки «нет доступа» (404, как чужая запись).
- web: стор CRM получает уже отфильтрованные данные; сводные экраны — по решению п. 4; в настройках должности — выбор уровня.
- Сводные отчёты и агрегаты: считаются под тем же RLS → автоматически «свои»; если нужны общие итоги — отдельный эндпоинт под системным контекстом,
  отдающий только суммы.
- Автоматизации «Назначить ответственного по кругу», распределение лидов из форм и обращений — работают под системным контекстом, не ломаются.
- Справка: статьи «Должности»/«Участники», CRM-разделы, «Права».

### Тесты
- Менеджер A видит свои сделки и не видит сделки B ни в списке, ни по id (404), ни в поиске, ни в палитре, ни в сводке, ни через MCP-токен.
- Руководитель подразделения видит записи подчинённых, но не соседнего подразделения; дочерние подразделения — по решению.
- Записи без ответственного — по решению п. 2. Дела и письма чужой сделки не видны.
- Админ видит всё; системные проходы воркера не потеряли записей; несколько должностей — берётся самая широкая.

### Оценка
3–5 дней (M): по инкрементам — модель и функция → политики CRM-сущностей → связанные таблицы → сводные экраны и интерфейс → справка.

## Часть 2 — права на уровне полей

### Решения перед началом
1. Охват: (а) малый — фиксированный список чувствительных системных полей + флажок у своих полей конструктора; (б) полный — любое поле любой
   сущности, чтение и запись отдельно по должностям (как Field Level Security в EspoCRM). Рекомендация — начать с (а).
2. Список полей для (а): сумма и вероятность сделки, телефоны и email контактов/лидов, реквизиты и банковские счета контрагента, цены
   закупки и себестоимость (уже скрыты), суммы документов? — согласовать.
3. Что видит пользователь без права: поле скрыто совсем или «•••» (видно, что значение есть).

### Модель (вариант а)
- В должности — список скрытых полей `hidden_fields text[]` (ключи вида `deal.amount`, `contact.phone`, `custom:deal.<key>`) или обратный список
  «видимых чувствительных». owner/admin видят всё.
- У своих полей конструктора (`docs/architecture/metadata.md`) — флажок «скрытое поле», доступ по должностям.

### Где проверять
- Сервер — единственная надёжная точка: сериализаторы ответов API (`deals`, `contacts`, `leads`, `companies`, поиск, палитра, экспорт, MCP, печать,
  подстановки `{{…}}` в автоматизациях, письма по шаблону) вырезают скрытые поля; запись скрытого поля — 403 `field_forbidden` (или игнор, решить).
- Общая функция `maskFields(entity, row, viewer)` в `packages/shared` + список мест вызова; тест-сторож: каждый маршрут, отдающий сущность из списка,
  проходит через маску (по образцу `position-sections.test.ts`).
- Агрегаты (сумма воронки) при скрытой сумме сделки — скрывать и итоги, иначе значение восстанавливается.
- Интерфейс: поле не показывается/показывается «•••», в таблицах — колонка недоступна.

### Оценка
(а) 2–3 дня; (б) 1,5–2 недели (каждый ответ API и экран; риск пропустить место — нужен сторож-тест).

## Порядок
1. Часть 1, решения → реализация. 2. Часть 2 (а). 3. Часть 2 (б) — только если понадобится.
