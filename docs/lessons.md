# Уроки ревью — чек-листы

Накопительные уроки из ревью. Читать в два момента: **при планировании** задачи, которая меняет общие механизмы, и **при ревью перед пушем**. Журнал инцидентов — внизу.

Корневая причина всех собранных здесь ошибок: «компилируется + новые тесты зелёные» ≠ «интеграция с существующими путями». Быстрые модели оптимизируются под первое; продукт — второе.

## При планировании

- **Общая функция — сначала все её вызовы.** Меняешь сигнатуру или поведение функции, которую зовут из многих мест (`applyStockMoves`, `saveLines`, `withContext`…) — grep-ни все вызовы и включи каждый вызывающий сценарий в план: production, documents, transfers, serials, отмена проводки. Параметр, который никто не передаёт, — это баг, а не опция.
- **Существующие сценарии — часть определения готовности.** Новая фича проходит через старые пути (перемещение, выпуск, частичная приёмка, отмена прихода с расходами) — тесты этих сценариев с включённой фичей обязательны, не только тесты самой фичи. Ошибки живут на границах нового и старого.
- **Общие остатки/балансы — тест на конкурентность.** Две параллельные транзакции списывают один остаток, ожидание — без перерасхода (пример: 7+7 из партии 10 → 0+6). Последовательные тесты гонку не ловят.
- **M-задачи (1,5+ дня) резать на инкремменты.** Делить по пути данных (приход → расход → перемещения → производство → отчёт), каждый этап со своими тестами и коммитом. Один коммит на всё — ревью и отладка ломаются.
- **UI в объёме задачи — значит и рендер в объёме задачи.** Не только типы и API-контракт, но и прогон компонента с тестовыми данными (render через vitest/bun test или визуально).

## Правила кода

- **`undefined` = «не трогать», `null` = «очистить».** `??` и деструктуризация с дефолтом стирают разницу — при partial-update проверять наличие поля явно (`'field' in body`), fallback делать только на `undefined`.
- **Схема Drizzle ↔ миграция — сверять после `drizzle-kit generate`.** В SQL глянуть FK: таблица-цель и `ON DELETE` совпадают со схемой (бывало: FK указывал на свою же таблицу). Эталонный тест — `packages/db/test/fk-set-null.test.ts` (сверка со `pg_constraint`).
- **Изменения общих остатков — внутри существующих блокировок балансов.** Распределение/списание партий — только после захвата lock'а остатка, иначе конкурентные проводки уводят партию в минус.
- **Поля дат — только `DateInput`** (`apps/web/src/components/gr8r/date-picker.tsx`), во всех документах, карточках, фильтрах и диалогах; нативный `type="date"` ловит `apps/web/src/lib/no-native-date.test.ts`. Значение — строка `YYYY-MM-DD`, `''` = пусто; фильтрам периода — `required` и `min`/`max`.

## Перед пушем (ревью)

- [ ] Зелёные тесты существующих сценариев, затронутых изменением (не только новых).
- [ ] Схема ↔ миграция ↔ `pg_constraint` не разошлись.
- [ ] Новый UI реально рендерится с данными (нет пустых `<span>` и молчащих fallback'ов).
- [ ] Черновик прошёл ревью более сильной моделью, найденное исправлено. Одна сильная модель находит почти всё за один проход — дешевле, чем 8 ошибок в `main`.
- [ ] `bun run typecheck`, `bun run docs:check`, `bun test <затронутое>` (по CLAUDE.md).
