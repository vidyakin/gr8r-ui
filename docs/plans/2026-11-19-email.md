# Почта: отправка и входящие (задача 1092, часть «почта»), 2026-11-19

Повод: главный пробел CRM по сравнению с EspoCRM (`2026-11-19-espocrm-gap.md`). Без почты нет переписки в истории клиента,
отправки счетов и КП, писем из автоматизаций, подтверждения заявок, будущих рассылок и обработки ответов (`2026-11-16-ai-lead-intake.md`).

## Решения пользователя (2026-11-19)

- Первый этап — **отправка и входящие**, двумя инкрементами подряд. Полный почтовый клиент (папки, фильтры, групповые ящики) — не сейчас.
- Ящики — **общий ящик воркспейса** (автоматизации, системные письма) **и личные ящики** сотрудников (письма из карточек уходят от имени менеджера).
- Подключение — **обычный SMTP/IMAP** (Яндекс 360, Mail.ru, Gmail, свой сервер; пароль приложения). Сервисы рассылок по API — позже.
- SMS — отдельной задачей на том же каркасе исходящих сообщений.

## Инкремент А — отправка

### Данные (db)
- `mailboxes`: `id`, `workspace_id`, `kind` (`shared` | `personal`), `member_id` (у личного; у общего null, общий — один на воркспейс),
  `email`, `display_name`, `smtp_host`, `smtp_port`, `smtp_secure` (`ssl` | `starttls` | `none`), `smtp_user`,
  `imap_host`, `imap_port`, `imap_secure`, `imap_user` (заполняются для инкремента Б), `signature` (текст), `status`
  (`ok` | `error` | `unchecked`), `last_error`, `checked_at`, `created_at`, `updated_at`. RLS — как у прочих таблиц арендатора.
  Пароль — в хранилище секретов (`docs/architecture/secrets.md`) под ключом `mailbox.<id>.password`, в таблице его нет.
- `email_messages`: `id`, `workspace_id`, `mailbox_id`, `direction` (`out` | `in`), `status` (`queued` | `sending` | `sent` | `failed` | `received`),
  `from_email`, `from_name`, `to` (массив адресов), `cc`, `subject`, `body_text`, `body_html` (очищенный), `message_id`, `in_reply_to`,
  `references`, `attempts`, `last_error`, `sent_at`, `received_at`, `created_by`, связи `lead_id`, `contact_id`, `company_id`, `deal_id`,
  `document_id` (все nullable), `created_at`. Вложения — через существующие вложения (`docs/architecture/attachments.md`).
- Письмо в истории: при отправке и приёме создаётся касание `crm_activities` типа `email` со ссылкой на письмо (`email_message_id`),
  чтобы письмо было в ленте лида, контакта, контрагента и сделки без отдельного экрана.

### Отправка (worker)
- Задача воркера `email.send`: берёт письмо `queued`, читает пароль через `readSecret`, отправляет через `nodemailer`, ставит `sent`
  или повторяет при временной ошибке (как flow: экспоненциально, до 5 попыток), затем `failed` с причиной. Заголовок `Message-ID`
  генерируем сами и храним — по нему инкремент Б свяжет ответы.
- Защита: адреса SMTP-серверов — через `net.ts` (SSRF: без локальных адресов в проде), таймауты, лимит писем на воркспейс в сутки.
- Выбор ящика: явный `mailboxId`; иначе личный ящик автора; иначе общий; нет ни одного — понятная ошибка `mailbox_required`.

### API
- `GET/POST/PATCH/DELETE /mailboxes` — общий ящик правит admin+, личный — его владелец; ответ без пароля, с фактом наличия.
- `POST /mailboxes/:id/check` — проверка SMTP (и IMAP, если заполнен) подключением, статус в ящик.
- `POST /emails` — поставить письмо в очередь: получатели, тема, текст, вложения (id существующих), привязки, `documentId` +
  `printForm` для PDF документа (печать уже есть у воркера). `GET /emails?leadId=…|contactId=…|companyId=…|dealId=…` — переписка.
- Realtime-событие на смену статуса письма.

### Интерфейс (web)
- «Настройки» → «Почта»: общий ящик (форма с пресетами Яндекс 360 / Mail.ru / Gmail, кнопка «Проверить»). «Профиль» → «Мой почтовый ящик».
- Окно «Новое письмо» (кому, копия, тема, текст, подпись ящика, вложения, выбор ящика «от кого») — из вкладки «Дела» лида, контакта,
  контрагента, сделки (рядом с «Записать звонок»), и кнопка «Отправить по почте» в документе (счёт, КП, заказ, реализация) с PDF.
- В ленте касаний письмо показывается со статусом (в очереди, отправлено, ошибка — с причиной и «Повторить»).

### Автоматизации
- Узел `action.email_send` (`packages/shared/src/automations/nodes/`, как `action-telegram-send`): ящик (общий по умолчанию или ответственного),
  кому (подстановки `{{…}}`), тема, текст, привязка к записи триггера. Порт `rt.sendEmail` в рантайме воркера.

### Тесты (инкремент А)
- Ящики: права (чужой личный ящик не виден и не правится), пароль не уходит в ответы, RLS между воркспейсами.
- Очередь: письмо → `sent` (фейковый SMTP-транспорт), временная ошибка → повтор, постоянная → `failed`; касание создаётся.
- Узел автоматизации отправляет письмо с подстановками.

## Инкремент Б — входящие

- Задача воркера `email.sync` по расписанию (раз в 2–5 минут) и вручную: для каждого ящика с IMAP — `imapflow`, новые письма из INBOX
  (по `UIDVALIDITY` + последнему `UID`, курсор в ящике), разбор `mailparser`, HTML — через ту же очистку, что в комментариях.
- Сопоставление: `In-Reply-To`/`References` → наше отправленное письмо → его привязки; иначе адрес отправителя → контакт → контрагент,
  иначе лид по email. Не нашлось — письмо хранится без привязки (виден в ящике), лид не создаётся (настройка «создавать лид из
  писем без привязки» — флажок общего ящика, по умолчанию выключен).
- Касание `email` направления «входящее», уведомление ответственному, триггер автоматизаций «Получено письмо» (запись, ящик, отправитель).
- Вложения входящих — в хранилище вложений с лимитом размера.
- Экран «Почта» (минимальный): входящие ящиков, доступных пользователю, «без привязки» — с действием «Привязать к контакту/лиду».
- Тесты: разбор письма, сопоставление по In-Reply-To и по адресу, повторная синхронизация не дублирует, RLS.

## Фактическая реализация инкремента А

Сделано 2026-11-19, архитектура — `docs/architecture/email.md`, статья — `docs/user/general/email.md`. Миграция `0127_email.sql` (написана вручную, в журнале idx 122).

- **Данные.** `mailboxes`, `email_messages` по плану; общий ящик один на воркспейс и личный один на участника — частичные уникальные индексы. Добавлено `crm_activities.email_message_id`
  (составной FK `ON DELETE SET NULL (email_message_id)`). Сверх плана в `email_messages`: `print_form`, `print_template_id` (PDF документа собирает воркер при отправке) и `attachment_ids uuid[]`
  (вложения — ссылки на существующие `attachments`, а не новый тип объекта: права проверяются при постановке, размер ≤ 20 МБ).
- **Пароль** — секрет `mailbox.<id>.password`; ключи `mailbox.*` скрыты из `GET /secrets`, запись и удаление через `/secrets` закрыты (`secret_reserved`).
- **Выбор ящика.** Явный `mailboxId` → личный ящик автора → общий → 422 `mailbox_required`. Чужой личный ящик не виден даже admin (404). Узел автоматизации: `mailbox=shared|owner` (личный ящик ответственного, иначе общий).
- **Повторы.** Задача `email.send` (`max_attempts=5`, пауза очереди `jobs` `2^n·5` с): временная ошибка (сеть, таймаут, SMTP 4xx) возвращает письмо в `queued` и повторяется; окончательная (`EAUTH`, 5xx, не собралось вложение/PDF) — сразу `failed`; на 5-й попытке — `failed`.
  `POST /emails/:id/retry` ставит заново. Исключение для повтора бросается после коммита итога, иначе откат стёр бы `last_error` (поймано тестом).
- **Защита.** SMTP/IMAP-адрес — через `shared/automations/net.ts` (проверка формы при сохранении, DNS-проверка и подключение к проверенному IP при отправке), таймауты, суточный лимит воркспейса `EMAIL_DAILY_LIMIT` (500).
- **API** — `/mailboxes` (+`/:id/check`), `/emails` (+`/:id`, `/:id/retry`), в `TENANT_PATHS`, модуль «ядро», токены агентов — раздел `crm`. Проверка подключения отвечает 200 с `ok:false`, чтобы статус `error` записался (ответ ≥ 400 откатил бы транзакцию).
- **Интерфейс.** «Настройки» → «Почта» (общий и личный ящики, пресеты Яндекс 360 / Mail.ru / Gmail, «Проверить подключение»), блок «Мой почтовый ящик» в профиле, окно «Новое письмо» (кнопка «Письмо» в карточке лида и в «Делах» сделки, контакта, контрагента; «Отправить по почте» в документе с выбором формы PDF),
  статус письма и «Повторить» в ленте касаний, события `mailbox`/`email` в `realtime.ts`.
- **Тесты.** `apps/api/test/email.test.ts` (17: права и пароль, RLS, SSRF, очередь, повторы, `failed`, касание, выбор ящика, лимит, PDF, узел), `packages/shared/test/email.test.ts`, `apps/web/src/app/email/EmailStatus.test.tsx`; SMTP — фейковый транспорт и stream-транспорт nodemailer.

### Отклонения от плана и не сделано
- Проверка IMAP — только приветствие сервера (без входа): настоящая проверка с `imapflow` придёт в инкременте Б.
- Подпись ящика подставляется в текст окна «Новое письмо» на клиенте; сервер добавляет её только письмам автоматизации.
- HTML-письма: API принимает `bodyHtml` (очищается `sanitizeRichText`), но окно отправляет только текст.
- Вложения в окне — файлы самой записи (документа, сделки, лида, контакта или контрагента); загрузки новых файлов прямо в окне нет.
- Прочее: в карту токенов агентов попутно добавлен `/departments` (на dev тест покрытия `TENANT_PATHS` уже падал).


## Фактическая реализация инкремента Б

Реализовано 2026-11-19 в worktree `codex-email-inbound`. Архитектура — `docs/architecture/email.md`, справка — `docs/user/general/email.md`.

- **Данные:** ручная миграция `0128_email_inbound.sql`, запись idx 123 в журнале. Курсор UIDVALIDITY + last UID в ящике, UID сообщения и уникальность по ящику/эпохе/UID.
  По Message-ID дополнительно убираются повторы после пересоздания INBOX (без Message-ID — только внутри эпохи).
- **Приём:** `email.sync` раз в три минуты и вручную, imapflow с входом/STARTTLS, SSRF/DNS pinning/таймаутами; mailparser, существующий sanitizeRichText.
  Снимок читается вне транзакции, курсор фиксируется вместе со всеми последствиями под RLS и блокировкой ящика. Устаревший снимок конкурентного воркера пропускается.
- **CRM:** In-Reply-To/References → sent с привязками; иначе контакт и его контрагент → лид. Без совпадений письмо остаётся непривязанным.
  Флажок общего ящика (false по умолчанию) включает создание лида, личные ящики его не используют. Касание, уведомление ответственному и `email.received` — в одной транзакции.
- **Вложения:** entityType=email в существующем FileStore, ограничения файла/квоты/тарифа; суммарно 20 МиБ, сырой MIME до 30 МиБ. Пропущенные размеры видны предупреждением.
- **Автоматизации:** узел `trigger.email_received`, фильтр ящика, контекст связанной записи и `trigger.email`. Полноценный IMAP login при `/check`.
- **API/UI:** `/mailboxes/:id/sync`, `/emails/:id/link`, direction/unlinked фильтры, раздел `/email` в SECTIONS, ручная проверка,
  чтение текста, скачивание вложений, привязка контакт/лид, новые i18n и realtime-инвалидации.
- **Тесты:** фейковый IMAP для разбора/сопоставления/курсорных повторов/флажка/вложений, API-права и изоляция, планировщик,
  проверка login и маскировки пароля, контекст и идемпотентность триггера, рендер входящего письма.

### Ограничения и отклонения

- Раздел показывает текстовую версию bodyText; очищенный HTML хранится, но не рендерится. Папки кроме INBOX не поддерживаются, как и запланировано.
- Касание создаётся при наличии CRM-привязки; при ручной привязке непривязанного письма создаётся тогда же.
- За проход читается диапазон до 100 UID с ограничением памяти пачки; большой старый INBOX догоняется последовательными проходами.
- Для писем без Message-ID после смены UIDVALIDITY возможен повтор импорта. Письмо сверх лимита MIME сохраняется без содержимого с предупреждением.
- В данной среде запуск отдельного PostgreSQL заблокирован sandbox (`shmget: Operation not permitted`), запись git index worktree — также (`index.lock: Operation not permitted`).
  Проверки БД и коммиты требуют доступной тестовой БД и записи gitdir; рабочая БД на 5432 не использовалась.
