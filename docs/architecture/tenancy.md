# Арендаторы и доступ

- `users` — глобальные учётные записи; `workspaces` — арендаторы; `memberships (user_id, workspace_id, role)`
  с ролями owner / admin / member / guest — источник правды для проверки доступа. Пользователь может состоять в нескольких воркспейсах.
- **Профиль участника** — отдельная таблица `members` (имя, должность, цвет, команда, часовой пояс, статус active / invited /
  deactivated). У `members.user_id` может быть NULL (приглашённый, ещё не зарегистрированный). На `members.id` ссылаются задачи,
  комментарии, сделки и т. д. (а не на `users.id`), поэтому участник остаётся в истории и после деактивации. Инвариант:
  если `members.user_id` задан, существует `memberships` с той же ролью — смена роли обновляет обе таблицы в одной транзакции.
- Вход: email + пароль (Argon2id через `Bun.password`), сессии в таблице `sessions` (в БД хранится sha256 токена, не сам токен),
  cookie httpOnly + SameSite=Lax (+ Secure в production, `COOKIE_SECURE`). Токен только в cookie — в теле ответов его нет.
  Вход и регистрация ограничены rate-limit'ом (таблица `rate_limits`, счётчики по IP и по email). OAuth (Google и т.п.) — позже,
  отдельной таблицей `identities`.
- Активный воркспейс передаётся заголовком `X-Workspace-Id` (для WebSocket — параметром `?workspace=`); API проверяет членство.
- Приглашения: `invites` с токеном вида `<workspace_id>.<секрет>` (в БД — sha256), срок 7 дней, принимается тем аккаунтом,
  чей email совпал с приглашённым. Воркспейс зашит в токен, поэтому принять приглашение можно до вступления в арендатора.
  Отправка писем — позже; пока токен возвращается администратору один раз.
- **Каждая таблица с данными арендатора** имеет `workspace_id uuid not null` и политику RLS по
  `current_setting('app.workspace_id', true)::uuid`; на таблицах `ENABLE` + `FORCE ROW LEVEL SECURITY` (владелец тоже подчиняется политикам).
  Исключения, у которых собственные политики: `workspaces` (арендатор — сама строка) и `memberships` (свои членства видны по
  `app.user_id`, чтобы определить, в какие воркспейсы пользователь может войти и вывести «мои воркспейсы»; изменять — только в рамках арендатора).
  Глобальные таблицы без RLS: `users`, `sessions`, `rate_limits` (минимальные права).
- **Роли БД** (создаёт миграция 0002, идемпотентно): `app_owner` — владелец таблиц, NOLOGIN; `app_user` — под ней работает API, NOLOGIN,
  NOBYPASSRLS; `app_worker` — воркер, BYPASSRLS (фоновые задачи и outbox идут через всех арендаторов). Рантайм подключается
  логин-ролью (`gr8r_app`, создаётся `db:migrate` по `APP_DB_USER`/`APP_DB_PASSWORD`): она не суперпользователь и NOINHERIT — сама прав на таблицы
  не имеет, пока код не сделает `SET ROLE`. Миграции выполняются под `ADMIN_DATABASE_URL` (суперпользователь/владелец БД); таблицы
  передаются `app_owner`. Таблица `events` для `app_user` только на добавление (UPDATE/DELETE отозваны).
- **DDL вне API.** Логин-роль API права владельца не получает (`SET ROLE app_owner` — ошибка): эту выдачу, появившуюся на этапе 3 ради
  индексов конструктора, этап 4 убрал. DDL выполняет только воркер через отдельное подключение `DATABASE_URL_DDL` — логин-роль
  `gr8r_ddl` (создаёт `db:migrate` по `DDL_DB_USER`/`DDL_DB_PASSWORD`): она наследует права `app_owner` (владельца таблиц), не суперпользователь,
  `SET ROLE` ей не нужен. API и сид лишь ставят задачу в `jobs`; воркер выполняет её по белому списку операций (см. «Конструктор сущностей»).
- **Конвейер запроса API**: сессия → пользователь → заголовок воркспейса → одна транзакция: `SET LOCAL ROLE app_user`,
  `app.user_id`, проверка членства, `app.workspace_id` → обработчик → COMMIT (при ответе ≥ 400 — ROLLBACK). Обработчики используют только
  `c.var.db` этого контекста; ручных фильтров по `workspace_id` в запросах нет — изоляцию гарантирует БД. `SET LOCAL` не «протекает»
  между запросами через пул соединений. Пустая настройка даёт NULL → строк не видно (fail closed).
- **Целостность между арендаторами**: связи внутри арендатора — составные внешние ключи `(workspace_id, id)`, поэтому запись одного
  арендатора не может сослаться на запись другого даже в обход API (FK-проверки обходят RLS, составной ключ их закрывает).
  **У составного FK с `ON DELETE SET NULL` — всегда список колонок**: `ON DELETE SET NULL ("x_id")` (Postgres 15+), иначе при удалении
  родителя обнуляется и `workspace_id` (NOT NULL) и удаление падает. drizzle-kit список не умеет: в схеме остаётся `.onDelete('set null')`,
  колонку дописывают руками в SQL миграции (пример — `0026_composite_fk_set_null.sql`). Тест `packages/db/test/fk-set-null.test.ts` проверяет все такие FK.
- Новая таблица с `workspace_id` обязана вызвать в своей миграции `select app_secure_tenant_table('имя')` (владелец, ENABLE+FORCE,
  политика, права); тест покрытия RLS падает, если таблица пропущена.
- Крупному клиенту позже можно выделить отдельную схему или БД — код от этого не меняется.
