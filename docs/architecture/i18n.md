# Языки интерфейса

Интерфейс двуязычный: English и Русский. Код — `apps/web/src/i18n`. Печатные формы (`packages/shared/src/print`) и демо-данные
остаются русскими и не переводятся.

**Выбор решения — свой словарь с типизированными ключами.** Сравнивали три варианта:

| | react-i18next | Lingui | свой словарь (выбран) |
|---|---|---|---|
| зависимости | i18next + react-i18next, ~40 КБ | макросы + плагин сборки + компиляция каталогов | нет |
| типизация ключей | через module augmentation, тяжело на больших словарях | по исходным строкам, ключей нет | `TKey` выводится из `en`, `ru` проверяется по форме |
| `t()` вне компонентов | да | да, через `i18n._` | да |
| плюрализация, ICU | плагины | ICU из коробки | `Intl.PluralRules` (one/few/many/other) |
| извлечение строк | внешние утилиты | `lingui extract` | вручную, по неймспейсам |

Двух языков и строк в сотни ключей на модуль хватает без библиотеки. Lingui требует шага сборки (SWC/Babel-плагин под Vite 8 и TS 7) —
лишний риск. Если появятся десятки языков, переводчики и ICU-сообщения, словари в том же формате переносятся в i18next почти механически.

**Устройство.**
- `locale.ts` — текущий язык во внешнем store (как `data/settings.ts`): `getLocale()`, `setLocale()`, `useLocale()`. Поэтому `t()` и форматтеры
  работают и в обычных функциях (`fmtDate`, `money`), а не только в компонентах. Меняется и `<html lang>`.
- `en/*.ts` — английский словарь, по файлу на неймспейс (`common`, `nav`, `settings`, `catalog`, `errors`, …): меньше конфликтов при параллельной
  работе. `ru/*.ts` объявлен как `Widen<typeof en>` — пропущенный или лишний ключ даёт ошибку типов.
- `t('catalog.product.added', { name })` — подстановки `{name}`; значение-объект `{ one, few, many, other }` выбирается по `params.count`.
  Нет перевода — английский текст, нет и его — сам ключ. `useT()` — тот же `t` с подпиской компонента на смену языка.
- `I18nProvider` (в `main.tsx`) перемонтирует дерево при смене языка: обычные функции перечитают язык. Состояние экранов при этом сбрасывается
  (язык меняют редко), кэш React Query живёт вне дерева и сохраняется.
- Названия разделов `SECTIONS` и вкладок `PROJECT_TABS` (`routes.ts`) — геттеры поверх словаря `sections.*` / `projectTabs.*`; английская
  подпись в `routes.ts` — запасной вариант для раздела без ключа.
- Подписи значений из `@gr8r/shared` (`VAT_LABELS`, `FIELD_TYPE_LABELS`, `STOCK_REPLENISHMENT_LABELS`, …) остаются английскими в shared,
  перевод — `tEnum('vat', value, VAT_LABELS[value])` по словарю `enums.*`.

**Форматирование** (`format.ts`) — только по языку интерфейса, жёстких `'en-US'`/`'ru-RU'` в компонентах нет: `fmtNumber`, `fmtAmount`
(две цифры), `fmtCurrency`, `fmtCompact`, `fmtDateTime`, `fmtDateTimeIntl`, `monthShort`, `weekdayShort`; форматтеры Intl кэшируются по
локали. `lib/dates.ts` (`fmtDate`, `relDate`, `ago`) и `money` каталога и CRM работают через них, календарь (react-day-picker) получает
локаль. Ввод суммы по правилам языка разбирает `parseNumber`. Формат только для показа: `ru-RU` даёт запятую и неразрывные пробелы, поэтому значения `input`, CSV и печать так не форматируются.

**Где хранится язык.** Порядок выбора: личный `users.locale` → язык воркспейса `workspaces.settings.locale` → запомненный в браузере
(`localStorage` `gr8r-ui.locale`, нужен экрану входа) → язык браузера → `en`. API: `PATCH /auth/me { locale: 'en'|'ru'|null }`
(null — «как в воркспейсе»), `PATCH /workspaces/:id { locale }` (admin и выше; null снимает), `GET /auth/me` и `GET /workspaces` отдают
`locale`. Переключатели — Settings → Language (личный и воркспейса) и меню аккаунта.

**Ошибки API.** Сервер по-прежнему пишет английский `message` (он же для логов и внешних клиентов), клиент переводит по `error.code`
(`errorMessage` в `data/api.ts`, словарь `errors.*`, параметры — из `error.details`). На английском приоритет у текста сервера — он точнее;
на русском — перевод по коду, нет перевода — текст сервера. Замер (`packages/db`, `apps/api`, `apps/worker`): 413 мест `DomainError`/`AppError`,
146 кодов, 71 сообщение с подстановкой в текст, у `invalid_reference` 77 разных сообщений, у `not_found` 43. Поэтому сейчас по коду
переводятся общие коды (`not_found`, `forbidden`, `validation_error`, `invalid_reference`, `rate_limited`, …) — обобщённо. Чтобы перевод был
точным, нужен рефакторинг: значения из текста — в `details` (`{ entity: 'warehouse', id }`), разные смыслы одного кода — отдельными кодами
(`warehouse_not_found` или `not_found` + `details.entity`), затем ключ `errors.<code>` на каждый код.

**Как перевести модуль.** Новый неймспейс `en/<модуль>.ts` + `ru/<модуль>.ts`, подключить в обоих `index.ts`; в компонентах `const t = useT()`
(до первого использования — `t` затеняет импорт), строки заменить на `t('<модуль>.…')`, подписи из shared — через `tEnum`, даты и суммы —
через `format.ts`. Образец — каталог (`app/catalog`). Демо-данные, ввод пользователя и печать не трогать.

**Что переведено.** Весь интерфейс (2026-10-23): каркас, каталог, CRM, автоматизации (в т. ч. тексты узлов — `automations.nodes.<тип>` через
`app/automations/node-i18n.ts`, точка в типе заменена на `_`), конструктор полей, задачи и проекты (`views`), оверлеи и страницы, настройки,
документы (типы документов `docs.types.*` через `typeLabel`, статусы `STATUS_LABEL` — геттеры поверх `docs.docStatus.*`), производство
(`production`, `productionEnums` через `tProductionEnum`), общие тексты ошибок; даты и числа во всём приложении. Предупреждения анализа закрытия
месяца переводятся на клиенте по `issue.kind` (сервер по-прежнему шлёт английский `message` — запасной вариант).
Не переводятся: витрина `/design-system`, значения по умолчанию, которые сохраняются в данные (`Untitled`, роль `Guest`), названия из справочников
и данных пользователя (сценарии, виды и состояния заказ-нарядов), подписи состояний в `DOCUMENT_META.states` и прочие тексты сервера.
