# Автоматизации

Реализовано на этапе 6. Код: общая часть — `packages/shared/src/automations` (реестр узлов, шаблоны, граф, cron, защита от SSRF), схема —
`packages/db/src/schema/automations.ts` (миграция `0006_automations.sql`), движок — `apps/worker/src/flows`, API — `apps/api/src/routes/flows.ts`,
интерфейс — `apps/web/src/app/automations`.

**Модель.** Все таблицы под RLS, как остальные.
- `flows` — название, `enabled`, **черновик** `graph jsonb`, `published_version`, `created_by` (members.id: от его имени flow создаёт задачи и пишет
  комментарии). Включить можно только опубликованный flow (CHECK в БД).
- `flow_versions` — неизменяемые опубликованные версии графа (`flow_id, version, graph, trigger_type`). Правка черновика на работающую версию не влияет.
- `flow_runs` — запуск: версия, статус (`queued → running → waiting → succeeded | failed`; `skipped` — отклонён защитой от зацикливания или выключенным flow),
  вид триггера, контекст триггера (`trigger`: запись и изменения на момент запуска), ход выполнения (`state`: очередь узлов, выходы шагов,
  счётчики), цепочка flow (`chain`), ошибка. Уникальность `(flow_id, event_id)` и `(flow_id, dedupe_key)` делает запуск по событию и по минуте
  расписания идемпотентным: повторная обработка события второго запуска не создаёт.
- `flow_run_steps` — шаг: узел, попытка, статус, **вход** (параметры после подстановок, секреты вроде `Authorization` скрыты), **выход**, ошибка, время.

**Граф.** `{ nodes: [{ id, type, position, params }], edges: [{ id, source, sourceHandle?, target }] }`; `sourceHandle` — идентификатор выхода узла
(`out` по умолчанию, `true` / `false` у условия, `case_N` / `else` у ветвления). Редактор превращает его в узлы и связи React Flow и обратно.
Перед публикацией `validateGraph` (тот же код проверяет и редактор): ровно один триггер, нет висящих узлов (всё достижимо от триггера), нет циклов,
у узла не больше одной входящей связи (слияние ветвей запрещено — запуск идёт по дереву, каждый узел выполняется не более раза), параметры
каждого узла проходят его zod-схему, лимиты (60 узлов, 150 связей).

**Реестр узлов — расширяемый.** Узел = **один файл** в `packages/shared/src/automations/nodes/` + строка в `nodes/index.ts`. Файл экспортирует
`defineNode({ type, category, label, description, icon, params, outputs?, match?, execute })`:
- `category`: `trigger | condition | action | flow`; `params` — zod-схема; подсказки интерфейса задаются в `.meta({ title, description, ui, dependsOn, … })`
  (`ui`: `entity`, `field`, `value`, `member`, `project`, `textarea`, `cron`, `url`);
- `outputs` — статический список или функция от параметров (ветвление строит выходы по своим вариантам);
- `match(params, event, { entity, action, changes })` — только у триггеров по событиям;
- `execute(params, rt)` возвращает `{ output?, next?, delayMs? }`. Исполнитель **не касается БД и сети напрямую**, а действует через порты `NodeRuntime`
  (`updateField`, `createTask`, `addComment`, `notify`, `http`), которые реализует воркер. Поэтому узел целиком проверяется тестом с подставными портами,
  а новый узел, которому хватает существующих портов, не требует правок воркера. Новый порт — метод в `NodeRuntime` и реализация в `apps/worker/src/flows/records.ts`.
- Форма параметров в редакторе строится из JSON Schema схемы (`z.toJSONSchema`) — писать UI узла не нужно. Иконка — имя lucide в `icon`; имена, которых нет в
  `app/automations/node-meta.tsx`, получают иконку по умолчанию.

Базовый набор: триггеры «запись создана», «запись изменена», «поле изменилось» (сущность: системные task / project / deal / company / contact / product,
`document` и пользовательские; необязательные фильтры from / to), «по расписанию» (cron в часовом поясе арендатора), «ручной запуск»; логика — «условие» (eq, ne, gt, gte, lt, lte,
contains, empty, not_empty; числа сравниваются как числа), «задержка» (до 30 суток), «ветвление»; действия — «обновить поле записи» (встроенного или пользовательского
поля; значение проверяется схемой поля конструктора, как в API), «создать задачу», «уведомить участника», «HTTP-запрос», «записать комментарий» (к задаче; к сделке — заметка CRM).

**Подстановки.** Любой строковый параметр поддерживает `{{путь}}` по контексту: `trigger.record.title`, `trigger.record.custom.<поле>` (у записей пользовательских
сущностей значения — на верхнем уровне), `trigger.changes.<поле>.from|to`, `trigger.project.leadId`, `trigger.recordId`, `steps.<id узла>.<выход>`, `flow.name`, `run.id`, `now`.
Шаблонизатор без eval: только путь через точку, индексы массивов числом, доступны лишь собственные свойства объектов (`__proto__`, `constructor`, `prototype` закрыты);
вызовов, операторов и фильтров нет. Результат всегда строка (объекты — JSON), недостающее значение — пустая строка; нужный тип получается при проверке схемой поля или узла.

**Движок (воркер).**
1. Событие outbox → `handleEvent` → `startRunsForEvent`: берёт опубликованные включённые flow арендатора события, проверяет `match` триггера, создаёт `flow_runs` и ставит
   задачу `flow.run` (очередь `flows`). Запись для контекста читается сразу (близко к моменту события). Расписание: раз в минуту `scheduleFlowsOnce` (UTC; пропущенные
   при остановке воркера минуты не догоняются). Ручной запуск — `POST /flows/:id/run` ставит запуск напрямую.
2. Задача `flow.run` → `executeRun`: **каждый шаг — отдельная транзакция под ролью `app_user` с `app.workspace_id` арендатора** (RLS действует, `BYPASSRLS` воркера здесь не
   используется; чужие записи недоступны даже по известному id). В транзакции: подстановки → проверка параметров схемой узла → действие под `SAVEPOINT` → запись шага → сдвиг курсора.
   Ошибка действия откатывает его записи, но журнал шага сохраняется; упавший воркер откатывает всю транзакцию, и шаг выполнится заново (для HTTP — «минимум один раз»).
3. **Задержка** не держит воркер: запуск уходит в `waiting`, задача `flow.run` ставится в `jobs` с `run_at`; досрочно пришедшая задача ничего не делает (`state.resumeAt`).
   Выключенный flow не продолжает ждущие запуски (они завершаются как `skipped`); ручные запуски от `enabled` не зависят.
4. **Повтор временных ошибок** (`TransientError`: сеть, таймаут, 408 / 429 / 5xx): шаг повторяется до `FLOW_MAX_ATTEMPTS` (3) раз с паузой `FLOW_RETRY_BASE_SEC` (5 с) × 2^(попытка−1),
   тоже через `jobs.run_at`; остальные ошибки (4xx, неверные параметры, запись не найдена) сразу завершают запуск как `failed`.
5. **Ограничения:** `FLOW_MAX_STEPS` (100) шагов на запуск; задержка ≤ 30 суток; HTTP — таймаут `FLOW_HTTP_TIMEOUT_MS` (10 с), ответ ≤ 1 МБ, ≤ 3 редиректов; вход и выход шага в журнале ≤ 20 КБ.
6. **Защита от зацикливания.** Каждое событие, которое порождает действие flow, несёт в payload метку `via: { runId, flowId, chain }` (`actor_id` у таких событий пуст). Flow, уже стоящий в цепочке события,
   этим событием не запускается — запуск фиксируется как `skipped` с причиной; другой flow может отреагировать (цепочка растёт), но длина цепочки ограничена (`MAX_FLOW_CHAIN` = 4).
   Действие, не менявшее значение, события не пишет. События служебных сущностей (`flow`, `flow_run`, `notification`…) триггерами не бывают.
7. Действия пишут события в outbox (`task.updated` с `changes {поле: {from, to}}`, `task.created`, `comment.created`, `notification.created`…), поэтому realtime и лента Activity видят их так же, как изменения из API;
   побочные эффекты API дублируются там, где они определяют целостность (ключ задачи по счётчику проекта, `prev_status` / `completed_at`, `closed_at` и заметка о смене этапа сделки, уведомление исполнителю).

**HTTP и SSRF.** Допустимы только `http(s)` без учётных данных в адресе. Имя хоста и **все** его адреса из DNS не должны быть частными / служебными (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16 с метаданными облака, 100.64/10,
multicast, `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped и NAT64 и т. д.); `localhost`, `*.local`, `*.internal` запрещены; редиректы идут вручную с той же проверкой на каждом шаге. `FLOW_HTTP_ALLOW_PRIVATE=1`
снимает запрет (закрытые установки, тесты). Известное ограничение: между проверкой DNS и подключением адрес теоретически может смениться (DNS rebinding) — полностью закрывает только исходящий прокси / фаервол сети.

**API** (`/flows`, `/flow-runs`; чтение — любой участник, изменение и запуск — admin и выше, потому что flow выполняет действия и HTTP-запросы от имени воркспейса): CRUD flow (`PATCH` — имя, описание, черновик, `enabled`),
`POST /flows/:id/publish` (`{ enable? }`; неверный граф — 422 `invalid_graph` со списком замечаний), `POST /flows/:id/run`, `GET /flow-runs?flowId=&status=&failed=`, `GET /flow-runs/:id` (с шагами).
Включить непубликованный flow и запустить его — 409 `not_published`. События `flow.*` и `flow_run.*` (запуск завершился / ждёт) обновляют интерфейс по realtime.

**Интерфейс.** Раздел Automations в сайдбаре: список (включение, версия и «unpublished changes», последний запуск, число ошибок за 7 дней) и общий журнал Runs. Редактор — `@xyflow/react`: палитра по категориям, холст,
правая панель с формой параметров из схемы (сущность и поля берутся из метаданных конструктора, включая пользовательские поля; участники и проекты — из воркспейса; меню `{}` вставляет переменные), живая проверка графа
(узлы с замечаниями подсвечиваются), Save draft / Publish / Enabled / Run (для ручного триггера), вкладка Runs flow: запуски, шаги со входом, выходом и ошибкой. Цвета — токены приложения, тёмная тема работает без отдельных правил.

**Демо-сид.** Два включённых flow: «Task moved to Review → notify the project lead» (поле `status` задачи стало `review` → уведомление `{{trigger.project.leadId}}`) и «Deal won → create a Kickoff task» (стадия сделки стала `won` → задача «Kickoff» в проекте).

**Что пока не так.** Нет слияния ветвей, циклов и «для каждой записи»; расписание живёт в часовом поясе арендатора (у существующих арендаторов после миграции — UTC) и без догона пропущенных минут; запуски и шаги не очищаются (политики хранения нет); действия flow не проверяют
доступ к закрытым проектам и существование записей, на которые ссылаются пользовательские поля `ref` / `refs` (внешние ключи системных колонок проверяет БД); запись в ленту Activity делается только для задач;
редактор рассчитан на одного автора (правка того же flow в двух вкладках — «последний сохранил»); входящий вебхук-триггер не реализован.
