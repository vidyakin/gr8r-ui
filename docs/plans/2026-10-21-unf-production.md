## Ограничения текущего кода, которые определяют дизайн

1. **Склад привязан к документу.** У `stock_moves.document_id` стоит `NOT NULL` и FK на `documents`. Любое складское движение (выпуск, списание, оприходование, перемещение, инвентаризация) должно быть строкой `documents`. Отсюда выбор: **новые типы документов, а не отдельные таблицы движений**.
2. **Типы документов перечислены в CHECK.** `documents_type_chk` знает 9 типов, а `DOCUMENT_TYPES` / `DOCUMENT_META` в `packages/shared/src/documents.ts` — только продажи и закупки. Для каждого нового типа нужна миграция, которая пересоздаёт CHECK, и строка в `DOCUMENT_META` (префикс номера, группа, движение, основания, печатные формы).
3. **Модель «один документ — одно направление».** У `DocumentTypeMeta.stock` значение одно: `'in' | 'out' | null`. Выпуск — это расход материалов и приход продукции в одном документе, перемещение — расход со склада A и приход на склад B.
4. **Контрагент обязателен.** `postDocument` безусловно требует `counterpartyId` (`counterparty_required`), а `party` принимает только `'customer' | 'supplier'`. У внутренних документов (выпуск, списание, перемещение, инвентаризация) контрагента нет.
5. **Строка документа — всегда товар каталога.** У `document_lines.product_id` стоит `NOT NULL`, а `manufactured_items.product_id` необязателен, и строки BOM `work` товарами не являются. Поэтому выпуск требует, чтобы у продукции был товар с `kind = 'goods'`, а работы хранятся отдельно от `document_lines`.
6. **Себестоимость прихода зависит от расходов того же документа.** `applyStockMoves` проводит все запросы за один проход, и цену прихода передают заранее. У выпуска цена продукции = фактическая стоимость списанных материалов (`stockOut().cost`) + работы + накладные, поэтому нужна двухфазная запись.
7. **Пересчёт средней не идёт по цепочке.** `revertStockMoves` / `replayMoves` переоценивают только расходы по той же паре (склад, товар). Если отменить проведение раннего поступления материала, себестоимость уже выпущенной из него продукции устареет.
8. **У спецификаций нет версий.** `bom_lines` хранят только текущее состояние, а версии в `docs/architecture.md` записаны как «следующий шаг». Заказ на производство должен **снимать снимок** развёрнутой спецификации в свои строки.
9. **Статус — это проведение.** `documents.status` принимает `draft | posted | cancelled`. Состояния заказа из УНФ («в работе», «выполнен», «закрыт») — отдельное поле, его нельзя смешивать с проведением. Кроме того, `recalcLines` при сохранении и проведении пересчитывает цену, НДС и итоги строк, а журнал суммирует `total`. Для внутренних документов это надо явно отключить (см. этап 0).
10. **Логика заказов зашита по типам.** В `packages/db/src/documents.ts`: `FULFIL_TYPES = ['realization','act','receipt']` (стр. 38, используется в `checkLimits`, `createBasedOn`, `documentDetail`); `isOrder = srcType === 'customer_order' || 'supplier_order'` в `createBasedOn` (стр. 379) и `documentDetail` (стр. 467); `syncAfterChange` проверяет `doc.type === 'customer_order'` (стр. 365); склад по умолчанию в `createDocument` — тоже `customer_order` (стр. 171). В `packages/db/src/stock.ts`, `syncReservations` (стр. 165–169): резерв только у `customer_order`, отгрузка — только `realization`. Новые заказы (`production_order`, `work_order` из плана услуг) не получат остатка к исполнению и резервов, пока эти места не будут обобщены через `DOCUMENT_META` (`isOrder`, `fulfils`, `reserves`, список «кто снимает резерв»).
11. **Языка формул нет.** Тип поля `formula` в конструкторе «позже», а шаблонизатор автоматизаций намеренно сделан без eval. Параметрическим спецификациям нужен безопасный вычислитель выражений.

**Архитектурный документ придётся обновить** (в том же коммите, что и код, по правилу из шапки `docs/architecture.md`): раздел «Документы продаж и закупок» (внутренние документы без контрагента, составные движения, состояние отдельно от проведения), раздел «Склад» (выпуск, перемещение, списание, инвентаризация, пересчёт себестоимости), раздел «Производство» (заказы, снимок спецификации, этапы, ресурсы), раздел «Этапы» (новые этапы).

## План реализации

Общие правила каждого этапа (чек-лист):
- **БД:** таблица — `workspace_id` (`wsCol()`), `unique(workspace_id, id)`, связи — составные FK `(workspace_id, …)`. В миграции `select app_secure_tenant_table('public.<таблица>'::regclass)`, иначе упадёт тест покрытия RLS. Деньги — `numeric(18,2)`, количества — `numeric(18,3)`, себестоимость — `numeric(18,4)`. Схема — `packages/db/src/schema/*.ts`, SQL — `bun run db:generate`, ручные правки (CHECK, RLS) — в том же файле `packages/db/drizzle/000N_*.sql`.
- **API:** новый префикс роута добавить в `TENANT_PATHS` в `apps/api/src/app.ts` (иначе путь останется без цепочки «сессия → членство → транзакция с RLS»). Права: чтение — участник, документы — member+, справочники и настройки — admin+. Ошибки — `DomainError(422|409, код)`.
- **Схемы:** zod — в `packages/shared/src/schemas/*.ts`, чистые расчёты — в `packages/shared/src/*.ts` (одна функция на сервере и в форме).
- **События:** каждое изменение пишет `recordEvent(...)` в той же транзакции. На клиенте — `collectionsFor` / инвалидация запросов по `entity`. Для автоматизаций — `BUILTIN_FIELDS` и `AUTOMATION_SYSTEM_ENTITIES` в `packages/shared/src/automations/entities.ts`.
- **Тесты:** `bun test`. Чистые функции — `packages/shared/test/*.test.ts`, API и проведение — `apps/api/test/*.test.ts`, воркер — `apps/worker/test/worker.test.ts`. Тесты с БД идут только на тестовую базу: `packages/db/src/testing.ts` отказывается работать с базой, имя которой не оканчивается на `_test` (локально — `scripts/pgtest.sh`, порт 5450). Для проведения обязателен конкурентный тест по образцу существующих (параллельные проведения, номера подряд, без ухода в минус).
- **Сид:** демо-данные этапа — в `packages/db/src/seed-*.ts`, чтобы экран был виден сразу после `db:seed`.
- **Номера миграций** в обоих планах условные (`0007…`): фактический номер — следующий свободный в `packages/db/drizzle/` на момент реализации.

### Этап 0. Фундамент: внутренние складские документы — пререквизит для производства и услуг

Расширить модель документов так, чтобы она выдерживала документы без контрагента и с несколькими направлениями движения. Без этого не сделать ни выпуск, ни заказ-наряд с материалами. Поведение сверено с 1С:УНФ вместе с пользователем 2026-10-21 (раздел «Уточнения этапов 0 и 1» в конце файла). Этап разбит на две задачи: **0а** (ядро) и **0б** (инвентаризация, перемещение «в пути», эксплуатация, печать).

#### Этап 0а. Ядро внутренних документов (M–L)

- **Shared:** в `DocumentTypeMeta` добавить `party: 'customer' | 'supplier' | null` (null — внутренний документ, контрагент не нужен) и группу `'stock'` (позже `'production'`). Направление движения задать функцией по строке, а не одним полем `stock`: `stockPlan(doc, lines) → MoveRequest[]`. Новые типы:
  - `stock_transfer` (ПМ) — перемещение между складами: расход со склада `warehouse_id` и приход на `target_warehouse_id` по средней склада-отправителя. Вид операции `documents.operation`: в 0а — `transfer` (одноэтапно); `in_transit` и `to_operation` / `from_operation` — в 0б;
  - `write_off` (СП) — списание (брак, порча, недостача, отходы): расход, **статья затрат обязательна**;
  - `stock_posting` (ОП) — оприходование (излишки, возвратные отходы): приход, статья доходов обязательна. Цена строки — себестоимость единицы прихода; по умолчанию подставляется **текущая средняя по (склад, товар)**, если её нет — цена последнего проведённого `receipt`; пользователь может править.

Сид: «Брак», «Порча», «Недостача», «Отходы», «Передача в эксплуатацию» (expense), «Излишки» (income). `documents.cost_item_id` — составной FK, CHECK вида статьи по типу документа — в сервисе. Проверка перехода — в сервисе, CHECK в БД только на формат ключа.
- **Роль строки:** `document_lines.stock_role text` — `in | out` (NULL у продаж и закупок: там направление задаёт `DOCUMENT_META.stock`). `stockPlan` строит движения так: у перемещения — `out` со склада шапки и `in` на `target_warehouse_id` по каждой строке; у выпуска (этап 2) — роль строки (продукция `in`, материалы `out`). #### Этап 0б. Инвентаризация, перемещение «в пути», эксплуатация, печать (M)

Зависит от 0а.

- **Инвентаризация как в УНФ:** `inventory_count` (ИНВ) **остатки не двигает**. Строки «учётное / фактическое / разница»: `document_lines.book_qty numeric(18,3)` заполняется кнопкой «Заполнить по остаткам» на дату документа (`GET /stock/count-sheet?warehouseId=&date=`) и пересчитывается по кнопке. Проведение фиксирует результат. На основании проведённой инвентаризации — «Создать списание» (строки с недостачей, статья «Недостача») и «Создать оприходование» (строки с излишком, статья «Излишки», цена по умолчанию — средняя). Количество в документах на основании ограничено разницей (`checkLimits` по `origin_line_id`, `over_fulfilment`); отменить проведение инвентаризации, по которой есть проведённые документы, нельзя. `inventory_count`: `isOrder: true` для этих двух типов-исполнителей.
- **Перемещение «в пути» — состояние одного документа:** `stock_transfer` с `operation = 'in_transit'` и состояниями `draft → shipped → received`. Проведение в `shipped`: расход с отправителя, приход на служебный склад вида `transit` (один на воркспейс, создаётся лениво). Переход в `received` (хук `onStateChange`): расход с `transit` и приход получателю по фактически принятому количеству (`document_lines.received_qty`, ≤ отправленного); расхождение остаётся на `transit` и оформляется списанием на основании (статья «Недостача»). Возврат из `received` в `shipped` отменяет вторую партию движений. `stock_moves` документа получают признак фазы (`phase smallint`), чтобы отмена шла по фазам.
- **Передача в эксплуатацию:** `stock_transfer` с `operation = 'to_operation'` — расход со склада, стоимость сразу на статью «Передача в эксплуатацию»; получатель — участник (`members`) или участок (`work_centers`). Количественный учёт «у кого» без стоимости: `in_use_balances (workspace_id, product_id, member_id?, work_center_id?, qty)` и движения `in_use_moves (document_id, document_line_id, …, qty)`, CHECK «ровно один получатель», `app_secure_tenant_table`. `operation = 'from_operation'` — возврат/списание из эксплуатации: уменьшает `in_use_balances` (без стоимости, без прихода на склад). Экран «В эксплуатации» — остатки по сотрудникам и участкам.
- **Печатные формы:** ИНВ-3 (инвентаризационная опись), ТОРГ-16 (акт о списании), ТОРГ-13 (накладная на внутреннее перемещение) — шаблоны в `packages/shared/src/print/templates.ts`, PDF через `document.pdf`.
- **Готово, когда:** инвентаризация с излишком и недостачей порождает списание и оприходование на разницу и не больше; перемещение «в пути» видно на складе `transit` до приёмки и корректно откатывается по фазам; переданное в эксплуатацию видно по сотруднику; три формы печатаются в PDF.
- **Тесты:** `apps/api/test/documents.test.ts` — инвентаризация и документы на основании, лимит по разнице, запрет отмены; «в пути»: частичная приёмка, откат `received → shipped`; эксплуатация: передача и возврат, RLS на новых таблицах; печать — снимок данных формы.

### Этап 1. Развёртка спецификации и потребность на количество (S)

- **Режим полуфабриката — настройка строки BOM** (решение 3): `bom_lines.semi_mode text` — `stock` (полуфабрикат выпускается отдельно и списывается со склада) или `explode` («фантом»: разворачивается до материалов в том же выпуске). Отдельная миграция `bom_semi_mode` (номер — следующий свободный; если этап 0а сливается раньше или позже — перегенерировать при слиянии). Переключатель в `line-dialog.tsx`.
- **Shared, `packages/shared/src/bom.ts`:** чистая функция `explodeBom(items, rootId, qty)` — материалы с учётом `scrap_pct`, работы (часы на количество по участкам), полуфабрикаты по `semi_mode` строки: `stock` — строка полуфабриката на списание, `explode` — его материалы и работы рекурсивно. Количество **пропорционально** `qty / batch_qty` (как в УНФ: спецификация задаёт норму на партию, а не кратность выпуска; округления до целых партий нет). Округление количеств — 3 знака. Цикл — `BomCycleError`.
- **Потребность с учётом остатков** — чистая функция `computeNeeds(explosion, availability)`: по каждому товару нужно / доступно / дефицит. Для полуфабриката в режиме `stock` **недостающая часть разворачивается дальше**: дефицит ПФ = нужно − доступно, и на этот дефицит считаются его материалы и работы (строка «выпустить ПФ × N»). Один и тот же товар на разных уровнях агрегируется до сравнения с остатком (расчёт по уровням: сначала верхний уровень, потом дети на дефицит), чтобы доступное не засчитывалось дважды.
- **API:** `GET /manufactured-items/:id/explode?qty=&warehouseId=` — развёртка плюс остатки и доступное (`available` из `stock_balances` минус `stock_reservations`; без `warehouseId` — по всем складам) по каждому материалу, дефицит и строки «выпустить ПФ». Стоимостные поля — только admin/owner.

Этот шаг `docs/architecture.md` уже называет следующим («производственные заказы со списанием материалов и выпуском продукции на склад»). Делать после этапов 0–1.

- **Типы документов** (группа `production`, `party: null`, контрагент необязателен — для заказа под клиента его можно указать):
  - `production_order` (ЗП) — заказ на производство: что, сколько, к сроку (`due_date`), склад материалов (`warehouse_id`) и склад продукции (`target_warehouse_id` из этапа 0), основание — `customer_order` (необязательно). Движений склада нет. Проведение резервирует материалы (этап 3).
  - `production` (ПР) — выпуск (в 1С — документ «Производство»): на основании заказа на производство, **заказа покупателя напрямую** (как в УНФ, без промежуточного заказа на производство) или самостоятельно. Списывает материалы и полуфабрикаты, приходует продукцию. Шапка: дата, участок-изготовитель (`work_center_id`), этап (`stage_id`, до этапа 4б — всегда предопределённый «Завершение производства»).
- **Способ пополнения и спецификация по умолчанию:** `products.replenishment text not null default 'purchase'` — `purchase | production`; `products.default_item_id` → `manufactured_items` (спецификация по умолчанию, если у товара их несколько). Заказ покупателя «производится», если у строки товар с `replenishment = 'production'` и есть спецификация.
- **Автоперемещение — у участка** (решение по справке 1С): `work_centers.warehouse_id` из этапа 0а — «списывать из»; добавить `output_warehouse_id` («продукция в») и `waste_warehouse_id` («отходы в»), составные FK на `warehouses`. Выпуск подставляет склады шапки и строк из участка; пользователь может поменять в документе.
- **Шапка заказа на производство** (по форме 1С, задача 1084): состояние, **старт и финиш** (`planned_start` / `planned_end timestamptz` вместо одного `due_date`), вид операции `documents.operation = 'assembly'` (разборка — позже, отдельной задачей), изготовитель — участок (`work_center_id`), необязательные основания — заказ покупателя и **родительский заказ на производство** (`parent_document_id`). Вкладки: «Продукция», «Материалы», «Операции».
- **Дочерние заказы на полуфабрикаты:** кнопка «Создать заказы на полуфабрикаты» — по дефициту ПФ из `computeNeeds` (этап 1) создаёт черновики `production_order` с `parent_document_id`. Выпуск дочернего заказа резервирует полуфабрикат под родительский заказ.
- **Автоматический резерв продукции под заказ покупателя:** выпуск, связанный с заказом покупателя напрямую или через заказ на производство с основанием `customer_order`, при проведении резервирует выпущенную продукцию за этим заказом (`stock_reservations` по строке заказа покупателя, не больше остатка к отгрузке). Выпуск без связи даёт свободный остаток. Отмена выпуска снимает такой резерв. В карточке заказа покупателя — колонки «Можно отгрузить / Обеспечено / Свободно для резерва».
- **Заказ покупателя в строке выпуска:** `production_order_items.customer_order_line_id` и у строки продукции выпуска — `origin_line_id` на строку заказа, поэтому один документ «Производство» (документ дня) может выполнять несколько заказов покупателей. В интерфейсе — колонка «Заказ покупателя» в табличной части (персональная настройка «в шапке / в табличной части» — позже).
- **Один документ за день на участок:** выпуск за ту же дату и участок дописывается в существующий документ `production` (как в УНФ). Если он проведён — отмена проведения, добавление строк и повторное проведение в одной транзакции под блокировкой документа (`SELECT … FOR UPDATE`); при нехватке материалов транзакция откатывается целиком, документ остаётся в прежнем виде. Номер документа не меняется.
- **БД, миграция `0008_production_orders.sql`:**
  - `production_order_items (workspace_id, document_id, sort_order, item_id → manufactured_items, qty, unit_code, planned_unit_cost numeric(18,4), customer_order_line_id → document_lines?)` — что выпускаем. Составные FK; `app_secure_tenant_table`.
  - `production_components (workspace_id, document_id, order_item_id?, kind: material|semi|work, product_id?, item_id?, work_center_id?, operation, qty, hours, rate, fixed_cost, planned_cost numeric(18,4), actual_qty, actual_cost numeric(18,4), sort_order)` — **снимок развёрнутой спецификации** (ограничение 8) у заказа и фактический расход у выпуска. CHECK формы строки по `kind`, как у `bom_lines`. `app_secure_tenant_table`.
  - Строки-товары выпуска (продукция на приход — `stock_role = 'in'`, материалы на расход — `'out'`) живут в `document_lines`, потому что `stock_moves.document_line_id` ссылается на строку документа. Работы и накладные — только в `production_components` (ограничение 5).
  - Остаток к выпуску по заказу считает обобщённый механизм из этапа 0: `production_order.isOrder = true`, `production.fulfils = true` (только строки `in`).
  - состояние заказа — общее поле `documents.state` из этапа 0 (для `production_order`: `planned | in_progress | done | closed`).
- **Сервис `packages/db/src/production.ts` (новый, по образцу `documents.ts`):**
  - `fillFromBom(orderId)` — снимок развёртки (`explodeBom`) в `production_components` с плановой стоимостью (`computeBomCost`, источник цены — `materialPriceSource`);
  - `createBasedOn(production_order → production)` — копирует продукцию и материалы с учётом остатка к выпуску (тот же приём, что `origin_line_id` и `checkLimits` для заказов покупателя: выпущено не больше заказанного, `over_fulfilment`);
  - проведение выпуска: (1) расход материалов `applyStockMoves` → фактическая стоимость каждой строки из `stock_moves.cost`; (2) себестоимость партии = Σ материалов + работы (`hours × rate` или ставка участка, `fixed_cost`) + накладные (`overhead_pct` продукции от прямых затрат, правило `computeBomCost`); (3) приход продукции по цене «себестоимость партии / количество» (двухфазная запись из этапа 0). Продукция без `product_id` или с услугой — 422 `item_not_stockable`;
  - отмена проведения выпуска — `revertStockMoves`; запрещена, если продукцию уже отгрузили или списали (`stock_conflict`).
- **Shared:** `PRODUCTION_STATES`, схемы `productionOrderCreate` / `productionComponentUpdate` в `packages/shared/src/schemas/production.ts`; чистая функция `computeProductionCost(components, overheadPct)` рядом с `computeBomCost` (план и факт одной функцией).
- **API:** `/production-orders` (журнал с фильтром `state`, `dueFrom` / `dueTo`, карточка с продукцией, компонентами, выпущено / осталось), `POST /production-orders/:id/fill-from-bom`, `POST /production-orders/:id/state { state }`, `POST /documents/:id/based-on { type: 'production_order' }` из заказа покупателя (строки, у которых товар связан с продукцией). Префикс `/production-orders` — в `TENANT_PATHS`. События `document.*` с `documentType`, плюс `production_order.state_changed`.
- **Web:** `/production/orders` — журнал заказов (`DataTable`, фильтр по состоянию, просрочка подсвечена); карточка заказа — продукция, вкладки «Materials» и «Work» (снимок, правится до проведения), «Outputs» (выпуски по заказу), кнопки **Fill from BOM / Create production / State**; форма выпуска — план против факта по каждому материалу. Пункты в `routes.ts` / сайдбаре (группа Production).
- **Печать:** «Задание на производство» и «Отчёт о выпуске» (шаблоны `print/templates.ts`, PDF через `document.pdf`).
- **Автоматизации:** в `BUILTIN_FIELDS.document` добавить `dueDate`, `type` (`state` — с этапа 0). Демо-flow «Production order done → notify the order responsible».
- **Готово, когда:** сквозные сценарии «заказ покупателя → заказ на производство → выпуск → реализация» и «заказ покупателя → выпуск → реализация» проходят; второй выпуск за ту же дату и участок попадает в тот же документ. Приход продукции оценён ровно в «материалы по средней + работы + накладные». Отмена выпуска возвращает остатки и среднюю. Выпустить больше заказанного нельзя. В демо-сиде есть заказ и выпуск.
- **Тесты:** `apps/api/test/production.test.ts` — себестоимость выпуска с полуфабрикатом и отходом; отмена; `item_not_stockable`; `insufficient_stock` по материалу без записи; два параллельных выпуска при остатке материала на один — проходит один. `packages/shared/test/bom.test.ts` — `computeProductionCost` план = факт при нормативном расходе.
- **Права на себестоимость** (решение 8): плановую и фактическую себестоимость видят только admin и owner. API не отдаёт поля стоимости (`planned_cost`, `actual_cost`, `stock_moves.cost`, `/manufactured-items/:id/cost`, `/stock/avg-costs`) ролям member и guest, интерфейс скрывает колонки. Это меняет и текущее поведение: сейчас себестоимость единицы видят все. Общая функция маскирования — в `packages/db` рядом с проверкой роли, тест на каждую роль.

### Этап 2а. Рабочее место «Выпуск продукции» (M–L)

**Фактическая реализация (2026-10-21, задача #1102, ветка `feat/unf-stage-2a`).** Отклонения от плана: (1) **таблиц и миграций нет** — этап 2а
не добавляет данных: он работает поверх заказов на производство, заказов покупателя и выпусков этапа 2, поэтому следующий свободный номер миграции
не занят; (2) **этап выпуска — константа, а не справочник**: пока один этап «Завершение производства» (`PRODUCTION_STAGES` в `shared`), виды производства
и этапы приходят в этапе 4б — тогда в рабочем месте появятся колонки этапов и остаток по этапу; (3) **исполнитель не сделан** (этап 4в) — в заказе
этапа 2а он не нужен; (4) **выпуск создаётся и сразу проводится** — от отдельного документа «Производство» пользователь не отвлекается: остаток

было бы пустым после `db:seed` (из-за этого в `packages/db/test/db.test.ts` поправлены счётчики демо-документов: 16 → 17 и резервов 1 → 2).

### Этап 3. Резервы и обеспечение заказов материалами (M)

- **БД, миграция `0009_reservations.sql`:** обобщить `stock_reservations` — сейчас уникальный ключ стоит на `document_line_id` строки заказа покупателя. Добавить `production_component_id` (составной FK), CHECK «ровно одно из двух»; уникальность — по каждому из полей.
- **Сервис:** `syncReservations` считает резерв материалов проведённого заказа на производство = нужно − списано выпусками. Продукция, выпущенная по заказу с основанием `customer_order`, уже покрыта резервом заказа покупателя (фича 1.5): резерв там количественный, связи с конкретным выпуском не нужно.
- **Shared/API:** `GET /production/needs?from=&to=` — сводная потребность по проведённым незакрытым заказам: нужно, в резерве, доступно, в пути (непроведённые `receipt` и проведённые `supplier_order` с остатком к поступлению), дефицит. `POST /production/needs/supplier-orders { lines, supplierId }` — черновики `supplier_order` по дефициту, сгруппированные по поставщику (решение 4): `products.default_supplier_id` (составной FK на `companies`), а если он пуст — поставщик последнего проведённого `receipt` по товару. Строки без поставщика показываются отдельной группой, заказ по ним не создаётся. Поле поставщика — в карточке товара каталога.
- **Web:** экран **Needs** (`/production/needs`) — таблица дефицита с выбором строк и «Create supplier orders».
- **Готово, когда:** резерв материалов появляется при проведении заказа и уменьшается выпуском; дефицит учитывает резервы других заказов; черновики заказов поставщикам создаются с количеством дефицита.
- **Тесты:** `apps/api/test/production.test.ts`, `documents.test.ts` (резерв заказа покупателя не сломан).

- **Решения пользователя по справке 1С «Заказ на производство» (2026-10-22, задача TaskFlow 1085)** — имеют приоритет над пунктами выше:
  - **Резерв материалов — автоматически с ручной правкой:** при проведении заказа на производство резервируется столько, сколько есть свободного (не больше «нужно − списано выпусками»); в строке материала — колонки «В резерв» и «Склад (резерв)», пользователь может уменьшить, увеличить в пределах свободного или перенести на другой склад. Выпуск снимает резерв на списанное количество; отмена проведения заказа снимает весь резерв.
  - **Резерв всегда под заказ на производство** (строка материала заказа), а не под заказ покупателя; связь с заказом покупателя — через основание заказа (отчёты показывают цепочку). Поле «заказ покупателя по строке» не делаем.
  - **Режим «Показать остатки» в заказе на производство:** колонки материалов — Зарезервировано (всего), Размещено (заказано заказами поставщикам и дочерними заказами на производство по этому заказу), Не обеспечено, Свободно (всего), Свободно для резерва (на складе резерва), К поступлению (свободные заказы поставщикам и непроведённые поступления) и дата поступления; цветовая индикация «Обеспечено» (зелёный полностью / оранжевый частично / красный нет); расшифровки — резервы по складам, размещение по документам, к поступлению по документам.
  - **Заказы поставщику под заказ (размещение):** строка заказа поставщику может быть привязана к заказу на производство (`supplier_order` с основанием `production_order` или ссылка строки на строку материала); при проведении поступления по такому заказу поставщику товар сразу резервируется под заказ на производство. Привязанное количество — «Размещено» и уменьшает «Не обеспечено».
  - **Дочерние заказы на полуфабрикаты:** кнопка «Create semi-finished orders» по дефициту ПФ (`computeNeeds`, этап 1) создаёт черновики `production_order` с `parent_document_id`; их количество — «Размещено»; выпуск дочернего заказа резервирует полуфабрикат под родительский заказ.
  - **Экран потребностей** `/production/needs` — как в пункте выше (сводный дефицит, создание заказов поставщикам по поставщику товара).
  - **Разборка — позже**, отдельной задачей.

**Фактическая реализация этапа 3 (2026-10-22, задача TaskFlow #1085, ветка `feat/unf-stage-3`).**

Модель данных (миграция `0019_production_materials.sql`; агент создал её как `0018`, при слиянии перенумерована — 0017 и 0018 заняли этапы 5 и 8 услуг):

`production_components.source_component_id` (строка состава выпуска → строка состава заказа: по ней снимается резерв), новая таблица `production_placements`
(размещение: строка материала заказа ↔ строка заказа поставщику или дочерний заказ), `products.default_supplier_id` (составной FK на `companies`).
Составной FK резервов на `production_components` добавлен в SQL вручную: `schema/documents.ts` не может ссылаться на `schema/production.ts` — схема документов зациклилась бы.
Бэкфилл миграции: у уже проведённых заказов на производство резерв материалов создаётся по свободному остатку на складе материалов.
Сервисы: `packages/db/src/materials.ts` (резерв, размещение, покрытие строки, резервирование поступления и выпуска дочернего заказа) и `packages/db/src/needs.ts`
(сводная потребность, черновики заказов поставщикам). Чистая функция `materialCoverage` — `packages/shared/src/supply.ts` (тесты — `packages/shared/test/supply.test.ts`).
API: `GET /production-orders/:id/materials` (покрытие и расшифровки), `PATCH /production-orders/:id/materials/:componentId/reservation` (правка резерва),
`POST /production-orders/:id/semi-orders` (дочерние заказы на ПФ), `POST /production-orders/:id/supplier-orders` (заказы поставщику = размещение),
`GET /production/needs`, `POST /production/needs/supplier-orders`. Интерфейс: переключатель **Show stock** в карточке заказа (колонки обеспечения с цветом и расшифровками),
правка **To reserve** / **Reserve warehouse**, кнопки **Create semi-finished orders** и **Create supplier orders**, экран **Needs** (`/production/needs`),
поле **Default supplier** в карточке товара. Демо-сид: партия стульев сверх остатка (частичный резерв) и заказ поставщику с размещением; числа сида поправлены в `packages/db/test/db.test.ts`.
Тесты: `apps/api/test/production-materials.test.ts` (16) и `packages/shared/test/supply.test.ts` (8). Оценка: M → **L** (фактически ≈3 рабочих дня).

Отклонения от плана и решения:
1. **Размещение привязано к заказу поставщику, созданному на основании заказа на производство** (`based_on_id` + запись `production_placements`), а не ссылкой строки в общем справочнике документов:
   привязка к строке материала в `document_lines` зациклила бы схему документов на производственные таблицы, а «на основании» совпадает с механизмом 1С и с готовым
   `based-on` — поступление по такому заказу наследует связь через `source_line_id`, и товар резервируется под заказ при проведении поступления.
2. **Резерв строки держится на одном складе** (увеличение — в пределах свободного остатка этого склада, иначе 422 `insufficient_free`); поступление по привязанному заказу
   добавляет резерв на складе поступления, если он другой, — тогда резерв раздваивается, и следующая ручная правка соберёт его на одном складе.
3. **«Закрытие заказа — остаток резерва»** прочитано как «закрытие снимает остаток резерва» (по аналогии с «отмена проведения — весь резерв»).
4. **«Не обеспечено» в карточке заказа = нужно − резерв − размещено** (свободный остаток не вычитается — как в 1С), а **дефицит на экране потребностей** считается с учётом
   свободного остатка (нужно − резерв − размещено − свободно): на экране решается, что закупать.
5. **Резерв снимается списанным, а не «нужно − списано»**: списанное выпуском уменьшает и резерв, и остаток потребности (обе величины живут в одной строке состава).
6. **К поступлению** считается по свободным заказам поставщикам (не привязанным к этому заказу) — черновики и проведённые; дата поступления — по документу.
7. Демо-данные этапа 3 добавлены в сид (частичный резерв + заказ поставщику с размещением); числа в `packages/db/test/db.test.ts` поправлены.

**Исправления при проверке этапа 3 (основной агент, 2026-10-22):** (1) «К поступлению» исключало только свои строки заказов поставщикам — заказ, размещённый под другой заказ на производство, считался свободным поступлением; теперь в «К поступлению» только строки, не привязанные ни к одному заказу; (2) на экране Needs «к поступлению» складывалось по каждому заказу, где нужен материал (два заказа — двойное поступление); теперь берётся один раз на товар; (3) отрицательный свободный остаток (заказы покупателей зарезервировали больше, чем есть) увеличивал дефицит и количество дочерних заказов на ПФ; теперь свободно не меньше нуля; (4) отмена проведения поступления по привязанному заказу поставщику оставляла резерв под несуществующий товар; теперь резерв снимается; (5) заполнение резерва уже проведённых заказов в миграции давало каждому заказу одно и то же свободное количество (сумма резервов больше остатка) и резервировало под закрытые заказы; теперь свободное распределяется по очереди (дата, id), закрытые и выполненные заказы пропускаются (проверено на тестовой базе в откатываемой транзакции). Тесты — `apps/api/test/production-materials.test.ts` (+4; хелпер `setup` допускает нулевой остаток). Ограничение: при заполнении резерва списанное прежними выпусками не вычитается — связи выпуска со строкой состава заказа до этапа 3 не было.

### Этап 4. Модуль задач, поэтапное производство, сдельный наряд, планировщик

Переписано по справке 1С:УНФ (задача TaskFlow 1086): этапы в УНФ — это не задачи с датами, а **справочник видов производства** с упорядоченным списком этапов; строки спецификации привязаны к этапу; выполнение этапа отмечается в рабочем месте «Выпуск продукции» и порождает документ «Производство» этапа и «Сдельный наряд» по операциям. Решение пользователя: операции с исполнителем остаются **задачами модуля production** (решение 2) и дополнительно оформляются **сдельным нарядом**.

#### Этап 4а. Модуль у задач (S–M; общий с планом услуг)

- **БД, миграция `task_modules`:** `tasks.module text not null default 'general'` с CHECK `general | production | services`; индекс `(workspace_id, module)`. Существующие задачи — `general`. `projects.module` с тем же набором: на каждый модуль воркспейса — системный проект (`Production`, `Services`), создаётся лениво. Задача модуля обязана лежать в проекте того же модуля (проверка в сервисе), потому что `tasks.project_id NOT NULL`.
- Списки задач, «Мои задачи», доски и сохранённые виды получают фильтр по модулю; в обычных проектах по умолчанию видны только `general`. `module` — в схемах задач и в `BUILTIN_FIELDS.task`.
- **Готово, когда:** задачи модуля не видны в обычных проектах и видны в «Моих задачах»; существующие задачи не пропали. **Обновить `architecture.md`:** раздел задач.

**Фактическая реализация этапа 4а (2026-10-21, задача #1083, ветка `feat/unf-stage-4a`).** Миграция `0010_task_modules.sql`: `tasks.module` и `projects.module` (`general | production | services`, CHECK, индексы, частичный уникальный индекс `(workspace_id, module) WHERE module <> 'general'`), системные проекты модулей для существующих воркспейсов. Оценка: S.

#### Этап 4б. Виды производства и поэтапный выпуск (L)

- **Настройка** воркспейса «Производство в несколько этапов» и «Этапы могут выполняться разными участками» (`production_settings`).
- **БД:** `production_kinds (workspace_id, name, comment)` и `production_stages (workspace_id, kind_id, sort_order, name, is_final)` — ровно один `is_final` на вид («Завершение производства», предопределённый, всегда последний, нельзя удалить). `app_secure_tenant_table`. `manufactured_items.production_kind_id` (необязательно: без вида — единственный этап «Завершение производства»). `bom_lines.stage_id` — этап, на котором расходуется материал или выполняется операция (CHECK в сервисе: этап того же вида, что у спецификации). Снимок заказа (`production_components`) копирует `stage_id`.
- **Выпуск этапа:** документ `production` с `stage_id` списывает материалы и учитывает работы только этого этапа. Продукция приходуется **только** документом финального этапа. Остаток к выполнению — по паре (строка заказа, этап): «Осталось N шт» на каждом этапе; этап нельзя выполнить больше, чем выполнен предыдущий (проверка `stage_order`). Стоимость списанного на промежуточных этапах накапливается как незавершённое производство по строке заказа (`production_wip (order_line_id, stage_id, qty, cost)`) и переходит в себестоимость продукции на финальном этапе.
- **Разные участки по этапам:** при включённой настройке участок выбирается на каждый этап (строка рабочего места), иначе один на продукцию.
- **Рабочее место (2а):** колонки этапов вида производства с переключателями и «Осталось», фильтр «Продукция с этапами» и «Вид производства».
- **Web:** справочник «Этапы» (Production → Справочники → Этапы: вид производства и список этапов с порядком), поле «Вид производства» в карточке спецификации и колонка «Этап» в строках состава и операций (`ItemPage.tsx`, `line-dialog.tsx`).
- **Готово, когда:** спецификация «Распил → Сборка → Завершение» выпускается в три дня на разных участках; материалы каждого этапа списаны своим документом; продукция пришла на склад только на финальном этапе по полной себестоимости; нельзя выполнить «Сборку» больше, чем «Распил».
- **Тесты:** API — порядок этапов, остаток по этапу, НЗП и итоговая себестоимость, отмена промежуточного этапа при выполненном следующем запрещена (`stock_conflict`/`stage_conflict`).

**Фактическая реализация (2026-10-22, задача #1086, ветка `feat/unf-stage-4b`).** Справочник «Этапы» — новые арендаторские таблицы
`production_kinds` и `production_stages` (последний этап вида — финальный, он один); вид производства у изделия (`manufactured_items.production_kind_id`),
этап у строки спецификации (`bom_lines.stage_id`), этап выпуска в шапке (`production_headers.stage_id`), этап в позиции и снимке состава
(`production_items.stage_id`, `production_components.stage_id`), фактическая себестоимость этапа в позиции (`production_items.stage_cost`).
Миграция `0012_production_stages.sql` (следующий свободный номер). Сервис справочника — новый файл `packages/db/src/production-stages.ts`.
Отклонения от плана:
(1) **отдельной таблицы `production_wip` нет** — НЗП считается как фактическая себестоимость этапа в позиции выпуска, а стоимость прихода
на финальном этапе = затраты своего этапа + средняя стоимость единицы выполненных промежуточных этапов; при равных количествах по этапам
сумма списанного равна стоимости прихода (проверено тестом), а при разных — работает оценка НЗП по средней, как в УНФ;
(2) **этап живёт в шапке выпуска**, а не в отдельной таблице «выполнение этапа»: документ дня теперь на участок, дату и этап — выпуски разных
этапов одного дня идут в разные документы;
(3) **промежуточный этап не создаёт строку продукции** в документе (приход только финальным этапом), поэтому склад продукции ему не нужен;
(4) **накладные начисляются на прямые затраты своего этапа** — по сумме это то же, что накладные на весь выпуск, и сходится с приходом;
(5) **порядок этапов проверяется дважды** — при планировании выпуска и при проведении документа (`stage_order`);
(6) **запрет отмены промежуточного этапа** сделан новым хуком типа документа `beforeUnpost` (в общем коде проведения хуков раньше не было) —
код ошибки `stage_conflict`;
(7) **настройки воркспейса** «производство в несколько этапов» и «этапы могут выполняться разными участками» не делались: этапы включаются
самим фактом наличия вида производства, а участок и так выбирается на строку рабочего места;
(8) **колонки этапов в рабочем месте** — объединение этапов всех строк таблицы (у строк без вида производства — предопределённый
«Completion of production»);
(9) **вид производства не удаляется, а архивируется** (его использует изделие), этап не удаляется, если он есть в спецификации или выпуске;
(10) **сид**: вид «Мебельное производство» с этапами «Распил → Сборка → Завершение производства», изделие «Стол письменный "Офис"» с этапами
у строк спецификации и заказ на производство на него — в рабочем месте видны колонки этапов.
Тесты: `apps/api/test/production-stages.test.ts` (15) — справочник, этап в строке спецификации, порядок этапов, выпуск по этапам с проверкой
затрат и прихода, запрет отмены промежуточного этапа, выполнение из рабочего места. Оценка: L (фактически ≈2,5 рабочих дня).

#### Этап 4в. Операции: задачи исполнителей и сдельный наряд (M–L)

Решения пользователя (интервью 2026-10-21, задача TaskFlow 1103):

- **Операция — вид номенклатуры** (как в УНФ): `products.kind = 'operation'` рядом с `goods` и `service`. Поля: норма времени на единицу (`norm_hours`), участок по умолчанию (`work_center_id`), единица. Операция не продаётся и не двигает склад (как услуга в проведении). Строка работ спецификации (`bom_lines.kind = 'work'`) получает `product_id` → операция; текстовое `operation`, `hours`, `rate`, `fixed_cost` остаются как переопределение в строке (по умолчанию берутся из операции). Миграция переносит существующие текстовые работы как есть (без операции).
- **Расценка на дату:** история расценок `operation_rates (workspace_id, product_id, valid_from date, rate numeric(18,2), unit: per_unit|per_hour)`; в наряд подставляется расценка, действующая на дату наряда, сумма в строке фиксируется и правится вручную до проведения. Настройка «Способ расчёта стоимости операций» — `fixed` (расценка за единицу) или `by_norm` (норма времени × ставка участка), по умолчанию `fixed`.
- **Исполнители — только сотрудники** (участники воркспейса, в том числе без аккаунта). Бригады — позже отдельной задачей.
- **Задачи создаются при назначении исполнителя:** в заказе на производство у операции выбирают исполнителя и количество → у него появляется задача модуля production (`production_operations`: `task_id`, заказ, компонент, этап, участок, `planned_qty`, `planned_hours`), сроки — из старта/финиша заказа. Без исполнителя задачи нет. **Одну операцию можно разделить между несколькими исполнителями по количеству** — у каждого своя задача; сумма назначенного ≤ количества операции.
- **Частичное выполнение:** по каждой задаче и по операции в целом — «выполнено / осталось N». Задача закрывается, когда выполнено всё назначенное.
- **Выполнение отмечают оба способа, в один наряд исполнителя за день:**
  - мастер в рабочем месте «Выпуск продукции» (этап 2а/4б) отмечает этап → создаётся выпуск и строки сдельных нарядов исполнителей;
  - исполнитель в своей задаче отмечает выполненное количество → строка дописывается в его черновик наряда за день; мастер проверяет и проводит.
- **Сдельный наряд** — тип документа `piecework_order` (СН), `party: null`: исполнитель (участник), дата, строки — операция, продукция, заказ на производство / выпуск, количество, расценка, сумма. Один документ на (исполнитель, дата), как выпуск на (участок, дата). Проведение: (1) фиксирует выполненное количество по задачам-операциям и закрывает выполненные; (2) сумма нарядов по выпуску — **фактическая стоимость работ в себестоимости продукции** (вместо оценки `hours × rate`; если наряд проведён после выпуска — пересчёт себестоимости выпуска, до этапа 6 — в той же транзакции, если выпуск ещё не отгружен, иначе корректировка в закрытии периода); (3) данные для отчёта «Выработка и к оплате по исполнителям за период». Начисление зарплаты — вне объёма.
- **Отчёты:** «Выработка сотрудников» (исполнитель, операция, количество, сумма за период) и «Выполнение операций по заказу» (кто, что, когда, сколько осталось).
- **Права:** назначать и проводить наряды — member+ (мастер); исполнитель видит свои задачи и свои наряды; суммы и расценки видят admin/owner и сам исполнитель — только свои.
- **Печать:** «Сдельный наряд».
- **Готово, когда:** операция из каталога в спецификации; назначение двух исполнителей по 5 из 10 создаёт две задачи; исполнитель отмечает 3 — строка в его наряде за день, осталось 2; мастер в рабочем месте отмечает остаток — строки в нарядах; проведение наряда закрывает задачи; стоимость работ выпуска = сумма нарядов; расценка берётся на дату наряда; отчёт выработки сходится с нарядами.
- **Тесты:** API — сумма назначений ≤ количества, частичное выполнение, слияние в наряд дня, расценка на дату, пересчёт себестоимости выпуска после проведения наряда, видимость сумм по ролям.

**Фактическая реализация (2026-10-22, задача #1103, ветка `feat/unf-stage-4v`).** Операция — **вид номенклатуры**
(`products.kind = 'operation'`): новая таблица `operations` (норма времени на единицу и участок по умолчанию) и `operation_rates`
(история расценок с датой начала действия; способ расчёта — `per_unit` или `per_hour`). Строка работ спецификации может
ссылаться на операцию (`bom_lines.product_id` для `kind = 'work'`), текстовые работы работают как раньше — оценка `hours × rate`
остаётся, пока по выпуску нет проведённых нарядов. Назначение операции исполнителю — новая таблица `production_operations`

Сдельный наряд — новый тип документа `piecework_order` (СН) группы production: свои строки `piecework_lines` (план и факт,

#### Решения пользователя по справке 1С:ERP «Планирование производства» (2026-10-22, задача TaskFlow 1089)

В УНФ планирования производства нет — модель взята из 1С:ERP 2.5 (раздел 2.10) в упрощённом виде. Этот блок важнее остального текста этапа.

1. **Периоды в колонках.** План — на диапазон дат с шагом «неделя» или «месяц» (выбирается в плане; дня и квартала нет). Ячейка «изделие × период» — сколько выпустить к началу периода. Хранить строку на (изделие, период) с датой выпуска = начало периода.
2. **Разрез плана:** склад готовой продукции (обязателен) и участок-диспетчер (необязателен); несколько планов на один период допустимы. Состояния: черновик → утверждён (заказы создаются только по утверждённым).
3. **Заполнение**, кроме ручного ввода: по статистике выпуска (среднее выпущенного проведёнными `production` за прошлые N периодов), по статистике продаж (среднее по проведённым реализациям за N периодов), по заказам покупателей (неотгруженный и не покрытый производством остаток открытых заказов — в период по сроку отгрузки). Импорт из таблицы не нужен. Заполнение заменяет или добавляет строки (выбор в диалоге).
4. **Полуфабрикаты — кнопкой, строками** («Plan semi-finished»): для ПФ с `semi_mode = stock` добавляются строки пропорционально продукции, со сдвигом периода на срок изготовления; одинаковые ПФ суммируются; строки ПФ помечены и правятся вручную. После правки продукции — предупреждение «перепланировать полуфабрикаты»; «Remove semi-finished» удаляет только строки ПФ.
5. **Дата запуска:** новое поле спецификации «дней на изготовление» (`manufactured_items.lead_days`, рабочие дни, по умолчанию 0). Запуск = выпуск − lead_days по рабочему календарю воркспейса (4г). Показывается в плане, переносится в старт заказа на производство.
6. **Потребности плана:**
   - вкладки в плане — материалы, полуфабрикаты (потребление / выпуск / излишек-дефицит), часы участков и ресурсов против мощности по календарям 4г (нехватка подсвечена), трудозатраты; считаются развёрткой `explodeBom` по периодам;
   - **экран Needs:** материалы утверждённых планов в части, ещё не переданной в заказы на производство, добавляются к потребности `/production/needs` (отдельный источник «Plan») и участвуют в создании заказов поставщикам;
   - **план-факт:** по изделиям и периодам — запланировано / заказано (заказы на производство по плану) / выпущено (проведённые `production`).
7. **Заказы на производство по плану — рабочее место по периодам:** выбор периода и строк утверждённых планов → черновики `production_order` на остаток «план − уже заказано по этой строке», финиш = дата выпуска, старт = дата запуска; повторный запуск не дублирует (связь заказа со строкой плана).
8. Не делать: виды плана «ремонт / разборка», стратегии вероятности материалов, формулы в нормах, подбор спецификации по периоду действия (версий спецификаций нет), фоновый расчёт потребностей (считаются запросом).

#### Решения пользователя по справке 1С:УНФ «Расчёт потребностей в запасах» (2026-10-22, задача TaskFlow 1089)

Пополнение по мин./макс. строится по обработке УНФ «Расчёт потребностей в запасах» (справка 5.13 и статья ИТС metod81 #8263); прогноз остатка — по ERP «Планирование остатков». Этот блок важнее пунктов «Shared/API/Web/Пополнение» этапа выше.

1. **Один общий экран** «Расчёт потребностей»: `/production/needs` этапа 3 расширяется до общего расчёта (товары, материалы, продукция), три шага: Recommendations → Planning → Orders. Открывается из Purchases, Stock и Production (настройки — свои по разделу, хранятся у пользователя). Старый сводный дефицит заказов на производство — частный случай «по заказам»; существующие маршруты и тесты этапа 3 не ломать.
2. **Нормы запаса** — `stock_levels`: строки по складу и необязательная строка без склада (норма по компании; частичные уникальные индексы). Колонки: min, max, способ пополнения (`purchase | production | transfer`, по умолчанию — из `product_manufacturing.replenishment`), склад-источник для transfer. Вкладка «Stock levels» в карточке товара. Расчёт — по складам или по компании в целом (переключатель).
3. **Методики:**
   - *по заказам + мин./макс.* — прогноз остатка по периодам (шаг день/неделя/месяц, число периодов, дата начала): текущий остаток + ожидаемые поступления (заказы поставщикам, заказы на производство, утверждённые планы производства — продукция) − потребление (заказы покупателей, материалы заказов на производство и утверждённых планов); резервы учитываются, без двойного счёта с заказами. Правило: остаток ≤ min → до max; при отгрузках — так, чтобы после них остался max (пример: min 10, max 20, заказы 5, остаток 2 → 25). Колонка «Overdue» — поступления/потребления с прошедшей датой и (max − остаток) при остаток ≤ min. Детализация до документов-источников;
   - *по продажам: min-max* — только текущий остаток против min/max;
   - *по статистике продаж* — средние продажи (проведённые реализации) за выбранное число прошлых периодов × срок поставки + страховой запас (по дням: доп. дни × средние продажи, или по % от плановой потребности, % может быть отрицательным); округление до 0,001.
   Методики пользователя (расширения) не делать.
4. **Срок поставки** — новое поле товара `products.lead_days` (дней поставки, для закупки); для продукции — `manufactured_items.lead_days` (решение 5 блока плана производства). Дата поступления в заказе = дата дефицита (или сегодня + срок, если позже).
5. **Шаг «Planning»:** отмеченные строки, «Fill by deficit» (Order = дефицит), ручная правка. Способ пополнения, источник (поставщик / участок / склад-источник), дата поступления, цена. Поставщик по умолчанию — `default_supplier_id`, можно выбрать другого из тех, у кого покупали, со сравнением цены и даты последнего поступления; цена в заказ — последняя цена этого поставщика. Нового справочника цен поставщиков не вводить.
6. **Шаг «Orders»:** purchase → черновик `supplier_order`; production → черновик `production_order` (старт = поступление − lead_days); transfer → черновик существующего документа перемещения со склада-источника (нового типа «заказ на перемещение» не вводить). Группировка: один заказ на (способ, поставщик/участок/склад-источник, дата поступления); переключатели «одной датой» и «отдельно под каждый заказ покупателя». Список созданных черновиков с массовым проведением.
7. Ежедневной задачи воркера и уведомлений нет (решение 5) — расчёт по кнопке «Calculate».

Отклонения от плана и решения:
1. **Связь заказа со строкой плана — колонка `production_items.plan_line_id`**, а не отдельная таблица: по ней сразу
   считаются план-факт «заказано» и остаток для заказов по плану, повторный запуск не дублирует, а лишней сущности и
   синхронизации не появляется. Обратная связь (какие строки плана закрыты) не нужна — сумма по строке и есть ответ.
2. **Правило рекомендации по мин./макс. сформулировано явно** (`minMaxRecommendation`): если **по итогу периода**
   (поступления минус потребление) остаток не выше минимума — заказать максимум **плюс потребление периода** минус излишек
   остатка над минимумом; если потребления в периоде нет — обычный добор до максимума. Это даёт пример справки
   (мин 10, макс 20, отгрузки 5, остаток 2 → 25) и разумное поведение в остальных случаях; срабатывание проверяется
   по итогу периода, поэтому ожидаемое поступление того же периода дефицит не создаёт.
3. **Резерв показывается, но в прогноз остатка не вычитается**: иначе потребность заказа покупателя считалась бы дважды
   (резерв заказа + потребление заказа). Покрыто тестом.
4. **Строка без склада в `stock_levels` — норма по компании**, складная строка её перекрывает (две строки на один товар
   видны в расчёте как отдельные строки «товар × склад», как в 1С при учёте по складам). Это не «норма по компании
   при расчёте по компании» — при расчёте по компании строки по складам отбрасываются.
5. **Полуфабрикаты плана попадают в период по сдвинутой дате**: дата сдвигается на срок изготовления рабочими днями, затем
   приводится к ближайшему началу периода плана (иначе строка со сдвигом на неделю назад не попала бы ни в одну колонку).
6. **Режим «add» при заполнении суммирует** с уже заполненными по (изделие, период), а не добавляет дубли строками.
7. **Утверждённый план после создания заказов потребность не удваивает**: в расчёте потребностей утверждённые планы дают
   поступление/потребление только в части `план − уже заказано` по строке (`planOrderedQty`), а материалы плана — расходом
   в той же части. Это же делает повторный «Orders by plan» идемпотентным.
8. **Дата поступления в заказе** — дата потребности (период, где нужен заказ), без добавления срока поставки: срок поставки
   влияет на методику «по статистике продаж» (объём покрытия), а не на дату строки заказа. План этого не уточнял.
9. **Участок для заказа на производство по потребности** задаётся пользователем в шаге «Planning» (в плане — «источник:
   подразделение производства»): привязки товара к участку в модели нет, придумывать её не стали.
10. **Массовое проведение** — `POST /production/needs/post` перебирает черновики по одному и возвращает проведённые и
    непрошедшие: один непроходимый документ не отменяет остальные.
11. **Расчёт потребностей берёт все заказы поставщикам**, в том числе привязанные к заказам на производство (размещения):
    это единый список ожидаемых поступлений, иначе один и тот же заказ считался бы дважды в разных разрезах.
12. Изменения в общих файлах точечные: `schema/catalog.ts` (+`products.lead_days`), `schema/production.ts`, `production.ts`
    (+`planLineId`), `routes/production.ts` (три маршрута), `app.ts`, `routes.ts`, `router.tsx`, `Sidebar.tsx`,

строк нужен фоновый пересчёт — решение 5 его запрещает); потребности плана считаются развёрткой каждой строки (без

#### Исправления при проверке этапа 5 (2026-10-22)

- **Склады в расчёте потребностей.** Движения (заказы покупателей и поставщикам, заказы на производство, планы) не фильтровались по складу: в расчёте по складам каждая строка склада получала спрос всей компании, а в расчёте по компании нормы складов давали дубли рекомендаций. Теперь у движения есть склад (документа; у заказа на производство — продукции/материалов; у плана — склад плана и склад участка-диспетчера), по складам действуют нормы складов и движения своего склада, по компании — норма без склада и все движения. Тесты: спрос другого склада не учитывается; нормы складов не дают строк в расчёте по компании.
- **Средние продажи** делились на «периоды × 7» при любом шаге — при шаге «месяц» завышались в ~4 раза. Теперь история — N прошлых периодов до даты начала, дни — по календарю шага. Тест на месячный шаг.
- **Черновики закупки** группировались под общим ключом `auto` и уходили поставщику первой строки, а склад не передавался (товар приходил бы на склад по умолчанию). Теперь поставщик — у каждой строки (выбор на шаге Planning из истории поступлений с ценой и датой — решение 5 блока, агент его не сделал), склад-получатель — часть ключа группировки и склад заказа.
- **Норма «перемещение» без склада** проходила CHECK (сравнение с NULL); CHECK требует склад у нормы перемещения.
- Тест «a warehouse level wins over the company level» ожидал обе строки в расчёте по складам — поправлен под правило «по складам — нормы складов».
- **Средние продажи по складам** брали продажи всей компании — теперь по складу реализации (без склада — склад по умолчанию).
- **Дата черновика** бывала в прошлом (период Overdue): теперь не раньше «сегодня + срок» (поставки у закупки, изготовления у производства), как в решении 4 блока.
- **Правка строки на шаге Planning** (решение пользователя 2026-10-22): способ пополнения (закупка / производство / перемещение), дата поступления (не раньше «сегодня + срок»), источник — поставщик, участок или склад-источник. Перемещение без склада-получателя (строка по компании) пропускается с причиной `no_target_warehouse`.

### Этап 6. Фактическая себестоимость, косвенные затраты, брак и отходы (L, высокий риск)

- **Модель затрат:** `cost_items` уже заведён в этапе 0а; здесь он получает способ распределения (статьи: материалы, труд, энергия, обслуживание, амортизация, прочее; способ распределения: по прямым затратам, по часам работ, по количеству выпуска) и `period_costs (workspace_id, period date, cost_item_id, work_center_id?, amount numeric(18,2), source: manual|document)` — косвенные затраты периода. Источник (решение 10) — строки-услуги проведённых `receipt` со статьёй затрат: `document_lines.cost_item_id` (составной FK на `cost_items`), поле видно в форме поступления только у строк-услуг; `period_costs` заполняется при проведении поступления и очищается при отмене. Ручного ввода затрат на этом этапе нет.
- **Закрытие периода — задача воркера `production.close_period`** (очередь `jobs`, ставится из `POST /production/periods/:month/close`, admin+): (1) пересчёт средней по цепочке «поступление → выпуск → полуфабрикат → выпуск» в порядке `stock_moves.seq` (закрывает ограничение 7); (2) распределение косвенных затрат периода на выпуски по выбранной базе; (3) корректировка себестоимости выпуска и последующих списаний. Результат — `production_cost_closings (period, status, totals jsonb, run_at)`. Корректировку стоимости нельзя записать движением `stock_moves` (CHECK `qty <> 0`), поэтому она хранится отдельной таблицей `stock_cost_adjustments (move_id, delta_cost)` и учитывается в стоимости остатка. **Это меняет модель «Склада» в `docs/architecture.md` — раздел нужно обновить.** Закрытый период (решение 9): `workspaces.closed_through date` — дата запрета. Проведение, отмена и правка проведённых документов с датой не позже неё дают 422 `period_closed`. Закрывает admin+, открывает (сдвигает дату назад) только owner; открытие сбрасывает результат закрытия затронутых месяцев, следующее закрытие пересчитывает их.
- **Режим распределения материалов** (фича 4.4): «при выпуске» (этап 2) или «по итогам смены» — документ `production` без материалов, затем `material_allocation` распределяет фактическое списание смены по выпускам пропорционально нормам.
- **Брак и отходы:** у строки выпуска — количество брака; брак оформляется `write_off` (на затраты), `stock_posting` возвратных отходов (по цене отходов) или переводом в товар «уценка» с продажей обычной реализацией. Возвратные отходы в BOM — новый `bom_lines.kind = 'waste'` (миграция CHECK).
- **Взаимные переделы:** полуфабрикат A в B и B в A невозможен — циклы в BOM запрещены (`wouldCreateCycle`). Решение систем уравнений не нужно, пока это правило действует.
- **Готово, когда:** закрытие месяца на тестовом наборе даёт себестоимость выпуска «до копейки» по ручному расчёту; повторное закрытие идемпотентно; отмена закрытия возвращает прежние значения.

#### Решения пользователя по справке 1С:УНФ «Закрытие месяца» (2026-10-22, задача TaskFlow 1090)

Модель — обработка УНФ «Закрытие месяца» (справка 12.5 и статья ИТС metod81 #4018), только операции, относящиеся к себестоимости: расчёт прямых затрат, распределение затрат, расчёт фактической себестоимости. Амортизация, курсовые разницы, финансовый результат и ЕНС — вне этапа. Этот блок важнее остального текста этапа.

1. **Способ оценки остаётся средней скользящей.** Средневзвешенную за месяц и FIFO не вводить. Закрытие пересчитывает цепочку скользящей средней в порядке `stock_moves.seq` (поступление → выпуск → полуфабрикат → выпуск, перемещения, возвраты) и добавляет распределённые косвенные затраты; корректировки — `stock_cost_adjustments`, как в тексте этапа.
2. **Базы распределения** (в статье затрат `cost_items`): по объёму выпуска (доля количества), по прямым затратам (доля прямых затрат выпуска после пересчёта цепочки), по часам работ (нормочасы выпуска: работы снимка состава и сдельные наряды). Плюс «не распределять» — такие затраты остаются нераспределёнными (ручного документа распределения нет). Остаток округления — на последнюю строку.
3. **Источники косвенных затрат** (`period_costs`, заполняются при проведении и очищаются при отмене):
   - строки-услуги проведённых `receipt` со статьёй затрат (`document_lines.cost_item_id`) и участком;
   - новый ручной документ «Прочие затраты» (`other_costs`: дата, строки — статья, участок, сумма, комментарий; без склада);
   - списание материалов на участок: `write_off` с указанием участка и статьи затрат — стоимость списания идёт в косвенные затраты участка (как «НЗП без номенклатуры» в УНФ).
4. **Порядок распределения как в УНФ:** сначала на выпуски своего участка за месяц; если на участке выпуска не было — на общий выпуск; если выпуска не было совсем — затраты остаются нераспределёнными, закрытие завершается с предупреждением. Корректировка идёт по цепочке: остаток продукции дорожает, уже проданная часть увеличивает себестоимость продаж (корректировки расходов `stock_cost_adjustments` на движения реализации).
5. **Закрытие и дата запрета:** режимы «месяц» и «за период» (последовательно по месяцам; отмена — в обратном порядке). Настройка воркспейса «переносить дату запрета при закрытии» (`workspaces.close_moves_lock`, по умолчанию выкл.): если включена, успешное закрытие сдвигает `closed_through` на конец закрытого месяца. Дату запрета сдвигает вперёд admin+, назад — только owner (решение 9); правка документов в закрытом периоде — 422 `period_closed`. Перед закрытием — предварительная проверка (отрицательные остатки, непроведённые документы месяца со ссылками).
6. **Отложено отдельными задачами:** режим «распределение материалов по итогам смены», брак и возвратные отходы (`bom_lines.kind = 'waste'`), НЗП по участкам («завершающее подразделение»). Отчёты «Незавершённое производство» и «Себестоимость выпуска» — в этап 9; в этапе 6 — только результат закрытия (`production_cost_closings.totals`) на экране закрытия: распределено по статьям, участкам и выпускам, нераспределённое, предупреждения.

#### Фактическая реализация (2026-10-22, задача TaskFlow 1090)

Сделано по блоку «Решения пользователя»: средняя скользящая остаётся единственной оценкой, базы распределения — по объёму
выпуска, по прямым затратам и по часам работ плюс «не распределять», источники косвенных — строки-услуги поступлений,
списание на участок и новый документ «Прочие затраты», порядок «свой участок → общий выпуск → нераспределено с предупреждением»,
проданная часть увеличивает себестоимость продаж, закрытие «месяц» и «за период» с отменой в обратном порядке, настройка
«переносить дату запрета при закрытии», назад сдвигает только owner. Отложенные задачи (1135–1137, отчёты этапа 9) не трогались.

1. **БД (миграция `0020_production_closing.sql`).** `cost_items.distribution_method` (`none | output_qty | direct_costs |
   work_hours`, CHECK; существующие статьи получают `none` значением по умолчанию); `period_costs (period, cost_item_id,
   work_center_id?, amount, source: receipt|write_off|other_costs, document_id, document_line_id?)` с уникальностью по строке
   документа; `other_cost_lines (document_id, cost_item_id, work_center_id?, amount, comment)` — строки «Прочих затрат» вынесены из
   `document_lines` (у строки документа всегда есть товар каталога, у косвенной затраты товара нет — так же, как сделано у
   производственных документов); `stock_cost_adjustments (move_id, delta_cost, closing_id)`; `production_cost_closings (period,
   status, totals jsonb, run_at)` с уникальностью по (воркспейс, месяц); `workspaces.closed_through` и `close_moves_lock`;
   `documents.work_center_id` (участок списания, без внешнего ключа — как `in_use_work_center_id`); `document_lines.cost_item_id`
   (составной FK) и `document_lines.work_center_id`; пересоздан `documents_type_chk` (+ `other_costs`); составной уникальный ключ
   `(workspace_id, id)` на `stock_moves` (нужен корректировкам — ссылка на движение составной); `app_secure_tenant_table` на четыре
   новые таблицы. Заполнения существующих данных, кроме `distribution_method = 'none`, не требуется: колонка статьи у строк
   документов добавлена этой миграцией, поэтому косвенных затрат у ранее проведённых документов ещё нет — их наберёт следующее проведение.
2. **Чистые функции `packages/shared/src/cost-closing.ts`** (`distributeOverhead`, `planOverhead`, `replayChain` — последняя в слое БД,
   `monthPeriod` / `monthRange` / `monthLabel`): сумма распределённого равна сумме затрат, остаток округления на последней строке,
   группировка по статье и участку, порядок распределения, промежуточные этапы (без строки продукции) косвенных не получают.
   Тесты — `packages/shared/test/cost-closing.test.ts` (18 тестов, включая пример УНФ 33,33 / 66,67).
3. **Закрытие — задача воркера `production.close_period`** (`apps/worker/src/production-closing.ts`, реестр в `handlers.ts`).
   Сервис `packages/db/src/cost-closing.ts`: `closePeriodMonth` / `reopenPeriodMonth` под ролью `app_user` в контексте арендатора;
   внутри месяца `pg_advisory_xact_lock` на воркспейс (два закрытия одного воркспейса не идут одновременно); месяцы периода — каждый
   в своей транзакции, ошибка одного не откатывает предыдущие (статус `failed`).
   Порядок: снять корректировки прошлого закрытия месяца → распределённое в приход продукции (`stock_cost_adjustments`) →
   пересчёт цепочек (`replayChain`: приходы со своей ценой и прибавкой, расходы по текущей средней; разница — корректировка расхода,
   `stock_balances` приводится к результату пересчёта) → результат в `totals`. Повторное закрытие идемпотентно, отмена удаляет
   корректировки закрытия и пересчитывает цепочки обратно.
4. **Читается себестоимость с корректировкой везде** (`packages/db/src/stock.ts`): стоимость документа в журнале, себестоимость строки,
   цена возврата от покупателя, карточка движений (`GET /stock/moves`). Средняя остатка пересчитывается при самом закрытии.
5. **Общая проверка периода** `assertPeriodOpen` — в проведении, отмене проведения и смене даты документа (`packages/db/src/documents.ts`);
   производственные сервисы следуют ей автоматически, потому что проводят документы общим кодом (проверено тестом на заказе
   на производство и на выпуске в закрытом месяце).
6. **Косвенные затраты набираются общим кодом** `syncAfterChange` (проведение → набор, отмена → очистка) — не хуками типа, поэтому
   работают для любого документа и не зависят от порядка регистрации хуков; «Прочие затраты» набирает хук типа (у него нет строк товаров).
7. **Документ «Прочие затраты»** (`other_costs`, префикс ПЗ) — свой сервис `packages/db/src/other-costs.ts` и маршруты `/other-costs`;
   общий `POST /documents` отвечает `production_api_only`. Свои строки, общие нумерация и проведение.
8. **API:** `/production/periods` (журнал + дата запрета), `/production/periods/:month/preview`, `/production/periods/:month/close`
   и `/reopen` (admin+ и owner), `PATCH /production/periods/settings`. Суммы маскируются `maskCost`.
9. **Веб:** экран «Month closing» (`/production/closing`), журнал и форма «Other costs» (`/other-costs`), поле «Allocation base»
   в справочнике статей, колонки «Cost item» / «Work center» у строк-услуг поступления, поле «Work center» в списании,
   дата запрета и перенос в Settings → Production. Пункты сайдбара: Month closing и Other costs в группе Production.
10. **Демо-данные:** статьи «Электроэнергия цеха» (по объёму выпуска) и «Аренда цеха» (не распределять), поступление услуги
    со статьёй и участком, проведённый документ «Прочие затраты» и закрытый месяц выпуска (косвенные распределены, дата запрета —
    на конец этого месяца). Счётчики демо-сида обновлены в `packages/db/test/db.test.ts`.

Отклонения от текста этапа: (1) закрытие не пересчитывает средневзвешенную и не вводит FIFO — так и решил пользователь; (2) промежуточные
этапы выпуска косвенных не получают (у них нет прихода продукции), их затраты идут в НЗП следующего этапа; (3) предупреждения закрытия
и тексты интерфейса — по-английски, названия статей демо-данных по-русски (как и остальные демо-данные); (4) распределение по
статье и участку идёт одной группой (в УНФ — по подразделению и способу распределения, то же самое). Оценка этапа: план L+,
фактически L+ (около четырёх рабочих дней) — примерно половина на сервис закрытия и миграцию, половина на API, интерфейс и тесты.

#### Исправления при проверке этапа 6 (2026-10-22)

- **Корректировка не шла дальше одной пары (склад, товар).** Пересчёт `recomputeChains` переоценивал только расходы той же пары: приход перемещения, приход изделия, списавшего подорожавший полуфабрикат, и приход возврата не дорожали — распределённое терялось по дороге (тест агента закреплял изделие 110 вместо 140). Заменён одним проходом по всем движениям воркспейса в порядке `seq` (`recomputeStockCosts` в `stock.ts`): удорожание идёт с расхода перемещения на его приход, с материалов выпуска — на приход продукции (с накладными %), с реализации — на возврат. У корректировки появилась своя часть `own_delta` (распределение закрытия), итог `delta_cost` пересчитывается. Тесты: цепочка «полуфабрикат → перемещение → изделие» (140), продажа из другого склада после перемещения.
- **Отмена проведения и переоценка после закрытия теряли косвенные в средней.** Базовый пересчёт пары в `revertStockMoves` / `revalueMove` не видел корректировок и писал среднюю без них. Теперь после него вызывается общий проход. Тест: продажа после закрытия проведена и отменена — средняя прежняя.
- **Отмена закрытия месяца при закрытом более позднем** давала неверную себестоимость позднего месяца — теперь 422 `later_month_closed` (отмена идёт от последнего закрытого месяца).
- **`closedThrough: null` игнорировался** (`if (body.closedThrough)`) — снять дату запрета было нельзя; теперь это сдвиг назад, только owner.
- **Составные FK** `documents.work_center_id` и `document_lines.work_center_id` → `work_centers (workspace_id, id)` добавлены в миграцию вручную (проверка в приложении была, FK не было).
- Тест «preview» ставил остаток бруса прямо в базе в 0 вместо прежнего — портил среднюю следующих тестов; теперь возвращает прежний остаток.
- **Гонка пересчёта с проведениями.** Общий проход писал остаток и среднюю всех пар без блокировки. Теперь при наличии корректировок все остатки воркспейса блокируются в порядке ключей до чтения движений (в `recomputeStockCosts`, а в `revertStockMoves` / `revalueMove` — до блокировки своих пар), количество остатка пересчёт не пишет. Тест: параллельные проведение и отмена по разным парам после закрытия — остаток равен сумме движений.
- **Закрытие раннего месяца при закрытом позднем** меняло себестоимость позднего без его пересчёта. Теперь диапазон закрытия расширяется до последнего закрытого месяца — поздние перезакрываются следом по порядку.
- Приход «по цене расхода той же строки» определяется по структуре (у строки есть расход в том же документе), а не по типу `stock_transfer`.
- Ограничение (задача 1137): удорожание материалов промежуточного этапа до финального этапа не доходит.
- **Цена решения:** после первого закрытия каждая отмена проведения и переоценка в воркспейсе пересчитывают все его движения и блокируют все остатки. Для текущих объёмов приемлемо; при росте — инкремент с первого затронутого `seq`.
- **Сдвиг даты запрета назад** (решение пользователя 2026-10-22): закрытия месяцев, которые снова можно править хотя бы частично (конец месяца позже новой даты), и всех поздних отменяются автоматически — задачей воркера от последнего к раннему; снятие даты (`null`) отменяет все закрытия. Ответ `PATCH /production/periods/settings` содержит `reopened`, интерфейс показывает их уведомлением.

### Этап 7. Параметрические спецификации и спецификация под заказ (L)

- **Спецификация под заказ** — уже покрыта снимком (этап 2): правка `production_components` заказа не трогает `bom_lines`.
- **Параметры:** `manufactured_items.params jsonb` — описание параметров (те же `FieldDef`, что у характеристик и полей конструктора, проверка `buildRecordSchema`); значения — в строке заказа (`production_order_items.params`).
- **Формулы:** `bom_lines.qty_expr text` и `bom_lines.condition text` — выражения над параметрами (`width * height / 1e6 * 1.1`, `color = 'white'`). Нужен **безопасный вычислитель** в `packages/shared/src/expr.ts`: свой разбор (числа, параметры, + − × ÷, сравнения, and/or, `if`), без eval, лимит длины и глубины. Он же закроет тип поля `formula` конструктора — **решение по языку выражений надо внести в `docs/architecture.md`** (сейчас там «formula — позже, нужен язык выражений»).
- **Варианты товара** (решение 6): каждая комбинация параметров — отдельная складская позиция со своим остатком. Предлагаемая модель — вариант это строка `products` с `parent_product_id` и `variant_values jsonb`: склад, документы, резервы и цены работают без изменений, потому что везде ссылаются на `products.id`. Уникальность (родитель, значения) — индекс по `parent_product_id, variant_values`. Вариант создаётся лениво при первом заказе комбинации или заранее генератором «все комбинации». Каталог показывает варианты вложенно под товаром. Выпуск по строке заказа с параметрами приходует вариант. **`docs/architecture.md` записывает варианты «позже» — раздел «Каталог» нужно обновить.**
- **Калькуляция заказа** (фича 2.8): в заказе покупателя — «Calculate» по продукции и параметрам → плановая себестоимость, наценка → цена строки.
- **Готово, когда:** окно 1200×1400 белое даёт ожидаемый состав и цену; некорректное выражение отклоняется при сохранении строки BOM.

**Решения пользователя по справке УНФ «Спецификации», «Параметрические спецификации», «Характеристики», «Калькуляция заказа» (2026-10-23, задача 1087; приоритет над текстом выше):**
1. **Варианты товара — строки `products`** с `parent_product_id` и `variant_values jsonb` (как предложено выше). Склад, резервы, цены и документы не меняются. В каталоге варианты показываются вложенно под товаром. Отдельного справочника характеристик и `characteristic_id` в документах, как в УНФ, нет.
2. **Параметры спецификации — свои + характеристики категории.** У спецификации (`manufactured_items`) свой список параметров: число (ширина, высота), select, boolean; описание — те же `FieldDef`. Если у товара есть категория, к ним добавляются её характеристики (`attribute_defs`, с унаследованными). Значения вводятся в строке заказа покупателя или заказа на производство и проверяются `buildRecordSchema`.
3. **Формулы — только количество строки и условие строки.** `bom_lines.qty_expr` (арифметика, round/ceil, min/max, if) и `bom_lines.condition` (сравнения, and/or/not). Подбор материала по значению параметра (цвет → краска) и формулы операций (часы, кол-во операций) — **не делаем, отдельной задачей**. Нужен безопасный вычислитель `packages/shared/src/expr.ts` без eval; ошибка выражения отклоняет сохранение строки (422). Язык выражений описать в `docs/architecture.md`.
4. **Спецификация под заказ — снимок в заказе.** Рассчитанный по параметрам состав сохраняется в строках заказа (`production_components`), справочник спецификаций не засоряется. Кнопка «Пересчитать» в заказе — при смене параметров. В черновике пересчёт свободный; после проведения — только с отменой проведения. Ручная правка снимка, как сейчас, остаётся.
5. **Вариант дают только отмеченные параметры.** У параметра флажок «Разрез склада» (цвет, размер); замеры (ширина) вариант не дают.    признак правится вручную (`PATCH /production-orders/:id/components/:componentId`, только в черновике). Проведение делит

5. **Модель себестоимости услуги (выбрана и описана в `architecture.md`).** Наши затраты выпуска (свои материалы по факту,

Отклонения от текста этапа и решения, принятые по ходу:
1. **Приём сделан отдельным типом `tolling_receipt`, а не видом операции поступления.** У поступления проверка статьи затрат у
   строк-услуг, свой сценарий резервирования материалов заказа и нумерация закупок — смешивать их с чужим смыслом опаснее, чем
   добавить тип; вид операции у него один.
2. **Печатная форма отчёта — акт** (пункт 10 выше): отдельный шаблон с вкладками не делался.
3. **Давалец берётся из заказа на переработку, а отдельного поля «давалец» у документов переработки нет** — иначе можно было бы
   оформить приём по чужому заказу; при несовпадении с контрагентом документа — 422 `tolling_owner_mismatch`.
4. **Заказ поставщику на переработку несёт только материалы в переработку** (вкладка «Товары» УНФ с результатом работы не заводили):
   результат планируется заказом на производство. Это отличие от справки 1С.
5. **Услуга переработчика вводится в отчёте переработчика** (`POST /processor-reports`, поле `services`), а не ссылкой на поступление
   услуги: поступление услуги остаётся обычным документом закупок, но его сумма не попадает в себестоимость именно этой продукции.
6. **Потребность по плану производства (этап 5) про давальческое сырьё не знает**: там материалы берутся из спецификации без заказа
   на переработку, поэтому дефицит по плану считается по-своему. Покрыто то, где заказ известен (заказ на производство, `/production/needs`).
7. **Возврат давальцу — расход с остатка давальца** (товар физически остаётся у нас, он просто перестаёт быть давальческим).
8. **Отчёт о переработке не сверяется с выпусками автоматически**: вкладка «Материалы» заполняется пользователем (тест сверяет
   остаток после отчёта, но не блокирует расхождение с выпусками) — строгая сверка потребовала бы хранить связь «строка отчёта →
   строка выпуска», чего в модели нет.
9. Унаследовано от этапа 7 и остаётся: если та же услуга подрядчика проведена поступлением со статьёй и участком, закрытие месяца
   распределит её повторно.

Оценка этапа: план M, фактически **L** (около пяти рабочих дней) — примерно четверть на модель данных и учёт давальцев,
четверть на выпуск и себестоимость услуги, четверть на API, интерфейс и демо-данные, остальное на тесты и документацию.

### Разборка (задача 1134, S–M)

По справке УНФ «Заказы на производство», «Выпуск продукции», «Спецификация продукции» (текст — в задаче 1134).

**Решения пользователя (2026-10-24, приоритет):**
1. **Разборка — в производстве**, как в УНФ: вид операции `documents.operation = 'disassembly'` у заказа на производство и выпуска (рядом с `assembly`). В «Продукции» — что разбираем (списывается со склада), в «Материалах» — выходные продукты (приходуются). Участок, операции, этапы и сдельный наряд работают как при сборке. Складской документ «Комплектация запасов» не делаем.
2. **Своя спецификация разборки:** у спецификации вид «Сборка | Разборка»; у разборки — исходный товар и строки выходных продуктов с количеством и **«Долей стоимости»**, плюс операции (работы). Пример: бревно → доски, туша → части.
3. **Распределение стоимости по выходным продуктам:** по доле стоимости из спецификации (сумма долей = 100 %); если доли не заданы — пропорционально цене продажи выходных продуктов (`products.price`), без цен — по количеству. Работы и накладные распределяются той же базой. Остаток округления — на последнюю строку; сумма приходов = стоимость списанного + работы + накладные.
4. Не делать: складскую комплектацию, возвратные отходы при разборке (задача 1136), разборку давальческого сырья.

#### Фактическая реализация разборки (2026-10-24, задача 1134, ветка `feat/unf-disassembly`)

Агент Pi (OpenRouter minimax-m3.1-flash) сделал всё по блоку решений и остановился на демо-данных — на OpenRouter закончились кредиты (402);

- **Схема (миграция `0024_disassembly.sql`):** `manufactured_items.mode` (`assembly | disassembly`), `bom_lines.cost_share` и

  строки в `bom_lines` и `production_components`), `documents.operation` — добавлено `disassembly` (пересоздан `documents_operation_chk`).
- **Спецификация разборки:** исходный товар — товар спецификации, строки — только `output` и `work` (422 `spec_kind_forbidden`); доли —
  все или ни одной, сумма ровно 100 % (422 `share_incomplete` / `share_sum`), проверка при сохранении спецификации и при проведении;

### Брак и возвратные отходы (задача 1136, M)

- стоимость отходов задаёт переключатель «Нулевая / Учётная»: учётная берётся по виду цены отходов из настроек и уменьшает себестоимость продукции;

Ответы 1С 1334–1336 описывают три способа учёта брака: как отходы, на прочие расходы (склад брака, затем «Списание запасов») и в себестоимость годной продукции.

#### Решения пользователя (2026-10-23)

1. **Где задаются отходы — и в спецификации, и в выпуске.**

   - У строки отхода нет `scrap_pct`, `cost_share`, `semi_mode`, `child_item_id` и полей работы.
   - Отходы разрешены в спецификациях сборки и разборки.
   - «Заполнить по спецификации» переносит отходы в снимок `production_components.kind = 'waste'` — это вкладка «Отходы» выпуска и заказа. В выпуске строки правятся по факту.
2. **Стоимость отходов — переключатель в шапке выпуска:** `production_headers.waste_valuation` (`zero | accounting`, по умолчанию `accounting`).
   - «Нулевая» — отходы приходуются по 0, себестоимость продукции не меняется.
   - «Учётная» — отходы приходуются по `production_components.price` × количество, сумма вычитается из себестоимости продукции выпуска.
   - Цена подставляется при заполнении и правится вручную.
3. **Учётная цена — настройка `workspaces.settings.wastePriceSource`** (Настройки → Производство): `purchase` (по умолчанию) | `price` | `avg_cost`. Нулевая цена считается незаданной, как у материалов.
4. **Стоимость отходов распределяется между продукцией по стоимости.**
   - Доли — по себестоимости строк продукции до вычета, остаток округления — на последней строке.
   - Если отходы дороже всех затрат выпуска — 422 `waste_exceeds_cost`.
5. **Брак — три способа.**
   - **Брак как отходы.** Бракованное изделие (отдельный товар «брак») пишется строкой во вкладку «Отходы» с нулевой ценой. Новых полей не нужно.
   - **Позиция выпуска получает `defect_qty`** (≥ 0, ≤ `qty`; `qty` — всё выпущенное вместе с браком) **и `defect_mode`** (`expense | cost`; задан только при `defect_qty > 0`).
     - `cost` — брак в себестоимость. Брак не приходуется: на склад продукции поступает `qty − defect_qty`, и все затраты ложатся на годное.
     - `expense` — брак на прочие расходы. Годное приходуется на склад продукции, брак — на **склад брака** по той же себестоимости единицы. Списывает его кнопка **«Списать брак»** в проведённом выпуске (решение 7).
   - **Исполнение заказа и резерв считаются по годному** (`qty − defect_qty`), поэтому брак не закрывает заказ.
6. **Склады в шапке выпуска:**
   - `production_headers.waste_warehouse_id` — «Отходы в»;
   - `production_headers.defect_warehouse_id` — «Брак в».

   У участка появляется четвёртый склад автоперемещения `work_centers.defect_warehouse_id` («брак в»).

   Склады подставляются из участка, с запасными вариантами:
   - для отходов: склад отходов, затем склад продукции;
   - для брака: склад брака, затем склад отходов, затем склад продукции.

   Пользователь может поменять склады в документе.
7. **Кнопка «Списать брак»** — `POST /production/:id/write-off-defects` (member и выше, только у проведённого выпуска с браком `expense`). Она создаёт **черновик** `write_off` на основании выпуска (`basedOn` у `write_off` дополняется `production`):
   - склад — склад брака;
   - строки — товар × количество брака, сгруппированные по товару;
   - статью расходов пользователь выбирает сам и сам проводит акт.

   Если неудалённое списание на основании этого выпуска уже есть — 409 `defects_written_off` со ссылкой на него.
8. **Разборка:** строки отходов в спецификации и выпуске разборки. Учётная стоимость отходов вычитается из распределяемой стоимости до `allocateDisassembly`, остаток делится между выходами как сейчас. Брака у разборки нет.
9. **Плановая себестоимость:** `computeBomCost` вычитает норму отходов по учётной цене (`wastePriceSource`).
   - В разбивке узла появляется строка «Отходы» со знаком минус.
   - Накладные считаются от прямых затрат без вычета отходов.
   - То же действует в `computeProductionCost` (план и факт выпуска).

#### Решения по умолчанию (не спрашивались)

- **Поэтапное производство:** отходы приходует выпуск **финального** этапа. `stage_id` у строки отхода не используется.
- **Выпуск из давальческого сырья** (по заказу на переработку): строки отходов запрещены (422 `waste_tolling_forbidden`). Отходы давальца по-прежнему идут через отчёт о переработке.
- **Пересчёт стоимости и закрытие месяца** (`recomputeStockCosts`, `production.close_period`, `recalcReleaseCost` сдельных нарядов):
  - стоимость прихода отходов фиксирована и при пересчёте не меняется;
  - удорожание материалов и косвенные затраты целиком идут на продукцию;
  - приход брака `expense` получает удорожание вместе с годным — по количеству, при той же себестоимости единицы.
- **Права:** цена и сумма отходов, как и вся себестоимость, видны только admin и owner (`maskCost`). Количество видно всем.
- **Миграция** — `0028_waste_defects.sql`:
  - CHECK `kind` у `bom_lines` и `production_components` дополняется `waste`;
  - новые колонки: `production_components.price`, `production_items.defect_qty` и `defect_mode`, `production_headers.waste_valuation`, `waste_warehouse_id` и `defect_warehouse_id`, `work_centers.defect_warehouse_id`;
  - ссылки на склады — составные FK с `ON DELETE SET NULL ("X")`, как в `0026`.
- **Интерфейс:**
  - тип строки спецификации «Отход»;
  - в выпуске и заказе вкладка «Отходы» (`DocTabs`) с колонками: товар, количество, цена, сумма;
  - в шапке выпуска — переключатель «Стоимость отходов: Нулевая / Учётная» и склады «Отходы в» и «Брак в»;
  - у позиции выпуска — колонки «Из них брак» и «Брак: в себестоимость / на расходы»;
  - кнопка «Списать брак»;
  - четвёртый склад в форме участка;
  - «Цена отходов» в Настройки → Производство.

  Все тексты — через `t()` с русским переводом.
- **Демо-данные:**
  - у одного изделия есть строка отхода («Обрезки», учётная цена);
  - один проведённый выпуск с браком `expense` и складом брака.
- **Готово, когда:**
  - себестоимость продукции = затраты − учётная стоимость отходов;
  - сумма приходов (продукция, брак, отходы) равна затратам выпуска;
  - отмена проведения возвращает остатки;
  - тесты в `apps/api/test/production.test.ts` и `packages/shared` покрывают все пять решений, разборку, поэтапный выпуск и пересчёт закрытия месяца.

#### Фактическая реализация (2026-10-26, задача 1136, ветка `feat/unf-waste`)

- **БД:** миграция `0028_waste_defects.sql` (CHECK `waste`, колонки отходов и брака, составные FK `SET NULL`); `document_lines.warehouse_id` создана, но не используется (приход отходов идёт движением без строки документа).
- **Расчёты** (`packages/shared/src/bom.ts`): `waste` в `computeBomCost` (разбивка `waste` только при ненулевом вычете; `wastePrice` необязателен, по умолчанию цена материала) и `explodeBom` (`wastes`, у «фантома» попадают в родителя, этап не задаётся).
- **Выпуск** (`packages/db/src/production.ts`): приход годного, брака `expense` и отходов отдельными движениями; цена единицы = (затраты + НЗП − отходы) / приходованное; `waste_exceeds_cost`, `waste_tolling_forbidden`, `defect_*`; `GOOD_QTY` в исполнении заказа, этапах, плане и пополнении; `writeOffDefects`, `updateProductionAccounting`, `maskProductionDetail`; разборка вычитает отходы до `allocateDisassembly`; `recalcReleaseCost` сохраняет вычет.
- **Пересчёт и закрытие:** `stock.ts` — материалы берутся только `material`/`semi`, делитель — приходованное; `cost-closing.ts` — косвенные делятся между годным и браком по количеству, на отходы не идут.
- **API/web:** `PATCH /production-orders/:id/accounting`, `POST /production/:id/write-off-defects`, `write_off` «на основании» выпуска; вкладка «Отходы» (`WasteTab`), переключатель стоимости и склады в шапке, колонки «Из них брак» и режим, кнопка «Списать брак», «Брак в» в форме участка, «Цена отходов» в настройках.
- **Отклонения:** режим брака `waste` не используется (брак как отходы — строка во вкладке «Отходы»); `wasteValuation` — только в шапке выпуска/заказа, не настройка воркспейса; цена брака (`defectUnitCost`) вычисляется при проведении, не вводится; брака у заказа нет (поля заказа убраны); в демо отход — у стола «Офис» (обрезки дуба), брак `expense` — в выпуске стульев «Лофт» (добавлены склады отходов и брака).
- **Тесты:** `apps/api/test/production-waste.test.ts` (23), дополнения в `packages/shared/test/bom.test.ts`; `fk-set-null` находит строку по ctid.

## Риски

- **Двухфазная запись движений** (этапы 0, 2) трогает самый нагруженный код склада. Сохранить порядок блокировок и конкурентные тесты.
- **Устаревшая себестоимость после отмены поступления** (ограничение 7) существует до этапа 6. Описать в интерфейсе выпуска и в `architecture.md` как известное ограничение.
- **Рост `documents`:** внутренние и производственные документы делят таблицу, журналы и нумерацию с продажами. Это плюс (одно проведение, одна печать), но CHECK типов и `DOCUMENT_META` разрастаются — держать метаданные типов единственным источником правды.
- **Планировщик ресурсов** — новый сложный UI; без выделения общего компонента с `timeline-view.tsx` код задвоится.
- **Закрытие периода** меняет смысл «проведённый документ можно отменить»: в закрытом месяце отмена запрещена, открыть период может только owner (решение 9).
- **Модуль у задач** (этап 4) трогает общие экраны задач; фильтр по умолчанию не должен спрятать существующие задачи (все они — `general`).
- **Варианты товара** (этап 7) увеличивают каталог; генератор «все комбинации» нужно ограничить по количеству.
- **Язык выражений** — поверхность для ошибок и злоупотреблений; только собственный разбор, лимиты, тесты на враждебный ввод.

## Задача 1135 — распределение материалов по итогам смены (решения 2026-10-26)

Модель УНФ: выпуск проводится без материалов, затем документ «Распределение затрат» за смену/день делит фактический расход
по выпускам пропорционально нормативной потребности спецификаций (материал вне норм — на все выпуски).

1. **Режим** — `work_centers.material_mode` (`on_release | shift`, по умолчанию `on_release`) и `production_headers.material_mode`
   (берётся у участка при создании, меняется в шапке черновика). Только сборка, включая этапы; разборка и давальческое —
   всегда «при выпуске» (422 `shift_mode_unsupported`).
2. **Выпуск в режиме смены** при проведении не списывает материалы и полуфабрикаты; строки состава остаются как нормы
   (вкладка «Материалы» только для чтения с пометкой). Отходы и брак работают как обычно.
3. **Документ `material_allocation`** («Распределение материалов»): шапка — участок (`documents.work_center_id`), период с/по
   (по умолчанию один день = дата документа), склад списания (по умолчанию склад-цех участка). Вкладки: «Материалы» (факт:
   товар, количество — ручной ввод, кнопки «Заполнить по нормам» и «Заполнить по остатку цеха» на конец периода), «Выпуски»
   (проведённые выпуски участка в режиме смены за период, ещё не вошедшие в другое проведённое распределение),
   «Распределение» (результат: выпуск, продукция, материал, количество, стоимость).
4. **Алгоритм** (чистая функция в `shared`): материал делится между позициями выпусков пропорционально нормативному количеству
   (норма × количество выпуска); материал без норм у всех позиций — пропорционально плановой стоимости материалов позиции,
   без стоимости — по количеству выпуска. Остаток округления — на последнюю строку.
5. **Проведение**: расход со склада списания по средней (недостаток — обычная ошибка остатков); строки распределения
   `material_allocation_rows`. Стоимость доходит до продукции корректировкой по цепочке, как при закрытии месяца:
   отдельная часть корректировки прихода продукции (не `own_delta` закрытия), `recomputeStockCosts` разносит её дальше, в т. ч.
   на себестоимость уже отгруженного. Промежуточный этап — прибавка к `stage_cost` (НЗП); если следующий этап уже выпущен —
   корректировка его прихода продукции.
6. **Отмена проведения распределения** возвращает всё назад. Отмена/правка выпуска, вошедшего в проведённое распределение —
   409 `has_posted_children`.
7. **Закрытие месяца**: выпуски в режиме смены без распределения — предупреждение со списком, закрытие идёт. Распределённые
   материалы входят в прямые затраты выпуска для баз распределения.

### Задача 1135 — доработка по справке УНФ 8.6 (решения 2026-10-26)

Справка 8.6.2 «Документ Распределение затрат»: начало периода задаётся, окончание = дата документа; вкладка «Продукция»
заполняется кнопкой «Заполнить по выпуску» и правится; «Запасы» — «Заполнить по нормативам / по остаткам»; табличное поле
«Распределение запасов» заполняется командами «Распределить по нормативам / по количеству» и правится вручную.

1. **Период как в 1С**: поле «Начало периода», окончание = дата документа (поле «Период по» убрать, `period_to` = `date`).
2. **«Продукция» — хранимая таблица** позиций выпусков (`material_allocation_items`): «Заполнить по выпуску» берёт проведённые
   выпуски участка в режиме смены за период, ещё не вошедшие в другое проведённое распределение; строки можно удалить.
   При проведении: каждая позиция проведена, режим смены, тот же участок, дата в периоде, не в другом проведённом распределении.
3. **«Распределение» — хранимая редактируемая таблица** (позиция × материал × количество): кнопки «Распределить по нормативам»
   (текущий алгоритм) и «По количеству» (пропорционально количеству выпуска); количества правятся. При проведении сумма по
   каждому материалу равна факту (иначе 422 `allocation_mismatch`), строки — только по позициям вкладки «Продукция»;
   пустое распределение при проведении заполняется по нормативам. Стоимость — по средней списания, пропорционально количеству.
4. **Нематериальные затраты** этим документом не распределяются — их распределяет закрытие месяца.

## Задача 1137 — НЗП по участкам (решения 2026-10-26)

Источник: встроенная справка УНФ «Сдельный наряд» — «Завершающее подразделение нужно указывать при использовании поэтапного
производства с возможностью выполнять этапы разными подразделениями. Содержит структурную единицу, на которой будет храниться
остаток незавершенного производства»; справка 8.5 «Производство в несколько этапов» (этапы — в разные дни и разных подразделениях).
Сейчас НЗП промежуточных этапов копится в `production_items.stage_cost` по позиции заказа и переходит в финальный этап
(`wipUnitCost`), но без участка; закрытие месяца промежуточным этапам косвенные не даёт.

1. **НЗП числится на завершающем участке.** Поле «Завершающий участок» — в шапке заказа на производство (по умолчанию — участок
   заказа) и в шапке выпуска (`production_headers.final_work_center_id`): выпуск этапа берёт его из заказа, в черновике можно
   сменить. НЗП промежуточного этапа принадлежит завершающему участку своего выпуска; этапы при этом выполняют любые участки.
2. **Финальный этап — на любом участке.** НЗП списывается с завершающего участка в себестоимость продукции, где бы ни выпускали
   финальный этап (без ошибки и предупреждения). Расчёт себестоимости финального этапа не меняется.
3. **Экран «Остаток НЗП»** (Производство): на выбранную дату (по умолчанию сегодня, выпуски по дату включительно), фильтр по участку;
   группировка участок → заказ → изделие: выполненные этапы, количество в НЗП (выполнено промежуточных этапов минус принято финальным),
   сумма НЗП, итоги по участкам. Суммы — только ролям, которым видна себестоимость. Полный отчёт с движением — этап 9 (1091).
4. **Закрытие месяца:** промежуточные этапы участвуют в распределении косвенных затрат. «Свой участок» — участок, выполнивший этап
   (`production_headers.work_center_id`), база — его затраты / часы / количество этапа. Распределённое на промежуточный этап
   входит в его НЗП и доходит до продукции на финальном этапе; если финальный этап уже выпущен — корректировкой по цепочке,
   как у закрытия сейчас. Порядок «свой участок → общий выпуск → нераспределено» сохраняется.

## Задача 1091 — отчёты производства (решения 2026-10-26)

Справка УНФ 8.9 «Отчёты раздела Производство»: Выпуск продукции, Заказы на производство, Нормативный состав изделия,
Себестоимость выпуска, План-фактный анализ производства, План-фактный анализ себестоимости выпуска, Сдельные наряды
(последний уже есть — `GET /production/piecework/report`, не трогаем).

1. **Состав — восемь отчётов:** выпуск продукции; заказы на производство (по заказу номенклатура с остатком на начало,
   приходом — заказано, расходом — выпущено, остатком на конец; срок и просрочка); себестоимость выпуска; план-факт
   себестоимости; план-факт производства (планы производства периода против выпуска); НЗП с движением (начало, приход,
   расход, конец по участкам и заказам — продолжение экрана «Остаток НЗП», тот же сервис `production-wip.ts`);
   нормативный состав изделия (развёртка спецификации, операции с нормативным временем, себестоимость N изделий);
   загрузка участков.
2. **Навигация:** один экран `/production/reports` с вкладками, вкладка в адресе (`?tab=`). Общие отборы: период, участок,
   изделие, где применимо.
3. **Форма:** сворачиваемые группировки с итогами по группам и общим итогом; выгрузка CSV (что на экране, с учётом
   отборов); клик по строке открывает документ-источник; графики над таблицей там, где уместно (план-факт производства,
   план-факт себестоимости, загрузка участков, себестоимость по видам затрат) — свой лёгкий SVG-компонент, без новых
   зависимостей.
4. **Себестоимость выпуска:** виды затрат колонками — материалы, полуфабрикаты, распределение по смене (`alloc_cost`),
   сдельная оплата, услуги переработчика, косвенные (`closing_cost`/корректировки закрытия месяца); косвенные
   расшифровываются по статьям затрат справочника `cost_items`. Сумма видов = себестоимость прихода продукции.
5. **План-факт себестоимости:** план = количество по снимку норм выпуска × фактическая средняя цена списания;
   факт = фактическое списание. Отклонение только по количеству (перерасход / экономия), по материалам.
6. **Загрузка участков:** мощность участка по графику (`capacity_hours_per_day`/календарь), запланировано — из
   планировщика (`/production/load`), факт — часы выполненных операций; процент загрузки, перегрузка выделяется.
7. **Нормативный состав изделия:** переключатель цены — «по виду цен» (выбор вида цен) или «по последней закупке».
8. **Права:** стоимостные отчёты и стоимостные колонки — только admin/owner (решение 8, маскирование как в `maskWipBalance`);
   количественные — любому участнику.
9. **Готово, когда:** итоги отчётов сходятся с суммами документов на демо-сиде (себестоимость выпуска = приход
   продукции; НЗП на конец = экран «Остаток НЗП» на ту же дату); тесты API на сверку и маскирование.
