# Архитектура платформы gr8r

Документ фиксирует решения для перехода от фронтенд-шаблона к многоарендной платформе (задачи, CRM,
каталог, документы продаж и закупок, склад, автоматизации, конструктор сущностей). Любой новый код
следует этим решениям; меняя решение — обнови документ в том же коммите.

## Стек

| Слой | Выбор |
| --- | --- |
| Рантайм | Bun (workspaces, `Bun.password`, `Bun.serve`, `bun test`) |
| HTTP | Hono (`hono/bun`), валидация `@hono/zod-validator`, типизированный клиент `hono/client` |
| БД | PostgreSQL 16, Drizzle ORM + drizzle-kit (миграции SQL в репозитории) |
| Схемы | Zod — общие для API и фронтенда (`packages/shared`) |
| Фронтенд | React 19 + Vite, TanStack Query для серверного состояния; клиент API — `@gr8r/api/client` (hono/client) |
| Реальное время | WebSocket (`upgradeWebSocket` из `hono/bun`), события по арендатору |
| Файлы | S3-совместимое хранилище (MinIO локально) |
| Фоновые задачи | таблица `jobs` + воркер на `FOR UPDATE SKIP LOCKED` (без внешних брокеров) |
| Запуск | Docker Compose: postgres, minio, api, worker, web; тот же compose — на VPS |

## Монорепозиторий

```
apps/
  web/        фронтенд (бывший корневой src/, vite); алиас `@/…` → apps/web/src
  api/        HTTP API (Hono) + WebSocket
  worker/     фоновые задачи: outbox событий, очередь jobs (DDL по белому списку — индексы полей конструктора); позже — автоматизации, печать PDF, пересчёты
packages/
  shared/     доменные типы, zod-схемы API, константы (статусы, приоритеты 1–10, роли, ставки НДС, единицы ОКЕИ),
              демо-данные (`@gr8r/shared/demo`: их используют и фронтенд в локальном режиме, и сид БД)
  db/         drizzle-схема, SQL-миграции (`drizzle/`), RLS, uuid v7, сид, утилиты администрирования БД
docs/
test/         preload для `bun test` (тестовая БД пересоздаётся при каждом запуске)
scripts/      dev.ts (api + worker + web), smoke.ts (сквозной сценарий против запущенного API)
docker/       конфиги контейнеров (nginx для web)
Dockerfile    цели api, worker, migrate, web (oven/bun; web раздаёт nginx)
docker-compose.yml
```

Команды из корня: `bun install`, `bun run dev` (api + worker + web), `bun run build`, `bun run typecheck`, `bun test`,
`bun run db:generate | db:migrate | db:seed | db:wipe | db:reset`. Переменные окружения — `.env` по образцу `.env.example`
(пакеты читают корневой `.env`, поэтому скрипты работают из любой папки).

## Арендаторы и доступ

- `users` — глобальные учётные записи; `workspaces` — арендаторы; `memberships (user_id, workspace_id, role)`
  с ролями owner / admin / member / guest — источник правды для проверки доступа. Пользователь может состоять в нескольких воркспейсах.
- **Профиль участника** — отдельная таблица `members` (имя, должность, цвет, команда, часовой пояс, статус active / invited /
  deactivated). У `members.user_id` может быть NULL (приглашённый, ещё не зарегистрированный). На `members.id` ссылаются задачи,
  комментарии, сделки и т. д. (а не на `users.id`), поэтому участник остаётся в истории и после деактивации. Инвариант:
  если `members.user_id` задан, существует `memberships` с той же ролью — смена роли обновляет обе таблицы в одной транзакции.
- Вход: email + пароль (Argon2id через `Bun.password`), сессии в таблице `sessions` (в БД хранится sha256 токена, не сам токен),
  cookie httpOnly + SameSite=Lax (+ Secure в production, `COOKIE_SECURE`). Токен только в cookie — в теле ответов его нет.
  Вход и регистрация ограничены rate-limit'ом (таблица `rate_limits`, счётчики по IP и по email). OAuth (Google и т.п.) — позже,
  отдельной таблицей `identities`.
- Активный воркспейс передаётся заголовком `X-Workspace-Id` (для WebSocket — параметром `?workspace=`); API проверяет членство.
- Приглашения: `invites` с токеном вида `<workspace_id>.<секрет>` (в БД — sha256), срок 7 дней, принимается тем аккаунтом,
  чей email совпал с приглашённым. Воркспейс зашит в токен, поэтому принять приглашение можно до вступления в арендатора.
  Отправка писем — позже; пока токен возвращается администратору один раз.
- **Каждая таблица с данными арендатора** имеет `workspace_id uuid not null` и политику RLS по
  `current_setting('app.workspace_id', true)::uuid`; на таблицах `ENABLE` + `FORCE ROW LEVEL SECURITY` (владелец тоже подчиняется политикам).
  Исключения, у которых собственные политики: `workspaces` (арендатор — сама строка) и `memberships` (свои членства видны по
  `app.user_id`, чтобы определить, в какие воркспейсы пользователь может войти и вывести «мои воркспейсы»; изменять — только в рамках арендатора).
  Глобальные таблицы без RLS: `users`, `sessions`, `rate_limits` (минимальные права).
- **Роли БД** (создаёт миграция 0002, идемпотентно): `app_owner` — владелец таблиц, NOLOGIN; `app_user` — под ней работает API, NOLOGIN,
  NOBYPASSRLS; `app_worker` — воркер, BYPASSRLS (фоновые задачи и outbox идут через всех арендаторов). Рантайм подключается
  логин-ролью (`gr8r_app`, создаётся `db:migrate` по `APP_DB_USER`/`APP_DB_PASSWORD`): она не суперпользователь и NOINHERIT — сама прав на таблицы
  не имеет, пока код не сделает `SET ROLE`. Миграции выполняются под `ADMIN_DATABASE_URL` (суперпользователь/владелец БД); таблицы
  передаются `app_owner`. Таблица `events` для `app_user` только на добавление (UPDATE/DELETE отозваны).
- **DDL вне API.** Логин-роль API права владельца не получает (`SET ROLE app_owner` — ошибка): эту выдачу, появившуюся на этапе 3 ради
  индексов конструктора, этап 4 убрал. DDL выполняет только воркер через отдельное подключение `DATABASE_URL_DDL` — логин-роль
  `gr8r_ddl` (создаёт `db:migrate` по `DDL_DB_USER`/`DDL_DB_PASSWORD`): она наследует права `app_owner` (владельца таблиц), не суперпользователь,
  `SET ROLE` ей не нужен. API и сид лишь ставят задачу в `jobs`; воркер выполняет её по белому списку операций (см. «Конструктор сущностей»).
- **Конвейер запроса API**: сессия → пользователь → заголовок воркспейса → одна транзакция: `SET LOCAL ROLE app_user`,
  `app.user_id`, проверка членства, `app.workspace_id` → обработчик → COMMIT (при ответе ≥ 400 — ROLLBACK). Обработчики используют только
  `c.var.db` этого контекста; ручных фильтров по `workspace_id` в запросах нет — изоляцию гарантирует БД. `SET LOCAL` не «протекает»
  между запросами через пул соединений. Пустая настройка даёт NULL → строк не видно (fail closed).
- **Целостность между арендаторами**: связи внутри арендатора — составные внешние ключи `(workspace_id, id)`, поэтому запись одного
  арендатора не может сослаться на запись другого даже в обход API (FK-проверки обходят RLS, составной ключ их закрывает).
- Новая таблица с `workspace_id` обязана вызвать в своей миграции `select app_secure_tenant_table('имя')` (владелец, ENABLE+FORCE,
  политика, права); тест покрытия RLS падает, если таблица пропущена.
- Крупному клиенту позже можно выделить отдельную схему или БД — код от этого не меняется.

## Общие соглашения по данным

- Идентификаторы — UUID v7 (сортируются по времени). В PostgreSQL 16 нативной `uuidv7()` нет (появилась в 18), поэтому первичные ключи
  по умолчанию получают значение от SQL-функции `uuid_generate_v7()` (миграция 0000, без расширений); в коде (сиды, заранее известные id)
  та же схема — `uuidv7()` из `@gr8r/db` с монотонным счётчиком внутри миллисекунды. Человекочитаемые ключи (`WEB-109`, `СЧ-2026-00042`)
  — отдельные поля с нумерацией по арендатору: ключ задачи выдаёт атомарный счётчик проекта (`projects.task_counter`).
- Время — `timestamptz`; даты без времени — `date`.
- Деньги — `numeric(18,2)`, количества — `numeric(18,3)`; в JSON передаются строками, на фронте —
  десятичная арифметика (без float).
- Мягкое удаление — `archived_at`; жёсткое — только из Archive.
- Мягкое удаление в API: `DELETE /:id` архивирует (`archived_at`), `?hard=true` (только admin и выше) удаляет, `POST /:id/restore` возвращает.
  Статусы задач хранятся ключом (`tasks.status` → `statuses.key`), а не id: ключ неизменен.
- **Журнал событий (outbox)**: любое изменение в той же транзакции пишет строку в
  `events (id, workspace_id, type, entity, record_id, actor_id, payload jsonb, created_at, processed_at)`. Из него
  питаются realtime-рассылка, лента Activity, уведомления и автоматизации. Типы: `task.created`, `task.updated` (payload `changes`:
  `{поле: {from, to}}`), `task.archived|restored|deleted`, `member.role_changed` и т. д. `actor_id` — `members.id`.
- **Realtime**: `recordEvent` делает `pg_notify('gr8r_events', конверт без payload)` в той же транзакции (доставка — только после коммита).
  Каждый экземпляр API держит одно соединение LISTEN и раздаёт события по WebSocket-комнатам воркспейсов. Это выбрано вместо опроса
  таблицы: нет периодической нагрузки, задержка — миллисекунды, масштабируется горизонтально. NOTIFY при обрыве теряется, поэтому
  клиент подключается с `?since=<id последнего события>` (uuid v7 сортируется по времени) и получает пропущенное из `events`;
  то же — `GET /events?since=`. Клиент дедуплицирует по `event.id`.
- **Воркер**: события берутся по `processed_at is null … FOR UPDATE SKIP LOCKED` (а не курсором по id: транзакции коммитятся не в порядке id,
  курсор пропустил бы поздно закоммиченное событие); очередь `jobs` — тот же SKIP LOCKED, повторы с экспоненциальной паузой, возврат
  «зависших» задач. Обработчик событий пока пуст — каркас; обработчики задач: `noop` и `index.create` / `index.drop` (DDL конструктора, подключение `DATABASE_URL_DDL`).

## Конструктор сущностей (метаданные + JSONB)

Реализовано на этапе 3. Код: схема `packages/db/src/schema/meta.ts` (миграция `0003_meta.sql`), общая логика
`packages/shared/src/fields.ts` и `schemas/meta.ts`, API `apps/api/src/routes/meta.ts`, `routes/records.ts`, `meta/*`,
клиент `apps/web/src/app/meta/*` и `settings/data-model.tsx`.

Таблицы на лету не создаются. Структура описывается метаданными:

- `entities (workspace_id, key, name, kind: system|custom, icon, title_field, settings, sort_order, archived_at)` —
  сущности, включая системные (task, project, deal, company, contact, product), чтобы к ним можно было добавлять поля.
  Системные регистрируются при создании воркспейса (`registerSystemEntities`), в сидах и миграцией для уже существующих
  воркспейсов. Ключ (`key`) не меняется. Для системных `title_field` — имя колонки (`title` / `name`); встроенные
  колонки (статус, сумма…) в `fields` **не** заводятся: это обычные колонки таблицы, `fields` описывает только
  пользовательские поля (`is_system` зарезервирован под будущее).
- `fields (entity_id, key, name, type, required, unique, filterable, options jsonb, sort_order, is_system, archived_at)` —
  типы: text, long_text, number, money, percent, date, datetime, boolean, select, multi_select, user, ref (связь с
  записью другой сущности — системной или пользовательской), refs, url, email, phone. `file` и `formula` — позже
  (нужны хранилище файлов и язык выражений). `options`: варианты select/multi_select `{value,label,color}`, `refEntity`
  (ключ целевой сущности), `min`/`max`, `maxLength`, `currency`. Ключ и тип поля после создания не меняются: от них
  зависят уже записанные данные.
- Хранение значений: у системных таблиц — колонка `custom jsonb` (есть у tasks, projects, deals, companies, contacts);
  пользовательские сущности — общая таблица `records (id, workspace_id, entity_id, data jsonb, created_by, created_at,
  updated_at, archived_at)`. Числа лежат числами, даты — ISO-строками, ссылки — uuid.
- Все три таблицы — арендаторские: `app_secure_tenant_table` (владелец app_owner, ENABLE + FORCE RLS, политика по
  `workspace_id`); составные FK `(workspace_id, entity_id)`.
- Проверка — zod-схема, собираемая из `fields` функцией `buildRecordSchema(fields, 'create'|'patch')`
  (`packages/shared`): на сервере перед записью и в формах клиента (`validateRecord`). create — обязательные поля
  заполнены, пустые значения не сохраняются; patch — проверяются только присланные ключи, `null` очищает поле (для
  обязательного — ошибка). Лишние ключи и ключи удалённых полей отклоняются. Сервер дополнительно проверяет, что
  ссылки (`user`/`ref`/`refs`) указывают на существующие записи **этого** воркспейса, и уникальность (`unique`).
- Запись `custom` у системных сущностей — те же маршруты (`/tasks`, `/deals`, `/companies`, `/contacts`, `/projects`),
  свойство `custom`: при PATCH присланные ключи проверяются и сливаются с имеющимися, `null` удаляет ключ,
  неизменённые значения не проверяются (клиент присылает объект целиком).
- Индексы: для полей с флагом `filterable` — индекс по выражению `((data->>'ключ'))` (для number/money/percent —
  `((data->>'ключ')::numeric)`), для записей пользовательских сущностей частичный (`WHERE entity_id = …`), для
  системных — по `custom` таблицы. Имя `idx_cf_<id поля>`. `CREATE INDEX CONCURRENTLY` нельзя выполнять в транзакции,
  а права владельца у API нет, поэтому **построение и удаление индекса — задача в таблице `jobs`** (очередь `ddl`, типы
  `index.create` / `index.drop`, `payload = {fieldId}`), которую запрос API вставляет в той же транзакции, что и изменение поля
  (откат запроса отменяет и задачу). Задачу берёт воркер и выполняет на отдельном подключении `DATABASE_URL_DDL` (роль-владелец).
  Белый список: воркер не доверяет содержимому задачи — из `payload` берётся только uuid поля, а ключ, тип и сущность читаются из
  метаданных; в SQL попадает лишь выражение над ключом, проверенным по `FIELD_KEY_RE`, таблица — из списка системных таблиц либо `records`
  (любой другой `type` задачи, негодный uuid или несуществующее поле — ошибка либо пропуск без DDL). Задача сверяется с метаданными
  **на момент выполнения**, а не постановки: `index.create` пропускается, если поле уже удалено, скрыто или не `filterable`;
  `index.drop` — если поле снова требует индекса (восстановлено раньше), поэтому порядок и повторы задач безопасны. DDL идёт строго по одному
  на всех воркерах (рекомендательная блокировка `pg_try_advisory_lock` с ожиданием в коде: ждущий `pg_advisory_lock` — открытая транзакция,
  а `CONCURRENTLY` ждёт такие, получился бы взаимный дедлок); сбой оставляет INVALID-индекс — его убираем, задача повторяется с паузой. Пока индекс не
  построен, фильтры работают без него. Запросы строят выражение из ключа, проверенного по метаданным и регулярке, значения идут
  параметрами. Поиск `q` — `ILIKE` по заголовку и текстовым полям (без индекса). GIN `jsonb_path_ops` по `records.data` ускоряет `@>`
  (фильтры по multi_select/refs).
- API (чтение — любой участник, изменение метаданных — admin и выше, записи — member и выше):
  `GET/POST /entities`, `GET/PATCH/DELETE /entities/:key`, `POST /entities/:key/restore`,
  `GET/POST /entities/:key/fields`, `PATCH/DELETE /entities/:key/fields/:id`, `POST …/fields/:id/restore`,
  `POST /entities/:key/fields/reorder`; записи — `GET/POST /data/:entity`, `GET/PATCH/DELETE /data/:entity/:id`,
  `POST /data/:entity/:id/restore`; поиск для палитры — `GET /data-search?q=`. Список записей:
  `filter=ключ:оператор:значение` (повторяется; eq, ne, gt, gte, lt, lte, in, contains, empty, notempty — набор
  зависит от типа поля), `sort=ключ,-ключ2`, `q`, `limit/offset`, `archived`.
- Удаление поля и сущности — с подтверждением (`DELETE …?confirm=<ключ>`), в два шага. Без `purge` поле/сущность только
  скрываются (`archived_at`): значения остаются в `records.data` / `custom`, ключ остаётся занятым, индекс убирается;
  `POST …/restore` возвращает всё, включая данные и индекс. С `purge=true` значения вычищаются из jsonb (`data - 'ключ'`),
  а строка метаданных (для сущности — вместе с записями) удаляется навсегда. Нельзя удалить поле-заголовок и сущность,
  на которую ссылаются поля других сущностей; системные сущности не удаляются и не переименовываются. Данные «скрытого»
  поля до очистки видны в БД и в сыром ответе API (`custom`), но не в интерфейсе.
- Интерфейс пользовательской сущности собирается автоматически из метаданных на готовых компонентах:
  `DataTable`, `Kanban` (по полю select), `EntityDrawer`, `FilterBar`, формы. Маршрут `/data/:key/:recordId?`, группа
  «Data» в сайдбаре, поиск в палитре команд. Пользовательские поля системных сущностей показываются в карточке задачи,
  колонками таблицы задач (меню Columns), в карточках сделки и контакта и на странице компании. Редактор модели —
  Settings → Data model.
- События outbox: `entity.*`, `field.*` (entity = `entity` / `field`) и `record.*` (entity = `record`, ключ сущности в
  `payload.entityKey`); клиент по ним перечитывает метаданные и списки записей.
- Если сущность станет «горячей» (миллионы записей, тяжёлая аналитика) — её можно материализовать в
  настоящую таблицу; это исключение, а не основной путь.

Известные ограничения этапа: порядок карточек внутри колонки доски не хранится (перетаскивание меняет только
значение select); сортировка в таблице пользовательской сущности — на клиенте по загруженным записям (до 2000); индексы
не покрывают поиск `q`; уникальность проверяется при записи (без уникального индекса БД, возможна гонка двух
одновременных записей); у проектов пользовательские поля доступны через API, но интерфейса для них нет.

## Каталог: товары и услуги

Реализовано на этапе 4. Код: схема `packages/db/src/schema/catalog.ts` (миграция `0004_catalog.sql`), схемы API
`packages/shared/src/schemas/catalog.ts`, API `apps/api/src/routes/catalog.ts` и `catalog/service.ts`, клиент `apps/web/src/app/catalog/*`.
Чтение — любой участник; единицы, категории и характеристики меняет admin и выше, товары — member и выше.

- `units (workspace_id, code, name, symbol, is_base)` — справочник единиц ОКЕИ **в каждом воркспейсе**: базовый набор (`OKEI_UNITS` в
  `packages/shared/src/constants.ts`: шт 796, кг 166, ч 356, усл. ед 876 …) воркспейс получает при создании (`registerBaseUnits`; для существующих —
  миграция), свои единицы добавляются рядом (код 3–4 цифры, не меняется). Базовые не удаляются; единица, на которую ссылаются товары и
  спецификации, не удаляется (составной внешний ключ). Единица товара — составной FK `(workspace_id, unit_code)`.
- `product_categories` — дерево: `parent_id` + материализованный `path` (id предков и самой категории через «/»), выборка поддерева по префиксу
  (`path = X or path like X/%`, индекс `text_pattern_ops`). Перенос ветки пересчитывает `path` всего поддерева; в себя и в потомков перенести нельзя.
  Удалить можно только пустую категорию (без подкатегорий и товаров).
- `attribute_defs (category_id, key, name, type, required, unit, options, sort_order)` — характеристики категории. Типы — как у полей
  конструктора, кроме ссылок (`user`/`ref`/`refs`) и `datetime`; `options` те же (варианты select, min/max, maxLength). **Наследование:** действующий набор
  категории = характеристики всех предков (от корня) + свои (`GET /product-categories/:id/attributes` отдаёт их с признаком `inherited` и названием
  категории-источника). Ключ уникален вдоль всей ветки: нельзя завести ключ, который уже есть у предка, самой категории или потомка
  (409), и перенести ветку к родителю с таким же ключом. Ключ и тип не меняются. Удаление характеристики — с подтверждением (`?confirm=<ключ>`) и
  необратимо: значения стираются у товаров всей ветки (`attrs - ключ`).
- `products (kind: goods|service, sku, name, description, barcode, unit_code, vat_rate, price, purchase_price, category_id, attrs jsonb, is_active,
  custom jsonb)`. `vat_rate` — `none|0|5|7|10|20`; `price` — цена продажи, `purchase_price` — закупочная (`numeric(18,2)`, строками). `sku` и
  `barcode` уникальны в воркспейсе (частичные уникальные индексы по непустым; sku — без учёта регистра), штрихкод — 8–14 цифр. Мягкое удаление — `archived_at`.
  Варианты товара (размер/цвет) — позже, отдельной таблицей. `product` — системная сущность конструктора: пользовательские поля товара лежат
  в `custom` (индексы по ним строит воркер, `SYSTEM_TABLES.product = products`).
- **Проверка `attrs` — тем же механизмом, что поля конструктора:** характеристики категории (с унаследованными) превращаются в `FieldDef`, значения проверяет
  `buildRecordSchema` (`packages/shared/src/fields.ts`) — на сервере (`validateAttrs`) и в формах клиента (`validateRecord`, те же `FieldInput` / `FieldValue`).
  Создание — обязательные заполнены, лишние ключи (в том числе характеристики соседней категории) отклоняются; без категории характеристик нет,
  любые `attrs` — ошибка. PATCH той же категории проверяет только изменённые ключи (как `custom`), `null` убирает ключ. Смена категории проверяет
  итоговый набор целиком по новой схеме, как создание: значения, которых в новой схеме нет, нужно убрать явно (`null`). Перенос категории с товарами,
  у которых есть значения унаследованных характеристик, пропадающих из цепочки, запрещён (422).
- API: `/units`, `/product-categories` (+ `/:id/attributes`), `/attribute-defs/:id`, `/products` (список: `categoryId` с подкатегориями — `subtree=false` отключает,
  `kind`, `active`, `q` по названию / sku / штрихкоду, `sort`). События outbox: `unit.*`, `product_category.*`, `attribute_def.*`, `product.*`.
- Интерфейс (маршрут `/catalog/:productId?`, группа «Catalog» в сайдбаре): дерево категорий слева (счётчики с подкатегориями, меню категории — подкатегория,
  характеристики, переименование и перенос, удаление), таблица товаров справа на `DataTable` + `FilterBar` (категория — из дерева, `?category=` в адресе;
  фильтры тип / активность, поиск), карточка товара на `EntityDrawer` (поля по типам, характеристики категории теми же `FieldInput`, пользовательские поля
  конструктора), форма создания с характеристиками выбранной категории. Редактор характеристик категории показывает унаследованные (только чтение, с
  пометкой «from …») и свои. Палитра команд находит товары и продукцию (`useCatalogHits`).

## Производство: спецификации и себестоимость

Реализовано на этапе 4. Код: схема `packages/db/src/schema/production.ts`, расчёт `packages/shared/src/bom.ts` (+ `decimal.ts`), схемы API
`schemas/production.ts`, API `apps/api/src/routes/production.ts`, клиент `apps/web/src/app/production/*`.
Чтение — любой участник; участки и настройки меняет admin и выше, продукцию и спецификации — member и выше.

- `manufactured_items` — справочник продукции (изделия и полуфабрикаты): код, название, `kind` (`product` — изделие, `semi` — полуфабрикат; на уровне
  данных разницы нет: любую продукцию можно включить в другую), единица, ссылка на товар каталога для продажи/склада (`product_id`, необязательно),
  выход на партию (`batch_qty`), процент накладных (`overhead_pct`). Архивируется; продукцию, которая входит в чужие спецификации, убрать нельзя.
- `bom_lines (item_id, kind: material|semi|work, sort_order, …)` — спецификация на `batch_qty` единиц (форма строки по типу проверяется `CHECK` в БД):
  - material — `product_id` из каталога (только товары: услуга материалом быть не может, её место — работа), `qty`, `scrap_pct` (отход);
  - semi — `child_item_id` (другая продукция со своей спецификацией), `qty`; дерево любой глубины, **циклы запрещены**: при записи строки сервер
    проверяет, достижимо ли изделие из включаемого полуфабриката (`wouldCreateCycle`), под рекомендательной блокировкой воркспейса, чтобы параллельные
    правки разных изделий не замкнули цикл (422 `bom_cycle`); интерфейс не предлагает полуфабрикаты, которые замкнули бы цикл;
  - work — `operation` (название), `work_center_id` (участок, необязательно), `hours`, `rate` за час (пусто — ставка участка) и `fixed_cost`;
    стоимость работы = hours × ставка + fixed_cost;
  - `unit_code` строки заполняет сервер из единицы товара / продукции (преобразования единиц нет: строка в единице своего товара).
- `work_centers` — участки со ставкой за час по умолчанию.
- Настройка воркспейса `workspaces.settings.materialPriceSource` (`GET/PATCH /production/settings`, меняет admin; интерфейс — Settings → Production) задаёт
  **источник цены материала**: `purchase` (закупочная, по умолчанию), `price` (цена продажи) или `avg_cost` (средняя себестоимость склада — заготовка до этапа 5:
  пока склада нет, берётся закупочная цена). Нулевая цена считается незаданной: материал оценивается в 0, строка помечается «No price».
- **Себестоимость единицы** считает чистая функция `computeBomCost` в `packages/shared` — одна и та же на сервере (`GET /manufactured-items/:id/cost`, тесты)
  и в интерфейсе (мгновенный пересчёт при правке строки, без ожидания сервера). Арифметика десятичная на BigInt (`decimal.ts`, масштаб 10^-6), без float;
  результат — строки с 4 знаками. Правила: стоимость партии / `batch_qty` = себестоимость единицы; material = цена × qty × (1 + отход%/100);
  semi = qty × себестоимость единицы полуфабриката (его спецификация считается рекурсивно, со своими накладными); **накладные узла = overhead_pct от
  прямых затрат его собственных строк (материалы + работы)** — полуфабрикат уже включает свои накладные, поэтому на него накладные родителя не начисляются
  (нет двойного счёта). Результат — дерево с разбивкой «материалы / работы / накладные / итого» по каждому узлу (партия и единица); затраты полуфабриката
  входят в разбивку родителя по своим статьям. Цикл — `BomCycleError` с цепочкой id.
- `GET /production/snapshot` отдаёт одним запросом всё для клиентского расчёта: продукцию со строками, участки, материалы из спецификаций (цены) и настройки.
  Клиент кэширует снимок, правит его оптимистично, realtime по событиям `manufactured_item` / `bom_line` / `work_center` / `product` / `workspace`
  перечитывает его. API: `/work-centers`, `/manufactured-items` (+ `/:id/lines`, `/:id/lines/reorder`, `/:id/cost`), `/bom-lines/:id`, `/production/*`.
- Интерфейс: `/production` — список продукции с себестоимостью единицы; `/production/:id` — шапка (тип, код, единица, партия, накладные), дерево спецификации
  (иконки по типу строки, количество и стоимость строки, количество правится на месте, перестановка перетаскиванием или «Move up/down», полуфабрикат раскрывается
  в своё дерево — только чтение, строки приведены к вкладу в партию родителя, накладные полуфабриката — отдельной строкой — и открывается переходом) и итог внизу
  (материалы / работы / накладные для партии и для единицы, себестоимость единицы); `/work-centers` — справочник участков; Settings → Production — источник цены.
- Версии спецификаций (действует с даты) и производственные заказы со списанием материалов и выпуском
  продукции на склад — следующими шагами.

## Фронтенд на сервере

Реализовано на этапе 2. Код — `apps/web/src/app/data` (`session.tsx`, `store.tsx`, `engine.ts`, `specs.ts`, `realtime.ts`, `api.ts`).

- **Сессия и воркспейсы.** `SessionProvider` держит `GET /auth/me` (TanStack Query, ключ `['session']`): пользователь и мои воркспейсы. Вход,
  регистрация и выход — настоящие `/auth/*` (cookie httpOnly; токена в JS нет). Без сессии `RequireAuth` ведёт на `/signin`, без воркспейсов — на
  онбординг. Ответ API с кодом `unauthorized` (сессия истекла) сам возвращает на экран входа. Активный воркспейс — настройка просмотра, хранится
  в `localStorage` (`gr8r-ui.workspace`), уходит в запросы заголовком `X-Workspace-Id` (`apiFor(workspaceId)` — типизированный клиент
  `@gr8r/api/client`, по экземпляру на воркспейс), в WebSocket — `?workspace=`. Переключатель в сайдбаре, создание воркспейса — `POST /workspaces`,
  удаление — `DELETE /workspaces/:id` (только owner, данные арендатора уходят каскадом).
- **Данные = кэш запросов.** Каждая коллекция воркспейса — один запрос `['ws', id, имя]` (все страницы по 200; активность — только свежие 200;
  задачи и проекты — с архивными, у них есть флаг `archived`). Строка API превращается в локальную сущность на границе (`specs.ts`: uuid, время в
  epoch-миллисекундах, `null` → `''`/`undefined`, `Project.last` и `Member.last` — минуты с `lastActivityAt`/`lastSeenAt`, `numeric` → число,
  размер файла ↔ байты). Компоненты и reducer остались на прежней модели (`app/data/types.ts`). `useWorkspace()` отдаёт `{ data, dispatch }`,
  `data` собирается из кэша: вложения задач — это `files` с `taskId`, порядок проектов — из `sortOrder`. Пока данные не загружены, показывается
  экран ожидания; ошибка загрузки — экран с «Try again».
- **dispatch = мутации.** Семантика действий по-прежнему описана одним reducer'ом (`store.tsx`, `crm/store.tsx`). Слой `engine.ts`:
  `before → reducer → after`, diff по коллекциям (добавлено / изменено с перечнем полей / удалено), `after` пишется в кэш (интерфейс обновляется
  сразу), diff превращается в запросы и уходит в **одну очередь воркспейса** (порядок записи сохраняется: родители раньше детей, удаление — в
  обратном порядке). Соответствие «локальное поле → поля API» — таблицы `fields` в `specs.ts`; PATCH уходит только с изменёнными полями.
  После очереди изменённые коллекции перечитываются (ключ задачи `WEB-109`, активность и уведомления считает сервер). Ошибка запроса: toast с
  сообщением сервера, остаток запросов этого действия пропускается, коллекции перечитываются — оптимистичное состояние откатывается к серверному.
- **Идентификаторы создаёт клиент.** `uid()` — uuid v7; все схемы создания принимают необязательный `id`, поэтому карточку можно открыть и менять
  до ответа сервера, а повторное создание при Undo возвращает ту же запись. Повторное использование id — 409. Статус-колонка идентифицируется
  ключом (`StatusDef.id` = `statuses.key`), uuid строки хранится рядом. Задача при повторном создании (Undo удаления) может принести прежний
  `key` — он должен принадлежать проекту и быть свободным, счётчик проекта не уменьшается.
- **Undo (`data/restore`).** Компоненты по-прежнему передают снимок `data`, захваченный до действия. Для снимка запоминается состояние ПОСЛЕ
  действия (`WeakMap`), и откатывается только разница между ними — чужие изменения, пришедшие по WebSocket в промежутке, не затрагиваются.
  Что делает откат на сервере: удалённая задача/проект создаются заново вместе с зависимыми записями (комментарии, часы, файлы, виды) под теми же
  id, мягко удалённые (файл, сделка) возвращаются через `POST /:id/restore`, архив задачи снимается, изменённые поля возвращаются PATCH'ем.
- **Удаление.** Задачи, проекты, комментарии, часы, статусы, команды удаляются насовсем (`?hard=true`; для задач и проектов это права admin и выше —
  у остальных будет toast и откат), файлы и CRM-сделки — архивированием (`DELETE` без `hard`, Undo = restore). У сделки активности остаются на
  сервере и скрываются на клиенте, пока сделка в архиве. «Архив» задачи и проекта — флаг `archived` (`DELETE` без `hard` / `restore`).
  Участник «удаляется» деактивацией (`status: deactivated`): профиль остаётся в истории.
- **Realtime.** Один WebSocket `/ws?workspace=` на вкладку (`realtime.ts`). Событие журнала (конверт без payload) помечает коллекции сущности
  устаревшими (`collectionsFor`), они перечитываются целиком; пока в полёте свои запросы — после них, чтобы не затереть оптимистичное
  состояние. Точка отсчёта — последнее событие на момент загрузки, обрыв — переподключение с `?since=<id>` и полное перечитывание. Дедупликация
  по `event.id`. Перечитывание целой коллекции выбрано вместо точечных патчей: код проще, а при 50–500 записях на воркспейс запрос дешёв;
  точечный патч (`GET /:id` + upsert) — следующий шаг, если коллекции вырастут.
- **Формат API** (для границы слоя): строки таблиц в camelCase, даты `YYYY-MM-DD` / ISO 8601, `numeric` — строки, реакции комментариев —
  `re: {эмодзи: [member id]}`, участники проекта — `members: [{memberId, permission}]`, контакты сделки — `contactIds`. Демо-данные
  генерируются в `packages/shared/src/demo` и общие для сида БД (`bun run db:seed`); типы `Task`, `Project`, … — в `packages/shared/src/domain.ts`
  (фронтенд реэкспортирует их из `app/data/types.ts`).
- **Локально остаётся только настройка просмотра**: тема, акцент, плотность, свёрнутый сайдбар, фильтры видов, плавающие окна задач, активный
  воркспейс (`localStorage`).
- Отладка и браузерные тесты (только `import.meta.env.DEV`): `window.__qc` (QueryClient), `window.__ws.dispatch/read/settled()`, `window.__crm`.

Что пока не так, как в локальной модели:
  «избранное» (`fav`) общее для воркспейса (позже — по пользователю); дерево подзадач хранится JSON'ом в задаче, поэтому одновременная правка
  подзадач двумя людьми — «последний записал»; вложения — только метаданные файла (загрузки в S3/MinIO нет); активность — последние 200 записей;
  доступ к закрытым проектам (`isPrivate`/`access`) хранится, но API ещё не фильтрует по нему; сброс пароля и подтверждение почты (нужна отправка писем)
  и вход через внешних провайдеров не реализованы — экраны остались, но честно сообщают об этом.
