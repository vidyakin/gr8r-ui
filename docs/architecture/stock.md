# Склад

Реализовано на этапе 5. Код: `packages/db/src/stock.ts` (движения, остатки, резервы), `packages/shared/src/documents.ts` (средняя скользящая — `stockIn`, `stockOut`, `replayMoves`),
API `/stock/*`, клиент `apps/web/src/app/docs/InventoryPage.tsx`.

- `warehouses` (у склада — `counterparty_id`, «склад контрагента»: место хранения на стороне контрагента, например переработчика —
  см. раздел «Переработка»); проведение реализации (расход), поступления (приход), возврата от покупателя (приход) и возврата поставщику (расход), а также внутренних документов
  (списание — расход, оприходование — приход, перемещение — расход и приход) пишет `stock_moves (warehouse_id, product_id, document_id,
  document_line_id, qty ±, cost, moved_at, seq)` по строкам-**товарам**; услуги на склад не влияют. `seq` — identity-колонка: порядок движений для пересчёта средней; `moved_at` — дата документа.
- Остатки — таблица `stock_balances (warehouse_id, product_id, qty, avg_cost)`, обновляется **в той же транзакции**, что и движения. Строка остатка блокируется `FOR UPDATE` (ключи в одном порядке — без
  взаимных блокировок), поэтому параллельные проведения не могут вместе уйти в минус, а `seq` совпадает с порядком блокировок (тест: 4 параллельные отгрузки по 2 при остатке 5 — проходят две).
- **Себестоимость — средняя скользящая по (склад, товар)**, 4 знака. Приход пересчитывает среднюю взвешенно (`(остаток × средняя + приход × цена) / новый остаток`); если остаток был нулевым или отрицательным,
  средней становится цена прихода. Расход списывается по текущей средней и её не меняет. Цена прихода по поступлению — сумма строки **без НДС** (у организации на УСН входной НДС входит в себестоимость, берётся
  сумма с НДС) / количество; возврат от покупателя приходуется по себестоимости исходной реализации (по `source_line_id`), без неё — по текущей средней; возврат поставщику списывается по средней.
- **Двухфазная запись.** `applyStockMoves` пишет сначала расходы, потом приходы: цена прихода перемещения — **фактическая цена расхода той же строки**
  (`costFromLine`), поэтому товар переезжает по своей себестоимости, а не по средней получателя. Нехватка остатка проверяется после расходов (приходы остаток не уменьшают).
  Тот же приём использует выпуск: цена прихода продукции — себестоимость партии из списанных материалов и работ (в `applyStockMoves` её считает колбэк `inCost`).
  У движения есть **фаза** (`stock_moves.phase`: 1 — основная, 2 — приёмка перемещения «в пути»): отмена приёмки откатывает только свою фазу.
- **Отмена проведения** удаляет движения документа и **пересчитывает остаток и среднюю по оставшимся движениям** (`replayMoves`): расходы после отменённого прихода переоцениваются; если после этого остаток
  уходит в минус — отмена запрещена (422 `stock_conflict`: сначала снимите с проведения зависимые документы).
- **Минус.** Настройка воркспейса `workspaces.settings.allowNegativeStock` (по умолчанию выключена; `GET/PATCH /stock/settings`, меняет admin; интерфейс — Settings → Warehouses). Выключена — проведение
  расхода, которому не хватает остатка, отклоняется (422 `insufficient_stock`, в `details.items` — товар, доступно, нужно), ничего не записывается и номер не выдаётся. Настройка общая для воркспейса, не по складам.
- **Резервы.** `stock_reservations (document_line_id | production_line_id | production_component_id, warehouse_id, product_id, qty)` — владелец резерва ровно один
  (CHECK `stock_reservations_owner_chk`), уникальность — по владельцу (для материала — по строке состава и складу). Три вида резерва:
  (1) по строке-товару проведённого заказа покупателя со складом: резерв = заказано − отгружено проведёнными реализациями цепочки, пересчитывается при проведении и отмене
  проведения заказа и реализаций; (2) выпущенная продукция под заказ покупателя (`production_line_id`, строка выпуска) — см. «Заказы на производство и выпуск»;
  (3) **материалы заказа на производство** (`production_component_id`, строка состава заказа) — см. «Обеспечение материалов заказа на производство».
  В остатках: `reserved` и `available = on hand − reserved` (сумма всех резервов); проведение расхода резервами не блокируется (проверяется физический остаток).
  Свободное количество для нового резерва считается под блокировкой строк остатков (`FOR UPDATE`) — два заказа не займут одно и то же количество.
- API: `GET /stock/balances` (склад, товар, `q`, `nonZero`; количество, резерв, доступно, средняя, стоимость, итог стоимости), `GET /stock/moves` (карточка движений: документ, склад, количество, себестоимость
  и остаток после движения по складу), `GET /stock/avg-costs`, `GET /stock/default-cost` (цена оприходования по умолчанию). Стоимость в этих ответах видят только admin и owner (см. «Внутренние складские документы»).
  Интерфейс: **Inventory** (`/inventory/:productId?`) — остатки с фильтром по складу и поиском, показатели (стоимость, позиции, резервы), карточка товара
  (`EntityDrawer`: остатки по складам и журнал движений со ссылками на документы).
- **Производство:** источник цены материала `avg_cost` (Settings → Production) берёт `loadAvgCosts` — среднюю по складам, взвешенную остатком; товар без остатка оценивается закупочной ценой. Снимок производства
  (`/production/snapshot`) отдаёт `avgCost` каждого материала, расчёт на клиенте и на сервере — одна функция.
- **Корректировки себестоимости закрытия периода.** Движений с нулевым количеством не бывает (CHECK `stock_moves_qty_chk`), поэтому изменение
  себестоимости записи движением невозможно: цена прихода/расхода меняется прибавкой в отдельной таблице
  `stock_cost_adjustments (workspace_id, move_id, delta_cost, own_delta, closing_id)`, у движения — не больше одной корректировки
  (уникальный индекс по `(workspace_id, move_id)`). **Себестоимость читается как `cost + delta` везде:** остаток средней
  (`stock_balances.avg_cost` пересчитывается при закрытии), стоимость документа в журнале (`documentCosts`), себестоимость строки
  документа (`documentLineCosts`), цена возврата от покупателя (`sourceMoveCosts`) и карточка движений (`GET /stock/moves`).
  Корректировку создаёт и снимает закрытие периода (раздел «Закрытие месяца»); она принадлежит своему закрытию (`closing_id`),
  поэтому отмена закрытия возвращает прежние значения.
- **Партионный учёт (задача 1187).** Товар с флагом `products.track_batches` (карточка товара, рядом с «учётом по серийным номерам»)
  учитывается по партиям: каждая приходная строка несёт номер партии (`document_lines.batch_number`), дату выработки (`batch_produced_at`, по умолчанию дата документа) и «годен до» (`batch_expires_at`, по умолчанию дата документа + `products.shelf_life_days`). Проведение прихода создаёт или пополняет партию — таблицу `stock_batches (склад, товар, номер)` (номер уникален с товаром и складом, дата истечения может быть пустой — такая партия списывается последней). Расход (реализация, списание, возврат поставщику, материалы) списывается **FEFO** (first expired, first out): строка разбивается по партиям с самой ранней датой истечения, каждая порция — отдельное движение `stock_moves` со своей `batch_id` и себестоимостью по средней склада. Себестоимость остаётся средней скользящей по (склад, товар) — партия влияет только на порядок списания и прослеживаемость (база для задачи 1253 и «Честного знака»). Перемещение «в пути» переносит партию: приёмка наследует партии отправки. Товар без флага не создаёт партий и списывается как раньше. Отмена проведения удаляет движения документа; партии, оставшиеся без остатка, удаляются, партии с остатком (их списали другие документы) сохраняются.
- **Отчёт по партиям:** `GET /stock/batches` (склад, товар, `days=N` — «истекает в течение N дней», `expired=1` — только просроченные) — остаток каждой партии как сумма её движений, сортировка по дате истечения (без срока — в конец). Интерфейс — **Batches** (`/batches`, раздел Documents → Batches) рядом с «Остатками» и «Серийными номерами».
- **Движения документа до проведения.** `GET /documents/:id/stock-moves` (`packages/db/src/stock-preview.ts`, кнопка «Движения» в форме документа). У проведённого — фактические движения из `stock_moves` (себестоимость `cost + delta` корректировки закрытия, партия по номеру, фаза). У черновика — **настоящее проведение (`postDocument`) внутри savepoint с обязательным откатом**, затем чтение `stock_moves` документа: логика `applyStockMoves` (FEFO, средняя, возврат по цене источника, выпуск, перемещение «в пути») не дублируется и не может разойтись с реальным проведением. Откат возвращает остатки, партии, номер и счётчик нумерации, резервы, взаиморасчёты, события outbox и NOTIFY. Блокировки остатков и документа живут до конца запроса (как у проведения), поэтому расчёт черновика — только `member`+ (гость получает 403). Правило проведения, не пускающее документ (нехватка остатка, закрытый период…), приходит ответом 200 с `error { code, message }` и пустым списком, а не ошибкой запроса. Цена и сумма (`cost`, `amount`) — только `canSeeCost` (admin, owner), иначе `null`; `costVisible` в ответе. Ограничение: пока проведение не проходит, движений не видно.
- **Старение запасов (`GET /stock/aging`, `packages/db/src/stock-aging.ts`, экран `/stock/aging`, раздел меню «Склад»).** Отборы `warehouseId`, `categoryId` (с вложенными, рекурсивно), `productId`, `asOf` (по умолчанию сегодня). Остаток на дату — движения с `moved_at ≤ asOf`. Слои возраста: движения с `batch_id` — слой на партию (остаток партии, возраст от первого прихода партии, цена — средневзвешенная по приходам); движения без партии — **FIFO по приходным движениям**: остаток = сумма движений, остаются самые свежие приходы (`rem − newer` в оконной сумме). Корзины 0–30, 31–60, 61–90, 91–180, >180 дней (`AGING_BUCKETS`). Оценка слоя — по цене его прихода с корректировкой закрытия, а не по средней, поэтому итог может отличаться от стоимости в «Остатках». Стоимость (`value`, `bucketsValue`) — только admin и owner, иначе `null`. Отрицательные остатки в слои не попадают. Тесты — `apps/api/test/stock-preview-aging.test.ts`.
- Инвентаризация, перемещения «в пути» и передача в эксплуатацию реализованы в этапе 0б (раздел «Внутренние складские документы»);
  закрытие периода — этап 6 (раздел «Закрытие месяца»); давальческое сырьё учитывается отдельными таблицами и своего склада не касается —
  раздел «Переработка»; ордера — следующими шагами.
- **Давальческое сырьё не проходит через этот слой.** Движения давальцев живут в `customer_stock_moves` и `customer_stock_balances`
  (раздел «Переработка»): ни `stock_moves`, ни средняя, ни `recomputeStockCosts` их не видят. Поэтому приём давальческого сырья,
  выпуск из него и отчёт о переработке не меняют остатки и себестоимость своего склада, а закрытие месяца их не пересчитывает.

## Дополнительные расходы в себестоимость

Задача 1385, «Дополнительные расходы» 1С УНФ. Код: `packages/db/src/landed-costs.ts` (документ и распределение),
чистая арифметика — `packages/shared/src/landed-costs.ts` (`allocateLandedCost`), API — `/landed-costs`,
экран — `/landed-costs` (журнал и форма) и `/landed-costs/report` (отчёт за период), миграция `0150_landed_costs.sql`.

- **Документ.** Запись `documents` типа `landed_cost` (номер `ДР-2026-00001`, дата, статус, организация — общим кодом
  документов) плюс своя шапка `landed_costs` (способ распределения, контрагент-исполнитель услуги, статья расходов,
  ссылка на счёт поставщика — документом в системе или строкой) и строки `landed_cost_lines` — доли по приходным
  строкам оснований. Документ ведётся в своём разделе (`section`), в общие журналы закупок не попадает; создавать его
  через `POST /documents` нельзя (422 `production_api_only`) — строки живут вне `document_lines`.
- **Основания.** Только документы, дающие приход на наш склад: поступление (`receipt`) и выпуск продукции
  (`production`, в том числе отчёт переработчика — выпуск на складе переработчика). `tolling_receipt` в списке нет:
  давальческое сырьё учитывается количественно и своей себестоимости не имеет. Строка основания берётся из приходных
  движений склада (`stock_moves.qty > 0`), поэтому строка без прихода отклоняется (422 `no_stock_moves`), а основание
  обязано быть проведённым (422 `base_not_posted`).
- **Распределение** — по сумме строки (`by_amount`), по количеству (`by_qty`), по весу (`by_weight`) или вручную
  (`manual`). Копейки делятся методом наибольших остатков (`apportionKop`), сумма долей строго равна сумме расходов;
  ту же функцию считает форма, поэтому предпросмотр совпадает с проводкой до копейки. «По весу» берёт
  `products.weight_kg × количество`: строки без веса получают нулевую долю, а если веса нет ни у одной строки —
  распределение уходит на количество, затем на сумму строки. Ручной способ: суммы строк вводит пользователь, итог —
  их сумма.
- **Себестоимость.** Движений склада документ не пишет: доля строки (`amount / qty`, 4 знака — как цена движения)
  читается `recomputeStockCosts` (`loadLandedCostDeltas`) и складывается со своей частью закрытия месяца в
  `stock_cost_adjustments.own_delta`. Поэтому дорожает и остаток (средняя склада), и себестоимость уже списанного и
  отгружённого, а дальше удорожание идёт по цепочке (перемещения, выпуски, реализации). Своя часть закрытия периода
  в `own_delta` **не перезаписывается**: доли доп. расходов живут в `landed_cost_lines`, иначе отмена проведения не
  смогла бы отличить их от косвенных. Отмена проведения доп. расходов пересчитывает цепочку обратно.
- **Порядок.** Пока на документ отнесены проведённые доп. расходы, сам документ-основание снять с проведения нельзя
  (409 `has_posted_landed_costs`) — доли остались бы без прихода. Сначала отменяется проведение доп. расходов.
- **Права.** Документ создаёт и проводит member и выше; суммы (итог, доли, отчёт) видят только admin и owner
  (`canSeeCost`, как у остальных складских стоимостей), остальным приходят `null`.
- **Отчёт** (`GET /landed-costs/report?from&to`): документы периода, суммы по статьям расходов, по основаниям и по
  товарам; в суммы входят только проведённые документы (`postedTotal`), черновики видны составом.

## Адресное хранение и таможенные данные

- `warehouses.use_bins` включает адресный учёт для одного склада. Дерево адресов хранится в `warehouse_bins`. Код уникален на складе, родитель принадлежит тому же складу. API проверяет отсутствие циклов. Отключённые адреса сохраняются в истории. Отключить адрес с остатком или действующими дочерними адресами нельзя.
- `document_lines.bin_id` задаёт адрес прихода или расхода. В перемещении `bin_id` задаёт адрес отбора, а `to_bin_id` — адрес назначения. Прямое перемещение внутри одного склада требует разных мест хранения. Одной из сторон может быть остаток без ячейки, например при первичном размещении. При перемещении «в пути» адрес назначения применяется только при приёмке.
- `stock_moves.bin_id` фиксирует адрес каждой порции движения. `stock_bin_balances` хранит количество по складу, ячейке и товару. Остаток без ячейки равен общему остатку за вычетом распределённого по ячейкам. Проведение и отмена обновляют остатки по ячейкам под блокировкой тех же пар «склад — товар», что и общий остаток. При запрещённом минусе проверяется доступное количество по выбранному адресу. FEFO учитывает доступность партии в этом месте хранения. При отмене проверяется последовательность оставшихся движений.
- API склада: `GET/POST /warehouses/:id/bins`, `PATCH/DELETE /warehouses/:id/bins/:binId`, `GET /warehouses/:id/bin-balances`. Списки доступны участникам, конфигурацию меняют администраторы. `DELETE` отключает адрес. Чтобы выключить адресное хранение, сначала освободите ячейки.
- `gtd_number` и `origin_country` сохраняются в строках документов и в движениях поступления, расхода и перемещения. При списании партии подставляются реквизиты, одинаковые во всех её приходах. Проведённая реализация подставляет значение в строку, когда оно совпадает у всех списанных порций. Значение, введённое пользователем в строку, имеет приоритет. Для товара без партионного учёта данные реализации заполняются вручную или передаются из исходного документа.
- Печатные формы `upd` и `vat_invoice` выводят цифровой код страны, краткое название и номер ГТД в графах 10, 10а и 11. В строке можно указать код ISO-2 или название страны с цифровым кодом ОКСМ. Форма `invoice` используется для счёта на оплату.

## Упаковки товара (единицы с коэффициентом)

План и решения — `docs/plans/2026-11-14-product-packages.md`. Кратко:
- `product_units (product_id, unit_code, factor)` — упаковки товара, базовая единица — `products.unit_code`. Сервис — `packages/db/src/product-units.ts`, API — `GET/PUT /products/:id/units`.
- `document_lines.qty` — **всегда в базовых единицах**; `unit_code` + `unit_factor` — единица строки и её коэффициент на момент ввода; `price` — за единицу строки.
  Суммы — `computeLine` с `unitFactor` (`qty / unit_factor × price`, одно округление). Склад, резервы, партии, серийные номера и остаток к отгрузке работают с `qty` без пересчёта.
- Вход API строки: `unitQty` (в единице строки, так шлёт форма — сервер умножает на коэффициент; не укладывается в 3 знака — 422 `invalid_qty`) или `qty` в базовых; `unitFactor` — явный коэффициент (копия строки «на основании»).
  Коэффициент строки: явный → прежний той же строки с той же единицей → 1 для базовой → упаковка товара → 1.
- Себестоимость прихода по поступлению — `net / qty` (уже за базовую); оприходование — `price / unit_factor`; цена оприходования по умолчанию и калькуляция заказа умножают себестоимость на коэффициент.
- Цена вида цен может быть за упаковку (`product_prices.unit_code/unit_factor`, пишет прайс поставщика); `resolvePrices` отдаёт цену за базовую единицу.

### Историческая себестоимость для P&L

`stock_moves.cost` сам по себе не является неизменяемым снимком на дату проведения. При отмене
более раннего движения `revertStockMoves` пересчитывает стоимость последующих расходов, а
`revalueMove` меняет цену прихода и последующие расходы. Поэтому чтение текущего `cost` без
корректировок закрытия не гарантирует себестоимость на момент первоначального проведения.
Для такого отчёта потребуется сохранять отдельный неизменяемый снимок при проведении;
уже перезаписанные значения из текущей схемы восстановить невозможно. Правила перехода
для существующих движений должны явно отражать отсутствие исходной истории.
